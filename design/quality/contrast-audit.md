# Аудит контраста

Значения посчитаны по формуле относительной яркости WCAG 2.x для реальных пар,
которые встречаются в консоли. Пороги: 4.5:1 для основного текста, 3:1 для крупного
текста (от 18.66px полужирного или 24px обычного), 3:1 для границ и графических
элементов, несущих смысл (критерий 1.4.11 Non-text Contrast).

Токены в `../tokens/tokens.css` намеренно не исправлены: там снимок продакшена.
Всё, что ниже, — рекомендации к применению.

## Что чинить

### Акцентный текст на белом

`h3_text_accent` `#51BA81` на белом даёт 2.42:1 — ниже даже
порога для крупного текста. Живой пример: строка «+ бонус 3 844,12 ₽» под балансом
в левой панели. Это не декоративная надпись, а сумма денег, и она должна читаться.

Замена из той же палитры:

| Вариант | Ratio на белом | Годится для |
|---|---:|---|
| `h3_mint-6` `#379A64` | 3.52 | только крупный текст |
| `h3_mint-7` `#1C7946` | 5.42 | любой текст, AA |
| `h3_mint-8` `#025829` | 8.64 | любой текст, AAA |

Рекомендация: `h3_mint-7` `#1C7946`. Он остаётся узнаваемо мятным и проходит AA
для обычного кегля.

В тёмной схеме `#51BA81` менять не нужно: там 7.13:1.
То есть токен `h3_text_accent` стоит развести по схемам, как разведены остальные
семантические токены.

### Вторичный текст

`h3_text_1` `#969696` на белом — 2.96:1, на панели
`#F8F8F8` — 2.79:1. Порог не берётся ни там, ни там.

Правило употребления: `h3_text_1` только для неактивных элементов и плейсхолдеров,
где текст дублирует уже видимую подпись. Всё, что пользователь должен прочитать
(подписи разделов, описания, вторичные значения), ведём через `h3_text_2` `#6E6E6E`
(5.10:1, AA).

Плейсхолдер `#969696` формально допустим, потому что не несёт информации сверх
видимой подписи поля. Но подпись обязана быть видимой — см.
[../components/forms.md](../components/forms.md).

В тёмной схеме та же проблема слабее: `#787878` на `#1B1B1B` даёт
3.90:1, а на панели `#272727` — 3.38:1.
Для служебного текста это приемлемо, для содержательного нет.

### Границы интерактивных контролов

`h3_border` `#E9E9E9` на белом — 1.21:1. Как разделитель
между блоками это нормально: разделитель ничего не сообщает, он просто структурирует.
Но та же граница очерчивает поле ввода, и тогда она попадает под критерий 1.4.11:
контур, по которому пользователь опознаёт границы контрола, должен давать 3:1.

`h3_border_1` `#B6B6B6` порог тоже не берёт (2.03:1).
Порог 3:1 на белом лежит примерно на `#949494`, то есть вся верхняя половина серой
палитры для этой роли не подходит.

Рекомендация: завести отдельный токен границы контрола со значением
`h3_gray-6` `#6E6E6E` (5.10:1), а `#E9E9E9` и `#B6B6B6`
оставить разделителям, неактивным состояниям и декоративным рамкам.

Компромисс, если сплошная тёмная рамка кажется слишком тяжёлой: оставить светлую
рамку в покое, но добавить полю заливку `h3_bg_1`, чтобы граница контрола читалась
по разнице фонов, а не по контуру.

### Мятные графические элементы

`h3_border_accent` `#6CDB9F` на белом — 1.71:1. Он рисует
заполненную часть слайдера и обводку выбранной карточки.

Ползунок остаётся различимым по форме, а выбранная карточка — по точке в радио,
поэтому смысл одним цветом не передаётся и формального нарушения нет. Но опираться
на этот цвет как на единственный признак состояния нельзя: подписи ступеней слайдера
и радио внутри карточки обязательны.

Если понадобится состояние, которое видно только цветом рамки, для светлой схемы
берём `h3_mint-6` `#379A64` (3.52:1).

## Что уже хорошо

Чёрная главная кнопка: 17.22:1. Мятная кнопка в тёмной схеме:
13.67:1. Точка внутри выбранного радио:
6.86:1. Текст на мягкой подсветке `#E4FFEF`:
16.28:1.

Основной текст в обеих схемах — 17.22:1, это AAA с запасом.

## Как пересчитать

```python
def lum(h):
    h = h.lstrip('#')
    c = [int(h[i:i+2], 16) / 255 for i in (0, 2, 4)]
    c = [x / 12.92 if x <= 0.04045 else ((x + 0.055) / 1.055) ** 2.4 for x in c]
    return 0.2126 * c[0] + 0.7152 * c[1] + 0.0722 * c[2]

def contrast(a, b):
    la, lb = lum(a), lum(b)
    hi, lo = max(la, lb), min(la, lb)
    return (hi + 0.05) / (lo + 0.05)
```
