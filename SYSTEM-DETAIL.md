## Схема PostgreSQL

Назначение таблиц и разделение настроек и наблюдений описаны в [разделе о данных](SYSTEM.md#4-данные-postgresql-18-миграции-goose). Ниже заданы колонки, ограничения и правила записи.

### `users`

`id` (UUIDv7), `email` (unique), `password_hash` (bcrypt), `is_blocked` (default false), `created_at`. Все ссылки `user_id` хранят это значение. Флаг `is_blocked` меняется вручную в базе и проверяется middleware на каждом запросе: это единственный способ закрыть доступ скомпрометированному аккаунту к API, потому что JWT отозвать нельзя ([раздел 10](SYSTEM.md#10-аутентификация)).

### `user_quotas`

`user_id` (pk), `max_vcpu` (default 4), `max_ram_gb` (default 16). Строка создаётся при регистрации. Меняется вручную в базе под общей транзакционной блокировкой `pg_advisory_xact_lock(1)`, интерфейса для этого нет.

### `valkey_instances`

Каждая колонка принадлежит либо обработчикам запросов, либо фоновой синхронизации внутри API.

Выбранные пользователем настройки и запросы на изменение далее называем намерением. Их записывают HTTP-обработчики `api`:

- `id`, `user_id`, `name` (отображаемое), `slug` (unique, DNS-имя), `mode` (`single`/`ha`), `vcpu`, `ram_gb`, `desired_generation` (default 1);
- `created_at`, `updated_at`: создание строки и последнее изменение намерения. Импорт наблюдений оператора `updated_at` не меняет;
- `configuration_requested_at`: время создания или последнего роста `desired_generation`. Имя, maintenance, удаление и запрос без изменения это время не обновляют;
- `app_password_hash` (64 hex-символа SHA-256 в нижнем регистре), `password_prefix` (первые 4 символа), `password_version` (default 1);
- `host`, `host_ro`, `port`: `api` вычисляет их из slug и env при создании. В `single` `host_ro=null`; адрес `-ro` создаётся только для `ha`;
- `is_whitelist_enabled`, `whitelist_cidrs text[]`;
- `maintenance_dow smallint`, `maintenance_hour_utc smallint`, `maintenance_duration_min smallint`;
- `deletion_requested_at`: намерение удалить, записывается HTTP-обработчиком. Фоновые циклы эту колонку не меняют.

Цикл доставки хранит сведения, необходимые для проверки принадлежности объектов и продолжения удаления после перезапуска:

- `kubernetes_namespace_uid`, `kubernetes_cr_uid`: UID однажды проверенных объектов. Новый объект с тем же именем и другим UID не считается прежним;
- `deletion_stage`: `cr_delete_prepared` перед удалением CR или `namespace_delete_prepared` перед удалением `Namespace`. Значение может только переходить вперёд после запроса удаления;
- `sync_recovery_reason`: причина, по которой доставка требует ручного восстановления. `NULL` означает, что такая причина не действует.

Результаты проверок оператора далее называем наблюдениями. Фоновый цикл `api` читает их из CR и записывает фактическое состояние в следующие колонки:

- `phase`, `phase_reason`, `observed_generation` (default 0), `observed_at`;
- `is_operator_recovery_required` и `operator_recovery_reason`: условие `RECOVERY_REQUIRED` и его причина из CR;
- `is_recovery_required` (default false): общий признак ручного восстановления. Он остаётся истинным, пока действует `sync_recovery_reason` или `is_operator_recovery_required`, и используется для диагностики, логов и ответа API (DTO);
- `network_verification_status` (`pending`/`verified`/`unknown`, default `pending`), `network_verified_at` (`null` до первой успешной сверки): состояние проверки загруженной конфигурации Envoy и время последней успешной сверки. Подробности проверки и идентификаторы процессов Envoy остаются в CR;
- `applied_password_version` (default 0);
- `applied_vcpu`, `applied_ram_gb`: размер, который фактически работает в кластере. Пока перекатка не закончена, он отличается от намерения, и квота считается по большему из двух. До первого применения оба значения равны 0;
- `deleted_at`: API ставит после подтверждённого удаления namespace инстанса из k8s. Это soft delete: строка остаётся в PostgreSQL, физическое удаление через рабочий API v1 запрещено.

`deleted_at` требует заполненного `deletion_requested_at`. Уникальность имени ограничена владельцем и строками с `deleted_at IS NULL`; deleting продолжает занимать имя. Slug уникален среди всех строк, включая удалённые, и не переиспользуется. Список и обычная карточка исключают подтверждённо удалённые записи. Проверка владельца для повторного DELETE и идемпотентного ответа умеет читать сохранённую удалённую запись. Повтор DELETE владельца отвечает `202` без нового аудита и изменения времени.

Общую gorm-модель инстанса нельзя записывать через `Save` или целиком передавать в `Updates`. HTTP-обработчики и фоновые циклы API обновляют явный список своих колонок через `Select` либо `Updates(map[string]any{...})`, включая `false`, `0` и `null`. Фоновые записи наблюдений отключают автоматическое обновление `updated_at`. Это исключает перезапись намерения устаревшей моделью и потерю нулевых значений. [Обновления GORM](https://gorm.io/docs/update.html).

Статус для интерфейса `api` вычисляет при чтении: `deleted_at` означает `deleted`, затем проверяется `deletion_requested_at` для `deleting`, иначе возвращается `phase`. `is_stale=true`, если `observed_at` отсутствует или старше 60 секунд. Оператор обновляет `status.observedAt` по свежему наблюдению каждые 10 секунд, даже если состояние не меняется; API переносит именно это время в `observed_at` ([раздел 6](SYSTEM.md#6-оператор)). Свежесть этого наблюдения независима от доступности admin API Envoy. Неизвестный результат сверки шлюза отражается в `network_verification_status`; сам по себе он не делает инстанс `is_stale`.

`is_updating = desired_generation != observed_generation`: запрошенная версия конфигурации ещё не совпадает с применённой. Номер такой версии далее называем поколением. Он растёт при изменении размера, whitelist или пароля; имя и maintenance его не меняют.

Оператор подтверждает поколение после применения всех изменённых полей конфигурации, а не после записи CR. Подтверждённые неизменившиеся поля повторно применять не нужно; правила повторного подтверждения сети описаны в [алгоритме проверки шлюза](#readiness-и-публичная-готовность). `applied_password_version` отдельно показывает завершение смены пароля.

DTO содержит маску `password_hint = password_prefix + "*****"`, версии и признаки состояния; хеш и служебные пароли сериализовать в DTO запрещено. DTO также содержит `configuration_requested_at`, `network_verification_status` и `network_verified_at`.

### `valkey_instance_nodes`

`instance_id`, `ordinal`, `role` (`primary`/`replica`/`unknown`), `pod_name`, `pod_uid`, `container_id`, `run_id`, `node_name`, `node_uid`, `is_ready`, `observed_at`. Пишет фоновая синхронизация API по `status.nodes`; первичный ключ `(instance_id, ordinal)` позволяет заменить идентичность процесса при новом наблюдении.

### `valkey_node_metrics`

`instance_id`, `ordinal`, `ts`, `role`, `run_id`, `used_memory_bytes`, `maxmemory_bytes`, `connected_clients`, `ops_per_sec`, `keyspace_hits`, `keyspace_misses`, `evicted_keys`, `cpu_millicores`. Индекс `(instance_id, ts desc)` и unique `(instance_id, ordinal, ts)` для защиты от повторного импорта. `ts` приходит из времени сбора снимка в CR, а не из времени записи в БД; точность при переносе сохраняется до микросекунд. `run_id` берётся из `INFO server`; он меняется при перезапуске процесса Valkey, вместе с ним обнуляются счётчики. `cpu_millicores` допускает `null`, если свежего измерения CPU нет. Снимок без успешного сбора `INFO` не создаёт строку метрик. Пишет фоновая синхронизация API по `status.metrics`, повторная вставка использует `ON CONFLICT DO NOTHING`.

Строки старше `VALKEY_METRICS_RETENTION` (7 дней) удаляет ежедневная задача в `api`. Верхняя оценка объёма при сохранении каждого снимка раз в 10 секунд; при пропущенных снимках строк меньше:


| Нод | Строк в сутки   | Строк за 7 дней    |
| --- | --------------- | ------------------ |
| 1   | 8 640           | около 60 тысяч     |
| 24  | около 207 тысяч | около 1,5 миллиона |


Партиционирование при таком объёме не нужно.

### `valkey_instance_phase_events`

`id`, `instance_id`, `from_phase`, `to_phase`, `reason`, `created_at`. Пишет фоновая синхронизация API при обнаруженном изменении `phase` в CR, а также после подтверждённого удаления namespace (`deleted`). Обновление наблюдаемого состояния и событие фазы выполняются одной транзакцией под блокировкой строки инстанса: повторный импорт того же состояния не создаёт событие. Для наблюдения `created_at` берётся из `status.observedAt`, для `deleted` из времени подтверждения удаления API. Промежуточные переходы между опросами могут быть пропущены. Таблица нужна для разбора инцидентов; рассчитать по ней доступность для клиента нельзя: оператор проверяет инстанс только изнутри кластера ([раздел 9](SYSTEM.md#9-отказоустойчивость-и-цель-по-доступности)).

### `billing_periods`

`id`, `user_id`, `service` (пока только `valkey`), `resource_id`, `started_at`, `ended_at` (`null` у текущего периода), `mode`, `vcpu`, `ram_gb`, `node_count`, `price_coins_per_hour`, `started_reason` (`created`/`resized`), `ended_reason` (`resized`/`deleted`/`null`). Частичный unique-индекс `(service, resource_id) where ended_at is null` гарантирует, что открытый период у ресурса только один.

Пишет `api` в той же транзакции, что и само изменение: при создании открывает период с `started_reason=created`; при изменении размера закрывает текущий с `ended_reason=resized` и открывает новый с `started_reason=resized`; при удалении закрывает текущий с `ended_reason=deleted`. У открытого периода `ended_at` и `ended_reason` равны `null`, у закрытого заполнены оба поля. Новая ставка действует с момента принятия изменения размера, включая время перекатки. При удалении тарификация заканчивается в момент запроса, хотя освобождение ресурсов может занять больше времени. Цена в копейках за час фиксируется в строке, поэтому смена тарифа не меняет стоимость прошлых периодов. Расход за период — сумма `длительность * price_coins_per_hour` по строкам. Инстанс в `error` тарифицируется, пока пользователь его не удалит, и так же занимает квоту. Смена пароля и whitelist не меняет биллинговые периоды.

Связь `ended_at` и `ended_reason` закрепляется CHECK-ограничением: `(ended_at is null) = (ended_reason is null)`.

Таблица общая для будущих managed-сервисов, отсюда `service` и `resource_id` вместо `instance_id`.

### `idempotency_keys`

`user_id`, `key`, `request_hash`, `response_status`, `response_body jsonb`, `created_at`. Unique `(user_id, key)`. `request_hash` считается от метода, пути с id ресурса и тела, поэтому одинаковое тело изменения размера для двух разных инстансов с одним ключом не вернёт ответ для другого инстанса. Тело запроса не сохраняется; `request_hash` — SHA-256 канонического запроса. `response_body` содержит только публичный DTO, без полного пароля, хеша ACL и служебных секретов. Строки старше 24 часов чистятся.

### `auth_registration_keys`

`key` (UUID, pk), `user_id` (fk на `users.id`) и `created_at`. Строка создаётся в одной транзакции с пользователем, квотой и аудитом `user.register`. Она действует 24 часа и не хранит тело запроса, пароль, bcrypt-хеш или JWT. При повторе API находит пользователя по ключу, сравнивает нормализованную почту и пароль с `users.password_hash`, после чего выпускает JWT. Истёкшие строки удаляются перед регистрацией.

### `audit_logs`

`id`, `user_id`, `user_email`, `action`, `service` (пока только `valkey`), `resource_id` (`null` у действий с аккаунтом), `request_id`, `created_at`. Индексы `(resource_id, created_at desc, id desc)` и `(user_id, created_at desc)`. Email копируется в строку на момент записи: журнал читается без join и не меняется задним числом, если пользователь потом сменит почту.

`action` — короткая строка на английском из фиксированного списка, константы лежат в `api/internal/audit`:


| `action`                    | Когда                             |
| --------------------------- | --------------------------------- |
| `user.register`             | Создан аккаунт                    |
| `user.login`                | Успешный вход                     |
| `instance.create`           | Принято создание инстанса         |
| `instance.update`           | Изменено имя или окно maintenance |
| `instance.resize`           | Принято изменение размера          |
| `instance.whitelist.update` | Сохранён whitelist                |
| `instance.password.rotate`  | Принята смена пароля Valkey       |
| `instance.delete`           | Принято удаление                  |


Пишет общий внутренний сервис аудита, который вызывают сервисы пользователей и Valkey через интерфейс записи. Audit-сервис принимает ID и снимок автора как значения, не зависит от модели Valkey и не вызывает сервис базы. Репозиторий пользователей больше не вставляет AuditLog напрямую. Вызывающая операция передаёт ту же транзакцию; аудит не открывает независимую транзакцию и не делает собственный commit. Ошибка любой записи откатывает и бизнес-изменение, и аудит. HTTP API журнала добавляется отдельно.

Событие создаётся одной вставкой в той же транзакции, что и само изменение. Отклонённый по квоте, фазе или конфликту запрос не оставляет строки в журнале. Успешный повтор по `Idempotency-Key` тоже не пишет вторую строку, потому что повтор не меняет данные. Регистрация пишет аудит в транзакции создания аккаунта. Успешный вход пишет аудит в короткой транзакции до выпуска JWT.

Тело запроса, пароли, хеши и списки CIDR в журнал не попадают. Строка содержит автора и действие; подробности изменения видны по `billing_periods` и `valkey_instance_phase_events`. `request_id` тот же, что в логах [раздела 11](SYSTEM.md#11-логи), и связывает строку с записями в VictoriaLogs. Журнал в v1 автоматически не чистим и не удаляем при soft delete инстанса. Политика длительного хранения, архивирования, удаления и применимых требований законодательства прорабатывается отдельно; конкретный срок и обеспеченное юридическое соответствие в v1 не заявляются.

### Квота кластера

Лимиты в таблицах не хранятся: `MANAGED_K8S_NODE_VCPU` и `MANAGED_K8S_NODE_RAM_GB` задают общий бюджет Valkey всего кластера, несмотря на NODE в имени. На число Kubernetes-нод бюджет не умножается. Использование считается запросом по всем строкам с `deleted_at is null` независимо от фазы: сумма `nodes * greatest(vcpu, applied_vcpu)` и `nodes * greatest(ram_gb, applied_ram_gb)`, где `nodes` равно 1 для `single` и 3 для `ha`. Дополнительно проверяется предел 32 инстанса на одном Gateway. Так квота не освобождается раньше, чем оператор фактически уменьшил поды или удалил namespace. Инстансы в provisioning, error и deleting квоту занимают до заполнения deleted_at. Изменение размера заменяет собственный резерв покомпонентным максимумом нового desired и прежнего applied. При снижении лимита ниже занятого объёма каждая размерность допускается, если результат помещается в лимит либо не увеличивает прежнее использование.

Если создание не помещается в общий CPU/RAM-бюджет или превышает 32 инстанса, исходный HTTP POST немедленно возвращает `422 NOT_ENOUGH_RESOURCES` до записи инстанса и связанных данных. Не создаём заявку в ожидании расширения кластера и не ждём операторского таймаута. Проверка идёт по PostgreSQL и env под общим lock; Kubernetes не вызывается. Неожиданный отказ размещения после принятия запроса остаётся задачей диагностики оператора.

## Транзакции API

### Общая блокировка на изменения ресурсов

Причины выбора advisory lock и часов PostgreSQL описаны в [основном документе](SYSTEM.md#общая-блокировка-на-изменения-ресурсов). Здесь задан порядок выполнения транзакции.

Создание, изменение имени и maintenance, изменение размера, смена пароля, изменение whitelist и удаление используют одну блокировку PostgreSQL: `SELECT pg_advisory_xact_lock(1)`. Ключ `1` обозначает общую блокировку операций сервиса, а не ID пользователя или инстанса. API удерживает её только на время транзакции в базе. Запуск Valkey и применение настроек происходят позже, без этой блокировки.

Транзакция использует READ COMMITTED и ограничивает ожидание lock тремя секундами. Истечение ожидания даёт `503 UNAVAILABLE` с `reason=lock_timeout` и rollback. Чтение квоты выполняется отдельным SQL-запросом после получения advisory lock. После получения блокировки API заново читает строку существующего инстанса. Данные, которые middleware прочитал при проверке владельца, могли измениться за время ожидания.

Для временных отметок принятого изменения API один раз получает `clock_timestamp()` PostgreSQL уже после получения блокировки. Одно значение используется для `updated_at`, границы биллинговых периодов и времени соответствующей операции. Так закрытие старого периода и открытие нового имеют одну временную границу.

Проверки внутри транзакции идут в следующем порядке:

1. Для создания, изменения размера и смены пароля API ищет сохранённый ответ по `Idempotency-Key`. Если тот же запрос уже выполнен, возвращает прежний ответ без повторного изменения данных. Тот же ключ с другим запросом даёт `422 IDEMPOTENCY_MISMATCH`.
2. Для существующего инстанса API проверяет, не начато ли удаление. После его начала изменения отклоняются с `INSTANCE_NOT_READY`. Повторный запрос удаления остаётся допустимым.
3. Для изменения размера и whitelist API проверяет, меняет ли запрос выбранные настройки. Если запрошен уже выбранный размер или тот же whitelist после нормализации CIDR, возвращает `200` с текущими данными инстанса. Это правило действует даже во время применения этих настроек. Нового поколения и биллингового периода нет.
4. Для нового изменения размера, whitelist или пароля API проверяет завершение предыдущего изменения, затем фазу и свежесть наблюдения. Незавершённое изменение даёт `OPERATION_IN_PROGRESS`; неподходящая фаза или отсутствие свежего наблюдения дают `INSTANCE_NOT_READY`.

Фаза описывает состояние инстанса: например, он создаётся (`provisioning`), работает (`running`) или временно недоступен (`unavailable`). Номер поколения отвечает на другой вопрос: какую версию настроек оператор уже применил. `desired_generation` хранит номер принятой API конфигурации, `observed_generation` — номер полностью применённой. Пока они отличаются, следующее изменение конфигурации принимать нельзя. Например, после принятия изменения размера `desired_generation` уже увеличен, а старые поды ещё работают с прежним размером.

У пароля есть собственный счётчик: `password_version` и `applied_password_version`. Он позволяет отдельно подтвердить замену пароля на всех необходимых процессах. Версия пароля не меняется от изменения размера или whitelist; при смене пароля увеличиваются и она, и общее поколение конфигурации.

Имя и окно maintenance не меняют настройки подов. Их можно править до начала удаления независимо от активной операции, без увеличения поколения. Удаление разрешено при любой фазе и при незавершённом изменении конфигурации.

При создании и каждом увеличении `desired_generation` API в той же транзакции записывает `configuration_requested_at`, используя полученное время PostgreSQL. По этой отметке интерфейс и диагностика определяют, сколько длится применение настроек. Запрос без изменения, правка имени или maintenance и удаление эту отметку не меняют.

### Создание инстанса по шагам

1. UI генерирует пароль пользователя Valkey `app` по [правилам генерации и одноразового показа](SYSTEM.md#одноразовый-показ-и-смена-пароля-valkey). API проверяет имя, DNS-префикс (3–20 символов, `[a-z0-9-]`, начинается и заканчивается буквой или цифрой), размер из сетки, режим и формат пароля.
2. API открывает транзакцию и получает общую блокировку. Сначала проверяет `Idempotency-Key`: если создание уже принято, возвращает сохранённый ответ. Для нового запроса проверяет квоты пользователя и кластера. Превышение квоты пользователя даёт `QUOTA_EXCEEDED` с предложением написать в поддержку; нехватка квоты кластера даёт немедленный `422 NOT_ENOUGH_RESOURCES` в исходном запросе без записи инстанса, аудита, периода и ключа. В v1 создание не ждёт новых ресурсов или таймаута запуска.
3. API создаёт уникальный slug `<prefix>-<6 случайных символов [a-z0-9]>`, не сохраняя prefix отдельно. Если такой slug уже занят, генерирует другой суффикс. Из пароля вычисляет SHA-256 и сохраняет первые четыре символа для маски; служебные пароли позже создаст оператор в Kubernetes Secret.
4. В той же транзакции API записывает инстанс и его адреса, устанавливает `password_version=1` и `desired_generation=1`. Whitelist по умолчанию выключен, список пуст; переданные в POST начальные флаг и CIDR нормализуются и сохраняются в том же первоначальном поколении, без второго PUT. API открывает биллинговый период, сохраняет ответ для повторных запросов с тем же ключом и фиксирует транзакцию.
5. API возвращает `202` с данными инстанса без пароля. Начальная фаза `provisioning` означает, что запрос принят, но инстанс ещё создаётся. `observed_generation` и `applied_password_version` равны 0: оператор пока не подтвердил ни конфигурацию, ни пароль. UI один раз показывает пароль, который сохранил в памяти на первом шаге, с подписью «Инстанс создаётся».

Цикл доставки API делает первый проход сразу после запуска, затем опрашивает базу раз в секунду. На успешном проходе он создаёт необходимые объекты Kubernetes, включая CR `ValkeyInstance`. Оператор получает уведомление об этом CR через механизм наблюдения Kubernetes (watch) и начинает запуск Valkey.

Если Kubernetes или фоновая синхронизация недоступны, запрос остаётся в PostgreSQL и будет передан после восстановления. Таймаут создания отсчитывается с момента создания CR: ожидание передачи запроса из базы в Kubernetes в него не входит.

`spec.instanceId` равен `valkey_instances.id`; CRD запрещает его изменение после создания. Имя CR равно slug, namespace равен `valkey-<slug>`. API сверяет все три значения с записью БД перед доставкой или импортом. Несовпадение блокирует работу с этим объектом и записывается в ERROR для ручного разбора. Пользователь не управляет этими идентификаторами через публичный API.

`desiredGeneration` копирует колонку базы и отличается от `metadata.generation`, которой управляет k8s. CR не содержит паролей и хешей. `VALKEY_IMAGE` задаёт закреплённый образ Valkey для всех инстансов. В v1 его нельзя менять, пока существуют активные инстансы. При расхождении с образом существующего StatefulSet оператор записывает `RECOVERY_REQUIRED` и не меняет его шаблон или образ подов. Наблюдения и безопасное восстановление с прежним шаблоном продолжаются; команда эксплуатации возвращает прежнее значение env. Обновление существующих инстансов относится к v2. Оно потребует целевого образа в намерении и запуска через ту же очередь с увеличением `desired_generation`; смена env сама по себе такой операцией не является.

`status.credentialsInitialized` отмечает сохранение полного комплекта служебных паролей и `users.acl` в Secret; оператор ставит его до создания первого StatefulSet. После этого отсутствие служебных полей требует ручного восстановления. `status.initialized` означает первую публичную готовность и устанавливается вместе с первым переходом в `running` или `degraded`. Оба флага по умолчанию равны `false` и после установки не сбрасываются. Подготовленный Secret при ещё не готовом инстансе даёт `credentialsInitialized=true`, `initialized=false`: создание остаётся в `provisioning` и может завершиться по таймауту в `error`.

`status.nodes` позволяет отличить прежний процесс Valkey от нового, даже если Kubernetes повторно использовал имя пода. Отдельный запуск процесса далее называем инкарнацией. Для него оператор сохраняет номер пода в StatefulSet (ordinal), Pod UID, container ID и `runId` (поле `run_id` из `INFO server`). В записи также есть роль, готовность, имя и UID worker-ноды (`nodeName`, `nodeUID`). Идентификаторы ноды должны быть записаны до открытия клиентского доступа.

Для выбора реплики при переключении оператор сохраняет идентификаторы истории репликации, позицию в потоке данных (offset) и время последней успешной синхронизации. Для восстановления зависшего процесса нужны отдельные отметки:

- `busySince`, вид занятого скрипта и `busyRecoveryStage` (`waiting`/`killing`/`stopping`, иначе `null`) описывают обработку ответа `BUSY`;
- `unresponsiveSince` и `unresponsiveRecoveryStage` (`waiting`/`stopping`, иначе `null`) описывают ожидание процесса, который вообще не отвечает.

Эти таймеры и стадии относятся к конкретному запуску Valkey и сохраняются при рестарте оператора. `busySince` не сбрасывается до восстановления. Если процесс сменился, он получает новую запись; сведения о прежнем остаются до подтверждения его остановки. Порядок повторных проверок задан в [алгоритме восстановления процесса](#зависший-процесс-на-доступной-ноде).

Если остановка подтверждена удалением ноды, CR хранит основание `node_deleted`, время проверки и идентификаторы ноды и процесса. Эта запись сохраняется до снятия finalizer, чтобы перезапущенный оператор мог завершить удаление.

Ход операций хранится отдельно от состояния отдельных процессов:

- `failover` содержит причину (`failure`/`resize`), прежний primary и выбранного кандидата с их идентификаторами, стадию (`fencing`/`choosing`/`promoting`/`reconfiguring`), `startedAt` и подтверждения изоляции прежнего primary (fencing). Если прежний primary доступен, после fencing сохраняются его replication ID, контрольный offset и крайний срок ожидания репликации. Кандидат с неизвестным результатом назначения primary остаётся потенциальным primary до проверки роли, подтверждённого fencing или остановки.
- `rollout` содержит поколение, целевой размер и образ, стадию перекатки и текущий под.
- `credentialRotation` содержит версию пароля, стадию смены и подтверждения применения для конкретных Pod UID/container ID.
- `deletion` содержит этап остановки и подтверждения завершения процессов.

`observedGeneration` подтверждается только после применения всех полей соответствующего `spec`. Отдельные поля `appliedPasswordVersion` и `applied` показывают завершение смены пароля и применения размера. Они нужны, даже если другая часть конфигурации ещё ожидает применения.

`status.network` позволяет понять, какую сетевую конфигурацию оператор уже проверил. В нём хранятся ожидаемый и последний подтверждённый отпечатки настроек, результат проверки, время успеха и идентификаторы процессов Envoy, включая имя и UID ноды каждого процесса. Отпечаток описывает только настройки этого инстанса: hostname, backend Service и порт, whitelist, сертификат и TCP idle timeout из общей ClientTrafficPolicy. Весь общий Gateway и меняющийся список Pod IP в него не входят: иначе изменение соседнего инстанса или переключение пода потребовало бы заново подтверждать неизменённые настройки шлюза. Закрытый ключ сертификата в CR не сохраняется. Условия использования прежнего подтверждения описаны в [правилах публичной готовности](#readiness-и-публичная-готовность).

Дочерние объекты получают ownerReference на CR; Pod принадлежит StatefulSet. Listener в общем Gateway убирает finalizer CR. Правка общего `Gateway` идёт с проверкой `resourceVersion` и повтором, потому что несколько инстансов могут менять его одновременно.

Anti-affinity одинаковый на dev и на проде. Нехватка хостов оставляет под в `Pending`; фазы и причины заданы в [разделе 4](SYSTEM.md#4-данные-postgresql-18-миграции-goose). `Parallel` позволяет создать все поды до готовности пода 0, чтобы начальная синхронизация не зависела от последовательного ожидания readiness контроллером StatefulSet.

PDB ограничивает добровольные выселения через Eviction API, например `kubectl drain`. Он не защищает от аварии ноды и прямого удаления Pod, поэтому порядок перекатки и проверки остановки остаются обязанностью оператора. В `degraded` с двумя готовыми подами drain может ждать восстановления третьего. [Disruptions и PDB](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/).

Шаблон StatefulSet ссылается на ConfigMap своего размера и образа. При изменении размера создаётся новая ConfigMap, существующая не переписывается: перезапуск ещё не заменённого пода должен сохранить прежний `maxmemory` в пределах прежнего лимита контейнера. Старую ConfigMap можно удалить, когда на неё больше не ссылаются ни шаблон, ни существующие поды.

У Pod в шаблоне стоит `restartPolicy: Always`, у контейнера Valkey `restartPolicy: Never`, без `restartPolicyRules`. Это требует `ContainerRestartRules` на API server и worker-нодах Kubernetes 1.35. При обычном завершении контейнер остаётся остановленным. Оператор сохраняет в CR состояние `state.terminated` вместе с идентификаторами остановленного процесса, затем завершает удаление Pod и допускает его замену. Finalizer удерживает объект до сохранения доказательства. Смена контейнера из-за потери состояния kubelet всё ещё возможна; отсутствие доказательства прежнего завершения требует проверки удаления его ноды или ручного восстановления по [правилам остановки](#поды-на-недоступной-ноде). Политика `Never` сама по себе остановку не подтверждает.

### Конфигурация Valkey

```text
port 6379
bind 0.0.0.0
protected-mode no
aclfile /etc/valkey/users.acl
primaryuser replica
primaryauth <пароль replica из Secret>
maxmemory <75% лимита RAM, в байтах>
maxmemory-policy allkeys-lru
lazyfree-lazy-user-flush yes
save ""
appendonly no
repl-diskless-sync yes
repl-diskless-load on-empty-db
repl-backlog-size <clamp(1% лимита RAM, 1 MiB, 64 MiB), целые байты>
replica-serve-stale-data yes
io-threads <1 при vcpu менее 4, иначе min(vcpu, 8)>
replicaof <slug>-primary.valkey-<slug>.svc 6379
```

Последняя строка нужна только в `ha`: каждый свежий процесс стартует репликой. Только оператор назначает primary. Шаблон с секретными значениями собирается при запуске во временный файл на `emptyDir.medium: Memory`; пароли не попадают в ConfigMap, аргументы процесса и логи. `users.acl` монтируется из Secret. Его начальное содержимое:

```text
user default off
user app off #<SHA-256 пароля app> ~* &* -@all +@read +@write +@pubsub +@transaction +@keyspace +@string +@list +@hash +@set +@sortedset +@stream +@bitmap +@hyperloglog +@geo +@blocking +@connection +@scripting -@dangerous +ping +echo +select +info +flushdb +flushall +sort +sort_ro
user operator on ><пароль operator> ~* &* +@all
user replica on ><пароль replica> -@all +psync +replconf +ping
user health on ><пароль health> -@all +ping +role +info
```

Учётная запись `app` выключена при каждом запуске Valkey, включая `single`. Перед открытием клиентского доступа оператор записывает в CR идентификаторы процесса и ставит на Pod finalizer `valkey.h3llo-demo.com/process-stopped`. Перед `ACL SETUSER app on` оператор проверяет актуальный хеш, отсутствие незавершённого fencing и назначенную этому процессу роль. Это защищает от старого ACL в смонтированном Secret после рестарта. Изменения Secret сами по себе не применяют ACL в работающем Valkey; их применяет оператор. `ACL LOAD` и `ACL SAVE` для обычной смены пароля не используются.

ACL проверяется на зафиксированной версии Valkey. `app` разрешены `EVAL`, `EVALSHA`, загрузка и вызов Functions в пределах разрешённых команд. Запрещены `CONFIG`, `REPLICAOF`, `FAILOVER`, `ACL`, `DEBUG`, `SHUTDOWN`, `MONITOR`, `KEYS`, а также `CLIENT KILL`, `CLIENT PAUSE`, `CLIENT LIST`. `CLIENT SETNAME`, `CLIENT SETINFO`, `CLIENT ID` разрешены: ими пользуются клиентские библиотеки при подключении. `health` имеет случайный пароль; readiness читает его из Secret, наружу эта учётная запись не выдаётся.

После `-@dangerous` явно разрешены `FLUSHDB`, `FLUSHALL`, `SORT` и `SORT_RO`: пользователь может очищать и обрабатывать данные своего инстанса. `lazyfree-lazy-user-flush yes` делает очистку без явного `SYNC` асинхронной; `FLUSHALL SYNC` всё ещё может блокировать процесс. Административные запреты выше сохраняются. [FLUSHDB](https://valkey.io/commands/flushdb/), [FLUSHALL](https://valkey.io/commands/flushall/), [SORT](https://valkey.io/commands/sort/), [SORT_RO](https://valkey.io/commands/sort_ro/).

Лимит `maxmemory` в 75% оставляет резерв на память процесса, фрагментацию, буферы клиентов и репликации. Полная синхронизация даже в diskless-режиме может делать fork; запись в это время увеличивает copy-on-write память. Резерв 25% не гарантирует отсутствие OOM. Размер backlog задаётся от RAM, но частичная синхронизация также зависит от истории репликации и объёма записей за время разрыва. Полная повторная синхронизация при параллельной записи входит в нагрузочную проверку перед запуском. [Репликация Valkey](https://valkey.io/topics/replication/).

## Алгоритмы оператора

### Три цикла

API передаёт выбранные пользователем настройки из PostgreSQL в ресурс
Kubernetes `ValkeyInstance` (CR). Оператор по этим настройкам управляет
Valkey и записывает результат в `status` CR. Второй цикл API переносит
состояние из CR обратно в базу. Далее передача настроек называется доставкой
намерения, а сохранение результатов проверок — импортом наблюдений.
Цикл оператора, который сверяет требуемое состояние с фактическим и устраняет
различия, называется reconcile.

В алгоритмах нужно различать под Kubernetes и запущенный в нём процесс Valkey.
Под с тем же именем может быть создан заново, а контейнер — перезапущен.
Отдельный запуск Valkey называем инкарнацией; его идентичность задают
Pod UID, container ID и идентификатор Valkey `run_id`. Подтверждение остановки
или применения пароля относится именно к этому запуску, а не ко всем будущим
процессам с тем же именем пода.

При старте оператор сначала получает Lease — запись Kubernetes, которая
закрепляет за ним право управления на ограниченное время. Для каждого
доступного процесса Valkey он открывает отдельное соединение, дожидается
успешного AUTH под
`operator` и выполняет `CLIENT KILL USER operator SKIPME YES`. Эта команда
закрывает оставшиеся соединения прежнего оператора, сохраняя текущее.
До завершения этого шага не запускаются другие соединения оператора к этому процессу,
включая сбор метрик. Затем оператор заново читает роли, идентичности,
ACL и состояния незавершённых операций. Закрытие старых соединений не
отменяет уже выполненный `REPLICAOF`: роль процесса проверяется отдельно.
[CLIENT KILL](https://valkey.io/commands/client-kill/),
[REPLICAOF](https://valkey.io/commands/replicaof/).

StatefulSet с одной репликой не допускает штатный запуск преемника до
остановки прежнего оператора. Для удаления worker-ноды через ЛК действует
[принятое в v1 условие](#удаление-worker-ноды-через-лк): облако уничтожает VM
до удаления Node. Kubernetes убирает старый под оператора и создаёт замену
на доступной ноде без участия самого оператора. Получение Lease и очистка
соединений остаются обязательными; истечение Lease при существующей
недоступной ноде не разрешает принудительную замену.
AUTH и команду изменения состояния нельзя отправлять одним пакетом (pipeline):
оператор сначала должен получить ответ об успешной авторизации.
Автоматические повторы изменяющих команд в клиенте отключены. При потере
Lease оператор отменяет текущие задачи, закрывает соединения и завершает
процесс. Если ответ на команду потерян, она уже могла выполниться.
Поэтому перед следующим действием оператор читает фактическое состояние.
Сам Lease не блокирует запоздалые команды к Valkey.

При `BUSY` сначала допускается только восстановление занятого процесса
по правилам ниже. Включать `app` и менять primary нельзя до очистки
старых подключений или подтверждённой остановки этой инкарнации. Процесс,
который был недоступен при старте оператора, проходит такую же процедуру
при первом восстановленном подключении.

Reconcile и сбор метрик запускает только оператор, владеющий Lease.
Проходы reconcile одного инстанса выполняются последовательно; разные
инстансы могут обрабатываться параллельно. Доставка намерения и импорт
наблюдений работают в API независимо от Lease оператора.
Оба цикла делают первый проход сразу, затем используют `config.SyncInterval`, равный одной секунде. В v1 API запускается одной репликой,
проходы одного цикла не перекрываются и не накапливаются. Ошибка одного инстанса не прерывает
обработку остальных. HTTP-обработчики сохраняют намерение в PostgreSQL
и не ждут записи в Kubernetes.

Цикл **база → CR** работает в API и читает строки с `deleted_at is null`.
Перед изменением объектов он заново читает из базы запрос удаления и
поколение, то есть номер принятой версии конфигурации. Для новой активной
строки создаёт namespace, Secret с `appPasswordHashes` по номеру версии,
затем CR с finalizer. Эта служебная отметка не даёт Kubernetes завершить
удаление CR, пока оператор не остановит процессы и не уберёт маршруты.
В `spec.instanceId` записывается ID строки PostgreSQL; CRD запрещает его изменение. Имя CR и
namespace должны совпадать с ожидаемыми slug и `valkey-<slug>`.
Несовпадение ID или имён блокирует доставку и импорт этого объекта;
API пишет ERROR для ручного разбора. Уже удаляемый CR не обновляется
и не создаётся заново.

API записывает в Secret хеши пароля `app` с номерами версий, сохраняя
остальные поля. При обновлении сначала добавляется хеш новой версии,
затем обновляются `spec.passwordVersion` и остальной `spec`. До подтверждения
новой версии Secret сохраняет предыдущий хеш. Reconcile выбирает только
хеш версии из текущего `spec`; отсутствие этой версии блокирует применение.
Если API успел обновить Secret, но ещё не записал новый `spec`, оператор
продолжает использовать хеш действующей версии. Он остаётся доступен для
failover даже при последующем отказе API или PostgreSQL.

Оператор при первом reconcile создаёт служебные пароли `operator`,
`replica` и `health` одной записью в существующий Secret. Он сохраняет
уже записанные пароли при повторе, формирует `users.acl`, затем устанавливает
`status.credentialsInitialized=true` до создания первого StatefulSet. При рестарте
между записью Secret и `status` оператор использует сохранённые пароли.
Файл `users.acl` формирует только оператор по хешу текущего `spec.passwordVersion`
и обновляет при смене этой версии; в нём `app` всегда выключен.
До старта подов Secret должен содержать весь комплект служебных паролей
и ACL с хешом версии из текущего `spec`.
Оба флага изначально равны `false`. `credentialsInitialized` подтверждает
только сохранение служебных паролей и ACL. `initialized` остаётся `false`
до первой публичной готовности; подготовка Secret не отменяет
`provisioning`, таймаут создания или переход в `error`.

При обновлении Secret и CR проверяется `resourceVersion`: объект должен
оставаться той же версии, которую прочитал автор изменения. Это защищает
от перезаписи чужих изменений между чтением и записью. При конфликте API
заново читает объект и свежую строку базы, оператор заново читает CR и Secret.
Доставка не откатывает `desiredGeneration` или `passwordVersion`,
не заменяет Secret целиком и не меняет `status` или служебные аннотации CR.
Оператор сохраняет доставленные хеши и меняет только служебные поля,
`users.acl` и предыдущий хеш после подтверждённой ротации. При следующей
передаче настроек API не должен возвращать уже удалённый хеш из устаревших данных.

Потеря Secret у существующего CR требует восстановления человеком;
API не создаёт вместо него пустой Secret. Если `status.credentialsInitialized=true`,
отсутствие любого служебного пароля также требует ручного восстановления.
Генерировать новые пароли для уже работающих подов нельзя. Оператор пишет
`RECOVERY_REQUIRED` в condition и Event, операция остаётся незавершённой.
Потеря CR с историей работающего инстанса также требует ручного восстановления.
При отсутствии CR у строки без запроса удаления API проверяет ранее
импортированные наблюдения и оставшийся Secret: служебные поля оператора означают, что обработка CR
уже началась. Создавать такой CR заново как для нового инстанса нельзя: в нём не будет
истории прежних процессов и незавершённых операций.
API пишет ERROR; без CR он не может записать его condition. После сбоя
доставки до первого CR разрешено продолжить создание с уже созданными
namespace и Secret, содержащим только хеши `app`.

Для `deletion_requested_at` API сначала запрашивает удаление CR, оставляя
namespace и Secret на месте. Оператор через finalizer CR удаляет listener
и маршруты, выключает `app` и закрывает его соединения на доступных подах,
переводит StatefulSet в 0 реплик и подтверждает остановку всех известных
процессов. Затем снимает finalizer, и k8s удаляет CR с дочерними объектами.
Только после подтверждённого исчезновения CR в ходе этого удаления API
удаляет namespace. Иначе namespace controller мог бы удалить Secret до
завершения остановки. Reconcile с `deletionTimestamp` никогда не восстанавливает
поды и маршруты. Неожиданная потеря CR с историей требует ручного разбора,
а не автоматического удаления namespace. Для отменённого до первого CR
создания API может удалить созданный им namespace без запуска Valkey.

После `NotFound` namespace API ставит `deleted_at` и пишет событие
`deleted` одной транзакцией; повтор после рестарта не создаёт второе событие.
После рестарта API заново читает `deletion_requested_at`, CR и namespace:
при `deletionTimestamp` ждёт finalizer, после завершённого удаления CR
продолжает удаление namespace, а после его `NotFound` завершает запись в БД.
Ошибка Kubernetes не считается `NotFound`.
До этого квота занята. Если недоступная worker-нода остаётся в Kubernetes,
удаление может ждать ручного подтверждения её выключения. Удаление ноды
через ЛК подтверждается автоматически по [общему правилу](#удаление-worker-ноды-через-лк).
Ручное снятие finalizer не является
штатным способом завершить удаление.

Без явного `deletion_requested_at` API не удаляет namespace. Отсутствие
строки в выборке, ошибка базы и несовпадающая схема не означают удаление.
Namespace без строки API отмечает в логах для ручного разбора.
При недоступной базе или Kubernetes доставка новых изменений
приостанавливается. После рестарта API повторяет сверку строк и объектов;
принятое намерение не зависит от очереди в памяти. Оператор продолжает
обрабатывать имеющиеся CR, если ему доступен Kubernetes.

Цикл **CR → объекты k8s** работает в операторе без обращения к PostgreSQL
и API сервиса. Он хранит в `status` текущий primary, UID подов, container ID,
идентификаторы процессов Valkey и стадии операций. Перед каждым действием,
меняющим состояние, записывает стадию, которую собирается выполнить,
а после действия проверяет результат. При рестарте оператор заново проверяет
состояние и продолжает операцию: запись стадии сама по себе не подтверждает
завершение команды. Если результат команды неизвестен, нужно повторно прочитать
фактическое состояние. Оператор сначала обрабатывает удаление. Если оно не запрошено,
восстанавливает primary; к текущей операции переходит после восстановления.

Оператор раз в 10 секунд выполняет свежую проверку состояния и записывает
`status.observedAt`, даже если фаза прежняя. Эта отметка времени служит
heartbeat: показывает, что оператор продолжает проверять инстанс. Если
k8s API недоступен или свежую проверку выполнить нельзя, отметка
не обновляется. Полученный таймаут отдельного пода при доступном k8s
считается свежим наблюдением его недоступности. Ответы `BUSY`, `LOADING` и ошибки AUTH тоже являются
свежими наблюдениями. Проверка Envoy работает с отдельным таймаутом и
не задерживает heartbeat: ошибка его admin API меняет только состояние
проверки сети.

Сбор метрик выполняется с `config.MetricsInterval`, равным 10 секундам, и сохраняет последние
успешные снимки текущих процессов в `status.metrics`. Снимок содержит
ordinal (номер пода в StatefulSet), Pod UID/container ID, `runId`,
время `collectedAt` и показатели из
[контракта метрик](SYSTEM.md#метрики-1). На ordinal приходится максимум один
снимок, на CR максимум три. При смене процесса оператор удаляет прежний
снимок и ждёт успешного сбора нового. Ошибка `INFO` не создаёт измерение
и не обновляет время прежнего снимка того же процесса. Ошибка CPU даёт `null`
для CPU, остальные показатели сохраняются. Сбор не блокирует heartbeat или
восстановление. Запись метрик не перезаписывает состояния операций в `status`:
обновления сериализуются с reconcile либо повторяются после конфликта
`resourceVersion` по свежему CR.

Цикл **CR → база** работает в API. Он начинает первый проход сразу и затем опрашивает CR каждую секунду,
проверяет `spec.instanceId` и ожидаемые имена, затем переносит `phase`, reason,
поколения, `applied_*`, ноды, состояние проверки сети и `is_recovery_required`
из condition `RECOVERY_REQUIRED`. API переносит `status.observedAt` в
`observed_at`, не ставит своё `now()` при повторном чтении старого CR.

В транзакции API блокирует строку инстанса, перечитывает сохранённые наблюдения
и обновляет только наблюдаемые колонки. При импорте нельзя уменьшать
сохранённое время проверки или подтверждённое поколение. Изменение фазы
записывается в той же транзакции; повторный импорт того же состояния не создаёт событие. Намерение пользователя
и `updated_at` не меняются; `deleted_at` заполняет только цикл удаления,
и запоздалые наблюдения не возвращают удалённый инстанс в работу.

Импорт снимков из `status.metrics` в `valkey_node_metrics` пока не подключён.
Будущий импорт проверяет принадлежность инстансу и идентичность процесса
по `status.nodes`, сохраняет исходный `collectedAt` как `ts` и остальные
показатели. Снимки старше срока хранения не вставляются. Уникальность
`(instance_id, ordinal, ts)` и `ON CONFLICT DO NOTHING` защищают от повторной
вставки. Отсутствующие измерения не заменяются нулями.

После восстановления API, PostgreSQL или связи с Kubernetes импортируется
последнее доступное состояние. Из текущего CR нельзя восстановить
промежуточные фазы, которые уже сменились между опросами. Когда появится
импорт метрик, он также не сможет восстановить уже вытесненные из CR снимки.
Чтение сохранённой истории пользователем проходит через API с проверкой
владельца инстанса и выборкой по его ID из PostgreSQL.

### Readiness и публичная готовность

Здесь проверяются две разные вещи: готов ли процесс Valkey и готовы ли
настройки, через которые к нему подключаются клиенты. Ответа самого Valkey
недостаточно: могут быть не готовы маршрут, whitelist или TLS. Проверку
всех этих условий называем публичной готовностью. Она выполняется изнутри
кластера и не измеряет доступность инстанса из интернета для SLA.

При изменении настроек прежняя конфигурация может продолжать работать,
пока новая ещё применяется. Например, ожидание нового whitelist или
подтверждений (`conditions`) после правки общего Gateway само по себе
не означает отказ прежнего маршрута: операция остаётся в `updating`.
В `unavailable` инстанс попадает при подтверждённой потере рабочего
маршрута, primary или действующего TLS. Новое поколение считается применённым
только после полной проверки целевой конфигурации.

Скрипт readiness из ConfigMap подключается под служебным пользователем
`health` и проверяет ответы `ROLE` и `INFO replication`:
готов процесс с `ROLE=master` либо с `ROLE=slave` и
`master_link_status:up`. Параметры probe: `periodSeconds: 5`,
`timeoutSeconds: 3`, `failureThreshold: 3`, `successThreshold: 1`.
Метки из downward API в этой проверке не участвуют.

Readiness определяет, включит ли Kubernetes под в endpoints — список
адресов, на которые Service направляет трафик. Эта проверка сама
не перезапускает контейнер. Отдельную liveness-пробу в v1 не ставим: зависший процесс
останавливает оператор по алгоритму ниже, с сохранением идентичности и
подтверждением остановки. [Виды проверок Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

Probe проверяет процесс, а оператор управляет допуском клиента. Он
сверяет реальные роли, хеш `app` и идентичность процесса до назначения
метки Service и включения `app`. Перезапущенный бывший primary в `ha`
стартует репликой, настроенной на Service своего инстанса. Пока рабочего
источника репликации (upstream) нет, связь с ним отсутствует (link down),
readiness не проходит и `app` выключен. Даже при задержке EndpointSlice
или обновления Secret новый процесс не принимает пользовательские команды.
Реплика с незавершённой синхронизацией не попадает в `-ro`.

Условия первоначальной публичной готовности должны выполняться одновременно:

- primary отвечает в роли master, `app` включён с текущим хешем, а
  `<slug>-primary` направляет трафик только к его текущему Pod UID/IP;
- нужные listeners приняты и запрограммированы Envoy Gateway, TCPRoute
  имеют актуальные `Accepted=True` и `ResolvedRefs=True`; проверяются
  conditions для текущей `metadata.generation` и того Gateway/listener,
  к которому маршрут привязан через `parentRefs`;
- включённые SecurityPolicy приняты и применены к своим маршрутам;
  выключенные удалены, и шлюз подтвердил актуальную конфигурацию.
  Пустой включённый whitelist с `defaultAction: Deny` является готовой
  конфигурацией и намеренно запрещает всех клиентов;
- общая ClientTrafficPolicy принята, а активные TCP-фильтры Envoy
  используют заданный в ней idle timeout; для dev и prod это 3600 секунд
  по [разделу 7 SYSTEM.md](SYSTEM.md#долгие-соединения);
- Secret сертификата содержит действующий сертификат для доменов. На
  проде соответствующий `Certificate` имеет `Ready=True`; на dev
  проверяется сертификат mkcert. Envoy принял ссылку и TLS-конфигурацию.

Даже успешные `conditions` подтверждают принятие настроек контроллером,
но не заменяют проверку их загрузки в каждый процесс Envoy. Поэтому оператор
читает активную конфигурацию непосредственно у прокси.
В v1 сверка рассчитана на две доступные штатные реплики Envoy:
оператор умеет прочитать формат закреплённой версии и сравнить нужные поля.
Универсальный разборщик конфигураций разных версий не нужен.

1. Прочитать актуальные `conditions` изменяемых объектов и определить
   текущие поды Envoy. Сохранить ожидаемый отпечаток конфигурации,
   по которому можно сравнить требуемые и загруженные настройки.
   В него входят только поля этого инстанса: hostname,
   backend Service/порт, нормализованные CIDR, сертификат и TCP idle timeout.
2. Через k8s port-forward к локальному admin-порту 19000 обеих реплик
   выполнить GET `/config_dump` с фильтром ресурсов и `/certs`.
   Сопоставить активные filter chains по SNI, backend-кластеры, правила
   RBAC, TCP idle timeout и загруженный сертификат. Конфигурация в состоянии
   warming ещё подготавливается и не подтверждает применение. Снимок
   переиспользуется для всех инстансов в одном цикле;
   содержимое дампа не логируется и не сохраняется в CR или PostgreSQL.
3. Убедиться, что Pod UID/container ID, состав реплик и ожидаемый отпечаток
   не изменились за время проверки. Совпадение на обеих репликах даёт
   `verified`; сохранить отпечаток, идентичности процессов и время успеха.
   Изменение listener соседа не отменяет подтверждение неизменённых полей
   проверяемого инстанса только из-за нового поколения общего Gateway.

Чтение одной реплики ограничено `config.NetworkVerifyTimeout`, равным 3 секундам, повтор
цикла идёт через `config.NetworkVerifyInterval`, равный 10 секундам. Ожидание известной целевой
конфигурации даёт `pending`; таймаут, недоступный admin API, неизвестный
формат или неоднозначный состав обслуживающих процессов дают `unknown`.
Один успешный ответ из двух недостаточен: другая реплика Envoy тоже
может принимать клиентские соединения. Последнее успешное подтверждение
сохраняется, `network_verified_at` при ошибке не обновляется. Эти состояния
попадают в DTO как `network_verification_status` и отдельное предупреждение;
они не мешают обновлять `observed_at` по свежим проверкам Valkey и k8s.

Первое создание и изменение собственных сетевых полей ждут `verified`
для целевого отпечатка. При смене только пароля или размера можно опереться
на ранее подтверждённые неизменные сетевые поля, даже если очередная
сверка стала `unknown`. Роль primary и актуальные EndpointSlice проверяются
отдельно; старый список Pod IP не используется как подтверждение после
переключения. Сбой проверки сам по себе не даёт `unavailable` и не запускает
failover. Подтверждённая поломка рабочего маршрута или истёкший TLS дают
`unavailable/NETWORK_NOT_READY` независимо от прежнего отпечатка.

Штатная замена Envoy требует проверки нового состава из двух реплик.
`NotReady` или исчезновение только Pod не доказывают остановку старого
процесса: при неподтверждённой остановке и неоднозначном составе проверка
остаётся `unknown`. В v1 оператор ждёт и повторяет проверку; после 10 минут API записывает
`ERROR` по [правилам диагностики](SYSTEM.md#ошибки-для-эксплуатации). Дежурный проверяет остановку прежнего
процесса и обслуживаемые балансировщиком backend, затем восстанавливает штатный
состав. После подтверждённого выключения ноды удаление её зависших объектов
разрешено по штатной инструкции; подмена результата проверки на `verified`
вручную не допускается. Если прежняя нода удалена по
[правилу v1](#удаление-worker-ноды-через-лк), её процессы Envoy считаются
остановленными без ручного подтверждения. Их `nodeName` и `nodeUID`
сохраняются вместе с Pod UID/container ID при наблюдении состава шлюза.
Оператор заново проверяет обе текущие реплики Envoy и маршруты; само удаление
Node не даёт `verified`. Автоматический разбор частичных отказов, обнаружение
оставшихся вне k8s процессов и вывод backend из балансировщика относятся
к v2. Локальный admin API не публикуется наружу.
[Доступ к admin API Envoy Gateway](https://gateway.envoyproxy.io/v1.8/troubleshooting/envoy-proxy-admin-interface/).

При первом запуске оператор сначала готовит маршруты, политику и TLS,
оставляя `app off`; после подтверждения шлюза включает проверенные
процессы и публикует метки Service. Клиенты не получают доступ до применения
первоначального whitelist. В `ha` объекты маршрута `-ro` должны быть готовы,
но отсутствие готовой реплики допускает выход в `degraded`.
Первое подтверждение поколения допускается при таком `degraded`: целевой
шаблон StatefulSet создан, primary готов, а хеш подтверждён на каждом
работающем процессе; будущие процессы стартуют с `app off`. Начальные
`applied_*` фиксируют размер primary и шаблона, квота учитывает все 3 ноды.
Для последующего изменения размера требуется полная перекатка по правилам ниже.
Проверка шлюза не гарантирует доступность внешнего балансировщика и DNS.
При невалидной конфигурации инстанс остаётся
в `provisioning` до таймаута; её поломка после создания даёт
`unavailable/NETWORK_NOT_READY`.

### Первый запуск

В `ha` все процессы Valkey запускаются в роли реплик. Когда под 0
отвечает, оператор фиксирует его Pod UID/container ID, выполняет `REPLICAOF NO ONE`, проверяет
`ROLE=master`, применяет актуальный хеш. После подтверждения конфигурации шлюза
включает `app` и ставит `role=primary`. Остальным задаёт `REPLICAOF <IP primary> 6379`; после
синхронизации и подтверждения шлюза проверяет ACL, включает `app` и ставит
`role=replica`. Для синхронизации используется служебный пользователь
`replica`, поэтому клиентскую учётную запись `app` можно пока не включать.
Первоначальный primary может быть пустым: истории данных ещё нет.
[REPLICAOF](https://valkey.io/commands/replicaof/),
[ROLE](https://valkey.io/commands/role/).

В `single` процесс сразу имеет роль master, но `app` также выключен до
проверки оператором. После публичной готовности инстанс становится
`running`; для `ha` отсутствие готовой реплики даёт `degraded`. Оператор
сохраняет `status.initialized=true` вместе с этим первым подтверждением.
Оба флага инициализации после установки не сбрасываются.

### Failover (`ha`)

Failover — переключение на реплику, которая станет новым primary. Главная
проверка перед переключением: прежний primary больше не должен принимать
клиентские команды. Для этого оператор запрещает ему клиентский доступ
и закрывает соединения либо получает подтверждение остановки процесса.
Эта изоляция называется fencing. Одной потери связи с прежним primary
недостаточно: он может продолжать обслуживать клиентов по другую сторону
сетевого сбоя.

В описании стадий источник — прежний primary, а цель или кандидат —
реплика, выбранная ему на замену. Запись вида `unavailable/FAILOVER`
означает фазу `unavailable` с причиной `FAILOVER`, а не отдельную фазу.

Оператор проверяет primary каждые `config.HealthCheckInterval=5s` с отдельными
`config.ValkeyDialTimeout=1s` и `config.ValkeyCommandTimeout=3s`. Чтобы признать
сетевой сбой устойчивым,
нужны минимум три неуспешные проверки подряд, охватывающие не менее 10 секунд.
Успех сбрасывает счётчик. Смена container ID или неожиданная роль требуют
отдельной проверки истории процесса; ожидаемая смена роли в сохранённых
стадиях `promoting` и `reconfiguring` не запускает второе переключение.

Ответы Valkey не смешиваются с транспортными ошибками:

| Ответ проверки | Действие |
|----------------|----------|
| Успешный PING и ожидаемая роль | Сбросить счётчик сетевых ошибок и `busySince` |
| `BUSY` от Lua/Function | Процесс жив; сбросить сетевой счётчик, сохранить `busySince`, проверять занятый скрипт по алгоритму ниже |
| `LOADING` | Процесс отвечает, но загружает данные; сбросить сетевой счётчик, ждать окончания загрузки; недоступный primary получает `DATA_LOADING` |
| `NOAUTH`/`WRONGPASS` | Проверить служебный Secret и подключение; не считать сетевым отказом, записать `RECOVERY_REQUIRED`; если готовность primary не подтверждается, причина `AUTH_FAILED` |
| Таймаут, отказ подключения, EOF | Увеличить сетевой счётчик; решение о failover только вместе с проверкой k8s и fencing |

Проверки с тем же интервалом и таймаутами выполняются для `single` и реплик.
При первой транспортной ошибке оператор записывает время в
`unresponsiveSince` и начинает стадию `waiting` для этой инкарнации. Любой
полученный ответ Valkey, включая `BUSY`, `LOADING`
и ошибку авторизации, сбрасывает ожидание отсутствия ответов. Эти ответы
обрабатываются своими алгоритмами. Сменившийся container ID требует
проверки остановки прежнего процесса и получает собственное состояние.
После принятого удаления Pod восстановившийся ответ уже не отменяет остановку.

Если процесс ненадолго ответил `BUSY`, а затем снова обслуживает команды,
переключать primary не требуется.
Пока primary не обслуживает команды, фаза `unavailable/SCRIPT_BUSY`
отражает недоступность; после восстановления она снимается. Порог
`config.ScriptBusyTimeout`, равный 30 секундам от первого `BUSY`, задаёт начало вмешательства;
отображение состояния не ждёт этого порога. Оператор пытается завершить скрипт:
`SCRIPT KILL` для Lua или `FUNCTION KILL` для Function. Если тип неизвестен,
пробует команды по очереди; `NOTBUSY` требует повторного чтения состояния.
При успешной остановке скрипта оператор повторно проверяет роль и ACL,
затем возвращает инстанс в работу без обязательного failover. `busySince` не является
измерением полной длительности скрипта: `BUSY` появляется после порога
Valkey. [Выполнение скриптов](https://valkey.io/topics/programmability/),
[SCRIPT KILL](https://valkey.io/commands/script-kill/),
[FUNCTION KILL](https://valkey.io/commands/function-kill/).

Если скрипт уже писал данные и получен `UNKILLABLE`, оператор сохраняет
стадию остановки и отправляет `SHUTDOWN NOSAVE`; при невозможности выполнить
команду запрашивает штатное удаление Pod без force. Разрыв соединения
не доказывает завершения команды: нужно подтверждение остановки конкретного
контейнера. Затем применяется обычный failover или восстановление `single`.
При этом возможна потеря кэша. Одного `BUSY` для автоматического promote недостаточно.
Для занятой реплики применяется та же остановка без переключения primary.
В Valkey 8.1.9 `AUTH` разрешён при `BUSY`, поэтому оператор может открыть
новое соединение для команды завершения скрипта. `CLIENT KILL` в этой
версии не разрешён при `BUSY`: очистка старых подключений ждёт завершения
скрипта. Если подключиться к уже наблюдавшемуся занятому процессу не
удаётся, остаётся штатная остановка Pod после порога вмешательства,
с актуальной проверкой k8s. Одна ошибка служебного пароля без `BUSY`
этот путь не разрешает.
[AUTH в 8.1.9](https://github.com/valkey-io/valkey/blob/8.1.9/src/commands/auth.json),
[CLIENT KILL в 8.1.9](https://github.com/valkey-io/valkey/blob/8.1.9/src/commands/client-kill.json).
[SHUTDOWN](https://valkey.io/commands/shutdown/).

Одних неуспешных `PING` недостаточно для разрушительных действий.
Оператор сверяется со свежим состоянием k8s: `Ready=False`, изменившийся
container ID, завершение контейнера или `Node NotReady`. Если из сети
оператора одновременно пропали поды, которые kubelet считает Ready,
он прекращает переключения для них, пишет общий Event/лог о возможном
сбое наблюдения и продолжает проверки. При недоступном k8s API команды,
меняющие роли и поды, не выполняются. Под с `Ready=True` из-за одних
таймаутов оператора удалять нельзя.

Если нода доступна, оператор может запросить штатное удаление Pod и
дождаться подтверждения остановки процесса от kubelet. Правила заданы
в подразделе «Зависший процесс на доступной ноде». Запросить такую остановку
можно и во время ожидания fencing. Само
истечение порога ожидания не разрешает назначить реплику новым primary.

После подтверждения сбоя либо при плановом переключении во время изменения размера
оператор проходит один алгоритм. В `status.failover` он сохраняет причину
(`failure` или `resize`), источник, цель и стадию до соответствующего действия.
Команды `FAILOVER` и `FAILOVER ABORT` оператор в v1 не использует: при потере
подтверждения `PSYNC FAILOVER` Valkey 8.1.9 может сам вернуть источнику роль
master после продвижения цели. Запрет на явный `ABORT` не предотвращает
такой откат. [Реализация переключения в Valkey 8.1.9](https://github.com/valkey-io/valkey/blob/8.1.9/src/replication.c#L3476).

Стадии идут последовательно:

1. `fencing`: сохранить идентификаторы прежнего primary и снять его метку
   Service. Если старый primary доступен, выполнить `ACL SETUSER app off`,
   затем `CLIENT KILL USER app` под `operator` и получить подтверждение
   обоих действий. `off` запрещает новую авторизацию, но сам не закрывает
   уже открытые соединения. Если процесс недоступен, ждать доказательства
   его остановки, описанного ниже. До этого нового primary не назначать.
2. `choosing`: выбрать доступную реплику, которая дальше остальных
   продвинулась в том же потоке репликации (имеет наибольший offset).
   Оператор должен ранее подтвердить синхронизацию именно этой инкарнации.
   Проверить `run_id`, replication ID и
   сохранённую идентичность. Новый пустой процесс или процесс с неизвестной
   историей нельзя использовать как копию данных. Если старый primary
   доступен, после fencing сохранить его replication ID, контрольный offset
   и крайний срок ожидания в `status.failover`. Ждать до `config.FailoverTimeout=5s`,
   пока offset кандидата не достигнет контрольного значения в той же истории.
   Рестарт оператора не начинает ожидание заново. Истечение этого срока
   разрешает продолжить с отстающей пригодной репликой с возможной потерей
   последних записей; оно не заменяет fencing или проверку истории.
   Сравнивать offset разных историй без проверки replication ID нельзя:
   одинаковая позиция в разных потоках не означает одинаковые данные.
   [История репликации](https://valkey.io/topics/replication/),
   [INFO replication](https://valkey.io/commands/info/).
3. `promoting`: сохранить идентификаторы выбранного кандидата до отправки
   команды. Ещё раз проверить fencing источника, роль и историю кандидата.
   На кандидате выполнить `ACL SETUSER app off` и `CLIENT KILL USER app`,
   подтвердить оба действия, затем выполнить `REPLICAOF NO ONE`.
   Подтвердить `ROLE=master` у того же процесса, применить актуальный хеш
   `app`, включить его и назначить единственную метку `role=primary`.
   Сохранить идентичность нового primary. На всём этом этапе прежний
   primary остаётся с `app off` либо подтверждённо остановлен.
   [REPLICAOF](https://valkey.io/commands/replicaof/),
   [ROLE](https://valkey.io/commands/role/).
4. `reconfiguring`: доступные остальные процессы перевести на новый
   primary. Старому primary вернуть `app on` только после подтверждённой
   роли replica, синхронизации и актуального хеша. Восстановить метки
   реплик. После публичной готовности продолжить прерванную операцию либо
   перейти в `degraded`/`running` по состоянию реплик.

При потерянном ответе на изменяющую команду стадия остаётся незавершённой.
Перед повторной проверкой доступного процесса оператор закрывает прежнее
административное соединение и выполняет процедуру очистки соединений
`operator` из раздела «Три цикла». Другие подключения оператора к этому
процессу, включая сбор метрик, на время очистки приостанавливаются.
Это исключает запоздалую команду из прежнего соединения после проверки.
Затем оператор читает роль и ACL того же процесса. Если кандидат уже master
и fencing источника подтверждён, он продолжает проверку ACL и открытие клиентского доступа.
Если кандидат остался пригодной репликой, повтор допустим только для той же
идентичности после проверки fencing. Потеря ответа не разрешает выбрать
другую цель или вернуть клиентский доступ старому primary.

Если кандидат пропал после возможного продвижения или включения `app`,
его идентичность сохраняется как потенциальный primary. Выбор другой цели
ждёт подтверждённого fencing этого процесса или доказательства его остановки;
истечение `config.FailoverTimeout` этого требования не снимает. После подтверждённой
остановки кандидата оператор возвращается к `choosing`, выбирает другую
пригодную реплику и продолжает переключение. Если пригодной реплики нет,
действуют правила запуска пустого primary ниже. При изменении размера после восстановления
primary оператор продолжает тот же `status.rollout`.

Свидетельство fencing связано с Pod UID и container ID. Перезапуск,
смена цели или неопределённый результат команды требуют проверки заново.
Уже подтверждённый `app off` не снимается общей синхронизацией ACL или
сменой пароля. `CLIENT PAUSE` с таймаутом не используется как fencing:
после таймаута запись возобновляется. Снятие метки закрывает путь только
новым соединениям и тоже не является fencing.
[ACL SETUSER](https://valkey.io/commands/acl-setuser/),
[CLIENT KILL](https://valkey.io/commands/client-kill/).

Если пригодных реплик нет, оператор ждёт в `unavailable`. Пустой primary
допустим, когда подтверждено завершение всех процессов с прежними данными,
либо прошло `config.EmptyPrimaryTimeout`, равное 2 минутам, и оператор подтвердил, что все
оставшиеся процессы пусты. В обоих случаях старый primary и любые
неизвестные потенциально работающие процессы должны быть изолированы или
подтверждённо остановлены. Таймаут никогда не заменяет fencing.
Событие потери кэша записывается в CR и лог.

Время недоступности включает обнаружение, fencing, promote, распространение
маршрутов и переподключение клиентов. Простой может длиться больше 15 секунд:
при сетевом разделении или отсутствии оператора ожидание может занять
минуты и потребовать человека. Старые соединения могут получить разрыв
или `READONLY`; клиенту нужно переподключиться к прежнему hostname.

В `single` при замене остановленного процесса кэш теряется. Оператор проверяет
новый процесс и пароль перед включением `app`; незавершённая остановка
старой инкарнации также блокирует допуск замены.

### Зависший процесс на доступной ноде

Алгоритм применяется к primary, репликам и `single` уже созданного инстанса,
в том числе во время изменения размера или смены пароля. Оператор начинает
вмешательство после
`config.ProcessUnresponsiveTimeout=60s`. Время отсчитывается от первой ошибки
в непрерывной серии неуспешных попыток связи с процессом. Ответивший `BUSY`
процесс обрабатывается по `config.ScriptBusyTimeout`;
`LOADING` и ошибки авторизации этот путь остановки не разрешают.

1. После порога заново прочитать Pod и Node напрямую через k8s API
   (`APIReader`, без локального кэша). Node должен иметь `Ready=True`,
   контейнер Valkey должен быть `Running`, но с `ready=false`, а Pod
   иметь `Ready=False`. Pod UID и container ID должны совпадать с записью
   в CR. Для уже завершённого или сменившегося контейнера применяется обычный
   алгоритм восстановления; новое удаление не запрашивается.
2. Повторить проверку Valkey с обычными таймаутами. Удаление допустимо,
   только если процесс по-прежнему не отвечает и выполнены пороги
   `config.PrimaryFailureThreshold` и `config.PrimaryFailureMinDuration`. После
   рестарта оператора нужны как минимум три новые неуспешные проверки
   за не менее 10 секунд, даже если сохранённый `unresponsiveSince` уже старше
   60 секунд. При успехе сбросить ожидание; при недоступном k8s API,
   `Node Ready=False/Unknown` или готовом контейнере продолжать наблюдение.
3. Сохранить `unresponsiveRecoveryStage=stopping` и идентичность процесса
   в CR до запроса удаления. Убедиться, что на Pod есть finalizer
   `valkey.h3llo-demo.com/process-stopped`, снять метку Service, затем
   повторно проверить условия шага 1. Отправить обычный DELETE Pod с
   preconditions по UID и `resourceVersion` этой свежей версии Pod,
   с `gracePeriodSeconds: 30`.
   Конфликт требует повторного чтения и проверки. Force delete не применяется.
4. Дождаться от kubelet статуса завершения именно этого контейнера,
   сохранить доказательство в CR и снять finalizer. Kubelet отправляет
   SIGTERM, а по истечении grace period отправляет оставшемуся процессу SIGKILL;
   один ответ на DELETE или истёкшие 30 секунд не доказывают остановку.
   Если нода стала недоступной, проверить её удаление через ЛК по общему
   правилу ниже; пока Node существует, ждать восстановления или ручного fencing
   по следующему подразделу. Для primary это `unavailable/FENCING_REQUIRED`.
5. После подтверждения остановки продолжить failover `ha` либо допуск
   нового `single`. Для остановленной реплики дождаться её замены и
   синхронизации с текущим primary. Затем продолжить прерванную операцию.

После рестарта стадия `stopping` требует сначала прочитать Pod: при
`deletionTimestamp` оператор ждёт завершения уже принятого удаления.
Если удаления ещё нет, он повторно проверяет все условия перед DELETE;
восстановившийся процесс можно оставить в работе, очистив стадию и таймер.
Возврат метки Service и включение `app` требуют обычной проверки роли,
ACL и отсутствия незавершённого fencing. При неопределённом
результате DELETE действует тот же порядок, `NotFound` для Pod без сохранённого
доказательства не завершает остановку. Удаление инстанса имеет приоритет
и продолжает уже начатую остановку через свой finalizer.
[Завершение Pod](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination).

### Поды на недоступной ноде

`Node NotReady`, удалённый объект Pod и истёкший таймаут не доказывают,
что процесс Valkey остановился. Принудительное удаление объекта может
оставить старый процесс живым. [Правила удаления StatefulSet Pod](https://kubernetes.io/docs/tasks/run-application/force-delete-stateful-set-pod/).

Подтверждением остановки служит статус завершения конкретного контейнера
от доступного kubelet или ручное подтверждение физического выключения
worker-ноды через консоль провайдера. Для завершённого удаления ноды через ЛК
также принимается автоматическое подтверждение по [правилу ниже](#удаление-worker-ноды-через-лк).
Для Valkey в обоих режимах шаблон
задаёт `spec.restartPolicy: Always` у Pod и `restartPolicy: Never` у самого
контейнера, без `restartPolicyRules`. Нужен включённый `ContainerRestartRules`
на API server и worker-нодах; его работу проверяют на dev и h3llo до запуска.
Обычное завершение Valkey оставляет контейнер остановленным, пока оператор
не сохранит доказательство и не разрешит замену Pod.

1. Прочитать Pod и Node через `APIReader`. Сопоставить `state.terminated`
   контейнера Valkey с сохранёнными Pod UID, container ID и worker-нодой.
   Этот порядок применяется и к аварийному завершению без запроса DELETE.
2. Сохранить идентификаторы процесса и его статус завершения в CR. Finalizer Pod
   `valkey.h3llo-demo.com/process-stopped`, установленный до допуска
   процесса к клиентам, удерживает объект даже при запросе удаления
   контроллером StatefulSet. Пока запись в CR не подтверждена, finalizer
   остаётся на месте. После рестарта оператор повторно читает доказательство.
3. Если удаления ещё нет, запросить штатный DELETE Pod с preconditions по
   UID и `resourceVersion`. После сохранения доказательств для всех известных
   процессов этого Pod снять finalizer. StatefulSet создаёт замену, если
   число реплик текущей стадии операции это допускает; удаление инстанса
   и стадия изменения размера с `replicas: 0` не запускают поды заново. Допуск нового
   процесса проходит обычные проверки роли и ACL.

Finalizer удерживает объект Pod, но не историю рестартов контейнера.
`lastState.terminated` содержит только последнее завершение и может
подтвердить лишь указанный в нём container ID. Сбой kubelet или потеря
состояния runtime могут привести к повторному запуску даже при `Never`.
Если контейнер неожиданно сменился, оператор проверяет точное совпадение
прежней идентичности с `state.terminated`, `lastState.terminated` либо
уже сохранённым доказательством в CR. Смена ID, рост `restartCount`,
политика `Never` и `NotFound` для Pod сами по себе остановку не подтверждают.

Если доказательство прежнего процесса утрачено, оператор сохраняет его
идентичность, выставляет `RECOVERY_REQUIRED` с причиной
`TERMINATION_PROOF_LOST` и Event. Допуск замены, завершение смены пароля
и удаления ждут подтверждения удаления прежней ноды по правилу ниже либо
ручного fencing; для primary действует
`unavailable/FENCING_REQUIRED`. Дежурный подтверждает физическое выключение
соответствующей ноды, даже если она сейчас доступна. Если kubelet перестал
отвечать, оператор также ничего не удаляет принудительно до подтверждения.
[Политики рестарта контейнеров и ограничения Kubernetes 1.35](https://v1-35.docs.kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#individual-container-restart-policy-and-rules).

После выключения ноды дежурный записывает на CR аннотацию
`valkey.h3llo-demo.com/fencing-confirmation` с JSON:
`{"nodeUID":"...","podUID":"...","containerID":"...","confirmedAt":"..."}`.
Для нескольких подов процедура повторяется отдельно после принятия
предыдущего подтверждения. Доступ к аннотации имеет только команда эксплуатации;
пользователю сервиса она недоступна. Оператор принимает её только для текущего
ожидающего процесса, сохраняет доказательство и Event, убирает аннотацию.
Устаревшая или чужая идентичность игнорируется. Включать ноду обратно
можно после остановки её прежних контейнеров; подтверждение не означает
разрешение вернуть изолированный процесс к клиентскому трафику.

`config.NodeUnreachableTimeout`, равный 60 секундам, задаёт задержку для причины `NODE_LOST`.
Его истечение не разрешает force delete. После подтверждения остановки
контейнера, удаления ноды через ЛК или ручного fencing оператор может
убрать зависший объект Pod, чтобы StatefulSet создал замену. С тремя
worker-нодами после удаления одной anti-affinity оставит замену в `Pending`
до добавления новой ноды; заранее выделенная четвёртая нода даёт место
для восстановления третьего пода. При временном отказе можно дождаться
возврата прежней ноды.

### Удаление worker-ноды через ЛК

В v1 доверяем порядку удаления managed Kubernetes: облако сначала уничтожает
VM, затем удаляет её объект Node. Наш сервис не вызывает API облака.
Оператор видит только результат в Kubernetes и не может отличить его от
ручного удаления Node при живой VM. Поэтому удалять только объект Node
до выключения VM запрещено. Этот порядок облака нужно подтвердить на стенде
h3llo; `NotReady` и истечение таймаута его не заменяют.

До допуска Valkey к клиентским запросам оператор сохраняет в записи процесса
`nodeName` и `nodeUID` вместе с Pod UID/container ID. Записи прежних процессов
не теряются при замене Pod или рестарте оператора. Имя ноды без UID
недостаточно: новая нода может получить прежнее имя.

1. Для известного процесса прочитать Node по сохранённому `nodeName` через
   `APIReader`, без кеша. `NotFound` либо существующий Node с другим UID
   подтверждает отсутствие прежнего объекта. Node с прежним UID, включая
   `NotReady` и `deletionTimestamp`, не подтверждает завершение удаления.
   Ошибка доступа, таймаут или отсутствие сохранённых имени/UID не дают
   автоматического подтверждения: оператор повторяет проверку либо ждёт
   ручного восстановления при утрате идентичности.
2. Сохранить в CR подтверждение с основанием `node_deleted`, временем
   наблюдения, прежними именем/UID ноды и идентичностью процесса. Это доверенный
   сигнал по принятому порядку эксплуатации, а не результат проверки питания VM.
   Для всех известных процессов на этой ноде сохранить отдельные подтверждения
   и Event. Не требовать статуса завершения контейнера от исчезнувшего kubelet.
3. Только после успешной записи CR снять собственный finalizer
   `valkey.h3llo-demo.com/process-stopped` у соответствующего старого Pod,
   запросив удаление, если его ещё нет. Проверить UID Pod, чтобы не затронуть
   замену с тем же именем. После рестарта использовать сохранённое подтверждение
   и повторить незавершённые действия. Уже исчезнувший Pod не мешает продолжению.
4. Продолжить текущую операцию: failover на пригодную реплику, восстановление
   `single` или реплики, изменение размера, смену пароля либо удаление инстанса.
   Подтверждение остановки действует и для прежней цели failover с неизвестным
   результатом команды. При удалении инстанса или стадии с нулём реплик
   поды заново не запускать. Новые процессы проходят обычные проверки роли,
   актуального пароля и допуска клиентов.

В `single` новый процесс запускается с пустым кэшем. В `ha` сохранённые реплики позволяют
продолжить работу с возможной потерей последних записей. Восстановление записи
не ждёт третьей копии, если выполнены условия failover; до её появления инстанс
остаётся `degraded`. Удаление Node само по себе не создаёт новую worker-ноду.

### E2E удаления ноды на k3s

Сценарии обязательны в `operator just test` и в полном CI-прогоне перед развёртыванием.
Используется отдельный стенд compose: оператор запускается внутри k3s с теми же
StatefulSet, ServiceAccount и Lease, что на проде. Процесс оператора на хосте
предварительно остановлен. `k3s-server` сохраняется: он обслуживает Kubernetes
API и вход через NodePort. Удаляемой нодой служит контейнер `k3s-agent`.
Для восстановления всех трёх копий `ha` стенд поднимает дополнительный agent,
чтобы всего было четыре ноды с достаточными ресурсами.

Тест фиксирует Node UID и Pod UID/container ID, затем принудительно останавливает
контейнер выбранного agent без предварительного drain. Docker должен подтвердить
его остановку вместе с вложенными процессами. Только после этого тест удаляет
объект Node: этот шаг имитирует действие managed Kubernetes после уничтожения VM.
Остановленный контейнер не должен автоматически перезапускаться. Тест не удаляет
поды вручную, не снимает finalizers и не пишет подтверждения в CR. Восстановление
проверяется по Kubernetes и через публичное TLS-подключение к Valkey с SNI.

Обязательные сценарии:

- Оператор и primary `ha` находятся на удаляемом agent. Новый оператор появляется
  на другой ноде и получает Lease; пригодная реплика принимает запись, замена
  потерянного пода синхронизируется. До отказа записать контрольный ключ и
  дождаться его наличия на обеих репликах; после восстановления ключ читается,
  новые записи проходят, старое соединение к уничтоженному primary не работает.
- Отдельно удалить agent с `single` и с репликой `ha`. Новый `single` принимает
  запись с прежними учётными данными, прежнего ключа нет. При потере реплики
  primary продолжает работать, новая реплика синхронизируется.
- Повторить потерю primary на трёхнодовом стенде без запасного agent: запись
  восстанавливается на двух оставшихся нодах, инстанс `degraded`, третий под
  остаётся `Pending`. Добавление нового agent возвращает три готовые копии.
- Перезапустить оператор после сохранения `node_deleted`, но до снятия finalizer,
  и проверить продолжение. Проверить удаление ноды во время смены пароля,
  изменения размера и удаления инстанса: операции завершаются по сохранённому намерению,
  старые процессы не требуют ручного подтверждения и удаляемый инстанс не оживает.
- Разместить на удаляемом agent также Envoy: прежний процесс не оставляет
  проверку шлюза в ручном ожидании, новый состав проходит обычную проверку.
  Повторная регистрация ноды с прежним именем и новым UID не связывает старое
  подтверждение с новыми процессами; использовать чистое состояние agent.
- Отдельным отрицательным сценарием разорвать связь живого agent с Kubernetes,
  сохранив Node и возможность старых процессов работать. Ожидание дольше
  таймаутов не должно разрешать force-delete или promote без fencing.
  Ошибку чтения Node и удаление только Pod без подтверждения остановки также
  проверить в envtest; ни один случай не создаёт `node_deleted`.

Для каждого ожидания задать конечный срок; при превышении тест падает и сохраняет
состояния Node/Pod/CR, Events и логи без секретов. После каждого сценария
восстанавливать стенд с чистыми agent, без запуска прежних контейнеров Valkey.
Эти e2e проверяют нашу реакцию на удаление ноды. Отдельная проверка через ЛК
h3llo должна подтвердить порядок уничтожения VM и удаления Node, включая
отсутствие зависания удаления на PDB или наших finalizers.

### Перекатка при изменении размера

Перед изменением StatefulSet оператор сохраняет в `status.rollout`
поколение, целевой размер и образ. Эти параметры фиксируются на всё время
операции, чтобы после рестарта продолжить то же изменение размера. Стратегия `OnDelete`
оставляет замену подов под контролем оператора: одно изменение шаблона
StatefulSet не запускает их автоматическую перекатку. Каждую старую
инкарнацию нужно подтвердить остановленной до допуска замены.
Неизменяемый ConfigMap целевого размера создаётся до обновления шаблона.
Образ в снимке берётся из существующего шаблона StatefulSet и при изменении размера
не меняется. Перекатка ради обновления образа появится в v2.

- `single`: закрыть `app` и его соединения, установить StatefulSet в
  0 реплик, подтвердить остановку, обновить шаблон и вернуть 1 реплику.
  Дождаться нового процесса и публичной готовности. Кэш пуст, на время
  остановки фаза `unavailable`.
- `ha`, RAM не уменьшается: обновить шаблон, заменить реплики по одной,
  для каждой дождаться синхронизации с primary и применения актуального ACL. Затем
  выполнить плановое переключение, описанное ниже. После него заменить
  бывший primary только после переподключения остальных реплик к новому
  primary; дождаться синхронизации нового процесса в роли реплики.
- `ha`, RAM уменьшается: новая реплика может не вместить данные старого
  primary. Закрыть `app` и соединения на всех доступных подах, остановить
  все старые процессы через `replicas: 0`, подтвердить остановку каждого,
  обновить шаблон, вернуть `replicas: 3` и поднять пустой инстанс.
  Не назначать пустой primary, пока старый процесс может принимать запросы или участвовать в прежней репликации.

Плановое переключение использует стадии `fencing`, `choosing`, `promoting`
и `reconfiguring` из [общего алгоритма failover](#failover-ha).
В `status.failover` сохраняются причина `resize` и идентичности процессов;
`status.rollout` сохраняет цель и ход перекатки. Кандидат должен иметь
целевой размер/образ и подтверждённую историю синхронизации.
Оператор выключает `app` и закрывает его соединения на прежнем primary,
ждёт достижения контрольной позиции репликации в пределах
`config.FailoverTimeout`, затем назначает проверенного кандидата новым primary
через `REPLICAOF NO ONE`. До публичной готовности нового primary фаза
`unavailable/FAILOVER`. Клиенты переподключаются к прежнему hostname;
при недогнавшей реплике возможна потеря последних записей.
Потеря ответа, смена идентичности и гибель кандидата обрабатываются по
общим правилам восстановления переключения.

На стадии `reconfiguring` оператор явно задаёт старому primary и каждой
остальной реплике `REPLICAOF <IP нового primary> 6379`.
Старый primary остаётся с `app off` до подтверждённой роли replica,
синхронизации и проверки актуального хеша. На каждой реплике проверить,
что она получает данные напрямую от нового primary. Для этого используются `INFO replication`/`ROLE`,
`master_link_status:up` и признак завершённой полной синхронизации
`master_sync_in_progress:0`. Только после этого разрешено заменить бывший primary. При непрерывной записи
постоянное равенство offset не требуется: проверяется завершённая синхронизация
с нужным upstream и продвижение offset, если на primary есть записи.
После рестарта на этой стадии оператор повторно читает upstream.
Сохранённого номера пода (ordinal) недостаточно: после рестарта оператор
должен заново убедиться, с каким primary синхронизируется каждая реплика.
[REPLICAOF](https://valkey.io/commands/replicaof/).

При аварии failover имеет приоритет перед перекаткой. Оператор сохраняет rollout,
но после восстановления заново проверяет роли, UID и стадию `status.failover`;
по сохранённому ordinal нельзя определить текущую роль процесса.
Во время стадии остановки reconcile сохраняет 0 реплик, даже если
`spec.mode` по-прежнему `ha` или `single`. Перекатка завершена, когда
все поды имеют целевой размер/образ, правильные роли и ACL,
реплики синхронизированы, публичная конфигурация готова.
Тогда обновляются `applied_*`, а после применения всех полей spec —
`observedGeneration`. До этого новое изменение размера запрещено.

Если применение принятой версии конфигурации длится больше 10 минут,
API записывает `ERROR`
по [правилам диагностики](SYSTEM.md#ошибки-для-эксплуатации). Команда эксплуатации смотрит ошибки в VictoriaLogs. Дежурный сверяет поколение и `status.rollout`,
идентичности процессов, Events планировщика, свободные ресурсы,
anti-affinity и состояние репликации. После устранения причины оператор
продолжает операцию по сохранённому снимку. Нельзя вручную выравнивать
`observedGeneration`, `applied_*` или менять цель CR ради разблокировки
кнопки: это скроет незавершённую перекатку и исказит квоту. При отсутствии
ресурсов остаются ожидание, добавление ресурсов командой эксплуатации или удаление
инстанса пользователем. Автоматического отката и отмены в v1 нет.

### Применение нового пароля

Когда в Secret есть хеш `spec.passwordVersion`, оператор сохраняет
`status.credentialRotation` и обрабатывает реплики, затем primary.
На каждом процессе:

1. Проверить, что Pod UID/container ID и версия пароля совпадают с
   сохранёнными для этой операции; выполнить
   `ACL SETUSER app resetpass #<новый SHA-256>` без флага `on`.
2. Через `ACL GETUSER app` проверить, что остался только новый хеш.
3. Выполнить `CLIENT KILL USER app` и получить ответ. Сохранить подтверждение
   версии и идентичности процесса в `status.credentialRotation`.

Команда `ACL SETUSER` из первого шага меняет только пароль, сохраняя
права и состояние on/off. Поэтому смена пароля не откроет доступ к процессу,
который оператор ранее изолировал.
Старые авторизованные соединения продолжают работать после одного
`resetpass`, поэтому их закрытие обязательно. При падении оператора до
записи подтверждения стадия повторяется и может ещё раз закрыть соединения
этого пода. После подтверждения для неизменившегося процесса повторных
закрытий нет. Пользовательские соединения с новым паролем, открытые до
окончания операции, тоже могут быть закрыты. UI показывает готовность только
после подтверждения версии; первого успешного AUTH недостаточно.
[ACL SETUSER](https://valkey.io/commands/acl-setuser/),
[ACL GETUSER](https://valkey.io/commands/acl-getuser/),
[CLIENT KILL](https://valkey.io/commands/client-kill/).

Завершение требует новой версии в Secret, подтверждения всех работающих
процессов и доказанной остановки недоступных прежних инкарнаций. Нельзя
подтвердить смену пароля только на primary, оставив старый пароль на
реплике. Новый или перезапущенный под начинает с `app off`; оператор
проверяет текущую версию и только после этого допускает его к клиентам.
Недоступность прежнего процесса оставляет операцию незавершённой до
восстановления или доказанной остановки. Реплика, которая ещё ни разу
не запускалась, и подтверждённо остановленная инкарнация не задерживают
завершение. Поэтому смена пароля может закончиться в `degraded`, без
ожидания трёх готовых подов. У будущей реплики допуск проверяется отдельно.

Failover имеет приоритет. Новый primary получает актуальный хеш до
включения `app` и публикации endpoint. Изолированный при fencing процесс
остаётся с `app off` при обновлении хеша; включение разрешено только
алгоритмом восстановления.
После подтверждения процессов оператор удаляет предыдущий хеш из Secret,
сохраняя остальные поля через проверку `resourceVersion`; цикл доставки
не возвращает его из устаревшего снимка. Затем выставляет
`appliedPasswordVersion`, очищает `credentialRotation` и подтверждает
поколение конфигурации. Удаление предыдущего хеша помечается отдельной
стадией, чтобы продолжить операцию после рестарта между очисткой Secret
и записью статуса. При смене пароля поды не перезапускаются.

## Конфигурация сети

### Caddy перед api

На виртуалке перед `api` стоит Caddy. Он получает и продлевает сертификат Let's Encrypt для `app.h3llo-demo.com`, ограничивает частоту запросов и отдаёт SPA из `/srv`.

```caddyfile
{
    order rate_limit before reverse_proxy
}

app.h3llo-demo.com {
    rate_limit {
        zone auth {
            match {
                path /v1/auth/*
            }
            key    {remote_host}
            events 10
            window 1m
        }
        zone api {
            match {
                path /v1/*
            }
            key    {remote_host}
            events 120
            window 1m
        }
    }
    @api path /v1/* /livez /readyz
    handle @api {
        reverse_proxy api:8080
    }
    handle {
        root * /srv
        try_files {path} /index.html
        file_server
    }
}
```

Для запросов авторизации и остального API заданы разные лимиты. Регистрация и вход вычисляют bcrypt (стоимость 12, время зависит от CPU), поэтому для них разрешено десять попыток в минуту с одного адреса. Этот лимит ограничивает перебор паролей. Для остального API лимит составляет 120 запросов в минуту; опрос статуса раз в 5 секунд занимает 12 запросов в минуту на вкладку. Ключ лимита — IP клиента. Пользователи с общим выходным IP делят лимит. Лимит запросов авторизации в самом `api` описан в [разделе 10](SYSTEM.md#10-аутентификация) и работает также без Caddy в среде разработки.

`rate_limit` не входит в стандартный образ Caddy, это плагин `mholt/caddy-ratelimit`. Мы собираем свой образ через `xcaddy`, версия плагина зафиксирована в Dockerfile.

Для логов тот же Caddy обслуживает отдельный домен. Приём OTLP и просмотр
через `vmui` временно доступны без имени и пароля:

```caddyfile
logs.h3llo-demo.com {
    @otlp {
        method POST
        path /insert/opentelemetry/v1/logs
    }
    handle @otlp {
        reverse_proxy victorialogs:9428 {
            header_up -Authorization
        }
    }
    handle /select/* {
        reverse_proxy victorialogs:9428 {
            header_up -Authorization
        }
    }
    handle {
        respond 404
    }
}
```

Пути передаются без изменения. Остальные пути VictoriaLogs снаружи закрыты.
Caddy не передаёт `Authorization` в VictoriaLogs. Публичный доступ к записи и
просмотру логов принят временно; защита этого домена будет отдельным изменением.

### Сеть на dev

Встроенные Traefik и servicelb в k3s выключены, поэтому Service шлюза типа `LoadBalancer` внешнего адреса не получит. На dev `EnvoyProxy` задаёт Service типа `NodePort` с фиксированным `nodePort` 31379 (диапазон NodePort не включает 41379), а compose публикует порт контейнера `k3s-server` как `41379:31379`. Клиент на хосте подключается к `<slug>.valkey.localhost:41379`. Разрешение имён `*.localhost` в 127.0.0.1 через nss-myhostname на Linux проверяется в первый день; если оно не работает, настраивается dnsmasq или добавляются записи в `/etc/hosts` для конкретных slug. Для примера `shop-a1b2c3`:

```text
127.0.0.1 shop-a1b2c3.valkey.localhost shop-a1b2c3-ro.valkey.localhost
```

Wildcard-записи в `/etc/hosts` не используются. Адрес `-ro` проверяется только для `ha`; в `single` соответствующего маршрута нет. Bootstrap устанавливает в Secret `valkey-wildcard-tls` сертификат на `*.valkey.localhost`, выпущенный mkcert. При работающем стенде и созданном инстансе проверка с хоста выглядит так (slug заменяется фактическим):

```sh
valkey-cli \
  -h shop-a1b2c3.valkey.localhost -p 41379 \
  --tls --sni shop-a1b2c3.valkey.localhost \
  --cacert "$(mkcert -CAROOT)/rootCA.pem" \
  --user app --askpass PING
```

Ожидается `PONG` с правильным паролем. Проверка маршрутизации использует два инстанса: ключ, записанный в один, отсутствует в другом. Для `ha` отдельно проверяется чтение через `-ro` с учётом задержки репликации. Соединения без SNI и с неизвестным SNI отклоняются шлюзом.

Для проверки whitelist сначала при выключенной политике фиксируется адрес клиента, который Envoy использует для IP-авторизации, через диагностический access log Envoy. Публичный IP разработчика, `127.0.0.1` и адрес контейнера нельзя считать этим адресом без измерения. Пароли и содержимое команд Valkey в диагностические логи не записываются.

Каждый сценарий выполняется после подтверждения целевого поколения оператором, с новым TCP-соединением и правильным паролем:

| Настройка whitelist | Ожидаемый результат |
| ------------------ | ------------------- |
| Выключен | `PING` возвращает `PONG` |
| Включён, список пуст | Шлюз запрещает доступ |
| Включён, наблюдаемый IPv4 клиента разрешён как `/32` | `PING` возвращает `PONG` |
| Включён, разрешён только другой IP | Шлюз запрещает доступ |
| Повторно выключен после запрета | Новое соединение получает `PONG` |

Для IPv6 используется `/128`. В `ha` сценарии выполняются для обоих адресов. Уже открытое соединение проверяется отдельно: изменение whitelist не обязано его разрывать.

Для одновременной проверки разрешённого и запрещённого клиентов в dev-compose предусматриваются два тестовых контейнера с фиксированными разными IP. Они обращаются к `k3s-server:31379`, передают hostname инстанса через `--sni` и получают корневой сертификат mkcert для проверки TLS. `localhost` внутри этих контейнеров указывает на сам контейнер. Перед проверкой требуется подтвердить, что Envoy видит два разных адреса. Если NodePort подменяет их одним IP, настраивается `externalTrafficPolicy: Local` и размещение готового Envoy на ноде `k3s-server`, через которую входит трафик, затем измерение повторяется. Эта политика сохраняет исходный IP на участке Kubernetes, но не отменяет подмену адреса до него. [Сохранение исходного IP в Kubernetes](https://kubernetes.io/docs/tutorials/services/source-ip/).

После подтверждения разных адресов whitelist разрешает только первый клиент; второй получает отказ. Проверяется также разрешение по CIDR подсети и отказ клиенту вне неё. Если два адреса различить не удалось, проверка двух клиентов считается непройденной. Локальные проверки подтверждают маршрутизацию и применение правил Envoy; сохранение реального внешнего IP балансировщиком h3llo проверяется отдельно на облачном стенде из двух источников с разными внешними IP ([проверки на облачном стенде](#проверить-в-первый-день)).

## Окружения

В корне репозитория находятся основной Compose и тестовое сетевое дополнение. Среда разработки запускается командой:

```
just run
```

### docker-compose.dev.yml

Dev compose содержит четыре сервиса: PostgreSQL 18, `k3s-server` и два
`k3s-agent`. PostgreSQL работает внутри контейнера на `5432` и публикуется на
`127.0.0.1:45432`. Kubernetes API и NodePort шлюза также доступны только через
loopback хоста. Три ноды нужны для проверки жёсткого anti-affinity режима
`ha`; встроенные Traefik и servicelb выключены. Сеть dev закреплена как
`172.27.0.0/16`, а адреса сервисов заданы явно, поэтому Node-объекты не получают
другие InternalIP после `just down` и повторного запуска.

Перед созданием кластеров `scripts/k3s_host_prerequisites.sh` проверяет лимиты
inotify. Если `fs.inotify.max_user_instances` меньше 1024 или
`fs.inotify.max_user_watches` меньше 1048576, скрипт поднимает значение через
`sudo sysctl`. Настройка действует до перезагрузки хоста. При исходном лимите
128 второй параллельный k3s уже может не запустить CRI на agent-нодах.

Кластер готовит `scripts/k3s_bootstrap.sh`. Он получает имя Compose-проекта,
профиль, ожидаемое число нод и пути явно. Скрипт устанавливает Gateway API,
Envoy Gateway, CRD, RBAC, общую инфраструктуру и dev-сертификат. Отдельные
kubeconfig API и оператора записываются в `tmp/k3s/dev` с режимом `0600`;
административный kubeconfig приложениям не передаётся.

Состояние server-ноды, база и пароли регистрации agent-нод лежат в отдельных
постоянных томах. Перед пересозданием контейнеров `just run` читает действующий
токен k3s из server-тома. Это позволяет продолжить работу с существующим
кластером, даже если значение `K3S_TOKEN` в `.env` позже изменилось.

Тестовые запуски используют тот же Compose вместе с
`docker-compose.test.yml`. Обвязка выбирает непересекающиеся Docker, Pod и
Service CIDR под блокировкой, назначает свободные localhost-порты и хранит
состояние в `tmp/k3s/<suite>/<run-id>`. Полный профиль настраивает только
маршруты выбранного кластера; профиль API устанавливает CRD и RBAC без Envoy.
Каждый кластер получает собственный токен и три kubeconfig: admin для обвязки,
API и operator для приложений.

В полном тестовом профиле NodePort каждой k3s-ноды публикуется на отдельном
случайном localhost-порту. Service Envoy использует `externalTrafficPolicy:
Local`, а обвязка передаёт тесту адрес ноды с готовым Envoy. Трафик не зависит
от межнодовой пересылки NodePort во вложенном k3s и сохраняет исходные адреса
контейнеров, которыми проверяется whitelist. В dev остаётся стабильный порт
`127.0.0.1:41379` на `k3s-server`.

Локальные API, integration и e2e-запуски используют один контейнер PostgreSQL,
но отдельную базу для каждого идентификатора запуска. Обвязка передаёт её URL поверх `.env`,
применяет миграции с `goose -allow-missing`, а после закрытия тестов удаляет
только эту базу. При очистке она сверяет записанные project, маршруты и базу;
dev-тома, общий PostgreSQL и ресурсы соседнего запуска не удаляются. `just run`
останавливает свои процессы по Ctrl+C, но сохраняет dev-кластер и базу;
`just down` останавливает их без удаления томов.

### docker-compose.prod.yml

На виртуалке работают `caddy`, `api`, `postgres` и `victorialogs`. PostgreSQL слушает 45432 внутри compose и требует пароль из `.env`. Для отладки Docker Compose публикует только `127.0.0.1:45432:45432`; удалённое подключение проходит через SSH-туннель до этого адреса. TLS PostgreSQL внутри compose отключён. VictoriaLogs слушает 9428 внутри compose без публикации порта на хост. Правила сети VM запрещают внешний доступ к 45432 и 9428; Docker также не публикует их на внешних интерфейсах.

Caddy обслуживает `app.h3llo-demo.com` и `logs.h3llo-demo.com` по HTTPS. Он отдаёт SPA из собственного образа, передаёт `/v1/*`, `/livez` и `/readyz` в API. Маршрут OTLP и `/select/*` с `vmui` временно открыты без пароля; остальные пути домена логов возвращают 404. Публичного доступа к порту VictoriaLogs в обход Caddy нет. Облачная база и резервные копии запланированы после v1 ([раздел 9](SYSTEM.md#9-отказоустойчивость-и-цель-по-доступности)).

В managed k8s h3llo стоят CRD, namespace `valkey-system` с оператором (StatefulSet, 1 реплика, `OnDelete`, headless Service и leader election), Envoy Gateway с `EnvoyProxy` на две реплики и Service типа LoadBalancer, общая `ClientTrafficPolicy valkey-connections`, cert-manager. Манифесты лежат в `deploy/prod` (kustomize). API на виртуалке использует отдельный kubeconfig с правами из [раздела 3](SYSTEM.md#3-кто-с-кем-разговаривает-и-где-авторизация); файл монтируется в контейнер только для чтения. Адрес Managed Kubernetes доступен с VM по HTTPS с проверкой CA. PostgreSQL использует только API по сети compose; у оператора нет конфигурации БД и адреса API сервиса. Оператор получает права Kubernetes через in-cluster ServiceAccount и отправляет логи через Caddy по HTTPS без отдельного секрета. Восстановление после удаления worker-ноды через ЛК следует [правилам раздела 6](SYSTEM.md#поды-на-недоступной-ноде); собственного клиента API h3llo и отдельной службы выключения VM в v1 нет.

GitHub Actions передаёт готовые образы и файлы версии по SSH. Сценарий `scripts/install_release.sh` размещает их в `/opt/managed-valkey/releases/<sha>`, а общие секреты хранит в `/opt/managed-valkey/shared/.env`. Файл `release.env` содержит SHA и полные имена образов. Файл `/opt/managed-valkey/secrets/kubeconfig/api.kubeconfig` создаётся на сервере заранее. Все версии используют проект Docker Compose `managed-valkey`, поэтому тома PostgreSQL, VictoriaLogs и Caddy сохраняются между запусками.

Пользователь `PRODUCTION_SSH_USER` должен иметь доступ к Docker Compose и право записи в `/opt/managed-valkey`. Каталог и файл kubeconfig создаёт команда эксплуатации до первой установки версии.

```text
/opt/managed-valkey/
  current -> releases/<sha>
  bin/
    activate_release.sh
    install_release.sh
  shared/.env
  secrets/kubeconfig/api.kubeconfig
  releases/<sha>/
    docker-compose.prod.yml
    release.env
    images/
```

После загрузки образов сценарий проверяет конфигурацию, запускает Docker Compose с ожиданием миграций и готовности сервисов, затем запрашивает `https://app.h3llo-demo.com/readyz`. Ссылка `/opt/managed-valkey/current` меняется только после успешного ответа. Для возврата к прежней версии запускают `/opt/managed-valkey/bin/activate_release.sh <sha>`; миграции `goose down` не выполняются.

Виртуалка отделяет API и PostgreSQL от control plane Kubernetes: вход, чтение последнего состояния и запись намерения удаления не требуют доступного kube-apiserver. VM и compose остаются собственной точкой отказа. Нужно обслуживать VM и доступ API к публичному endpoint Kubernetes. При потере этой связи доставка и импорт остановятся, после чего конфигурационные изменения блокируются по `is_stale`; запущенные Valkey и failover по существующим CR от связи с VM не зависят. Восстановление доступа запускает повторную сверку, но не возвращает пропущенную историю метрик.

## Тесты, Justfile, CI

Юнит-тесты проверяют расчёты и переходы без инфраструктуры. `api just test` создаёт базу запуска и однонодовый k3s, применяет миграции, а затем выполняет HTTP-тесты. `operator just test` последовательно запускает envtest и медленный жизненный цикл на отдельном трёхнодовом k3s с настоящими Valkey и Envoy. `web just test` вызывает полный `pnpm test`. Корневой `just test` запускает эти независимые наборы параллельно и ждёт их завершения. Общие integration и Playwright e2e-сценарии пока не подключены и отображаются как не реализованные. Временные зависимости изолируются интерфейсом `Clock`.

### Проверки текущего этапа API Valkey

Для change `add-valkey-management-api` бизнес-сценарии проверяются интеграционно через настоящий TCP HTTP (`httptest.Server` и `http.Client`), рабочие middleware/сервисы и PostgreSQL managed_valkey_test. Регистрация и создание идут через API; SQL используется для подготовки observed/applied состояния и проверки скрытых записей аудита, периодов и хешей. Отдельных миграционных тестов нет: goose -allow-missing запускается до интеграционных тестов. Kubernetes и k3s в этот этап не входят.

Обязательный сценарий немедленного отказа: общий бюджет 4 CPU / 16 GB, уже занято 3 CPU / 3 GB, личная квота вызывающего свободна; создание single 2 CPU / 8 GB возвращает в исходном POST `422 NOT_ENOUGH_RESOURCES`. В PostgreSQL нет нового инстанса, аудита, периода и ключа, резерв не изменился. Отдельно повторить для нехватки RAM, обоих ресурсов и точной границы. Тест не запускает синхронизацию и не ждёт/перематывает timeout оператора. Два сервера с разными пулами одновременно претендуют на последний остаток: принимается ровно один запрос.

Также проверяются удержание квоты при всех фазах до deleted_at, сохранение истории soft delete, общий сервис аудита для регистрации/входа/Valkey, откат всей транзакции при отказе аудита и отсутствие повторных событий по ключу или DELETE. Полная матрица находится в design.md соответствующего change.

### E2E восстановления после удаления ноды

В `operator just test` обязательно включаем удаление ноды на k3s после реализации этого сценария. Оператор для него работает внутри кластера как на проде; обычный процесс оператора на хосте остановлен. Тест останавливает контейнер agent со всеми вложенными процессами и только затем удаляет объект Node, имитируя завершённое удаление VM через ЛК. Сервер k3s и вход через NodePort остаются доступны. Сам тест не удаляет поды, не снимает finalizers и не подтверждает остановку через CR.

Проверяем потерю ноды с оператором и primary одновременно, отдельно с `single` и репликой, а также с Envoy. На стенде с четырьмя нодами сервис восстанавливает весь состав; при трёх нодах `ha` продолжает работу в `degraded` до добавления замены. Проверяем публичные чтение и запись, восстановление операций после рестарта оператора и отсутствие автоматического переключения при одной лишь потере связи с существующей нодой.

[Подготовка стенда, последовательность и критерии e2e](#e2e-удаления-ноды-на-k3s). Эти сценарии пока запускаются отдельно и не входят в `.github/workflows/ci-cd.yml`. Проверка удаления через ЛК h3llo остаётся отдельной: локальный тест подтверждает наш алгоритм, но не порядок действий облака.

### Justfile

Корневой `Justfile` управляет всей dev-средой и общим запуском тестов. У каждого
приложения также есть свой `Justfile`; его команды выполняются из каталога
приложения. Инструменты Go берутся из `go.mod` через `go tool`, поэтому отдельно
устанавливать goose, golangci-lint, controller-gen и setup-envtest не нужно.

Из `api/`:

```text
just run                         # миграции и запуск api на хосте
just test                        # отдельная база, однонодовый k3s и все тесты API
just migration-generate <name>   # новая SQL-миграция с временным префиксом
just migration-up                # goose up к DATABASE_URL
just migration-down              # откат последней миграции
```

Из `operator/`:

```text
just run   # запуск оператора на хосте с dev-kubeconfig
just test  # unit/envtest и жизненный цикл на отдельном трёхнодовом k3s
```

Pre-commit hook отклоняет частично добавленные в индекс Go-файлы до
форматирования, затем напрямую запускает линтер и сборку затронутого приложения.
Для оператора он вызывает `controller-gen` во временной копии и сравнивает
результат с DeepCopy, CRD и RBAC в репозитории. Тестовые команды используют ту
же проверку и не меняют рабочее дерево.

Из корня `just run` запускает всю dev-среду, `just down` останавливает её без
удаления томов, а `just test` параллельно выполняет все подключённые наборы.

### CI

Файл `.github/workflows/ci-cd.yml` запускается для каждого запроса на слияние и `push`. Задания `lint-api`, `lint-operator` и `lint-web` выполняются параллельно. После всех трёх запускаются параллельные `test-api`, `test-operator` и `test-web` через локальные команды `just test`. API готовит однонодовый k3s и отдельную базу, оператор выполняет envtest и жизненный цикл на трёхнодовом k3s. При ошибке задание CI публикует диагностические состояния Kubernetes без kubeconfig, Secret и паролей.

После тестов задания `build-api` и `build-web` параллельно собирают для `linux/amd64` образы API, миграций и Caddy со SPA. Полный SHA коммита входит в каждый тег. Архивы Docker сохраняются как результаты текущего запуска на один день и передаются заданию `deploy`; рабочая VM не компилирует исходный код.

Задание `deploy` запускается только после успешного `push` в `main`, использует окружение GitHub `production` и группу последовательного выполнения `production`. Оно создаёт закрытый `.env`, передаёт архивы и сценарии по SSH, а затем запускает `scripts/install_release.sh`. Новая ссылка `current` появляется после успешной миграции, готовности Docker Compose и внешнего запроса к `/readyz`. Процесс разворачивает только VM. Оператор и `deploy/prod` остаются отдельной частью управляемого Kubernetes.

CodeQL, Trivy, общие integration и Playwright e2e-тесты пока не входят в `.github/workflows/ci-cd.yml`. Реальный набор подключается одновременно к корневому `just test` и отдельному обязательному job. Файлы клиентского приложения входят в образ Caddy; API собирается независимо от `web/dist`.

Корневого `Justfile` нет: команды Go живут в `api/Justfile` и
`operator/Justfile` (раздел 14). Сквозной набор `e2e/` проверяет путь от
регистрации пользователя до подключения к инстансу и потому не принадлежит ни
одному приложению.


HTTP, авторизация, PostgreSQL и фоновые циклы синхронизации принадлежат
`api/internal/`. Управление Kubernetes и Valkey принадлежит
`operator/internal/`. Приложения не импортируют внутренние пакеты друг
друга. Исключение составляет контракт CRD: пакет `operator/api/v1alpha1`
доступен обоим приложениям, поскольку API записывает `spec` и читает
`status`. Корневой `internal/` содержит только общий код.

Миграции принадлежат схеме PostgreSQL, с которой работает API. Процесс
`.github/workflows/ci-cd.yml` загружает готовые образы, применяет миграции и
запускает API с Caddy на VM. Манифесты `deploy/prod/` разворачивают CRD и
оператор в Kubernetes отдельно от этого процесса. Схему CRD устанавливают до
запуска версии API или оператора, которая использует её новые поля.
