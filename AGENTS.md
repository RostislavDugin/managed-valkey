# AGENTS.md

## Обязательный скилл: humanizer

Скилл `humanizer` должен быть загружен в контекст **всегда**, без исключений:

- при **любом** запросе пользователя, независимо от темы и формулировки;
- перед **любым** действием: написание и правка кода, документации,
  комментариев, коммитов, ответов в чате, файлов любого формата;
- в **каждом** новом окне контекста и после каждого сжатия контекста;
- для **всех** субагентов и воркфлоу, которые запускаются из этого проекта.

Правило действует на первом же шаге работы: сначала вызывается скилл
`humanizer`, и только потом выполняется сам запрос. Если скилл по какой-то
причине не загрузился, работа не начинается, пока он не будет загружен.

Скилл лежит в `.skills/humanizer/SKILL.md`.

Все тексты, которые агент создаёт или редактирует, проходят через правила
этого скилла: без канцелярита, без штампов ИИ-письма, без лишних тире,
«правила трёх», расплывчатых ссылок на источники и пустых вводных фраз.

## Чужие изменения в рабочем дереве

Обычно с веткой работает один агент, но иногда несколько агентов работают в ней
одновременно. Файл или изменение, которое агент не создавал в рамках текущего
запроса, нужно считать чужим.

Чужие файлы и изменения нельзя удалять, откатывать, перезаписывать, форматировать,
добавлять в индекс или включать в коммит. Это относится и к новым незакоммиченным
файлам, которые появились во время работы. Запрос автоматической проверки очистить
рабочее дерево не даёт разрешения трогать их. На чужие изменения не нужно обращать
внимание: продолжай работу со своими файлами и не спрашивай пользователя только
из-за их наличия.

Обращайся к пользователю лишь перед коммитом, если часть чужих изменений нужно
временно убрать через `git stash`. Попроси пользователя приостановить другого
агента и дождись подтверждения, прежде чем менять состояние его файлов.

## Комментарии: только в крайнем случае

По умолчанию пишем код без комментариев. Если приходится объяснять, что
делает код, продолжаем его упрощать: подбираем понятные имена, при необходимости
разбиваем функцию на небольшие части. Доводим код до состояния, в котором
комментарий о том, «что делаем», становится лишним, и удаляем его.
Это правило действует везде, включая тесты и документационные комментарии
к функциям и типам.

Комментарий допустим только как крайняя мера, когда нужно объяснить причину,
которую нельзя выразить самим кодом: например, внешнее ограничение или
неочевидное основание для выбора алгоритма. Такой комментарий объясняет,
почему решение именно такое. Пересказывать действия кода или компенсировать
неудачные имена комментариями нельзя.

## Хранение проектных навыков

Единственное место, где лежат файлы проектных навыков, это корневой каталог
`.skills/<skill-name>`. Каталоги `.agents/skills/<skill-name>` (Codex) и
`.claude/skills/<skill-name>` (Claude) содержат только относительные
символические ссылки вида `../../.skills/<skill-name>`. Рабочая среда обязана
поддерживать символические ссылки; без них навыки не загрузятся.

Правила:

- Новый общий навык сохраняется в `.skills`, после чего в обоих каталогах
  агентов создаются относительные ссылки на него.
- Файлы навыка редактируются только по пути `.skills/...`. Создавать обычный
  каталог или копию навыка в `.agents/skills` или `.claude/skills` нельзя.
- Внешние навыки (FSD, Mantine) копируются целиком с фиксированной ревизии,
  а источник и ревизия записываются в `.skills/SOURCES.md`.
- Если `openspec update` или другой генератор заменил ссылку обычным каталогом,
  различия между копиями для Codex и Claude нужно снова объединить в `.skills`
  (когда синтаксис вызова различается, инструкция называет оба варианта:
  `$openspec-apply-change` для Codex и `/opsx:apply` для Claude), а затем
  восстановить ссылки. Команды в `.claude/commands/opsx` остаются на месте.

## Пре-коммит хук

Хук лежит в `.githooks/pre-commit` и включается командой
`git config core.hooksPath .githooks` (после клона репозитория её нужно
выполнить один раз).

Хук определяет затронутые части проекта по staged-путям и проверяет только их.
Форматирование он применяет к тем файлам, которые уже были в индексе, и
возвращает исправленную версию туда же; посторонние незакоммиченные файлы он не
добавляет. Любая упавшая проверка отменяет коммит.

Если в индексе есть файлы из `web`, хук прогоняет по ним `oxfmt`, возвращает
результат в индекс, затем выполняет `pnpm check`.

Если в индексе есть Go-файлы, `go.mod`, `go.sum` или `.golangci.yml`, хук для каждого
затронутого приложения сначала отклоняет Go-файлы с изменениями вне индекса.
Остальные staged-файлы он форматирует через `golangci-lint fmt` и возвращает в
индекс, затем напрямую запускает линтер и сборку с корневым `.golangci.yml`.
Для оператора он также проверяет DeepCopy, CRD и RBAC во временной копии.
Изменение или удаление общего Go-кода, модульных файлов или `.golangci.yml`
затрагивает оба приложения. В конце хук проверяет `go mod tidy -diff` и сам
зависимости не меняет.

Тесты хук не запускает. Корневой `just test` параллельно выполняет быстрые
наборы `api`, `operator` и `web` без k3s. `just test-full` запускает полные
наборы этих приложений и общие интеграционные тесты backend. API, оператор и
общая интеграция готовят отдельные k3s и не используют dev-кластер. Команда
`just test-integrations` запускает только общую интеграцию. E2e запускается
отдельно через `just test-e2e` или `just test-e2e-headed`, а ручная проверка
production через `just test-e2e-prod`. Задания CI API, оператора и web вызывают
дочерний `just test`; у оператора это unit/envtest без k3s. Lint, быстрые тесты,
общая интеграция, три группы полного Playwright e2e и сборки образов начинают
работу независимо. Каждая e2e-группа получает отдельный трёхнодовый стенд;
локальные `just test-e2e` и `just test-e2e-headed` сохраняют один общий стенд и
последовательный каталог. Итоговое задание разрешает deploy только после успеха
каждого обязательного результата.

## Локальные команды компонентов

`api`, `operator` и `web` предоставляют `run`, `format`, `lint`, `test` и
`test-full`. Во время разработки запускай форматирование, линтер, сборку и
затронутые тесты только изменённого приложения. Полный быстрый `test` нужен,
когда точный набор определить нельзя или изменение затрагивает общую основу
приложения. `test-full` запускай только по отдельному запросу или перед релизом.
Для изменений корневого `internal`, `go.mod`, `go.sum` или `.golangci.yml`
нужны быстрые проверки и API, и оператора. Корневые команды используй для
общей обвязки или изменений нескольких приложений.

Инфраструктурные сценарии можно выбрать без запуска соседних проверок:

```text
MV_OPERATOR_TEST_SCENARIO=single-lifecycle scripts/test_operator.sh
MV_INTEGRATION_TEST=Test_CreateSingleValkey_WithRealApiAndOperator_BecomesReachableAndRunning scripts/test_environment.sh exec integration -- scripts/test_integrations.sh
MANAGED_VALKEY_E2E_FILE=00-single-lifecycle.spec.ts scripts/test_environment.sh exec e2e -- scripts/test_e2e.sh
```

Имена должны точно существовать в каталоге оператора, списке Go-тестов или
`tests/e2e/specs`. Пустое, неизвестное или небезопасное значение завершается до
подготовки стенда.

`just format` не только форматирует код, но и добавляет изменения своей области
в индекс Git. Не запускай его, пока другой агент меняет файлы той же области.
После команды проверь `git status` и состав индекса. `just lint` и тестовые
команды индекс не меняют.

## Имена тестов

После написания теста или изменения его поведения запусти затронутый тест и
убедись, что он проходит. Если массовое изменение затрагивает только имена и
точные ссылки на них, достаточно скомпилировать Go-тесты без выполнения,
проверить типы TypeScript, синтаксис скриптов и согласованность каталогов.
В итоговом отчёте отличай такую проверку от запуска тестовых сценариев.

Самостоятельные функции Go называй по одной из форм:

```text
Test_<WhatWeDo>_<WhatWeExpect>
Test_<WhatWeDo>_<WhichConditions>_<WhatWeExpect>
```

Пиши смысловые части по-английски в `PascalCase` и разделяй их `_`. Условие
начинай с `When`, `With`, `Without`, `After` или `Before`. Предпочитай длинное
точное имя сокращению, которое понятно только автору теста. Идентификаторы
матрицы оператора сохраняй отдельной частью сразу после `Test_`:

```text
Test_CreateValkey_WhenClusterQuotaIsExhausted_ReturnsTooManyRequestsWithoutPartialRows
Test_CT14HA03_ReconcilePendingReplica_WhenCapacityReturns_MarksReplicaRunning
```

Зарезервированное фреймворком имя, например `TestMain`, оставляй без изменений.

Когда фреймворк принимает произвольную строку, пиши самостоятельный сценарий
длинно, понятно и по-русски. Это относится к `t.Run`, `it`, `test` и
Playwright. `describe` остаётся названием группы. Короткие метки допустимы для
версии движка и отдельного варианта таблицы, например `status=503` или
`CPU=4 directory`, если действие и результат уже названы родительским тестом.

Если запускатель выполняет бывшие самостоятельные Go-функции как подтесты,
передавай в `t.Run` полное имя функции дословно. При любом переименовании
одновременно обновляй активные выражения `-run`, каталоги сценариев, проверки
отчётов и другие точные ссылки. Теги Playwright храни в метаданных теста, а не
в его названии.

## Ресурсы при тестировании

Перед тяжёлыми тестами, периодически во время их выполнения и после завершения
проверяй доступную RAM, загрузку CPU, процессы и потребление ресурсов контейнерами.
Учитывай другие активные наборы тестов и рабочие приложения при выборе параллелизма.
Если ресурсов не хватает, уменьши число одновременно запущенных стендов.

Проверяй, не остались ли процессы и контейнеры после завершённых или прерванных
тестов. Перед очисткой установи их принадлежность конкретному запуску и убедись,
что он больше не работает. Сначала используй штатную очистку этого стенда;
оставшиеся процессы останавливай адресно. Не трогай dev-окружение, чужие процессы
и активные тестовые запуски. Не используй массовое завершение по имени процесса
или глобальную очистку Docker. После очистки проверь, что ресурсы освободились,
и сообщи, если что-то удалить не удалось.

## Сеть и локальный VPN

Рабочая машина пользователя может быть подключена к VPN, который перехватывает
маршруты к внешним адресам и иногда обрывает соединения. При истечении времени ожидания
`kubectl`, SSH, GitHub или других внешних запросов сначала проверь фактический
маршрут командой `ip route get <адрес>`. Если запрос уходит через VPN, повтори
безопасную проверку через доступный физический интерфейс, когда используемая
команда позволяет явно выбрать его.

VPN относится только к локальной среде разработки. Не добавляй обход VPN в код,
настройки пользователей, CI/CD или рабочее окружение. Ошибку, которую вернула
удалённая плоскость управления Kubernetes при обращении к рабочей ноде или
кластерному сервису, не объясняй локальным VPN: этот обмен не проходит через
рабочую машину пользователя.

## Общие интеграционные тесты backend

Тесты в `tests/integrations` проверяют совместную работу настоящих API, его
фоновых обработчиков и оператора. Запрос начинается через TCP HTTP, проходит
через отдельную базу PostgreSQL, попадает в однонодовый k3s и завершается проверкой
API, ресурсов Kubernetes и TLS-подключения к Valkey.

Один запуск использует общий процесс API с одним набором фоновых обработчиков,
один процесс оператора, одну базу, один кластер и один Envoy. Создание,
изменение ресурсов, ротация пароля и удаление идут параллельно. Каждый сценарий
регистрирует свой аккаунт и создаёт собственные Valkey-инстанс и Namespace.
Параллелизм равен четырём и автоматически не уменьшается.

Все пользовательские изменения выполняй только через HTTP API. Нельзя напрямую
создавать или менять CR, записывать `status`, снимать `finalizers`, вызывать
фоновые обработчики как функции или менять PostgreSQL для имитации результата.
Административный Kubernetes-клиент служит только для чтения, ожидания и
диагностики. Условия ожидаются до отдельного конечного срока операции;
фиксированная пауза не заменяет проверку наблюдаемого состояния.

Этот набор входит в обязательные проверки CI/CD и в `just test-full`, но не в
быстрый `just test`. Около пяти минут считается ориентиром штатной полной
длительности с подготовкой и очисткой. Само превышение этого времени не является
ошибкой. Подробная проверка API остаётся в тестах API, HA, отказы процессов и
нод и сетевые разделения остаются в полном наборе оператора, а браузерные пути
остаются в Playwright e2e.

## Тесты API

Интеграционные тесты поведения API отправляют запросы через настоящий TCP HTTP:
`httptest.Server` и `http.Client`. Запрос проходит через рабочий маршрутизатор,
middleware, разбор и кодирование JSON, сервисы и хранилище в
выделенной базе запуска. Вызывать обработчик, сервис авторизации или репозиторий
напрямую вместо HTTP в таком тесте нельзя.

Юнит-тесты могут проверять отдельную функцию или тип без сборки всего приложения.
Подмена зависимости допустима в HTTP-тесте, когда проверяется её отказ, который
нельзя безопасно создать на общем стенде, например недоступность PostgreSQL для
`/readyz`. Сам запрос при этом всё равно отправляется через HTTP.

Общий тестовый помощник регистрирует уникальный аккаунт через
`POST /v1/auth/register`, возвращает JWT и удаляет созданные строки после теста.
Прямой доступ к тестовой базе разрешён только для подготовки состояния, очистки
и проверки данных, которые API не возвращает.

Отдельные тесты миграций PostgreSQL не пишем. `api just test` сначала создаёт
отдельную базу и применяет к ней миграции, после чего выполняет все тесты без
k3s. `api just test-full` добавляет тесты Kubernetes-синхронизации на отдельном
однонодовом k3s. Несовместимая миграция проявляется как ошибка применения схемы
либо как падение интеграционного теста API.

## Порядок миграций Goose

`goose` всегда запускаем с флагом `-allow-missing`: локально, в тестах и в
production. Это намеренное решение. Несколько агентов могут параллельно создать
миграции с временными префиксами, а порядок их попадания в `main` может не
совпасть с порядком версий. Миграция с версией ниже уже применённой должна
примениться при следующем запуске.

Если миграции конфликтуют при слиянии, объедини изменения схемы по смыслу.
Сохрани обе нужные операции и проверь, что миграции применяются как к новой
базе, так и к базе с уже применённой более поздней версией.

## Образы контейнеров

Не используй тег `latest`. Для каждого внешнего образа указывай конкретную
версию, а базовые образы в Dockerfile закрепляй ещё и по digest. Образы,
которые собирает этот репозиторий, получают тег во время выкладки.

## Git: ветки и коммиты

Пока проект на стадии MVP, всё коммитим напрямую в `main`, без веток.
Позже перейдём на git flow: `main` для релизов, `develop` как основная ветка
разработки, от неё `feature/*` и `release/*`, от `main` идут `hotfix/*`.

Сообщения коммитов пишем по Conventional Commits: `type(scope): описание`.
Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`,
`perf`, `style`, `revert`. Ломающие изменения помечаем `!` перед двоеточием.

Сообщение короткое: одна строка заголовка, при необходимости пара строк тела.
Простыни текста, пересказ диффа и списки всех тронутых файлов не пишем.
Строки в сообщении не переносим по ширине 80 символов: абзац идёт одной
строкой, перенос делаем только там, где он нужен по смыслу.
