# Проблема с сетью между нодами

## В чём проблема

В кластере две ноды:

| IP | Имя ноды |
|---|---|
| `10.17.0.33` | `k8sc-worker-md-929247fc-ddba-4516-909c-8ca395dc7927-jljnb-kz68r` |
| `10.17.0.34` | `k8sc-worker-md-929247fc-ddba-4516-909c-8ca395dc7927-jljnb-h76z5` |

Обе ноды имеют статус `Ready`. Версия Kubernetes: `v1.34.1`. На нодах установлены Ubuntu 24.04.3 и `containerd 1.7.25`.

Я проверил подключение с `.33` к `.34` и обратно. Между нодами не проходят ICMP, TCP и UDP. Если запрос остаётся на той же ноде, соединение работает.

```text
10.17.0.33 -> 10.17.0.33  работает
10.17.0.33 -> 10.17.0.34  не работает

10.17.0.34 -> 10.17.0.34  работает
10.17.0.34 -> 10.17.0.33  не работает
```

Статус `Ready` говорит только о том, что `kubelet` подключён к `control plane`. Связь между самими нодами в эту проверку не входит.

## Проверка

### Сеть самих нод

Сначала запустил на каждой ноде по временному `Pod` с настройкой `hostNetwork: true`. Такой `Pod` подключён прямо к сети ноды: он использует её IP, а открытый в нём порт доступен на IP ноды. Отдельного IP из сети обычных `Pod` у него нет.

На обеих нодах работал HTTP-сервер на TCP 18080. Локальные запросы к `127.0.0.1:18080` прошли. Запрос с `.33` к `10.17.0.34:18080` и обратный запрос с `.34` к `10.17.0.33:18080` завершились по таймауту.

Отдельные проверки `ping` и UDP на порту 20082 между нодами тоже не прошли. `ping` в обе стороны показал `100% packet loss`, UDP-пакеты не пришли. При локальной проверке UDP работал на обеих нодах.

В этой части проверки не участвовали `Service`, отдельные IP обычных `Pod` и `VXLAN`. Проверялся прямой путь по приватной сети от IP одной ноды до IP другой.

### Обычные `Pod`

После прямой проверки нод запустил обычные `Pod` без `hostNetwork`:

| `Pod` | Нода | IP |
|---|---|---|
| `pod-33` | `.33` | `10.243.0.177` |
| `pod-34` | `.34` | `10.243.1.73` |

HTTP внутри каждого `Pod` работает на `127.0.0.1:8080`. Между нодами результат другой:

```text
pod-33 -> 10.243.1.73:8080  таймаут
pod-34 -> 10.243.0.177:8080 таймаут
```

`ping` между `10.243.0.177` и `10.243.1.73` также не прошёл ни в одну сторону. Потери составили 100%.

UDP проверял на другой паре `Pod`:

| `Pod` | Нода | IP |
|---|---|---|
| `udp-33` | `.33` | `10.243.0.70` |
| `udp-34` | `.34` | `10.243.1.104` |

Локальная отправка UDP прошла на обеих нодах. Пакеты с `10.243.0.70` на `10.243.1.104` и обратно не пришли.

### `ClusterIP`

Для каждого `Pod` создал отдельный `Service`:

| `Service` | `ClusterIP` | Адрес `Pod` |
|---|---|---|
| `svc-33` | `10.95.103.48` | `10.243.0.177:8080` на `.33` |
| `svc-34` | `10.95.217.155` | `10.243.1.73:8080` на `.34` |

Локальные запросы через `ClusterIP` прошли:

```text
pod-33 -> svc-33 работает
pod-34 -> svc-34 работает
```

Когда `Service` должен передать запрос на другую ноду, соединение завершается по таймауту:

```text
pod-33 -> svc-34 не работает
pod-34 -> svc-33 не работает
```

UDP через `ClusterIP` дал такой же результат:

| `Service` | `ClusterIP` | Адрес `Pod` |
|---|---|---|
| `udp-svc-33` | `10.95.249.227` | `10.243.0.70:20081` на `.33` |
| `udp-svc-34` | `10.95.58.37` | `10.243.1.104:20081` на `.34` |

Каждый `Pod` получил ответ от локального `Service`. При обращении к `Service`, который направлял пакет на соседнюю ноду, ответа не было.

### `NodePort`

Для проверки `NodePort` создал `Service` с портом 30207. Он направлял запросы в один `Pod`: `10.243.0.171:8080` на `.33`.

Из четырёх запросов прошёл только запрос с ноды `.33` на эту же ноду:

```text
Pod на .33 -> 10.17.0.33:30207 работает
Pod на .33 -> 10.17.0.34:30207 не работает
Pod на .34 -> 10.17.0.33:30207 не работает
Pod на .34 -> 10.17.0.34:30207 не работает
```

Даже локальный `NodePort` на `.34` не помог. После выбора `Pod` на `.33` запрос всё равно должен был перейти на соседнюю ноду.

### Что работает

- Kubernetes API отвечает.
- Обе ноды имеют статус `Ready`.
- Через Kubernetes API можно запустить `Pod` на любой из двух нод и выполнить в нём команду.
- HTTP внутри `Pod` работает.
- `ClusterIP` работает, пока запрос и выбранный `Pod` находятся на одной ноде.
- CoreDNS отвечает на запросы с той же ноды.
- Обе ноды отвечают на `ping` шлюза `10.17.0.1`.
- Каждая нода получает MAC-адрес соседней ноды.

На `.33` интерфейс `enp1s0` имеет адрес `10.17.0.33/16`. На `.34` его адрес `10.17.0.34/16`. Маршрут к соседней ноде на обеих машинах идёт напрямую через `enp1s0`.

Таблица соседей показывает состояние `REACHABLE`:

```text
на .33: 10.17.0.34 -> a2:9c:3d:1b:87:c4
на .34: 10.17.0.33 -> a2:3e:8a:54:d4:6d
шлюз:   10.17.0.1  -> b6:f6:a5:86:3f:fb
```

То есть получение MAC-адреса по ARP работает. IP-пакеты между теми же нодами не проходят.

### Что не работает

- `ping` между IP нод;
- TCP между IP нод;
- UDP между IP нод;
- прямое соединение между `Pod` на разных нодах;
- `ping` между `Pod` на разных нодах;
- `ClusterIP`, если выбранный `Pod` находится на другой ноде;
- прямой запрос к CoreDNS на соседней ноде;
- `NodePort`, если для запроса нужно перейти между нодами.

## DNS

В кластере две реплики CoreDNS, по одной на каждой ноде:

| Нода | IP CoreDNS |
|---|---|
| `.33` | `10.243.0.112` |
| `.34` | `10.243.1.221` |

Запрос к локальной реплике прошёл на обеих нодах. Запрос к реплике на соседней ноде каждый раз завершился по таймауту:

```text
pod-33 -> CoreDNS на .33 работает
pod-33 -> CoreDNS на .34 не работает

pod-34 -> CoreDNS на .34 работает
pod-34 -> CoreDNS на .33 не работает
```

Обычный запрос через адрес DNS-сервиса в двух проверках тоже завершился по таймауту. У сервиса две реплики, и одна из них для каждого `Pod` находится на недоступной соседней ноде. Поэтому DNS может срабатывать или зависать в зависимости от выбранной реплики.

## Что сообщает `Cilium`

В кластере установлен `Cilium 1.18.4`. Он использует `VXLAN` для связи между сетями `Pod` на разных нодах. Замена `kube-proxy` отключена: `KubeProxyReplacement: False`.

На обоих агентах `Cilium` команда `cilium-health status --succinct` показывает:

```text
Cluster health: 1/2 reachable
```

Каждый агент видит свою ноду и адрес, который `Cilium` использует для проверки сети. Соседняя нода недоступна:

```text
агент на .33: локальные 10.17.0.33 и 10.243.0.16 доступны
               удалённые 10.17.0.34 и 10.243.1.50 недоступны

агент на .34: локальные 10.17.0.34 и 10.243.1.50 доступны
               удалённые 10.17.0.33 и 10.243.0.16 недоступны
```

Правил, которые могли бы запрещать этот трафик внутри Kubernetes, нет:

```text
NetworkPolicy: 0
CiliumNetworkPolicy: 0
CiliumClusterwideNetworkPolicy: 0
Host firewall: Disabled
```

## Проверка через `tcpdump`

Чтобы увидеть, где пропадает трафик, запустил `tcpdump` одновременно на обеих нодах.

### Прямой TCP

С `.33` ушёл запрос к `10.17.0.34:18080`. На исходной ноде `tcpdump` показал четыре попытки открыть соединение:

```text
10.17.0.33:39698 -> 10.17.0.34:18080 Flags [S]
```

На `.34` не появился ни один из этих пакетов. Сервер не ответил, соединение завершилось по таймауту.

### `VXLAN`

Затем ушёл запрос из `Pod` на `.33` к `Pod` на `.34`. На исходной ноде `tcpdump` показал три повторных TCP SYN, упакованных в UDP 8472:

```text
внешний пакет: 10.17.0.33 -> 10.17.0.34:8472/UDP
внутри:         10.243.0.171:45678 -> 10.243.1.34:8080
```

На `.34` не появился ни один из этих пакетов. `Cilium` сформировал `VXLAN`-пакет и отправил его с исходной ноды, но до сетевого интерфейса второй ноды пакет не дошёл.

## Где искать причину

Прямой запрос `10.17.0.33 -> 10.17.0.34:18080` не использует `Service`, IP обычного `Pod` или `VXLAN`. Он всё равно не проходит. `tcpdump` видит пакет на исходной ноде и не видит его на целевой. Поэтому проблему нужно искать в сети между нодами, а не в маршрутизации трафика `Pod` внутри Kubernetes.

В первую очередь стоит проверить сеть, к которой подключены ноды:

1. Разрешает ли `security group` входящий трафик от других нод этой же группы.
2. Нет ли на сетевых интерфейсах изоляции, при которой нода видит шлюз, но не соседнюю ноду.
3. Разрешает ли `network ACL` трафик внутри `10.17.0.0/16`.
4. Добавляет ли автоматика создания кластера правила для связи между нодами.

Причина в `Cilium` менее вероятна. Прямой TCP между IP нод не зависит от сети обычных `Pod` и тоже не работает. Кроме того, `Cilium` формирует правильный внешний пакет UDP 8472.

Версия с `firewall` внутри целевой ноды тоже менее вероятна. Входящий пакет обычно виден в `tcpdump` до применения его правил, а на `.34` пакет не появился.

Похожий результат уже был в двух других кластерах этого поставщика. Там локальные соединения тоже работали, а связь между нодами отсутствовала. Это больше похоже на общую настройку виртуальной сети или шаблона создания кластеров, чем на ошибку одного кластера.
