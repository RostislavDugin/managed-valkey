## Context

См. `proposal.md`. Сейчас `checkQuota` получает общий резерв из PostgreSQL под транзакционной блокировкой, а `MANAGED_K8S_NODE_*` передаются в сервис как общий бюджет. Резерв процесса равен покомпонентному максимуму желаемых и применённых размеров, HA учитывается трижды. HTTP не обращается к Kubernetes. В рабочем окружении синхронизация выключена; управляемый кластер содержит три одинаковые рабочих ноды и пока только системные компоненты.

## Goals / Non-Goals

Цель расчёта: до принятия намерения доказать, что все логические резервы можно разместить в заданной топологии. Сохранить атомарность, идемпотентность и возможность уменьшения уже превышенной квоты.

Расчёт не закрепляет `Pod` за нодой, не гарантирует совпадение с текущей раскладкой Kubernetes и не выполняет перебалансировку. Автоматическое обнаружение нод, автоматическое масштабирование и переработка планировщика оператора не входят в изменение. Новые тесты находятся только в `api/`; существующие обязательные CI задания сохраняются.

## Decisions

### Топология и бюджет

Ввести обязательные `MANAGED_K8S_NODE_COUNT`, `MANAGED_K8S_NODE_CAPACITY_VCPU`, `MANAGED_K8S_NODE_CAPACITY_RAM_GB`, `MANAGED_K8S_NODE_RESERVED_CPU_MILLI` и `MANAGED_K8S_NODE_RESERVED_RAM_MIB`. Первые три положительные целые, резервы неотрицательные. Доступный бюджет ноды вычислять в целых тысячных долях CPU и MiB, без округления вверх; поле `ram_gb` существующих инстансов трактовать как GiB согласно запросам оператора. Проверять переполнение и положительный остаток. Общий бюджет равен количеству нод, умноженному на остаток одной ноды.

Для рабочего окружения физическая топология равна 3 × 4 vCPU / 16 GiB. Резерв одинаков для всех нод: 1000m CPU и 2048 MiB. Доступный бюджет Valkey равен 3000m CPU / 14336 MiB на ноду и 9000m CPU / 43008 MiB на кластер. Не представлять все физические 12 / 48 как свободные ресурсы Valkey.

Старые переменные общей ёмкости удалить с явной диагностикой при обнаружении. Автоматически выводить число нод из прежнего общего бюджета нельзя. Каталог размеров сохраняет свой контракт; размер из каталога, превышающий доступную ёмкость ноды, получает ресурсную ошибку при мутации. Изменить все конфигурации запуска API, чтобы они передавали новые параметры, не добавляя сценарии в общую интеграцию или сквозные тесты.

### Размещение как проверка существования

После личной квоты, лимита 32 инстансов и общей квоты прочитать все неудалённые инстансы в той же транзакции. Для изменения размера заменить изменяемую запись кандидатом с прежним применённым размером. Для каждого процесса использовать максимум желаемых и применённых размеров CPU и RAM. `single` даёт одну задачу, HA даёт три связанные задачи, которым запрещена общая нода.

Пересчитывать возможное размещение из сохранённых намерений при каждом изменении; отдельная таблица назначений не нужна. Сохранение виртуальных назначений без управления `Pod` породило бы ложное соответствие с Kubernetes. Источником остаётся PostgreSQL, одинаковым для всех API-процессов.

Использовать точный поиск с возвратом по остаткам нод: сначала наиболее ограниченные группы, стабильный порядок, отсечение эквивалентных нод и запоминание неуспешных состояний. HA размещать группой на различных нодах. Жадный проход может найти решение быстро, но его неудача не доказывает невозможность. Общая квота и проверка размера процесса дают ранние отказы.

Ограничить поиск 100 мс в контексте HTTP-запроса. Этот срок короче трёх секунд ожидания общей транзакционной блокировки. При исчерпании времени возвращать `503 UNAVAILABLE` с `reason=placement_check_timeout`, а не ложный `422`. Отмена запроса прекращает поиск и освобождает транзакцию.

Модульная проверка сравнивает результат с независимым полным перебором на небольших наборах. Измерение раскладки 32 инстансов на `linux/amd64`, AMD Ryzen 9 7950X, дало 11,1–11,5 мкс на операцию в пяти запусках, 9680 байт и 281 выделение памяти на операцию. Тест ограничивает такой набор сроком 100 мс и отдельно проверяет отмену поиска. Истечение срока проверки в HTTP проверяется уже завершённым отдельным контекстом, поэтому результат не зависит от скорости машины.

### Изменение и освобождение резервов

Создание и увеличение выполняют проверку под существующей общей транзакционной блокировкой. `ImportValkeyObservation` и `CompleteValkeyDeletion` берут тот же `AcquireValkeyMutationLock` перед изменением применённых размеров и `deleted_at`. Поэтому проверка размещения читает согласованный снимок резервов, а подтверждение освобождения не может пройти параллельно с мутацией.

Уменьшение желаемого размера не освобождает ресурс до подтверждения применённого размера, запрос DELETE не освобождает его раньше `deleted_at`. `error`/`degraded` и устаревшее наблюдение сами по себе ничего не освобождают. Если конфигурация кластера уменьшена и прежние резервы больше не размещаются, разрешать операции, не увеличивающие ни одну компоненту резерва; рост отклонять. Удаление не требует размещения. Идемпотентный повтор успешного запроса не запускает новое резервирование.

### Ошибка размещения

Сохранить HTTP 422 и `NOT_ENOUGH_RESOURCES`. Общая нехватка остаётся `cluster_quota`, после неё проверяется `placement_capacity`. Сохранить поля `limit`, `used`, `requested`, `missing` общей квоты; при фрагментации `missing` может быть нулевым.

Дополнить `details` объектом `placement`: `node_count`, `required_distinct_nodes` (1 или 3), `process` с `cpu_milli`/`ram_mib` и `node_budget` в тех же единицах. Сообщение объясняет, что процессы нельзя разместить по нодам. Не включать идентификаторы чужих инстансов, имена реальных нод и раскладку других пользователей. Для таймаута использовать отдельную причину 503. Ошибки не сохраняют намерение, аудит, биллинг или ключ.

### Развёртывание рабочего окружения

Собирать оператор для `linux/amd64` с SHA выпуска в отдельном задании, публиковать в общедоступном пакете `ghcr.io/rostislavdugin/managed-valkey-operator` и учитывать публикацию при итоговой проверке `CI`. Встроенный `GITHUB_TOKEN` получает только право `packages: write`. Тег образа равен SHA коммита. Публичность пакета настраивается отдельно от видимости репозитория; после первой публикации пакет нужно один раз перевести в состояние `Public`. Кластер скачивает образ без `imagePullSecrets`.

Доставлять CRD и RBAC до оператора и API. Установить закреплённые версии Gateway API и Envoy Gateway, настроить внешний сервис, TLS `Secret` и DNS. Исправить границу ресурсов `Kustomize`. Вместо неявного обновления `StatefulSet` с `OnDelete` определить явный управляемый перезапуск оператора и дождаться готовности нужного образа. При развёртывании проверять, что запущен образ выбранного SHA.

Сохранить API в `Docker Compose` на существующем сервере. Выдать ему отдельные права по существующему API RBAC, смонтировать файл подключения Kubernetes только для чтения и включить синхронизацию после готовности инфраструктуры. Оператор использует свой `ServiceAccount` внутри Kubernetes. Административный файл подключения Kubernetes хранится в секрете `PRODUCTION_KUBECONFIG` окружения GitHub `production`, временные файлы имеют режим 0600 и удаляются после развёртывания. Не включать учётные данные в результаты сборки и логи. Определить выпуск и ротацию учётных данных API до выкладки; административный сертификат не подменяет их.

Записывать успешный SHA только после готовности Kubernetes-компонентов и прежней внешней проверки API. `/readyz` API сам по себе не доказывает работу синхронизации: нужны отдельная проверка подключения с правами API и состояния фоновых циклов. Не применять тестовый CR с пользовательскими данными из CI.

### Проверка кластера и доставка образа оператора

Проверка 11 сентября 2026 года показала, что три рабочие ноды имеют только внутренние адреса `10.17.0.26`–`10.17.0.28`, идентификаторы провайдера `kubevirt://...` и среду выполнения `containerd` 1.7.25. Порт SSH этих адресов недоступен с сервера API. Файл подключения даёт доступ к Kubernetes API, но не к среде выполнения нод, поэтому прямой импорт архива нельзя надёжно повторить после замены ноды.

Для v1 выбран общедоступный пакет `GHCR`. Он позволяет новой ноде получить образ через обычный механизм Kubernetes. Перенос оператора на сервер и привилегированный загрузчик внутри кластера не нужны. Если пакет не опубликован или остался закрытым, развёртывание завершается до обновления оператора.

Также до выкладки в рабочее окружение нужны подтверждённый способ получения внешнего адреса, TLS-сертификат и его продление, а также численные резервы инфраструктуры. Это параметры эксплуатации, их нельзя угадывать из файла подключения Kubernetes.

Секрет `PRODUCTION_KUBECONFIG` добавлен в окружение GitHub `production`. `CLOUDFLARE_API_TOKEN` там отсутствует. Он нужен `cert-manager` для проверки `DNS-01`; значение не передаётся на сервер API. Внешний адрес Envoy появится после создания `Service` типа `LoadBalancer`, затем запись `*.valkey.h3llo-demo.com` нужно вручную направить на этот адрес в режиме `DNS only` и повторить выпуск.

На момент проверки ноды имеют 4 CPU и 16376144 KiB памяти, из них Kubernetes сообщает доступными 4 CPU и 16273744 KiB. На наиболее занятой по объявленным запросам ноде системные контейнеры запрашивают 215m CPU и 188 MiB памяти. Часть Cilium и `kube-proxy` не объявляет запросы, поэтому эти числа нельзя считать достаточным резервом. В кластере пока нет CRD Gateway API, Envoy Gateway, `cert-manager` и `ValkeyInstance`, нет внешнего `Service`; DNS-имена `valkey.h3llo-demo.com` и `probe.valkey.h3llo-demo.com` не разрешаются.

Две реплики Envoy расходятся по разным нодам и запрашивают по 100m CPU / 512 MiB. Контроллер Envoy Gateway запрашивает 100m / 256 MiB, оператор 100m / 128 MiB, три постоянных процесса `cert-manager` по 50m / 64 MiB. Если все управляющие процессы и одна реплика Envoy окажутся на наиболее занятой ноде, суммарный запрос инфраструктуры составит 565m CPU / 1276 MiB. Резерв 1000m / 2048 MiB оставляет 435m CPU / 772 MiB для компонентов без запросов и кратковременных задач установки.

Kubernetes API и три процесса `kubelet` рабочей среды имеют версию `v1.34.1`. Серверная пробная проверка принимает `restartPolicy: Never` у контейнера при `restartPolicy: Always` у `Pod`, но проверка на рабочей ноде завершилась перезапуском контейнера. Значит `ContainerRestartRules` на рабочих нодах не действует. Развёртывание проверяет это коротким служебным `Pod` на каждой ноде и удаляет такие `Pod` после проверки. До обновления кластера или отдельной переработки механизма остановки Valkey оператор и синхронизацию API включать нельзя.

Проверка рабочей PostgreSQL 11 сентября 2026 года показала 0 неудалённых инстансов, резерв 0 vCPU / 0 GiB и 0 незавершённых удалений. При первом включении синхронизации накопленных пользовательских намерений нет; удалять или переносить строки не требуется. Если записи появятся до первого выпуска, проверку нужно повторить.

## Risks / Trade-offs

- Возможная раскладка отличается от фактической: Kubernetes может оставить `Pod` `Pending` даже при успешной проверке API. Не обещать гарантированное физическое размещение и не выдавать виртуальные назначения за наблюдения.
- Точный поиск имеет дорогие случаи: ранние проверки, симметрии, запоминание неуспешных состояний и конечный срок ограничивают время; истечение срока не маскируется под нехватку ресурсов.
- Разные конфигурации одновременно работающих API дают разные бюджеты: при смене топологии согласованно перезапускать все API; текущее рабочее окружение имеет один экземпляр.
- Доступность оператора зависит от общедоступности пакета `GHCR`: проверять скачивание образа без учётных данных до обновления `StatefulSet`.
- Ошибка после обновления Kubernetes и до обновления Compose оставляет частичный выпуск: повторное развёртывание должно быть идемпотентным, успешный SHA не записывается заранее.

## Migration Plan

1. Обновить конфигурацию и тестовые настройки API вместе с потребителями переменных окружения; сохранить текущий смысл резервов без изменения строк инстансов.
2. Прогнать тесты API и проверить план размещения существующих резервов на целевой топологии. При превышении не удалять записи и не освобождать резервы искусственно.
3. До первого включения синхронизации проверить существующие намерения в рабочем окружении: включение начнёт доставлять все активные записи, а не только новые запросы. Согласовать обработку накопившихся записей при невозможности размещения.
4. После закрытия эксплуатационных решений подготовить Kubernetes, учётные данные и образ оператора, затем обновить Compose и проверить выпуск.
5. При откате API на прежнюю версию восстановить прежние переменные окружения с суммарным доступным бюджетом, рассчитанным из новых настроек. Не удалять CRD, CR и пользовательские ресурсы при откате. Откат оператора выполнять только на совместимую с текущим CRD версию.
