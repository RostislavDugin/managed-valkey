## Purpose

Проверка расчётного размещения резервов Valkey по одинаковым Kubernetes-нодам до принятия HTTP-запроса, с учётом HA, изменения размеров и конкурентных операций.

## ADDED Requirements

### Requirement: Конфигурация описывает ноды и резерв инфраструктуры

API SHALL принимать обязательные целые параметры `MANAGED_K8S_NODE_COUNT`, `MANAGED_K8S_NODE_CAPACITY_VCPU`, `MANAGED_K8S_NODE_CAPACITY_RAM_GB`, `MANAGED_K8S_NODE_RESERVED_CPU_MILLI`, `MANAGED_K8S_NODE_RESERVED_RAM_MIB`. Количество и физическая ёмкость SHALL быть положительными, резерв SHALL быть неотрицательным и оставлять положительный бюджет обоих ресурсов. Параметр `MANAGED_K8S_NODE_CAPACITY_RAM_GB` SHALL задавать память в GiB, как в запросах Valkey. Доступный бюджет одной ноды SHALL равняться физической ёмкости за вычетом инфраструктурного резерва; общий бюджет SHALL равняться произведению этого остатка на число нод. Расчёт MUST NOT округлять доступные ресурсы вверх. Неверные, отсутствующие или переполняющие расчёт значения и прежние двусмысленные переменные окружения SHALL давать ошибку запуска с именем параметра.

#### Scenario: Три одинаковые ноды

- **WHEN** заданы 3 ноды по 4 vCPU / 16 GiB и резерв каждой 500 тысячных долей CPU / 1024 MiB
- **THEN** API использует 3500 тысячных долей CPU / 15360 MiB на ноду и 10500 тысячных долей CPU / 46080 MiB на кластер

#### Scenario: Инфраструктура занимает всю память

- **WHEN** резерв RAM не меньше физической RAM ноды
- **THEN** API завершает запуск с ошибкой конфигурации

### Requirement: Каждый принятый рост резервов имеет допустимое распределение

При создании и увеличении резервов API SHALL проверять существование распределения всех неудалённых инстансов и кандидата по настроенным нодам, одновременно соблюдающего CPU и RAM. `single` SHALL занимать одну ноду, HA SHALL занимать три различные ноды процессами одинакового резервируемого размера. Резерв процесса SHALL равняться покомпонентному максимуму желаемых и применённых размеров. Проверка SHALL использовать конфигурацию и сохранённые намерения без синхронного обращения к Kubernetes. Она MUST NOT считать неудачу одного жадного распределения доказательством невозможности. Расчётная раскладка MUST NOT выдаваться за фактическое размещение `Pod` и MUST NOT перемещать `Pod`.

#### Scenario: Общего остатка хватает, а места на ноде нет

- **WHEN** доступны три ноды по 3 vCPU / 12 GiB, уже есть три `single` по 2 vCPU / 8 GiB и запрошен ещё один `single` 2 vCPU / 8 GiB
- **THEN** API отклоняет запрос по размещению, хотя итоговые 8 vCPU / 32 GiB не превышают общий бюджет

#### Scenario: HA требует разные ноды

- **WHEN** у кластера только две ноды с достаточными CPU и RAM для трёх процессов запрошенного HA
- **THEN** API отклоняет HA по размещению

#### Scenario: HA помещается точно

- **WHEN** есть три пустые ноды и процесс HA точно равен доступному бюджету одной ноды
- **THEN** API принимает HA, если остальные проверки пройдены

#### Scenario: Другая раскладка решает задачу

- **WHEN** первый выбранный порядок распределения не размещает все процессы, но существует другое допустимое распределение
- **THEN** API принимает запрос после нахождения допустимого распределения

#### Scenario: CPU и RAM должны помещаться вместе

- **WHEN** проверка CPU отдельно и RAM отдельно допускает распределение, но ни одно распределение не соблюдает оба ограничения одновременно
- **THEN** API отклоняет запрос по размещению

### Requirement: Резерв согласован между запросами и подтверждениями

API SHALL проверять размещение и сохранять намерение атомарно относительно других изменений резервов. При изменении размера SHALL заменяться резерв изменяемого инстанса без двойного учёта. Неподтверждённое уменьшение, `error` и запрос удаления SHALL удерживать резерв; освобождение SHALL следовать подтверждённому уменьшению применённого размера либо `deleted_at`. Повтор успешного идемпотентного запроса MUST NOT резервировать повторно. При уменьшении конфигурационного бюджета API SHALL допускать операции, не увеличивающие ни CPU-, ни RAM-резерв инстанса, даже если прежняя раскладка больше не помещается; остальные правила готовности сохраняются.

#### Scenario: Конкуренты запрашивают последнее размещаемое место

- **WHEN** два пользователя через разные экземпляры API одновременно запрашивают ресурсы, каждый запрос помещается отдельно, но оба вместе не размещаются
- **THEN** принимается ровно один запрос, другой получает отказ после учёта принятого резерва

#### Scenario: Уменьшение и удаление ещё не подтверждены

- **WHEN** желаемый размер уменьшен или принят DELETE, а подтверждение освобождения не сохранено
- **THEN** последующее создание продолжает учитывать прежний резерв

#### Scenario: Ресурс подтверждённо освобождён

- **WHEN** API сохранил подтверждённое уменьшение применённого размера либо `deleted_at`
- **THEN** следующий запрос использует освободившийся бюджет в расчёте размещения

#### Scenario: Конфигурация уменьшена ниже резервов

- **WHEN** резервы не размещаются после изменения топологии, а готовый инстанс запрашивает уменьшение без увеличения ни одного резервируемого ресурса
- **THEN** API допускает уменьшение, не освобождая неподтверждённые ресурсы заранее

### Requirement: Отказ размещения отличается от общей нехватки

При достаточных личной и общей квотах, но невозможном распределении API SHALL возвращать `422 NOT_ENOUGH_RESOURCES` с `details.reason=placement_capacity`. Объект `details` SHALL сохранять общие `limit`, `used`, `requested`, `missing` и дополнительно содержать `placement.node_count`, `placement.required_distinct_nodes`, `placement.process` и `placement.node_budget`; последние два объекта SHALL содержать целые `cpu_milli` и `ram_mib`. Общий `missing` SHALL быть нулевым, если общая квота не превышена. Ответ MUST NOT раскрывать чужие инстансы или реальные имена нод. Отказ MUST NOT сохранять частичные записи, аудит, биллинг и идемпотентный ключ.

#### Scenario: Фрагментация без общего дефицита

- **WHEN** запрос не размещается по нодам, хотя общих CPU и RAM хватает
- **THEN** ответ содержит `placement_capacity`, нулевой общий `missing` и параметры процесса и ноды для объяснения отказа

#### Scenario: Поиск не успел завершиться

- **WHEN** истёк срок проверки до доказательства возможности или невозможности размещения
- **THEN** API возвращает `503 UNAVAILABLE` с `reason=placement_check_timeout`, откатывает попытку и освобождает блокировку
- **AND** не сообщает ложную нехватку ресурсов

#### Scenario: Личная квота исчерпана

- **WHEN** одновременно нарушены личная квота и размещение
- **THEN** API сохраняет приоритет `422 QUOTA_EXCEEDED` с `reason=user_quota`
