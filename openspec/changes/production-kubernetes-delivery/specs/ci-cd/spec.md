## MODIFIED Requirements

### Requirement: Образы выпуска собираются для x86-64

Независимые задания сборки SHALL быть готовы к запуску одновременно с проверкой исходного кода и тестами и SHALL параллельно собирать образы API, Caddy и оператора для `linux/amd64`. Образ API SHALL иметь отдельный вариант для применения миграций. Образ Caddy SHALL содержать рабочую сборку клиентского приложения. Все образы выпуска SHALL иметь тег с SHA исходного коммита. Образы API и Caddy SHALL сохраняться как результаты текущего процесса CI/CD. Образ оператора SHALL публиковаться в общедоступном пакете `ghcr.io/rostislavdugin/managed-valkey-operator` с тегом, равным SHA. Задание публикации SHALL использовать `GITHUB_TOKEN` только с правом `packages: write`. Процесс развёртывания SHALL получать готовые образы без повторной компиляции на рабочем сервере только после успешного итогового задания.

#### Scenario: Workflow начался

- **WHEN** GitHub Actions создаёт задания одной ревизии
- **THEN** `build-api`, `build-web` и `build-operator` могут начинаться без ожидания проверки исходного кода, тестов, общей интеграции или сквозных тестов

#### Scenario: Тесты завершились успешно

- **WHEN** все задания тестирования приложений, общей интеграции и сквозных тестов завершились успешно
- **THEN** уже начатые сборки продолжаются либо их готовые результаты ожидают завершения проверки исходного кода перед итоговым заданием

#### Scenario: Сборка завершилась до проверок

- **WHEN** образы готовы, а обязательные проверки ещё выполняются
- **THEN** результаты сборки сохраняются, но развёртывание не начинается до успешного итогового задания

#### Scenario: Архитектура образа выпуска

- **WHEN** задание `deploy` загружает собранный образ на рабочий сервер x86-64
- **THEN** Docker определяет платформу образа как `linux/amd64`

#### Scenario: Образ оператора опубликован

- **WHEN** задание `build-operator` завершилось успешно для отправки коммита в `main`
- **THEN** пакет `ghcr.io/rostislavdugin/managed-valkey-operator` содержит образ `linux/amd64` с тегом SHA текущего коммита

#### Scenario: Проверка запроса на слияние

- **WHEN** задание `build-operator` запущено для запроса на слияние
- **THEN** оно собирает и проверяет образ `linux/amd64`, но не публикует его

### Requirement: Ревизия доставляется и запускается по SSH

Задание `deploy` SHALL передать по SSH образы выпуска, `docker-compose.prod.yml`, данные ревизии и закрытый `.env`, загрузить образы в Docker, применить миграции, запустить сервисы и дождаться их готовности. Рабочие файлы SHALL находиться непосредственно в `/opt/managed-valkey`; каталоги `releases/<sha>` и ссылка `current` MUST NOT использоваться. Архивы образов SHALL удаляться вместе с временным каталогом передачи. Рабочий сервер MUST NOT собирать приложения из исходного кода. Успех выпуска SHALL дополнительно требовать готовности компонентов Kubernetes рабочего окружения нужной ревизии и подключения API с включённой синхронизацией. Ошибка подготовки Kubernetes MUST NOT записывать успешный SHA.

#### Scenario: Успешное развёртывание

- **WHEN** образы загружены, миграции завершились, сервисы стали готовы и Kubernetes-часть выпуска прошла проверки
- **THEN** внешний запрос к `/readyz` проходит через Caddy к API, SHA записан в `/opt/managed-valkey/.deployed-sha`, а устаревшие каталоги прежней схемы удалены

#### Scenario: Ошибка миграции или готовности

- **WHEN** миграция, запуск `Docker Compose`, подготовка Kubernetes, проверка подключения API или проверка `/readyz` завершается с ошибкой
- **THEN** задание `deploy` завершается с ошибкой и не меняет `/opt/managed-valkey/.deployed-sha`

### Requirement: Рабочие настройки отделены от секретов

Адрес рабочего сервера, SSH-пользователь, порт и проверенный ключ хоста SHALL храниться в переменных окружения GitHub `production`. Закрытый SSH-ключ, пароль PostgreSQL, ключ подписи JWT, токен Cloudflare и административный файл подключения Kubernetes SHALL храниться в секретах этого окружения. Передаваемый `.env` SHALL содержать только `POSTGRES_PASSWORD` и `JWT_SECRET`, иметь режим `0600` и MUST NOT сохраняться как общедоступный результат сборки или выводиться в журнал процесса. Административный файл подключения Kubernetes SHALL храниться в `PRODUCTION_KUBECONFIG`. Файл подключения Kubernetes для API SHALL содержать отдельные учётные данные с правами API и доставляться отдельным закрытым файлом, смонтированным только для чтения. Эти файлы MUST NOT попадать в результаты сборки и журналы; временные копии SHALL удаляться и при ошибке развёртывания. Токен Cloudflare SHALL попадать только в Kubernetes `Secret` для `cert-manager`. Остальные рабочие настройки SHALL находиться в `Docker Compose` или данных версии; топология и инфраструктурный резерв SHALL задаваться явно.

#### Scenario: Формирование рабочего файла переменных

- **WHEN** задание `deploy` готовит `.env`
- **THEN** файл содержит только пароль PostgreSQL и ключ JWT из секретов окружения GitHub `production`

#### Scenario: Секрет отсутствует

- **WHEN** `POSTGRES_PASSWORD`, `JWT_SECRET`, `CLOUDFLARE_API_TOKEN`, закрытый SSH-ключ или `PRODUCTION_KUBECONFIG` не задан
- **THEN** задание `deploy` завершается до подключения к рабочему серверу

## ADDED Requirements

### Requirement: Kubernetes рабочего окружения входит в выпуск

Процесс развёртывания SHALL подготовить CRD `ValkeyInstance`, RBAC и учётные записи API и оператора, закреплённые версии Gateway API и Envoy Gateway, инфраструктуру Envoy и оператор из той же ревизии, что API. CRD SHALL стать доступным до запуска потребителей. Оператор SHALL использовать свою учётную запись Kubernetes; его обновление SHALL приводить к запуску нужного образа с проверкой готовности. API SHALL включать синхронизацию с отдельными правами после подготовки кластера. CI MUST NOT создавать пользовательские `ValkeyInstance` CR как часть применения инфраструктуры. Сборка оператора SHALL входить в обязательную итоговую проверку результатов без ослабления существующих проверок.

#### Scenario: Первый выпуск в пустой кластер

- **WHEN** все обязательные задания CI успешны и доступны необходимые учётные данные, образ и параметры инфраструктуры
- **THEN** развёртывание устанавливает CRD и инфраструктуру, запускает оператор и подключает API к Kubernetes
- **AND** пользовательские CR доставляет фоновая синхронизация API из сохранённых намерений

#### Scenario: Образ оператора не запустился

- **WHEN** оператор нужной ревизии не достиг готовности
- **THEN** развёртывание завершается ошибкой и не записывает успешный SHA

#### Scenario: HTTP готов, а Kubernetes недоступен API

- **WHEN** внешний `/readyz` API успешен, но проверка подключения с учётными данными API не проходит
- **THEN** развёртывание не считает выпуск успешным

#### Scenario: Повтор частично выполненного выпуска

- **WHEN** развёртывание повторяется после ошибки между подготовкой Kubernetes и запуском API
- **THEN** процесс повторно применяет ту же ревизию без удаления пользовательских ресурсов

### Requirement: Клиентский доступ Valkey подготовлен до включения сервиса

Рабочее окружение SHALL иметь внешний адрес Envoy, DNS для домена инстансов и действующий TLS-сертификат в ожидаемом `Secret`. Версии внешних образов SHALL быть закреплены. Образ оператора SHALL скачиваться из общедоступного пакета `ghcr.io/rostislavdugin/managed-valkey-operator` по тегу SHA выпуска без `imagePullSecrets`. Процесс развёртывания SHALL проверять доступность образа до обновления оператора. Отсутствие образа или обязательных сетевых параметров MUST NOT подменяться тестовой конфигурацией.

Процесс развёртывания SHALL использовать оператор с прямым управлением пользовательскими `Pod` по `valkey-pod-lifecycle` и MUST NOT включать его до завершения и проверки этого перехода. Сам процесс оператора SHALL оставаться в `StatefulSet`. Наличие пользовательского `StatefulSet` прежнего оператора SHALL останавливать выпуск до выполнения порядка перехода.

Процесс развёртывания SHALL проверять `spec.restartPolicy: Never` самого `Pod` короткими служебными процессами на каждой рабочей ноде для нулевого и ненулевого кода завершения. Проверочные контейнеры MUST NOT задавать собственное поле `restartPolicy` или требовать `ContainerRestartRules`. Процесс SHALL дождаться завершения без повторного запуска, удалить проверочные `Pod` при любом исходе и остановить выпуск при ошибке. Такая проверка MUST выполняться до включения синхронизации API и MUST NOT создавать пользовательские `ValkeyInstance`.

#### Scenario: Оператор ещё зависит от прежней политики

- **WHEN** переход `valkey-pod-lifecycle` ещё не реализован и не проверен
- **THEN** выпуск остаётся заблокированным; простое удаление проверки `ContainerRestartRules` не разрешает запуск оператора или включение синхронизации API

#### Scenario: В кластере остались пользовательские `StatefulSet`

- **WHEN** перед обновлением оператора обнаружен пользовательский `StatefulSet` Valkey
- **THEN** выпуск завершается с ошибкой без его удаления, а `StatefulSet` самого оператора не считается таким ресурсом

#### Scenario: Не готов клиентский TLS

- **WHEN** TLS `Secret` отсутствует или не соответствует домену инстансов
- **THEN** подготовка рабочего окружения не считается завершённой

#### Scenario: Нода оператора заменена

- **WHEN** провайдер Kubernetes заменяет ноду, которая может запускать оператор
- **THEN** новая нода скачивает требуемый образ из общедоступного пакета `GHCR` без дополнительных учётных данных

#### Scenario: Рабочая нода перезапускает остановленный контейнер

- **WHEN** контейнер проверочного `Pod` с `spec.restartPolicy: Never` перезапускается на любой рабочей ноде либо не завершается за отведённое время
- **THEN** развёртывание удаляет проверочные `Pod`, завершается с ошибкой и не включает синхронизацию API
