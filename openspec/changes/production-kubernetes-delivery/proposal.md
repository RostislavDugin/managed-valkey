## Why

Рабочий API пока не подключён к созданному управляемому кластеру Kubernetes, а образ оператора нельзя надёжно доставить на новую ноду. Выпуск должен готовить кластер, проверять его обязательные возможности и только затем включать синхронизацию API.

Продолжение выпуска зависит от `valkey-pod-lifecycle`: сначала оператор должен перейти на прямое управление пользовательскими `Pod` Valkey с `spec.restartPolicy: Never`. Текущий прогресс сохраняется, но изменение остаётся незавершённым до проверки рабочего выпуска.

## What Changes

- Публиковать образ оператора для `linux/amd64` в общедоступном пакете `ghcr.io/rostislavdugin/managed-valkey-operator` с тегом SHA выпуска.
- Устанавливать CRD, права API и оператора, Gateway API, Envoy Gateway, `cert-manager`, TLS-сертификат и оператор до обновления API на сервере.
- Хранить административный файл подключения Kubernetes и токен Cloudflare в секретах окружения GitHub `production`; создавать для API отдельный файл с ограниченными правами.
- После завершения `valkey-pod-lifecycle` заменить предварительную проверку `ContainerRestartRules` проверкой `spec.restartPolicy: Never` самого `Pod` на каждой рабочей ноде; проверить доступность образа оператора, внешний адрес Envoy, DNS, TLS и права API. Не создавать пользовательские `ValkeyInstance` из CI/CD.
- Монтировать файл подключения API только для чтения и включать `KUBERNETES_BACKGROUND_SYNC_ENABLED=true` после успешной подготовки Kubernetes.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `ci-cd`: выпуск включает общедоступный образ оператора, подготовку Kubernetes и отдельные учётные данные API.

## Impact

Изменятся процесс CI/CD, `deploy/prod`, сценарии установки выпуска, рабочая конфигурация `Docker Compose` и эксплуатационная документация. Пакет `GHCR` должен быть общедоступным. Изменение `valkey-pod-lifecycle` убирает зависимость Valkey от `ContainerRestartRules`; этот план отвечает за последующую проверку нод и выпуск. Сам оператор остаётся в `StatefulSet`.
