## Context

См. `proposal.md`. API работает на отдельном сервере под управлением `Docker Compose`, а оператор должен работать внутри управляемого кластера Kubernetes со своей учётной записью. Административный файл подключения даёт доступ к Kubernetes API, но не к среде выполнения рабочих нод.

В кластере три одинаковые рабочие ноды по 4 vCPU и 16 GiB. Kubernetes API и процессы `kubelet` имеют версию `v1.34.1`; ноды используют `containerd` 1.7.25 и доступны только по внутренним адресам `10.17.0.26`–`10.17.0.28`. Проверка 11 сентября 2026 года показала, что `ContainerRestartRules` не задан в настройках ни одного из трёх процессов `kubelet`: поле принимается сервером, но завершившийся контейнер перезапускается. До исправления этой возможности включать оператор и синхронизацию API нельзя.

Секреты `PRODUCTION_KUBECONFIG`, `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` добавлены в окружение GitHub `production`. Cloudflare подтверждает, что токен аккаунта активен и имеет доступ к активной зоне `h3llo-demo.com`. Общедоступный пакет `ghcr.io/rostislavdugin/managed-valkey-operator` появится только после первой публикации образа.

## Goals / Non-Goals

Цель состоит в том, чтобы один выпуск идемпотентно подготовил Kubernetes, установил оператор той же ревизии, выдал API отдельные права и включил синхронизацию только после всех проверок.

В изменение не входят перенос API в Kubernetes, частное хранилище образов, автоматическое изменение DNS Cloudflare и создание пользовательского `ValkeyInstance` из процесса CI/CD. Изменение также не подменяет исправление `ContainerRestartRules` внутри оператора или у поставщика кластера.

## Decisions

### Оператор работает внутри Kubernetes

Оператор запускается как `StatefulSet` в `valkey-system` и использует `ServiceAccount` `managed-valkey-operator`. API остаётся на существующем сервере и обращается к Kubernetes по отдельному файлу подключения. Запуск оператора рядом с API через `Docker Compose` отвергнут: тогда процессу потребовался бы административный доступ извне, а его доступность и обновление не управлялись бы самим Kubernetes.

### Образ оператора хранится в общедоступном пакете `GHCR`

Задание `build-operator` собирает `linux/amd64`, помечает образ SHA коммита и публикует `ghcr.io/rostislavdugin/managed-valkey-operator:<sha>` только при отправке коммита в `main`. Для публикации используется встроенный `GITHUB_TOKEN` с правом `packages: write`. Запрос на слияние только собирает и проверяет образ.

Кластер скачивает образ без `imagePullSecrets`. Это позволяет заменённой ноде восстановить оператор обычным механизмом Kubernetes. Прямой импорт архива на ноды отвергнут: SSH к их внутренним адресам недоступен, а файл подключения Kubernetes не даёт доступа к `containerd`. Запуск привилегированного загрузчика образов в кластере добавил бы лишние полномочия.

После первой публикации пакет нужно один раз перевести в состояние `Public`. Процесс выпуска проверяет доступность точного тега до изменения оператора и останавливается, если образ нельзя скачать без учётных данных.

### У Kubernetes и API разные учётные данные

Административный файл подключения хранится только в `PRODUCTION_KUBECONFIG` окружения GitHub `production`. Процесс выпуска использует его для установки системных ресурсов. Для API создаётся токен `ServiceAccount` `managed-valkey-api`, из адреса Kubernetes API, сертификата центра сертификации и токена собирается отдельный файл с режимом `0600`.

Права API разрешают управлять пространствами имён, `ValkeyInstance` и нужными `Secret`, но не разрешают обновлять `ValkeyInstance/status`. Файл монтируется в контейнер API только для чтения. Административный файл и временные копии удаляются после выпуска и не попадают в журналы или результаты сборки. Оператор использует только свою учётную запись внутри кластера.

Токен Cloudflare передаётся только в `Secret` `cloudflare-api-token` пространства имён `cert-manager`. Идентификатор аккаунта сохранён для проверки токена и не требуется `cert-manager`. На сервер API эти значения не копируются.

### Подготовка кластера предшествует обновлению API

Выпуск выполняет действия в следующем порядке:

1. Проверяет доступ к Kubernetes API, наличие образа оператора и работу `ContainerRestartRules` на каждой рабочей ноде.
2. Устанавливает пространство имён, `Gateway API` v1.5.1, `Envoy Gateway` v1.8.4 и `cert-manager` v1.21.1.
3. Создаёт секрет Cloudflare, CRD, RBAC, сетевые ресурсы и TLS-сертификат.
4. Применяет образ оператора с SHA выпуска. Для стратегии `OnDelete` удаляет прежний `Pod`, ждёт готовности нового и сверяет фактически запущенный образ.
5. Создаёт файл подключения API, проверяет его права, готовность сертификата и шлюза, внешний адрес Envoy и соответствие DNS.
6. Передаёт образы API и Caddy, закрытые файлы и настройки на сервер, применяет миграции и запускает `Docker Compose` с `KUBERNETES_SYNC_ENABLED=true`.
7. Записывает `/opt/managed-valkey/.deployed-sha` только после внешней проверки `/readyz` и проверки подключения API к Kubernetes.

Каждый шаг повторно применяет нужное состояние и не удаляет пользовательские ресурсы. Процесс CI/CD не создаёт пробный пользовательский CR. Такой CR мог бы запустить тарифицируемый ресурс и не проверил бы доставку намерения фоновым процессом API.

### Проверка `ContainerRestartRules` выполняется на каждой ноде

До установки оператора процесс создаёт на каждой рабочей ноде короткий служебный `Pod`. Его контейнер завершается успешно с `restartPolicy: Never`, а сам `Pod` имеет `restartPolicy: Always`. Ненулевой счётчик перезапусков означает, что нода не поддерживает требуемое поведение. Все проверочные `Pod` удаляются и при успехе, и при ошибке.

Серверная проверка схемы недостаточна: текущий Kubernetes API принимает поле, хотя процессы `kubelet` его не исполняют. Проверка только одной ноды тоже недостаточна, потому что пользовательский процесс может оказаться на любой из трёх нод.

### DNS настраивается после появления внешнего адреса

Envoy получает адрес через `Service` типа `LoadBalancer`. После его появления запись `*.valkey.h3llo-demo.com` нужно вручную направить на этот адрес в режиме `DNS only`, затем повторить выпуск. Процесс сверяет адрес `probe.valkey.h3llo-demo.com` с адресом Envoy и ждёт готовности `Certificate` `valkey-wildcard` и `Gateway` `valkey`.

Автоматическое изменение DNS через токен Cloudflare не входит в процесс. Токен нужен только `cert-manager` для проверки `DNS-01`, поэтому его права и область применения не расширяются.

### Инфраструктурный резерв одинаков на всех нодах

Для Valkey резервируется по 1000m CPU и 2048 MiB памяти на каждой ноде. При физической ёмкости 4 vCPU и 16 GiB API считает доступными 3000m CPU и 14336 MiB на ноду.

На наиболее занятой ноде существующие системные контейнеры запрашивают 215m CPU и 188 MiB. Одна реплика Envoy запрашивает 100m / 512 MiB, контроллер Envoy Gateway 100m / 256 MiB, оператор 100m / 128 MiB, а три постоянных процесса `cert-manager` вместе 150m / 192 MiB. Сумма равна 565m CPU и 1276 MiB. После неё резерв оставляет 435m CPU и 772 MiB для компонентов без объявленных запросов. Временная проверка `startupapicheck` запрашивает ещё 10m / 32 MiB только при установке.

## Risks / Trade-offs

- Риск: пакет оператора после первой публикации останется закрытым. Мера: проверить общедоступное скачивание точного тега до изменения `StatefulSet`.
- Риск: ошибка после подготовки Kubernetes, но до обновления API оставит частично выполненный выпуск. Мера: повторно применять ту же ревизию идемпотентно и не записывать успешный SHA заранее.
- Риск: статическая учётная запись API использует долгоживущий токен. Мера: хранить его только в файле с режимом `0600`, ограничить RBAC и предусмотреть замену токена повторным выпуском.
- Риск: внешний адрес Envoy неизвестен до первого применения ресурсов. Мера: остановить первый выпуск после получения адреса, настроить DNS вручную и повторить выпуск.
- Риск: текущий кластер не исполняет `ContainerRestartRules`. Мера: блокировать выпуск на проверке каждой ноды до обновления кластера или отдельной переработки остановки Valkey.

## Migration Plan

1. Проверить, что `CLOUDFLARE_API_TOKEN` открывает зону `h3llo-demo.com`, а `PRODUCTION_KUBECONFIG` по-прежнему открывает нужный кластер.
2. Добиться работы `ContainerRestartRules` на всех трёх нодах либо принять отдельное изменение оператора, которое не зависит от этой возможности.
3. Отправить ревизию в `main`, дождаться первой публикации образа и перевести пакет `GHCR` в состояние `Public`.
4. Перед первым включением синхронизации повторно проверить рабочую PostgreSQL. На 11 сентября 2026 года в ней было 0 неудалённых инстансов, 0 незавершённых удалений и нулевой резерв.
5. Запустить выпуск. После появления адреса Envoy направить на него `*.valkey.h3llo-demo.com` в режиме `DNS only` и повторить выпуск.
6. Убедиться, что оператор запущен с нужным SHA, сертификат и шлюз готовы, API использует ограниченную учётную запись, а внешний `/readyz` отвечает успешно.

При откате сначала выключить синхронизацию API или вернуть прежнюю конфигурацию `Docker Compose`. Оператор откатывается только на образ, совместимый с установленным CRD. CRD, пользовательские CR и пространства имён при откате не удаляются.
