## Context

См. `proposal.md`. API работает на отдельном сервере под управлением `Docker Compose`, а оператор должен работать внутри управляемого кластера Kubernetes со своей учётной записью. Административный файл подключения даёт доступ к Kubernetes API, но не к среде выполнения рабочих нод.

В кластере три одинаковые рабочие ноды по 4 vCPU и 16 GiB. Kubernetes API и процессы `kubelet` имеют версию `v1.34.1`; ноды используют `containerd` 1.7.25 и доступны только по внутренним адресам от `10.17.0.26` до `10.17.0.28`. Проверка 11 сентября 2026 года показала, что `ContainerRestartRules` не задан в настройках ни одного из трёх процессов `kubelet`: поле принимается сервером, но завершившийся контейнер перезапускается. Пользователь исключил обращение к поставщику за изменением настроек. Выпуск ждёт реализации `valkey-pod-lifecycle`, которая переносит пользовательские процессы Valkey в отдельные `Pod` с `spec.restartPolicy: Never`.

Секреты `PRODUCTION_KUBECONFIG`, `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` добавлены в окружение GitHub `production`. Cloudflare подтверждает, что токен аккаунта активен и имеет доступ к активной зоне `h3llo-demo.com`. Пакет `ghcr.io/rostislavdugin/managed-valkey-operator` открыт для общего доступа. Образ ревизии `4a8a5dfe0d2d69623906b2c6c1c9dfd3fcd9c8df` имеет платформу `linux/amd64` и загружается без учётных данных.

На момент сохранения прогресса выполнены 10 из 15 задач. В [запуске CI/CD](https://github.com/RostislavDugin/managed-valkey/actions/runs/34636969104) прошли проверки исходного кода, тесты API, оператора и клиентского приложения, общая интеграция, все три группы сквозных проверок и сборки образов. Развёртывание остановила ошибочная проверка прав: `kubectl` воспринял `/status` как имя ресурса. Текущая правка передаёт `--subresource=status`; ограниченная учётная запись возвращает `no`, а точечная проверка сценария проходит. Полный CI/CD ещё не завершался успешным выпуском.

Ручной выпуск установил `Gateway API`, `Envoy Gateway`, `cert-manager`, CRD, RBAC и оператор с точным образом ревизии `3658f5def9baafad97b73055d4fbdd511b924890`, не создавая пользовательский `ValkeyInstance`. Отдельный файл подключения API имеет режим `0600`: управление пространствами имён и `ValkeyInstance` разрешено, изменение `status` запрещено. Сертификат `valkey-wildcard` готов, а `Service` Envoy получил адрес `91.188.213.174`.

Шлюз остаётся в состоянии `Programmed=False`. Все три агента Cilium сообщают `1/3 reachable`: каждая рабочая нода видит только себя и свою сеть `Pod`. Проверка из сети ноды `10.17.0.27` также не смогла подключиться по TCP 443 к `10.17.0.26` и `10.17.0.28`. Политики Kubernetes отсутствуют, а локальные правила `iptables` не содержат запрета на эти адреса. Без межнодовой связи не работают CoreDNS, канал управления Envoy и репликация Valkey. Поэтому клиентский DNS не направлен на адрес Envoy, а API не подключён к Kubernetes. Локальный VPN может мешать запросам рабочей машины к Kubernetes API, но не влияет на обмен между рабочими нодами.

Название сценария `Workflow начался` сохранено дословно как ключ сопоставления с основной спецификацией OpenSpec; оно обозначает создание заданий CI/CD.

## Goals / Non-Goals

Цель состоит в том, чтобы один выпуск идемпотентно подготовил Kubernetes, установил оператор той же ревизии, выдал API отдельные права и включил синхронизацию только после всех проверок.

В изменение не входят перенос API в Kubernetes, частное хранилище образов, автоматическое изменение DNS Cloudflare и создание пользовательского `ValkeyInstance` из процесса CI/CD. Жизненный цикл пользовательских `Pod` и его проверки входят в отдельное изменение `valkey-pod-lifecycle`. Этот план отвечает за проверку рабочего кластера и продолжение выпуска после перехода.

## Decisions

### Оператор работает внутри Kubernetes

Оператор запускается как `StatefulSet` в `valkey-system` и использует `ServiceAccount` `managed-valkey-operator`. API остаётся на существующем сервере и обращается к Kubernetes по отдельному файлу подключения. Запуск оператора рядом с API через `Docker Compose` отвергнут: тогда процессу потребовался бы административный доступ извне, а его доступность и обновление не управлялись бы самим Kubernetes.

### Образ оператора хранится в общедоступном пакете `GHCR`

Задание `build-operator` собирает `linux/amd64`, помечает образ SHA коммита и публикует `ghcr.io/rostislavdugin/managed-valkey-operator:<sha>` только при отправке коммита в `main`. Для публикации используется встроенный `GITHUB_TOKEN` с правом `packages: write`. Запрос на слияние только собирает и проверяет образ.

Кластер скачивает образ без `imagePullSecrets`. Это позволяет заменённой ноде восстановить оператор обычным механизмом Kubernetes. Прямой импорт архива на ноды отвергнут: SSH к их внутренним адресам недоступен, а файл подключения Kubernetes не даёт доступа к `containerd`. Запуск привилегированного загрузчика образов в кластере добавил бы лишние полномочия.

После первой публикации пакет нужно один раз перевести в состояние `Public`. Процесс выпуска проверяет доступность точного тега до изменения оператора и останавливается, если образ нельзя скачать без учётных данных.

### У Kubernetes и API разные учётные данные

Административный файл подключения хранится только в `PRODUCTION_KUBECONFIG` окружения GitHub `production`. Процесс выпуска использует его для установки системных ресурсов. Для API создаётся токен `ServiceAccount` `managed-valkey-api`, из адреса Kubernetes API, сертификата центра сертификации и токена собирается отдельный файл с режимом `0600`.

Права API разрешают управлять пространствами имён, `ValkeyInstance` и нужными `Secret`, но не разрешают обновлять `ValkeyInstance/status`. Файл монтируется в контейнер API только для чтения. Административный файл и временные копии удаляются после выпуска и не попадают в журналы или результаты сборки. Оператор использует только свою учётную запись внутри кластера.

Токен Cloudflare передаётся только в `Secret` `cloudflare-api-token` пространства имён `cert-manager`. Идентификатор аккаунта сохранён для проверки токена и не требуется `cert-manager`. На сервер API эти значения не копируются.

### Подготовка кластера предшествует обновлению API

Выпуск выполняет действия в следующем порядке:

1. Использует ревизию с завершённым `valkey-pod-lifecycle`, проверяет доступ к Kubernetes API, наличие образа оператора, межнодовую связность Cilium и работу `spec.restartPolicy: Never` самого `Pod` на каждой рабочей ноде.
2. Устанавливает пространство имён, `Gateway API` v1.5.1, `Envoy Gateway` v1.8.4 и `cert-manager` v1.21.1.
3. Создаёт секрет Cloudflare, CRD, RBAC, сетевые ресурсы и TLS-сертификат.
4. Применяет образ оператора с SHA выпуска. Для стратегии `OnDelete` удаляет прежний `Pod`, ждёт готовности нового и сверяет фактически запущенный образ.
5. Создаёт файл подключения API, проверяет его права, готовность сертификата и шлюза, внешний адрес Envoy и соответствие DNS.
6. Передаёт образы API и Caddy, закрытые файлы и настройки на сервер, применяет миграции и запускает `Docker Compose` с `KUBERNETES_BACKGROUND_SYNC_ENABLED=true`.
7. Записывает `/opt/managed-valkey/.deployed-sha` только после внешней проверки `/readyz` и проверки подключения API к Kubernetes.

Каждый шаг повторно применяет нужное состояние и не удаляет пользовательские ресурсы. Процесс CI/CD не создаёт пробный пользовательский CR. Такой CR мог бы запустить тарифицируемый ресурс и не проверил бы доставку намерения фоновым процессом API.

### Проверка политики перезапуска выполняется после перехода Valkey на `Pod`

Сначала `valkey-pod-lifecycle` меняет управление пользовательскими процессами и проверяет его без `ContainerRestartRules`. Затем в рамках выпуска `scripts/deploy_kubernetes.sh` и его проверки переходят на короткие служебные `Pod` с `spec.restartPolicy: Never` без поля политики перезапуска у контейнера. До этого существующая блокирующая проверка остаётся в коде; просто отключать её нельзя.

До установки оператора процесс создаёт проверочные `Pod` на каждой рабочей ноде. Контейнеры завершаются с нулевым и ненулевым кодом в отдельных проверках. Процесс ждёт завершения и подтверждает отсутствие повторного запуска; счётчик перезапусков должен оставаться нулевым. Все проверочные `Pod` удаляются и при успехе, и при ошибке. Проверка не требует `ContainerRestartRules` и не доказывает безопасность при потере истории процесса: её обеспечивает оператор по отдельной спецификации.

Проверка прежней контейнерной политики показала, что одного принятия поля Kubernetes API недостаточно: процессы `kubelet` его не исполняли. Новую политику самого `Pod` также проверяем фактическим завершением. Проверка только одной ноды недостаточна, потому что пользовательский процесс может оказаться на любой из трёх нод.

### Выпуск требует связности всех нод Cilium

Перед созданием проверочных `Pod` сценарий получает работающие агенты Cilium. Каждый агент должен сообщить `N/N reachable`, где `N` равно числу рабочих нод. Проверка учитывает и сеть нод, и конечные точки в сети `Pod`. При неполном результате выпуск останавливается до изменения инфраструктуры.

Проверка нужна не только Envoy. Реплики Valkey обмениваются данными между нодами, а оператор может обращаться к любому пользовательскому `Pod`. Размещение всех процессов на одной ноде скрыло бы неисправность, но отменило бы устойчивость `ha` при потере ноды.

### DNS настраивается после появления внешнего адреса

Envoy получает адрес через `Service` типа `LoadBalancer`. После его появления запись `*.valkey.h3llo-demo.com` нужно вручную направить на этот адрес в режиме `DNS only`, затем повторить выпуск. Процесс сверяет адрес `probe.valkey.h3llo-demo.com` с адресом Envoy и ждёт готовности `Certificate` `valkey-wildcard` и `Gateway` `valkey`.

Автоматическое изменение DNS через токен Cloudflare не входит в процесс. Токен нужен только `cert-manager` для проверки `DNS-01`, поэтому его права и область применения не расширяются.

### Плоскость управления обращается к `cert-manager-webhook` через ноды

Плоскость управления рабочего кластера не имеет рабочего маршрута к `Service` или адресам пользовательской сети `Pod`. `hostNetwork` с портом `10260` не помог, потому что этот порт закрыт. `hostNetwork` с портом `443` также не помог, пока конфигурация допуска обращалась через кластерный `Service`. Внешний `LoadBalancer` получил адрес, но не принимал соединения снаружи.

`cert-manager-webhook.valkey.h3llo-demo.com` содержит три записи A в режиме `DNS only`, по одной для каждого внутреннего адреса рабочей ноды. Конфигурации допуска обращаются к этому имени напрямую. `cert-manager-webhook` запускается в трёх экземплярах с `hostNetwork` и обязательным распределением по разным нодам. Обновление использует `maxSurge: 0` и `maxUnavailable: 1`, а `PodDisruptionBudget` сохраняет не меньше двух готовых экземпляров.

Порт `443` требует UID 0 и `NET_BIND_SERVICE`. Эти права получает только контейнер `cert-manager-webhook`; для него запрещено повышение прав, удалены остальные возможности Linux, включён `RuntimeDefault`, а корневая файловая система доступна только для чтения. Адреса нод не являются постоянными, поэтому процесс выпуска до установки `cert-manager` сверяет DNS со всем текущим набором `InternalIP` и останавливается при расхождении. После замены ноды запись исправляют вручную и повторяют выпуск.

Обе реплики CoreDNS рабочего кластера находятся на одной ноде, а DNS-запросы к ним с двух соседних нод завершаются по времени ожидания. Контроллер `cert-manager` попал на одну из таких нод и не мог разрешить имя сервера ACME. Значение `podDnsPolicy: Default` даёт только этому контроллеру системный DNS рабочей ноды. Обработчик допуска сохраняет `ClusterFirstWithHostNet`, потому что его адреса обслуживает Kubernetes API.

### Инфраструктурный резерв одинаков на всех нодах

Для Valkey резервируется по 1000m CPU и 2048 MiB памяти на каждой ноде. При физической ёмкости 4 vCPU и 16 GiB API считает доступными 3000m CPU и 14336 MiB на ноду.

На наиболее занятой ноде существующие системные контейнеры запрашивают 215m CPU и 188 MiB. Одна реплика Envoy запрашивает 100m / 512 MiB, контроллер Envoy Gateway 100m / 256 MiB, оператор 100m / 128 MiB, а постоянные процессы `cert-manager` вместе 250m / 320 MiB с учётом трёх экземпляров `cert-manager-webhook`. Сумма равна 665m CPU и 1404 MiB. После неё резерв оставляет 335m CPU и 644 MiB для компонентов без объявленных запросов. Временная проверка `startupapicheck` запрашивает ещё 10m / 32 MiB только при установке.

## Risks / Trade-offs

- Риск: пакет оператора после первой публикации останется закрытым. Мера: проверить общедоступное скачивание точного тега до изменения `StatefulSet`.
- Риск: ошибка после подготовки Kubernetes, но до обновления API оставит частично выполненный выпуск. Мера: повторно применять ту же ревизию идемпотентно и не записывать успешный SHA заранее.
- Риск: статическая учётная запись API использует долгоживущий токен. Мера: хранить его только в файле с режимом `0600`, ограничить RBAC и предусмотреть замену токена повторным выпуском.
- Риск: внешний адрес Envoy неизвестен до первого применения ресурсов. Мера: остановить первый выпуск после получения адреса, настроить DNS вручную и повторить выпуск.
- Риск: удалить прежнюю проверку раньше, чем оператор перестанет зависеть от `ContainerRestartRules`. Мера: продолжать выпуск только после реализации и проверки `valkey-pod-lifecycle`; затем заменить проверку нод, сохранив остановку выпуска при ошибке.
- Риск: замена ноды изменит внутренний адрес, а конфигурация допуска продолжит обращаться к старому DNS. Мера: держать три экземпляра `cert-manager-webhook`, сверять все адреса перед выпуском и вручную обновлять служебную запись после замены ноды.
- Риск: `cert-manager-webhook` слушает привилегированный порт с UID 0. Мера: оставить ему только `NET_BIND_SERVICE`, запретить повышение прав, использовать профиль `RuntimeDefault` и файловую систему только для чтения.
- Риск: межнодовой доступ к CoreDNS снова потребуется контроллеру `cert-manager`. Мера: контроллер использует DNS рабочей ноды только для внешних запросов, а доступ к Kubernetes API получает через адрес из окружения `Pod`.
- Риск: сеть нод или сеть `Pod` Cilium остаётся разделённой. Мера: останавливать выпуск по результату `cilium-health`; обход через размещение всех процессов на одной ноде не использовать.

## Migration Plan

1. Проверить, что `CLOUDFLARE_API_TOKEN` открывает зону `h3llo-demo.com`, `PRODUCTION_KUBECONFIG` по-прежнему открывает нужный кластер, каждый агент Cilium видит все рабочие ноды, а `cert-manager-webhook.valkey.h3llo-demo.com` содержит их внутренние адреса.
2. Завершить и проверить `valkey-pod-lifecycle`, затем заменить предварительную проверку нод в сценарии выпуска. Убедиться, что в кластере нет пользовательских `StatefulSet`, оставшихся от прежнего оператора; при обнаружении остановить выпуск и выполнить согласованный порядок перехода.
3. Отправить новую ревизию в `main` и проверить её образ в уже общедоступном пакете `GHCR`.
4. Перед первым включением синхронизации повторно проверить рабочую PostgreSQL. На 11 сентября 2026 года в ней было 0 неудалённых инстансов, 0 незавершённых удалений и нулевой резерв.
5. Запустить выпуск. После появления адреса Envoy направить на него `*.valkey.h3llo-demo.com` в режиме `DNS only` и повторить выпуск.
6. Убедиться, что оператор запущен с нужным SHA, сертификат и шлюз готовы, API использует ограниченную учётную запись, а внешний `/readyz` отвечает успешно.
7. Выполнить весь CI/CD от начала до конца с обязательными тестами. Пропуск промежуточных запусков по просьбе пользователя не меняет постоянные условия допуска выпуска. Сверить эксплуатационную документацию с переходом на `Pod` и только после этого завершать задачи и архивировать изменение.

При откате сначала выключить синхронизацию API или вернуть прежнюю конфигурацию `Docker Compose`. Оператор откатывается только на образ, совместимый с установленным CRD и прямым управлением `Pod`. Возвращать версию с пользовательскими `StatefulSet` поверх прямых `Pod` нельзя; такой переход требует отдельной согласованной остановки по `valkey-pod-lifecycle`. CRD, пользовательские CR и пространства имён обычный откат выпуска не удаляет.
