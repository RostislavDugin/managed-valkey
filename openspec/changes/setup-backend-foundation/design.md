## Context

См. [proposal.md](proposal.md). Сейчас в репозитории работает только `web`; корневого Go-модуля, серверных приложений, compose-файлов, миграций и манифестов нет. `SYSTEM.md` уже задаёт границы компонентов, структуру каталогов, версии инфраструктуры, переменные окружения и порядок выкладки.

API и оператор должны делить один Go-модуль, но не внутренние пакеты друг друга. Единственное направление общего контракта между приложениями проходит через публичные типы CRD в `operator/api/v1alpha1`; общий корневой `internal` предназначен только для действительно общего кода. Оператор не имеет доступа к PostgreSQL или HTTP API сервиса.

## Goals / Non-Goals

**Goals:**

- Получить каркас, который одинаково собирается на рабочей машине и в контейнере.
- Проверить сквозной запуск процессов, PostgreSQL, миграций, k3s и экспорта логов до реализации предметного поведения.
- Оставить генерацию Kubernetes-кода и инструменты воспроизводимыми через локальные команды приложений.
- Зафиксировать локальные правила Go до появления основного объёма серверного кода.

**Non-Goals:**

- Не реализовывать регистрацию, JWT, управление инстансами, биллинг и остальные HTTP-контракты из `SYSTEM.md`.
- Не создавать предметные таблицы PostgreSQL в рамках технического каркаса.
- Не реализовывать управление StatefulSet, failover, ресайз, ACL, метрики и проверку Envoy в reconcile.
- Не настраивать GitHub Actions, выпуск образов и развёртывание на реальной инфраструктуре h3llo.
- Не выполнять проверки из раздела 15 `SYSTEM.md`, кроме проверки, что подготовленное dev-окружение запускается.

## Decisions

### 1. Версии Go и зависимостей

Использовать модуль `github.com/RostislavDugin/managed-valkey` с директивами `go 1.27.0` и `toolchain go1.27.1`. Версия toolchain фиксирует исправляющий выпуск для локальной сборки и CI, а production-образы используют тот же выпуск.

Начальные версии прямых runtime-зависимостей:

- Gin `v1.12.0`;
- GORM `v1.31.2` и PostgreSQL driver `v1.6.2`;
- `controller-runtime v0.23.3` и Kubernetes-модули ветки `v0.35`, соответствующей Kubernetes 1.35;
- OpenTelemetry API/SDK и OTLP log exporter из совместимого набора актуальных выпусков;
- `otelslog v0.20.1`;
- `google/uuid v1.6.0`.

Инструменты добавляются через `go get -tool` и секцию `tool` в `go.mod`:

- `goose v3.28.0`;
- Air `v1.67.4`;
- golangci-lint `v2.13.2`;
- controller-gen `v0.20.1`;
- `setup-envtest` на совместимой с `controller-runtime v0.23` ревизии.

Локальные `Justfile` используют `go tool <name>`, поэтому отдельная установка Air, `goose`, линтера и генераторов не нужна. Альтернатива с глобальными бинарниками делает результат зависимым от машины. Отдельные `go.mod` для приложений противоречат структуре из `SYSTEM.md` и усложняют совместимость CRD-типов.

### 2. Минимальный процесс API

`api/cmd/api` собирает конфигурацию из env, создаёт `slog`, открывает GORM-соединение с PostgreSQL и запускает Gin через стандартный `http.Server`. Используется `gin.New()`, чтобы запросы не проходили через независимый стандартный логгер Gin. Middleware добавляет recovery, `request_id` и одну итоговую запись о запросе без тела и заголовков авторизации.

Технические маршруты не входят в версионированный продуктовый API:

- `GET /livez` отвечает, пока работает HTTP-процесс;
- `GET /readyz` выполняет ограниченную по времени проверку PostgreSQL.

Kubernetes не входит в readiness API. Это сохраняет описанную в `SYSTEM.md` возможность входа и чтения сохранённого состояния при недоступном control plane. Подключение Kubernetes и фоновые циклы появятся вместе с первым серверным поведением.

`signal.NotifyContext` передаёт отмену серверу. После сигнала API вызывает `Shutdown` с ограниченным сроком, закрывает соединение базы и завершает экспорт логов. Ошибка обязательной конфигурации или подключения PostgreSQL до старта возвращает ненулевой код.

Альтернатива с автоматическим применением миграций внутри API смешивает права и позволяет нескольким репликам соревноваться за миграцию. Миграции запускает отдельный процесс до API.

### 3. Kubebuilder как источник каркаса оператора

Использовать Kubebuilder `v4.13.1`: его Go-плагин закрепляет `controller-runtime v0.23.3`, соответствующий Kubernetes 1.35 из `SYSTEM.md`. Operator SDK не используется. Его Go-проект основан на тех же Kubebuilder-плагинах и `controller-runtime`, а дополнительные OLM bundle, OperatorHub и scorecard этому внутреннему оператору не нужны.

Kubebuilder нельзя запускать прямо в `operator`, потому что он создаст вложенный Go-модуль и собственные корневые Makefile и Dockerfile. Каркас генерируется во временном каталоге с параметрами проекта Managed Valkey, после чего применимые части переносятся и адаптируются:

```text
operator/
  cmd/operator/          manager и проверки состояния
  api/v1alpha1/          ValkeyInstance и сгенерированный DeepCopy
  internal/operator/     начальный reconciler
  config/                сгенерированные CRD и RBAC
```

Тип `ValkeyInstance` на этом этапе содержит минимальный корректный `spec` и `status`, необходимые генератору. Начальный reconciler регистрируется в manager, но возвращает управление без записи `status` и без создания зависимых объектов. Полный контракт полей и поведение reconcile добавит отдельное изменение по разделам 6 и 15 `SYSTEM.md`.

Файл `PROJECT`, Kubebuilder Makefile и лишние примеры не переносятся. После первоначального каркаса источником генерации служат Go-маркеры и закреплённый `controller-gen`; его вызывают внутренние рецепты `operator/Justfile` перед сборкой и тестами. Такой подход сохраняет структуру монорепозитория, но требует осознанно переносить изменения шаблона при обновлении Kubebuilder.

Manager использует leader election, `signal.NotifyContext`, `/healthz` и `/readyz`. До появления фоновых циклов готовность означает успешный запуск manager и синхронизацию его cache. Production-манифест создаёт одну реплику оператора, но leader election остаётся включённым для безопасного будущего перезапуска.

### 4. Структурированное логирование

`internal/logging` создаёт один `slog.Logger` с fan-out в текстовый или JSON handler stdout и OTLP handler. Формат stdout выбирается по окружению: читаемый текст на dev, JSON на prod. Уровень задаёт `LOG_LEVEL`.

Применимые правила из Go-гайда Databasus адаптируются так:

- сообщения начинаются со строчной буквы и не заканчиваются точкой;
- ключи имеют вид `snake_case`;
- ошибки записываются атрибутом `error`;
- известные идентификаторы добавляются через `logger.With` на границе операции;
- API передаёт `context.Context` с `request_id` и `user_id`, оператор добавляет `instance_slug`;
- секреты и полные запросы не логируются.

Размеры, счётчики и переходы состояния остаются структурированными атрибутами, а не встраиваются в сообщение через `fmt.Sprintf`: VictoriaLogs сможет фильтровать их по полям. Недоступность OTLP не останавливает приложения. Ошибка начальной настройки экспортера попадает только в stdout, а накопленные записи сбрасываются с ограниченным сроком при завершении.

### 5. Goose и начальное состояние миграций

`migrations/` содержит SQL-файлы `goose` с временными префиксами. Первая техническая миграция `baseline` не создаёт предметных таблиц, но даёт проверяемую начальную версию и позволяет `goose up` успешно работать до изменения со схемой данных. Она содержит только директивы `goose` и безопасную SQL-операцию без постоянного эффекта.

Команды `api/Justfile`, запускаемые из `api`:

```text
just migration-generate <name>  # создать timestamp SQL migration
just migration-up               # применить goose up к DATABASE_URL
just migration-down             # откатить одну последнюю миграцию
```

Рецепты обращаются к корневому каталогу `../migrations`. Миграции по умолчанию транзакционные. `NO TRANSACTION` допускается только для операции PostgreSQL, которую нельзя выполнить в транзакции, с пояснением причины в самом файле. `migration-down` предназначена для явного локального отката; compose и порядок production-выкладки вызывают только `migration-up`.

Отдельная цель Dockerfile собирает закреплённый `goose` и копирует `migrations`. Сервис `migrate` использует этот образ и завершается до старта API. В runtime-образ API `goose` и исходные SQL-файлы не попадают.

Правила SQL из внешнего гайда уточняются требованиями `SYSTEM.md`: UUIDv7 и встроенная `uuidv7()` PostgreSQL 18 вместо `gen_random_uuid()`, только `TIMESTAMPTZ`, аддитивная выкладка, префикс `valkey_`, отдельные именованные ограничения и индексы. Эти правила относятся к `api/AGENTS.md`; `operator/AGENTS.md` вместо них запрещает зависимость от базы.

### 6. Dockerfile приложений

Каждое приложение получает многоступенчатый Dockerfile в своём каталоге, но контекст сборки всегда корень репозитория. Это даёт доступ к общему модулю; API также сможет получить собранную статику `web` в следующем продуктовом изменении.

Dockerfile содержит цели:

- `dev` с Air и кэшем модулей;
- `build` для статического Linux-бинарника;
- `runtime` на минимальном non-root образе с CA-сертификатами;
- для API отдельную цель `migrate`.

Production-контейнеры запускаются без root, не содержат Go toolchain и не записывают в файловую систему приложения. Версии базовых образов фиксируются тегом и digest. Сборка frontend и его `embed` не включаются, пока API не начнёт отдавать SPA; production compose на этом этапе проверяет серверный каркас, а продуктовое изменение добавит статику до первой выкладки.

### 7. Dev compose

Граф запуска следует разделу 13 `SYSTEM.md`:

```text
postgres --> migrate --> api

k3s-server --> k3s-agent-1
           --> k3s-agent-2
           --> k3s-bootstrap --> operator

api ---------> victorialogs
operator ----> victorialogs
```

PostgreSQL имеет healthcheck и создаёт отдельные базы `managed_valkey` и `managed_valkey_test`; создание баз не заменяет миграции схемы. VictoriaLogs публикует `9428`. API публикует `8080` для Vite. k3s-server публикует Kubernetes API и NodePort `41379`; встроенные Traefik и servicelb выключены.

Bootstrap ждёт Kubernetes API, затем идемпотентно применяет закреплённые Gateway API CRD, Envoy Gateway, CRD Managed Valkey, RBAC, namespace и общую сетевую инфраструктуру. Сертификат mkcert и kubeconfig приложений хранятся в Docker volumes и не попадают в Git.

Оператор использует собственный kubeconfig и `network_mode: service:k3s-server`, как требует `SYSTEM.md`. Air следит только за каталогом приложения и общим `internal`; каталоги `web`, `migrations`, `.git` и временные сборки исключены.

### 8. Production compose и манифесты

Production compose запускает на виртуальной машине PostgreSQL, `migrate`, API, VictoriaLogs и Caddy. API зависит от успешного `migrate` и готовой базы; Caddy зависит от готовности API. Порты PostgreSQL `45432` и VictoriaLogs `9428` публикуются по контракту v1 из `SYSTEM.md`.

Образ Caddy собирается через `xcaddy` с закреплённой ревизией `mholt/caddy-ratelimit`. В репозитории хранится Caddyfile из раздела 7 `SYSTEM.md`; секретов в нём нет.

Оператор собирается отдельным образом и устанавливается через `deploy/prod` в managed Kubernetes. Kustomize связывает сгенерированные CRD и RBAC из `operator/config` с StatefulSet оператора и инфраструктурой Envoy. В production compose сервиса `operator` нет.

`.env.example` перечисляет переменные из раздела 13 `SYSTEM.md`, но содержит только безопасные примеры и обязательные пустые значения. Compose проверяет обязательные переменные через `${NAME:?message}` там, где значение нельзя выбирать по умолчанию.

### 9. Локальные Justfile и границы тестов

Корневого `Justfile` нет. У каждого Go-приложения свой короткий интерфейс команд.

`api/.golangci.yml` и `operator/.golangci.yml` адаптируют [конфигурацию Databasus](https://github.com/databasus/databasus/blob/main/backend/.golangci.yml) под общий модуль Managed Valkey. Оба файла используют формат конфигурации golangci-lint v2, `timeout: 5m`, `tests: false`, `concurrency: 4` и `default: standard`. Дополнительно включаются `funcorder`, `bodyclose`, `errorlint`, `gocritic`, `unconvert`, `misspell`, `errname`, `noctx` и `modernize`; `errcheck` проверяет type assertions. Форматирование выполняют `gofumpt` с `module-path: github.com/RostislavDugin/managed-valkey` и `extra-rules: true`, `golines` с длиной строки 120 и `gci` с секциями `standard`, `default`, `localmodule`. Файлы почти одинаковы намеренно: приложение можно проверять из его каталога, а правила не зависят от глобальной конфигурации.

Публичная команда `lint` сначала форматирует область приложения, затем запускает проверки. Для API область состоит из `./api/...` и общих пакетов, которые оно использует; для оператора из `./operator/...` и его общих пакетов. Внутренний рецепт `_lint-check` выполняет только проверку и нужен pre-commit hook, которому нельзя форматировать посторонние незакоммиченные файлы.

`api/Justfile` содержит:

```text
just migration-up
just migration-down
just migration-generate <name>
just test
just lint
just run
just build
```

`just test` применяет миграции к `managed_valkey_test` и запускает все тесты API. Отдельных `test-fast` и `test-full` нет, потому что API не выполняет длительный provisioning Kubernetes. `run` запускает API локально с конфигурацией из окружения, `build` создаёт только бинарник API.

`operator/Justfile` содержит:

```text
just test-fast
just test-full
just lint
just build
just run
```

`test-fast` включает unit-тесты и `envtest`: он проверяет API Kubernetes и reconcile, но не ждёт настоящие поды Valkey. `test-full` собирает и устанавливает текущий оператор тем же внутренним рецептом, что и `run`, затем работает с k3s из `docker-compose.dev.yml`, создаёт ресурсы и ждёт реальные изменения Kubernetes и provisioning с явными таймаутами.

`just run`, запущенная из `operator`, собирает dev-образ оператора, загружает его в containerd нод k3s, применяет CRD и манифесты, затем ждёт готовности StatefulSet. Повторный запуск обновляет образ и перезапускает только оператор. `build` создаёт только бинарник оператора.

Генерация, установка манифестов и сборка dev-образа оформляются закрытыми рецептами с префиксом `_`. Они вызываются публичными командами, но не расширяют основной список `just --list`.

Корневой `.githooks/pre-commit` сохраняет существующий порядок проверок frontend и добавляет проверки Go. Хук определяет затронутое приложение по staged-путям. Изменение общего Go-кода, `go.mod` или `go.sum` затрагивает оба приложения. Для каждого затронутого приложения хук:

1. Передаёт форматтеру только staged Go-файлы, а после успешного форматирования добавляет эти же файлы в индекс.
2. Запускает `_lint-check` и `build` из локального `Justfile`.
3. Проверяет `go mod tidy -diff`, не меняя и не добавляя зависимости автоматически.

Ошибка форматтера, любое замечание линтера, расхождение `go mod tidy -diff` или ошибка сборки возвращают ненулевой код и отменяют коммит. Полные тесты оператора не запускаются в pre-commit, потому что требуют dev k3s. `api test` также остаётся явной командой, поскольку ему нужна тестовая PostgreSQL. Хук не добавляет в индекс незакоммиченные файлы, которые не были staged до форматирования.

Окружения запускаются напрямую:

```text
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.prod.yml up -d
```

### 10. TODO для будущих тестов отказа

`operator/TODO.md` кратко фиксирует будущий `test-full`: остановить активный процесс или pod Valkey, наблюдать отсутствие primary, дождаться безопасного выбора и запуска нового primary, затем проверить запись. Потеря целой worker-ноды записывается отдельным пунктом, потому что такой сценарий по `SYSTEM.md` требует подтверждённого fencing и не всегда допускает автоматический promote.

Корневой `e2e/TODO.md` фиксирует два будущих сквозных теста без подробной реализации:

1. Создать пользователя через API, создать Valkey, дождаться `running` и проверить подключение.
2. После той же подготовки выполнять запросы каждые 100 мс, остановить активный pod Valkey, увидеть временные ошибки, дождаться восстановления оператором и убедиться, что запросы снова проходят.

Корневой e2e-набор не получает `Justfile` на этом этапе. Способ его запуска будет выбран вместе с реализацией тестового каркаса и CI.

### 11. Локальные инструкции приложений

`api/CLAUDE.md` и `operator/CLAUDE.md` являются относительными символическими ссылками `CLAUDE.md -> AGENTS.md`, как уже сделано в `web`.

Оба `AGENTS.md` сначала ссылаются на корневые инструкции и нужные разделы `SYSTEM.md`. Повторение правил Go допустимо: локальный файл должен оставаться понятным без переходов между двумя почти одинаковыми приложениями.

Из Databasus переносятся пустые строки между логическими блоками, комментарии только о неочевидной причине, UTC, правила `slog`, формат SQL и современные средства стандартной библиотеки. Не переносятся обязательный Swagger, их DI с глобальными singleton, структура CRUD, имена тестов и специальные правила backup. `api/AGENTS.md` описывает Gin, GORM и `goose`; `operator/AGENTS.md` описывает `controller-runtime`, идемпотентный reconcile, запрет базы и работу через контекст.

## Risks / Trade-offs

- [Kubebuilder не владеет итоговой структурой проекта] -> Зафиксировать исходную версию, сохранить стандартные маркеры и сравнивать новый временный каркас при обновлении `controller-runtime`.
- [Начальный reconciler может создать ложное ощущение реализованного оператора] -> Он не меняет ресурсы; production-развёртывание до реализации предметного reconcile считается только технической проверкой процесса.
- [Go 1.27.1 может отсутствовать на машине разработчика] -> Директива `toolchain` загружает нужную версию, а контейнерная сборка использует закреплённый официальный образ.
- [Полный dev compose требует много памяти] -> Оставить инфраструктурные сервисы отдельными и разрешить запуск нужных сервисов через явные имена Docker Compose.
- [Публичные PostgreSQL и VictoriaLogs в v1 небезопасны для долгой эксплуатации] -> Сохранить только явно принятый контракт `SYSTEM.md`; реальные секреты не хранить в Git, а последующее усиление доступа оформить отдельным изменением.
- [No-op baseline остаётся в истории миграций] -> Дать ему явное техническое имя и не смешивать с первой предметной схемой.
- [Недоступный OTLP endpoint может задерживать остановку] -> Ограничить экспорт и flush отдельными таймаутами, после которых процесс завершается.

## Migration Plan

1. Создать общий Go-модуль и закрепить runtime-зависимости и инструменты.
2. Сгенерировать Kubebuilder-каркас во временном каталоге, перенести manager, минимальный API ресурса и контроллер, затем удалить чужие корневые файлы и примеры.
3. Создать общий logger, минимальный API, настройки Air и тесты запуска и завершения.
4. Добавить каталог миграций, baseline и три команды `goose` в `api/Justfile`; проверить применение, повторное применение и откат одной миграции на PostgreSQL 18.
5. Создать Dockerfile приложений и Caddy, затем dev compose и его bootstrap.
6. Создать production compose, production-манифесты оператора и `.env.example`.
7. Добавить локальные `.golangci.yml`, `Justfile`, два коротких TODO и инструкции API и оператора с символическими ссылками Claude.
8. Расширить pre-commit hook проверками Go и обновить его описание в корневом `AGENTS.md`.
9. Обновить разделы 14 и 16 `SYSTEM.md` под локальные команды и корневой каталог e2e.
10. Выполнить `just lint` и тесты из обоих приложений, собрать их и запустить dev compose.
11. Проверить `docker compose config` для обоих файлов, отсутствие секретов и незакреплённых production-образов, затем выполнить `openspec validate setup-backend-foundation --strict`.

Изменение добавляет новые файлы и не меняет данные существующего окружения. До первой production-выкладки откат выполняется возвратом коммита. После появления предметных миграций откат приложения не должен запускать `goose down`; старая версия API обязана работать с аддитивно расширенной схемой.
