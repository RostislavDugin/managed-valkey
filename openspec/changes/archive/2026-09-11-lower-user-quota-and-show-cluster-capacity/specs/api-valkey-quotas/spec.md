## ADDED Requirements

### Requirement: API сообщает личную квоту и общий резерв Managed Kubernetes

Защищённый `GET /v1/managed/valkey/capacity` SHALL возвращать `{user, cluster, instances}`. `user` и `cluster` SHALL содержать `limit` и `used` с целыми полями `vcpu` и `ram_gb`; `instances` SHALL содержать целые `limit` и `used`. Личный лимит SHALL читаться из `user_quotas`, общий лимит CPU и RAM SHALL равняться сумме доступных после инфраструктурного резерва ресурсов нод из настроенной топологии, а предел инстансов SHALL совпадать с проверкой мутаций. Личный и общий расход SHALL считаться по тем же строкам и правилам резерва, что и окончательная проверка создания и `resize`.

Ответ SHALL представлять один согласованный снимок PostgreSQL: принятая мутация видна во всех связанных величинах либо не видна ни в одной. Запрос MUST NOT изменять или резервировать ресурсы и MUST NOT зависеть от доступности Kubernetes. Снимок служит для предварительной оценки; создание и `resize` SHALL повторно проверять квоты и общий бюджет внутри своей транзакции.

#### Scenario: Кластер и аккаунт свободны

- **WHEN** новый пользователь запрашивает `/v1/managed/valkey/capacity` в кластере без инстансов
- **THEN** `user.used`, `cluster.used` и `instances.used` равны нулю
- **AND** ответ содержит личные лимиты 4 vCPU / 12 GB, настроенные общие лимиты и предел 32 инстанса

#### Scenario: В кластере есть инстансы разных владельцев

- **WHEN** у вызывающего пользователя и других владельцев есть неподтверждённо удалённые `single` и `ha`
- **THEN** `user.used` содержит только резерв вызывающего пользователя
- **AND** `cluster.used` и `instances.used` учитывают строки всех владельцев

#### Scenario: Мутация выполняется одновременно со чтением

- **WHEN** создание, `resize` или подтверждённое удаление фиксируется одновременно с запросом `/v1/managed/valkey/capacity`
- **THEN** ответ соответствует состоянию целиком до либо целиком после зафиксированной мутации
- **AND** следующий запрос отражает уже зафиксированное состояние

#### Scenario: Снимок устарел перед отправкой

- **WHEN** после успешного ответа `/v1/managed/valkey/capacity` другой запрос занимает последний доступный ресурс
- **THEN** последующая мутация всё равно отклоняется окончательной проверкой с `422`

#### Scenario: Запрос без JWT

- **WHEN** клиент вызывает `/v1/managed/valkey/capacity` без заголовка авторизации
- **THEN** API отвечает `401 UNAUTHORIZED`

## MODIFIED Requirements

### Requirement: Личная квота и общий бюджет дают разные ошибки

Лимиты пользователя SHALL читаться из `user_quotas`; значения по умолчанию остаются 4 CPU / 12 GB. Личная квота SHALL проверяться раньше общей. Ошибка SHALL быть `422 QUOTA_EXCEEDED` с `reason=user_quota`. Для ошибок `user_quota`, `cluster_quota` и `placement_capacity` `details` SHALL содержать `limit`, `used`, `requested`, `missing`, где каждая величина содержит `vcpu` и `ram_gb`, а `requested` означает суммарный резерв после принятия кандидата. Для предела числа `details` SHALL содержать `limit`, `used`, `requested` как целые числа. Для `placement_capacity` `details` SHALL дополнительно содержать сведения из контракта `api-cluster-placement`; нулевой общий `missing` не означает, что размещение возможно. Отказ по квоте или размещению MUST NOT занимать ключ идемпотентности.

#### Scenario: CPU и RAM проверяются независимо

- **WHEN** кандидат превышает только один личный лимит
- **THEN** API отклоняет его и возвращает ненулевой дефицит только соответствующего ресурса

#### Scenario: Два запроса одного пользователя

- **WHEN** каждый из двух конкурентных запросов отдельно помещается в личный остаток, но вместе они превышают квоту
- **THEN** один запрос принимается, другой получает `QUOTA_EXCEEDED`

#### Scenario: Лимит уменьшен ниже занятого объёма

- **WHEN** новое изменение размера не увеличивает резерв ни CPU, ни RAM относительно текущего, но текущий резерв уже выше нового лимита
- **THEN** API допускает уменьшение при выполнении остальных правил готовности
- **AND** увеличение любой превышающей лимит величины отклоняется
