## Context

Причина изменения описана в [proposal.md](proposal.md). Регистрация явно создаёт квоту 4 vCPU / 16 GB, и такой же `DEFAULT` хранится в схеме PostgreSQL. `/v1/me` возвращает только личную квоту. Окончательная проверка создания и `resize` уже считает общий резерв всех владельцев из PostgreSQL, проверяет размещение по настроенной топологии и ставит личную квоту раньше общего бюджета под `pg_advisory_xact_lock(1)`.

Страница создания загружает личную квоту один раз. Страница базы опрашивает карточку, каталог и `/v1/me` примерно раз в 5 секунд, поэтому окно изменения тарифа получает свежую личную квоту, но не знает общий остаток. Карточка размера принимает только признак доступности и любую недоступность подписывает как нехватку квоты.

Production описывает три одинаковые ноды по 4 vCPU / 16 GiB и вычитает из каждой 1000m CPU / 2048 MiB для инфраструктуры. Настроенный бюджет Valkey равен 9 vCPU / 42 GiB и не зависит от фактического потребления `Pod`.

## Goals / Non-Goals

**Goals:**

- дать обеим формам один согласованный снимок тех ограничений, которые проверяет сервер;
- не допустить перекрывающихся периодических запросов и поздних обновлений после смены контекста;
- сохранить личную квоту первой причиной отказа;
- понизить стандартную квоту всех текущих и будущих аккаунтов без изменения существующих инстансов.

**Non-Goals:**

- измерять фактическую загрузку CPU и RAM через Kubernetes Metrics API;
- добавлять моделирование размещения по нодам в предварительный снимок или предсказывать решение планировщика Kubernetes;
- резервировать ресурс чтением `/v1/managed/valkey/capacity`, вводить очередь или автоматически расширять кластер;
- менять каталог размеров, выбранные размеры существующих баз или топологию рабочего окружения и её инфраструктурный резерв.

## Decisions

### 1. Новая миграция меняет `DEFAULT` и все существующие квоты

Новая Goose-миграция устанавливает `max_vcpu=4` и `max_ram_gb=12` во всех существующих строках `user_quotas`, затем меняет `DEFAULT` обоих столбцов на 4 и 12. Такое полное обновление допустимо, потому что до изменения никому не выдавали индивидуальную квоту. Код регистрации использует общие константы стандартной квоты вместо числовых литералов.

Миграция не трогает `valkey_instances`. Пользователь с расходом выше нового лимита остаётся выше квоты: сервер уже разрешает уменьшение, которое не увеличивает превышение, и запрещает дальнейший рост. Это безопаснее принудительного `resize`, который мог бы очистить кеш или потребовать недоступные `Pod`.

Секция `Down` меняет `DEFAULT` обратно на 4 vCPU / 16 GB и возвращает 16 GB строкам с точной стандартной квотой 4 vCPU / 12 GB. Такой откат нельзя запускать после выдачи индивидуальной квоты ровно 4/12 без отдельной проверки данных.

Альтернатива: изменить только регистрацию. Она оставила бы существующие аккаунты на 16 GB и не выполнила подтверждённое требование.

### 2. Capacity относится к Valkey API, а не к `/v1/me`

Добавляется `GET /v1/managed/valkey/capacity` с ответом:

```json
{
  "user": {
    "limit": { "vcpu": 4, "ram_gb": 12 },
    "used": { "vcpu": 1, "ram_gb": 2 }
  },
  "cluster": {
    "limit": { "vcpu": 9, "ram_gb": 42 },
    "used": { "vcpu": 7, "ram_gb": 22 }
  },
  "instances": { "limit": 32, "used": 8 }
}
```

Один SQL-запрос читает строку `user_quotas` и агрегирует активные `valkey_instances` с отдельными суммами для владельца и всего кластера. Запрос получает один согласованный снимок PostgreSQL, поэтому ответ не смешивает состояние до и после конкурентной фиксации транзакции. Расчёт переиспользует выражение резерва `node_count * greatest(desired, applied)` и учитывает `deleted_at IS NULL` независимо от фазы.

Запрос чтения не берёт `pg_advisory_xact_lock(1)`. Иначе открытые формы каждые пять секунд конкурировали бы с мутациями за общую блокировку. Снимок может устареть сразу после ответа, поэтому `POST` сохраняет существующую окончательную проверку под блокировкой.

Маршрут возвращает только агрегаты. Он не раскрывает владельцев, имена или размеры чужих баз. Точный общий расход всё же позволяет наблюдать активность платформы; это осознанный компромисс ради запрошенного отображения загрузки небольшого кластера.

Альтернативы:

- Расширить `/v1/me`. Тогда восстановление любой сессии зависело бы от агрегата Valkey, а auth-сервис получил бы конфигурацию кластера.
- Вернуть готовую доступность каждой карточки. Для `resize` понадобился бы параметр текущей базы, контракт сильнее связался бы с каталогом, а клиент не смог бы объяснить недостающий ресурс.
- Читать Node и Pod из Kubernetes. Фактическое потребление нестабильно, не совпадает с requests и сделало бы HTTP-проверку зависимой от Kubernetes.

### 3. Клиент применяет одинаковый расчёт к двум бюджетам

Модель клиента хранит личный и общий `ResourceBudget` с `limit` и `used`. Для кандидата одна функция вычитает резерв изменяемой базы, добавляет `node_count * greatest(candidate, applied)` и сохраняет действующее правило уменьшения при уже превышенном лимите.

Результат проверки содержит причину: `user_quota`, `cluster_resources`, `instance_limit` или `available`. Сначала вычисляется личная квота. Общий бюджет становится видимой причиной только когда личная квота подходит. Предел инстансов применяется только к созданию.

`SizePlans` получает причину вместо `boolean`. Карточка остаётся доступной для выбора и просмотра цены, но подпись объясняет конкретное ограничение. Для личной квоты сохраняются недостающие CPU/RAM и ссылка на поддержку. Для общего бюджета показывается сообщение «Недостаточно ресурсов Managed Kubernetes» без предложения увеличить личную квоту.

### 4. Capacity опрашивается только пока форма открыта

Страница создания и окно изменения тарифа запускают запрос `/v1/managed/valkey/capacity` сразу после открытия. После завершения запроса следующий старт планируется через `max(0, 5 секунд - длительность запроса)`. Если ответ занимает больше пяти секунд, новый запрос начинается только после его завершения. Так интервал между стартами остаётся примерно пять секунд без параллельных запросов ресурсов.

Статические начальные запросы каталога и списка могут выполняться параллельно с первым запросом ресурсов. Запрет перекрытия относится к повторным запросам `/v1/managed/valkey/capacity` одного открытого представления.

При закрытии, уходе со страницы, смене аккаунта или ID базы клиент очищает таймер и отменяет активный `AbortController`. Проверка идентификатора контекста не позволяет позднему ответу прежней сессии обновить новую форму. Окно `resize` владеет своим опросом ресурсов; общий `ValkeyInstanceLayout` продолжает независимо обновлять карточку базы.

До первого успешного снимка ресурсов кнопка мутации недоступна. После принятой мутации или ресурсного `422` форма запрашивает новый снимок сразу. Если периодический запрос уже выполняется, немедленное обновление использует его результат либо сначала отменяет его, но не запускает второй запрос параллельно.

### 5. Серверный отказ остаётся обязательным

Предварительный запрет уменьшает число заведомо неуспешных запросов, но не заменяет окончательную проверку допуска. Между снимком и `POST` другой пользователь может занять ресурс. Сервер по-прежнему возвращает `QUOTA_EXCEEDED` раньше `NOT_ENOUGH_RESOURCES`, не сохраняет частичные данные и сообщает точный дефицит из транзакционного состояния. Клиент сохраняет введённые значения, показывает полученную причину и обновляет снимок ресурсов.

## Risks / Trade-offs

- [Снимок устаревает в пределах интервала] → окончательная транзакционная проверка остаётся единственным решением о приёме мутации.
- [Опрос раскрывает изменение общего резерва между аккаунтами] → API возвращает только агрегаты без данных владельцев и доступен после авторизации.
- [Частые агрегаты создают нагрузку на PostgreSQL] → в v1 учитывается не больше 32 активных строк, запрос выполняется одним SQL-выражением и только при открытой форме.
- [Настроенный инфраструктурный резерв может перестать соответствовать составу служебных `Pod`] → эксплуатация должна обновлять `MANAGED_K8S_NODE_*` вместе с топологией; API не выдаёт настроенный бюджет за фактический `allocatable`.
- [Полная миграция перезаписала бы индивидуальные квоты] → решение опирается на подтверждение, что индивидуальных квот ещё нет; перед миграцией рабочего окружения это проверяется запросом к `user_quotas`.
- [Существующий расход может превысить 12 GB] → инстансы сохраняются, рост блокируется, уменьшение и удаление остаются доступны.

## Migration Plan

1. Перед применением проверить, что все строки `user_quotas` имеют прежние стандартные значения 4 vCPU / 16 GB, и зафиксировать число строк.
2. Применить новую Goose-миграцию с `-allow-missing`; проверить `DEFAULT` столбцов, число строк и квоту существующих аккаунтов.
3. Развернуть API с новым маршрутом `/v1/managed/valkey/capacity` и стандартной квотой регистрации 4 vCPU / 12 GB.
4. Развернуть web с новым опросом и причинами недоступности.
5. Проверить `/v1/me`, `/v1/managed/valkey/capacity`, предварительный запрет обеих форм и окончательный конкурентный отказ API.

При откате сначала вернуть прежний `web`, затем API. Секцию `Down` применять только после проверки, что квоты 4/12 не выдавались вручную; она восстанавливает прежний `DEFAULT` и стандартные строки до 4/16. Инстансы и биллинговые периоды при прямом или обратном переходе не меняются.
