## Context

API уже ставит `slug`, ID инстанса и ID пользователя на `Namespace`, `Secret` и `ValkeyInstance`. Оператор использует на своих объектах только `app.kubernetes.io/name` и `slug`. Роль Pod хранится в непредиксной метке `role`, по которой primary и read-only Services выбирают Pod.

Email есть в контексте аутентифицированного пользователя, но не сохраняется в строке инстанса и не попадает в Kubernetes. Значение email нельзя надёжно представить как метку: допустимый набор символов не содержит `@`, а длина ограничена 63 символами. Для точного значения подходит аннотация.

`StatefulSet.spec.selector` неизменяем. Он, селекторы Service, правила запрета совместного размещения, PDB и NetworkPolicy используют общий набор `workloadLabels`, поэтому добавлять в эту функцию описательные метки нельзя. Порядок production-выкладки остаётся прежним: миграции и CRD, оператор, API.

## Goals / Non-Goals

**Goals:**

- Дать администратору одинаковые ID владельца и инстанса на всех ресурсах Valkey в пространствах имён.
- Показывать точный снимок email и подтверждённую роль на Pod без перезапуска процессов.
- Сохранить работу старой версии API между применением миграции и завершением выкладки.

**Non-Goals:**

- Не помечать Kubernetes `Node`: на одной физической ноде могут находиться процессы разных пользователей.
- Не делать email или служебные метаданные частью публичного HTTP DTO либо `ValkeyInstance.spec`.
- Не переводить селекторы Service на новую префиксную метку роли в этом изменении.

## Decisions

### Сохранять email как снимок строки инстанса

В `valkey_instances` появится обязательная колонка `user_email`. Новое создание заполнит её из проверенного `Actor.Email` в общей транзакции. Остальные мутации не будут менять значение.

Миграция заполнит существующие строки через связь `valkey_instances.user_id = users.id`. Чтобы предыдущая версия API могла создавать инстансы после миграции, триггер `BEFORE INSERT` установит `user_email`, когда INSERT не передал колонку. Триггер останется защитой для старых клиентов, а новая версия API будет передавать снимок явно.

Альтернатива без новой колонки требует присоединять `users` в каждом проходе доставки. Она сохраняет текущее значение аккаунта, а не явно зафиксированный снимок, и связывает метаданные Kubernetes с дальнейшими изменениями модели пользователя. Снимок соответствует уже используемому подходу для `audit_logs.user_email`.

### Разделить идентификационные и описательные метаданные

API продолжит считать существующие метки с ID и UID признаками принадлежности. Email-аннотация не участвует в решении, чужой ли объект: после успешной проверки идентичности API может безопасно добавить или исправить только свою аннотацию. Это позволяет дополнить старые объекты вместо перевода инстанса в ручное восстановление.

Поток данных будет таким:

```text
Actor.Email
    --> valkey_instances.user_email
    --> аннотация Namespace и ValkeyInstance
    --> аннотация ресурсов оператора и Pod
```

API управляет следующими метаданными на `Namespace` и `ValkeyInstance`:

| Тип | Ключ | Значение |
|---|---|---|
| метка | `valkey.h3llo-demo.com/instance` | `slug` |
| метка | `valkey.h3llo-demo.com/instance-id` | UUIDv7 инстанса |
| метка | `valkey.h3llo-demo.com/user-id` | UUIDv7 владельца |
| аннотация | `valkey.h3llo-demo.com/user-email` | точный снимок email |

При изменении API сохраняет `status`, `finalizers` и посторонние метаданные. Обновление аннотации на `ValkeyInstance` уже проходит через `valkeyInstancePredicate` и запускает перенос в дочерние ресурсы.

### Не расширять рабочие селекторы

Оператор разделит метаданные на два набора:

- селекторные метки сохранят текущие `app.kubernetes.io/name` и `valkey.h3llo-demo.com/instance`;
- описательные метки добавят `instance-id` и `user-id`, а аннотации добавят `user-email`.

Первый набор останется в `StatefulSet.spec.selector`, селекторах Service, правилах запрета совместного размещения, PDB и NetworkPolicy. Метаданные самих объектов и шаблон Pod получат объединённый набор. Поэтому обновление не затронет неизменяемый селектор и не изменит выбор целевых Pod.

### Дополнять существующие Pod отдельным изменением

Обновление шаблона `StatefulSet` не меняет уже работающие Pod при стратегии `OnDelete`. Текущий проход `reconcilePrimaryLabel` уже изменяет метаданные конкретного Pod при смене роли. Он станет сверкой управляемых метаданных и будет одновременно поддерживать ID, email и обе метки роли, сохраняя посторонние ключи.

Если email ещё не доставлен старой версией API, оператор пропустит только эту аннотацию. Отсутствие описательного email не блокирует управление данными или failover. После обновления API изменение аннотации CR вызовет новую сверку.

### Добавить префиксную роль без смены маршрутизации

Pod будет получать `valkey.h3llo-demo.com/role` вместе с действующей `role`. Обе метки вычисляются из одного подтверждённого состояния и удаляются вместе. Services пока продолжают выбирать `role`, поэтому появление нового ключа не создаёт окно без Endpoint. В следующем отдельном изменении непредиксную метку можно удалить после поэтапной миграции селекторов.

## Risks / Trade-offs

- [Email становится доступен всем субъектам с правом читать метаданные соответствующих ресурсов] -> хранить его только в аннотации объектов в пространствах имён, не переносить на `Node`, не включать в метки, события и логи.
- [Миграция применяется при работающей старой версии API] -> триггер INSERT заполняет новую обязательную колонку по `user_id`; интеграционный тест проверяет этот путь.
- [Сверка шаблона случайно изменит `StatefulSet.spec.selector`] -> выделить неизменяемый набор селекторных меток и проверить обновление существующего StatefulSet в `envtest`.
- [На Pod на короткое время расходятся две метки роли] -> менять или удалять оба ключа одним обновлением Kubernetes и проверять тестом failover.
- [Ручная правка email-аннотации выглядит как смена владельца] -> API исправляет её как описательное поле только после отдельной проверки ID и UID.

## Migration Plan

1. Применить SQL-миграцию: добавить `user_email`, создать совместимый триггер INSERT, заполнить существующие строки и установить обязательность значения.
2. Выкатить оператор. Он добавит ID и префиксную роль на существующие Pod, но продолжит работу при отсутствующем email.
3. Выкатить API. Новые инстансы начнут явно сохранять снимок, а цикл доставки добавит email-аннотацию на существующие `Namespace` и `ValkeyInstance`.
4. Дождаться сверки ресурсов оператором и проверить Pod через `kubectl` по ID, email и роли.

При откате старая версия API продолжит создавать строки через триггер и сохранит посторонние аннотации на CR. Старый оператор проигнорирует дополнительные метаданные. Колонку и триггер можно удалить секцией `Down` только после отката новой версии API; уже записанные метаданные Kubernetes не влияют на маршрутизацию.
