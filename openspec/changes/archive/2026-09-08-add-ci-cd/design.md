## Context

В репозитории нет `.github/workflows`, но локальные команды уже разделяют проверки API, оператора и клиентского приложения. Рабочая конфигурация Docker Compose сейчас собирает образы на месте, требует обычные настройки через `.env` и не содержит готовой SPA. API возвращает JSON 404 для неизвестных маршрутов.

Рабочая VM имеет архитектуру `linux/amd64` и запускает Caddy, API, PostgreSQL и VictoriaLogs. Оператор работает отдельно в управляемом Kubernetes. Репозиторий находится на GitHub, разработка на стадии MVP идёт напрямую в `main`.

## Goals / Non-Goals

**Goals:**

- получать одну проверенную версию для каждого SHA без компиляции на рабочей VM;
- сохранить параллельность независимых проверок и сборок;
- позволить повторный запуск предыдущей версии без пересборки;
- держать рабочий `.env` коротким и не смешивать секреты с обычными настройками;
- раздавать SPA и проксировать API одним Caddy на общем домене.

**Non-Goals:**

- развёртывание оператора и манифестов Kubernetes;
- полный тест `k3s`, сквозные тесты, CodeQL, Trivy и сканирование секретов;
- реестр образов для собранных версий;
- резервное копирование PostgreSQL и VictoriaLogs;
- защита домена VictoriaLogs до отдельного изменения.

## Decisions

### Один процесс GitHub Actions с барьерами между этапами

`.github/workflows/ci-cd.yml` запускается для запроса на слияние и `push`. Три задания `lint` стартуют без зависимостей. Каждое из трёх заданий `test` зависит от завершения всего этапа `lint`, а обе сборки зависят от всего этапа `test`. Это сохраняет порядок `lint -> test -> build`, который запросил пользователь, и не смешивает результат одной части проекта с ещё не проверенной ревизией.

Задание `deploy` зависит от обеих сборок, использует условие `push` в `main`, окружение GitHub `production` и группу последовательного выполнения `production`. Новый `push` не прерывает уже начатое развёртывание: следующее задание `deploy` ждёт освобождения группы.

Для внешних действий GitHub используются закреплённые SHA коммитов. Go берётся из `go.mod`, Node соответствует `web/package.json`, а `pnpm` соответствует `packageManager`. Кеши Go и `pnpm` ускоряют задания, но не заменяют файлы блокировки версий.

### Проверки повторяют границы локальных команд

`lint-api` запускает `go tool golangci-lint fmt --diff`, линтер для `./api/... ./internal/...` и `go mod tidy -diff`. `lint-operator` проверяет форматирование и линтер для `./operator/... ./internal/...`, затем вызывает `scripts/check_operator_generated.sh`. Общий `internal` намеренно проверяется в обоих контекстах.

`lint-web` запускает `pnpm format:check`, `pnpm lint` и `pnpm typecheck`. `test-api` поднимает только PostgreSQL из `docker-compose.dev.yml` и вызывает `just test` из `api`. Пароль этой одноразовой базы фиксированный и не является рабочим секретом. `test-operator` вызывает `just test-fast`, `test-web` вызывает `pnpm test`. Рабочая сборка клиентского приложения остаётся в задании `build-web`, поэтому тестовое задание её не повторяет.

### Caddy хранит рабочую статику

`caddy/Dockerfile` получает отдельный этап сборки с Node и `pnpm`, выполняет установку по файлу блокировки версий и `pnpm build`, затем копирует `web/dist` в конечный образ Caddy. Caddy сначала передаёт `/v1/*`, `/livez` и `/readyz` в API. Для остальных путей `app.h3llo-demo.com` он ищет статический файл и использует `/index.html` как запасной путь SPA.

API больше не зависит от клиентского приложения и собирается одновременно с Caddy. Файлы клиентского приложения входят в Caddy, который уже отвечает за TLS и ограничение частоты запросов. Один домен сохраняет текущую модель без CORS.

Альтернатива с Go `embed` потребовала бы завершить клиентскую сборку до компиляции API и связала бы два независимых образа. Отдельный nginx дублировал бы функции уже обязательного Caddy.

### CI передаёт Docker-образы без реестра

`build-api` через Docker Buildx создаёт для `linux/amd64` конечный образ API и образ миграций. `build-web` создаёт для той же платформы образ Caddy с SPA. Образы получают тег с полным `${GITHUB_SHA}`, экспортируются в архивы Docker, сжимаются и загружаются как внутренние результаты текущего процесса. Задание `deploy` скачивает эти файлы и не публикует их как постоянный выпуск.

Передача по SSH подходит одному рабочему серверу и не требует отдельного токена реестра. Рабочая VM выполняет только распаковку, `docker load` и запуск Docker Compose. При появлении нескольких серверов образы можно перенести в реестр без изменения контрактов `lint`, `test` и `build`.

### Каждая версия хранится в отдельном каталоге

На VM используется структура:

```text
/opt/managed-valkey/
  current -> releases/<sha>
  shared/.env
  secrets/kubeconfig/api.kubeconfig
  releases/<sha>/
    docker-compose.prod.yml
    release.env
    images/
```

`release.env` содержит только SHA и имена образов. Закрытый `shared/.env` содержит `POSTGRES_PASSWORD` и `JWT_SECRET`. Разделение позволяет передавать обычные сведения о версии без копирования секретов в каждый каталог.

Переменные окружения GitHub `production` называются `PRODUCTION_HOST`, `PRODUCTION_SSH_USER`, `PRODUCTION_SSH_PORT` и `PRODUCTION_SSH_KNOWN_HOSTS`. Секреты этого окружения называются `PRODUCTION_SSH_PRIVATE_KEY`, `POSTGRES_PASSWORD` и `JWT_SECRET`. Процесс проверяет наличие значений, создаёт временный `.env` с `umask 077`, не печатает его и передаёт с режимом `0600`.

Пароль PostgreSQL должен состоять из допустимых в URL символов, потому что Docker Compose строит `DATABASE_URL` из значения `POSTGRES_PASSWORD`. Процесс проверяет это условие до подключения к VM. Путь к заранее выданному файлу конфигурации Kubernetes, имена базы и пользователя, домены, порты, срок хранения логов и уровень журналирования задаются в `docker-compose.prod.yml`.

### Установка выполняется с проверкой результата

Задание `deploy` создаёт новый каталог версии, передаёт файлы во временные имена, проверяет их наличие и загружает образы. Затем оно проверяет разрешённую конфигурацию Docker Compose с `shared/.env` и `release.env`, запускает `docker compose up -d --remove-orphans --wait` и выполняет внешний HTTPS-запрос к `/readyz` с повторами.

Сервис `migrate` остаётся одноразовой зависимостью API. При ошибке миграции API не стартует. Символическая ссылка `current` меняется только после успешной проверки HTTPS. Тома PostgreSQL, VictoriaLogs и Caddy остаются общими для версий благодаря постоянному имени проекта Docker Compose `managed-valkey`.

### VictoriaLogs временно работает без проверки имени и пароля

Caddy передаёт только точный маршрут OTLP и `/select/*`, остальные пути домена логов возвращают 404. Проверка имени и пароля и переменные с хешами `bcrypt` удаляются. Оператор отправляет OTLP по HTTPS без имени пользователя и файла пароля; объект Kubernetes `Secret` с именем `valkey-logs-export` и его том больше не нужны.

Удаление заголовка `Authorization` перед передачей запроса сохраняется, чтобы случайные данные клиента не попадали во внутренний сервис. TLS защищает трафик, но не ограничивает клиентов. Запись и `vmui` становятся публичными. Это осознанное временное ограничение MVP.

## Risks / Trade-offs

- [Публичный OTLP позволяет постороннему записывать данные и расходовать диск] -> Ограничить доступные пути Caddy и вынести авторизацию или сетевое ограничение в следующее изменение до хранения чувствительных рабочих логов.
- [Публичный `vmui` раскрывает содержимое логов] -> Не записывать секреты по действующему контракту логирования и восстановить защиту до появления чувствительных данных.
- [SSH-соединение оборвётся после запуска миграции] -> Повторное задание `deploy` той же ревизии безопасно загрузит те же образы и повторит идемпотентный запуск Docker Compose.
- [Новая миграция окажется несовместимой с предыдущим API] -> Сохранять принятый контракт аддитивных миграций; при ошибке запуска повторно поднять предыдущую версию без `goose down`.
- [Архивы передаются дольше, чем образы загружаются из реестра] -> Для одной VM принять стоимость передачи; перейти на реестр при росте размера или числа серверов.
- [Полный сквозной тест пока не блокирует `deploy`] -> Явно считать это ограничением первого процесса CI/CD и добавить отдельный обязательный этап после реализации сквозных тестов.

## Migration Plan

1. Обновить рабочую конфигурацию под Caddy со статикой, минимальный `.env` и VictoriaLogs без проверки имени и пароля.
2. Добавить проверяемый сценарий развёртывания и процесс GitHub Actions.
3. Подготовить на VM `/opt/managed-valkey`, Docker Compose и файл конфигурации Kubernetes для API; настроить окружение GitHub `production`.
4. Выполнить первое задание `deploy` из `main`, проверить миграцию, готовность API, маршруты SPA, OTLP и `vmui`.
5. При неуспехе запустить Docker Compose из каталога предыдущей версии с теми же томами и `shared/.env`; миграции назад не выполнять.
