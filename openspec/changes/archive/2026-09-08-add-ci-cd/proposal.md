## Why

Репозиторий пока не проверяет и не разворачивает изменения автоматически, хотя рабочее окружение уже описано через Docker Compose. Нужен воспроизводимый процесс GitHub Actions, который проверяет все приложения, собирает образы для VM и запускает принятую ревизию по SSH.

## What Changes

- Добавить последовательные этапы `lint`, `test`, `build` и `deploy` с параллельными заданиями для API, оператора и клиентского приложения внутри каждого подходящего этапа.
- Собирать образы API и Caddy с клиентским приложением для `linux/amd64`, помечать их SHA коммита и передавать на рабочий сервер по SSH без отдельного реестра образов.
- Автоматически разворачивать успешный `push` в `main` через окружение GitHub `production`, выполнять миграции, ждать готовности Docker Compose и проверять готовность HTTP.
- Формировать рабочий `.env` только из конфиденциальных значений; обычные настройки получать из значений по умолчанию в Docker Compose.
- Перенести раздачу SPA из API в Caddy: Caddy хранит `web/dist`, обслуживает маршруты клиентского приложения и передаёт API только `/v1/*`, `/livez` и `/readyz`.
- Временно убрать проверку имени и пароля с приёма и просмотра VictoriaLogs. `logs.h3llo-demo.com` будет публично обслуживать OTLP и `vmui` до отдельного изменения защиты доступа.

## Capabilities

### New Capabilities

- `ci-cd`: проверки GitHub Actions, сборка образов выпуска и автоматическое развёртывание рабочего окружения по SSH.

### Modified Capabilities

- `backend-environments`: рабочая конфигурация Docker Compose получает готовые образы, значения по умолчанию, раздачу клиентского приложения через Caddy и временно публичный VictoriaLogs.
- `web-frontend-foundation`: рабочая сборка SPA размещается в образе Caddy и не встраивается в бинарник API.

## Impact

Изменение затронет GitHub Actions, `caddy/Dockerfile`, рабочую конфигурацию Docker Compose, `caddy/Caddyfile`, параметры рабочего окружения и сценарий развёртывания по SSH. На VM продолжат работать Caddy, API, PostgreSQL и VictoriaLogs; оператор останется в управляемом Kubernetes и не войдёт в этот процесс развёртывания. Для первого варианта развёртывание будут блокировать быстрые этапы `lint`, `test` и `build`; CodeQL, Trivy, полный тест `k3s` и сквозные тесты останутся отдельной работой.
