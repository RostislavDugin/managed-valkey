## Context

Причина и границы изменения описаны в [proposal.md](proposal.md). Сейчас `auth.Service` вызывает `store.Register` и `store.RecordLogin`, которые сами создают `AuditLog`. Репозиторий регистрации также владеет транзакцией. Valkey на фронте хранится в localStorage и сразу становится running. В PostgreSQL есть users, user_quotas, audit_logs и auth_registration_keys; предметных таблиц Valkey нет.

Дизайн нужен из-за общей транзакции между сервисами, конкурентной квоты и изменения контракта фронта. Kubernetes и оператор не участвуют в выполнении HTTP-запроса. Сервис аудита здесь является Go-сервисом внутри API, а не отдельным процессом.

## Goals / Non-Goals

Цель: одинаковые правила для одного запроса и конкурирующих запросов через разные экземпляры API. Успешный ответ означает commit всего изменения. Отказ не оставляет инстанс, событие, новый период или занятый ключ.

Наблюдаемое состояние моделируем для будущего импорта и проверяем через подготовку PostgreSQL. Не добавляем endpoint ручной смены фазы, эмулятор готовности, вызовы Kubernetes, фоновые циклы, API аудита, API метрик или расчёт месячного расхода. Созданная база остаётся provisioning, запрос удаления остаётся deleting. Механизм подтверждения soft delete будет отдельной задачей.

## Decisions

### 1. Сервис аудита и транзакционная граница

Сервисы пользователей и Valkey зависят от узкого интерфейса AuditWriter с операцией записи события. Интерфейс определяется у потребителя, audit.Service его реализует. Контракт события принадлежит пакету audit и содержит значения UUID, email, action, service, resource ID, request ID и время. Audit не импортирует auth, сервис Valkey или их GORM-модели. Реализация репозитория аудита находится в store и реализует интерфейс, объявленный audit. Сборка зависимостей находится в cmd/api.

```text
auth.Service   --> AuditWriter <-- audit.Service --> audit.Repository
Valkey service --> AuditWriter                          ^
                                                       |
                                                store implementation
```

ID новой базы получаем после INSERT с uuidv7() и передаём в аудит до commit. Ссылка на ID не требует вызова сервиса базы. Аудит не проверяет владельца через обратную зависимость: это уже сделал инициатор операции. Существующий resource_id остаётся общей ссылкой на ресурс сервиса без внешнего ключа только на valkey_instances; событие пользователя имеет null service/resource_id.

Транзакцией управляет прикладная операция. Минимальный контракт TxRunner выполняет callback с `*gorm.DB`, а репозитории и AuditWriter получают этот же tx явно. Это осознанная зависимость внутренних сервисов от уже выбранного GORM; отдельная универсальная Unit of Work с реестром репозиториев здесь не нужна. Вызов аудит-сервиса не создаёт новую транзакцию, goroutine или асинхронное событие. Все записи используют tx, а не корневой pool. Неудача аудита возвращается вызывающему и откатывает callback.

Регистрацию переработать так, чтобы сервис управлял транзакцией пользователя, квоты, ключа и аудита. Сохранить обработку конкурентных уникальных конфликтов и поиск принятой регистрации после отката. Replay не вызывает аудит и сохраняет текущую проверку нормализованной почты и пароля. Вход проверяет пароль, записывает аудит короткой транзакцией и только после commit выдаёт JWT. Общий Valkey advisory lock для входа и регистрации не нужен.

Альтернатива с отдельным процессом аудита потребовала бы outbox и доставки; она выходит за объём. Прямой INSERT аудита из репозитория пользователей сохраняет нынешнюю связанность и не удовлетворяет общей точке записи.

### 2. Схема и soft delete

Новая goose-миграция добавляет valkey_instances, billing_periods, idempotency_keys. AuditLog и user_quotas переиспользуются. Таблицы наблюдаемых нод, метрик и событий фаз пока не создаются. Все времена TIMESTAMPTZ, ID сущностей UUIDv7 через PostgreSQL 18. Новые FK и индексы объявляются отдельно после таблиц с явными именами.

Колонки valkey_instances соответствуют разделу схемы SYSTEM-DETAIL.md: намерение, credentials, сетевые настройки, maintenance, наблюдения, applied-ресурсы и две отметки удаления. `prefix` используется только при создании `slug`, отдельно не сохраняется. Наблюдения имеют безопасные начальные значения: provisioning, поколения/версии и applied-ресурсы 0, observed_at NULL, network_verification_status pending, network_verified_at NULL, is_recovery_required false.

Ограничения базы: mode и phase из заданных множеств; положительный допустимый desired-размер; неотрицательные applied-ресурсы; desired_generation/password_version не меньше 1; наблюдаемые версии неотрицательны и не больше запрошенных; app_password_hash 64 lowercase hex, password_prefix 4 символа; maintenance полностью NULL либо все поля в диапазоне; deleted_at требует deletion_requested_at. Структурные проверки не используют изменяемые env.

Уникальные индексы: глобальный slug, `(user_id,name) WHERE deleted_at IS NULL`, один открытый billing-период на `(service,resource_id)`, `(user_id,key)` идемпотентности. Индексы чтения: активные инстансы владельца `(user_id,created_at DESC,id DESC)`, время истечения ключей, периоды ресурса. Кластер максимум на 32 активных записи позволяет считать SUM без отдельного изменяемого счётчика.

Soft delete выражаем явным nullable deleted_at и явными фильтрами репозиториев. HTTP DELETE ставит только deletion_requested_at; он не вызывает GORM Delete. Будущий импорт после подтверждения удалит ресурс логически. Рабочий код v1 не выполняет физический DELETE инстанса. Поиск обычной карточки исключает tombstone, поиск для DELETE и проверки replay включает его. Это сохраняет идемпотентный DELETE после завершения и не раскрывает чужие ресурсы. Подтверждённое удаление освобождает имя, но не slug.

HTTP пишет только свои поля через явный набор колонок, включая false, 0 и NULL. GORM Save и обновление всей модели запрещены. Изменение имени не должно записать старую копию размера, а импорт в будущем не должен изменить updated_at намерения.

### 3. Публичный DTO и валидация

Использовать отдельные request/response-типы с snake_case. DTO инстанса содержит id, name, slug, mode, vcpu, ram_gb, applied_vcpu, applied_ram_gb, host, host_ro, port, is_whitelist_enabled, whitelist_cidrs, maintenance, password_hint, password_version, applied_password_version, status, phase_reason, desired_generation, observed_generation, observed_at, is_stale, is_updating, is_recovery_required, network_verification_status, network_verified_at, created_at, updated_at, configuration_requested_at, deletion_requested_at. Поле deleted_at отсутствует у обычного активного DTO; удалённый ресурс через GET не выдаётся. Owner не принимается от клиента. Список возвращает items в стабильном порядке; при лимите кластера 32 пагинация инстансов пока не нужна.

Декодер ограничивает JSON 16 KiB, отклоняет неизвестные и повторяющиеся ключи, несколько документов, дроби в целых полях и неправильные null. PATCH различает отсутствие maintenance и явный null. Ограничения имени и prefix из спеки проверяются без молчаливого преобразования регистра. Значения системных колонок нельзя передавать в мутации.

Начальный whitelist входит в POST: второй PUT заблокировало бы provisioning. IPv4 с необязательным CIDR приводится к сети, дубликаты удаляются, сети сортируются; IPv6 отклоняется. Лимит 100 входных записей применяется до дедупликации. Пустой включённый список означает deny-all; при выключении список сохраняется ровно по запросу. Maintenance выбран как полный объект либо null; это исключает неоднозначность частичной правки окна.

### 4. Общая блокировка и свежий снимок

Все мутации Valkey используют `BEGIN ISOLATION LEVEL READ COMMITTED`, `SET LOCAL lock_timeout = '3s'`, затем отдельный `SELECT pg_advisory_xact_lock(1)`. Синтаксическую валидацию и вычисление SHA-256 выполняем до lock. Под ним нет сетевых вызовов и bcrypt.

```text
authenticate + owner check + parse
                  |
                  v
BEGIN --> advisory lock --> re-read --> replay lookup
                                              |
                                              v
                      deletion --> no-op --> generation
                                              |
                                              v
                        phase/freshness --> version/quota
                                              |
                                              v
                      instance + audit + billing + response
                                              |
                                              v
                                           COMMIT
```

Middleware подтверждает владельца, но не предоставляет актуальный снимок для записи. После lock повторно читаем `(id,user_id)`, для существующего инстанса берём row lock в порядке advisory, затем row. Квоту читаем отдельным statement после advisory, не совмещаем ожидание lock и SUM в одном SQL. READ COMMITTED даёт новый снимок следующему запросу. REPEATABLE READ с ранее установленным снимком здесь не нужен.

Проверка replay стоит раньше удалённости, no-op и готовности; до replay авторизация и владелец обязательны. Новый resize с текущим desired-размером получает 200 и сохранённый ответ даже при незавершённом поколении. При deletion_requested_at no-op уже запрещён. Новый rotate сначала проверяет общую готовность, затем expected_password_version, затем отличие нового хеша.

После lock один вызов clock_timestamp() даёт время принятия и проверки TTL/свежести; это значение передаётся в запись инстанса, аудит и биллинг. Для тестов чистого сравнения свежести применяется Clock, для интеграционных точных временных границ источник времени внедряется через узкий интерфейс с production-реализацией PostgreSQL. В обычных тестах используются реальные часы базы. clock_timestamp() исключает дату начала долгоживущей ожидавшей транзакции, которую вернул бы now().

Все обращения используют контекст HTTP-запроса. Lock timeout отображается как 503 UNAVAILABLE/reason=lock_timeout. Отмена до commit откатывает транзакцию. При потере связи после commit клиент может не получить ответ; ключ разрешает повтор без нового изменения. Обычные GET не берут advisory lock.

Обновление квот вручную в эксплуатации должно брать тот же общий lock. Будущий импорт, изменяющий applied-резерв или deleted_at, обязан согласовать освобождение ресурсов с тем же протоколом; детали его реализации откладываются. Иначе advisory lock защищал бы только часть писателей.

### 5. Немедленная проверка бюджета

CPU/RAM env с историческим NODE в имени являются общими лимитами сервиса во всём кластере. Дополнительного множителя Kubernetes-нод нет. Это бюджет, который эксплуатация уже выделила Valkey с учётом системного резерва, а не сумма показаний загрузки CPU и памяти.

Резерв каждой строки с deleted_at IS NULL: `nodes * max(desired,applied)` отдельно для CPU/RAM. Кандидат resize заменяет прежний резерв, не добавляется к нему. Для каждой размерности допускается результат в пределах лимита либо результат не больше прежнего использования. Это позволяет уменьшаться после ручного снижения лимита. Проверяются обе размерности и сначала пользователь, затем кластер. Лимит 32 проверяется по итоговому числу записей; resize не увеличивает число.

При нехватке бюджета исходный POST сразу возвращает 422. В базу не пишется provisioning, не открывается период и не ставится отложенная заявка на появление ресурсов. В v1 нет autoscaling кластера. Тест не запускает фоновый цикл и не перематывает операторский таймер.

Это проверка настроенного бюджета. Она не обещает предсказать отказ worker-ноды, фрагментацию размещения или неисправный scheduler. Такие отказы после принятия операции относятся к будущему оператору. Проверять их синхронным запросом к Kubernetes нарушило бы границу задачи и доступности API. Существующий timeout первоначального запуска остаётся механизмом диагностики иных проблем запуска, а не заменой admission-проверки бюджета.

### 6. Идемпотентность и коллизии

Ключ scoped по user_id, срок 24 часа от времени принятия. Канонический запрос состоит из метода в верхнем регистре, фактического пути с каноническим UUID и JSON декодированного request DTO. Порядок полей фиксирован сериализатором; семантические defaults и CIDR нормализованы; пароль участвует в отпечатке без сохранения тела. Повторяющиеся JSON-ключи отклоняются. Неизвестные query-параметры на мутациях отклоняются, чтобы путь и отпечаток не скрывали разные действия.

При обращении к истёкшему ключу удалить именно эту запись в текущей транзакции и обработать запрос заново. Отсутствие фоновой очистки не продлевает TTL. Пакетную очистку старых строк можно добавить отдельной задачей. Сохранённый response_body содержит только DTO; jsonb не гарантирует байтовый порядок ключей, поэтому повтор обеспечивает одинаковые значения и статус, а не побайтовую идентичность JSON.

Все успешные статусы, включая 200 resize без изменения, сохраняются. Ошибки не записываются. После подтверждённого удаления повтор успешного create/resize/rotate по действующему ключу возвращает исходный DTO, обычный GET возвращает 404. Это причина повторного чтения фронтом после принятого ответа.

Slug генерируется криптографически; ограничить подбор 100 попытками. Коллизию unique slug обрабатывать через INSERT ON CONFLICT по конкретному ограничению с возвратом результата либо savepoint; нельзя после unique violation продолжать уже прерванную PostgreSQL-транзакцию. Конфликт имени классифицируется отдельно, не запускает новый подбор slug. Исчерпание попыток даёт INTERNAL с полным откатом.

### 7. Контракт ошибок

| Code / HTTP | details |
| --- | --- |
| VALIDATION_FAILED / 400 | fields: объект field -> машинная причина; общий reason для тела; без значения password |
| CONFLICT / 409 | reason=name_taken, field=name; либо reason=password_version_mismatch, expected_password_version, password_version |
| OPERATION_IN_PROGRESS / 409 | desired_generation, observed_generation, configuration_requested_at |
| INSTANCE_NOT_READY / 409 | reason=deleting, invalid_phase или stale_observation; status, observed_at |
| QUOTA_EXCEEDED / 422 | reason=user_quota; limit, used, requested, missing как пары vcpu/ram_gb |
| NOT_ENOUGH_RESOURCES / 422 | reason=cluster_quota с теми же парами либо reason=instance_limit с целыми limit/used/requested |
| IDEMPOTENCY_MISMATCH / 422 | пустой объект; чужое тело или ответ не возвращается |
| UNAVAILABLE / 503 | reason=lock_timeout |
| INTERNAL / 500 | пустой объект, общий текст; SQL и детали исключения не раскрываются |

requested в квотной ошибке означает суммарный резерв после кандидата. missing равен max(0,requested-limit). Ошибка валидной конфигурации по квоте отличается от недопустимого размера. Клиент разбирает code/details, сообщение предназначено для человека.

### 8. Подключение фронта

Срез pages/valkey сохраняется; его api использует shared/api/client. DTO преобразуется в UI-модель в одном месте. Автор и owner не отправляются в мутациях. Начальный каталог даёт размеры, ставки и предварительные domain/port; существующие адреса берутся из DTO. Ошибка каталога сохраняет форму, но запрещает отправку до получения допустимых размеров и ставок.

Удалить временное хранилище и таймеры успешного применения, локальную миграцию данных Valkey и генерацию событий/метрик. Не импортировать mv_valkey_instances в сервер. Сохраняем существующую обработку JWT. На вкладках метрик и аудита показывается недоступность источника; нет фиктивной пустой истории и запросов несуществующих endpoints.

Список, карточка и credentials получают серверные данные. Опрос последовательный, раз в 5 секунд, с AbortSignal и защитой от ответа прежнего маршрута/аккаунта. Успешная мутация перечитывает карточку и /v1/me. При квотной ошибке обновляются usage/лимит, при конфликте состояние базы; заполненная форма сохраняется.

Пароль и ключ одной отправки остаются в памяти для повторов, включая ручной повтор после исчерпания трёх автоматических попыток. Изменение формы создаёт новую отправку. Одноразовый показ сохраняет pagehide/bfcache и защиту от позднего ответа. DELETE подтверждается вводом slug, показывает принятие удаления и сохраняет строку deleting. В maintenance используются день недели, UTC-час и длительность; в v1 окно только хранится.

### 9. Интеграционные проверки

Каждый сценарий принятия/отказа идёт через httptest.Server и http.Client, рабочий router, middleware, сервисы и managed_valkey_test. Аккаунт создаётся через POST регистрации; инстанс также создаётся HTTP. SQL допустим для подготовки observed/applied состояния, квоты, срока ключа и проверки недоступных через API аудита/периодов/хешей. API аудита ради тестов не добавляется.

После успешной операции проверяем ответ и повторный GET; после отказа сравниваем весь значимый снимок: настройки, observed/applied поля, поколения, времена, резерв, аудит, периоды и ключ. Не ограничиваемся HTTP-кодом. Таблица ниже задаёт набор интеграционных случаев; табличные тесты покрывают перечисленные варианты отдельно.

Глобальные квотные тесты запускаются без t.Parallel в одном выделенном запуске managed_valkey_test. Уникальный пользователь сам по себе не изолирует кластерную квоту. Очистка удаляет только данные тестовых аккаунтов, в порядке зависимостей; не используется TRUNCATE общей базы. HTTP-помощник расширяется поддержкой отменяемого контекста и потокобезопасным сбором логов для конкурентных запросов.

Обычные тесты используют реальный audit.Service и PostgreSQL. Для отказов внедряем декоратор узкого репозитория конкретного тестового экземпляра: он делегирует реальную запись и возвращает управляемую ошибку до/после неё. Так проверяется rollback настоящей транзакции без отключения PostgreSQL, глобальных триггеров или изменения схемы. Отдельно отказ перед записью ключа после аудита/биллинга проверяет обратное направление атомарности. Отдельных тестов миграций нет: just test применяет их с goose -allow-missing.

Юнит-тесты ограничены точными чистыми расчётами/канонизацией/границами времени, если их неудобно покрывать HTTP без инфраструктурной подмены. Они не заменяют перечисленные интеграционные сценарии. Frontend-проверки сохраняют настоящий общий HTTP-клиент с подменой fetch на границе, проверяют payload, ключи, 422 без retry, состояния, отмену и пароль; обращения к локальному хранилищу больше не являются тестом бизнес-логики API.

## Risks / Trade-offs

- Общий lock ограничивает параллельность мутаций. Короткие транзакции, отсутствие сети внутри и лимит 32 инстанса делают его приемлемым для v1; таймаут не позволяет бесконечно занимать пул.
- Кластерная квота не доказывает физическое размещение. Эксплуатация задаёт доступный бюджет, а поздние сбои запуска диагностирует будущий оператор.
- Без синхронизации удаляемые базы сохраняют резерв. Интерфейс показывает deleting; тесты готовности используют подготовку БД, а не скрытый production-обход.
- Аудит входит в критический путь и может отклонить изменение. Это сохраняет правило отсутствия принятых действий без истории.
- История не очищается в v1. Политика длительного хранения и применимых правовых требований фиксируется как отдельная работа; сохранение строк не объявляется обеспечением юридического соответствия.
- Смена браузерного источника несовместима с демонстрационными локальными базами. Их не переносим в сервер, чтобы не принимать клиентские owner/status/credentials за достоверные данные.

## Migration Plan

1. Добавить аддитивную миграцию; users, user_quotas и audit_logs сохранить. Применить goose с -allow-missing через штатный тестовый/production-запуск.
2. Настроить общий бюджет, границы размера, ставки и домен/порт в env API и примерах окружения. Согласовать изменения compose с текущим add-ci-cd, не перезаписывая его правки.
3. Выложить API и совместимый фронт в принятом репозиторием порядке. Старый API продолжает работать с аддитивной схемой, но старый localStorage-фронт не является допустимым fallback для серверных данных.
4. При откате приложения оставить схему и историю на месте. Down-миграция после появления пользовательских данных не является способом production-отката. Ни физическое удаление инстансов, ни возврат к демонстрационной готовности не используются для восстановления.
