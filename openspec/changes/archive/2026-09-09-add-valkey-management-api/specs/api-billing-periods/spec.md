## Purpose

История биллинговых периодов сохраняет цену принятых конфигураций Valkey и момент прекращения тарификации, чтобы будущий расчёт расхода не зависел от текущего размера ресурса.

## ADDED Requirements

### Requirement: Принятая конфигурация открывает период стоимости

Создание SHALL открывать один период с `started_reason=created`. Изменивший размер resize SHALL закрывать текущий период с `ended_reason=resized` и открывать новый с `started_reason=resized`. Период SHALL фиксировать пользователя, `service=valkey`, resource ID, mode, CPU, RAM, node count и целую цену в копейках за час из действующих ставок. Граница периодов SHALL совпадать с временем принятия изменения после ожидания lock и сохранять микросекундную точность. API расчёта месячного расхода SHALL быть вне этой задачи.

#### Scenario: Изменение размера

- **WHEN** API принимает resize
- **THEN** старый `ended_at` равен новому `started_at`, `updated_at` и `configuration_requested_at` инстанса
- **AND** остаётся ровно один открытый период с новой ценой, независимо от applied-размера

#### Scenario: Новые ставки

- **WHEN** изменились ставки сервера и принят новый resize
- **THEN** новый период использует новые ставки, прежние цены не переписываются

### Requirement: Запрос удаления прекращает тарификацию

Первый DELETE SHALL закрывать открытый период с `ended_reason=deleted` и `ended_at=deletion_requested_at`. Ожидание фактического удаления SHALL сохранять квоту, но MUST NOT продолжать открытый период. Soft delete MUST NOT удалять периоды. У открытого периода SHALL быть одновременно NULL ended_at/ended_reason, у закрытого оба значения SHALL быть заполнены.

#### Scenario: Удаление ждёт кластер

- **WHEN** DELETE принят, но `deleted_at` отсутствует
- **THEN** открытых периодов у инстанса нет, а прежняя история сохранена

### Requirement: Неизменяющие размер операции не дробят историю

Имя, maintenance, whitelist, смена пароля, запрос текущего размера, повтор по ключу и повтор DELETE MUST NOT создавать новые периоды или менять прежние временные границы. Сбой любой части транзакции SHALL сохранять прежнюю историю целиком.

#### Scenario: Отклонённый resize

- **WHEN** размер отклонён по квоте или операция откатилась после записи нового периода
- **THEN** прежний период остаётся открытым, новый отсутствует

#### Scenario: Ресайз конкурирует с удалением

- **WHEN** resize первым принят под lock, затем DELETE
- **THEN** DELETE закрывает новый период; интервалы не перекрываются и открытых периодов не остаётся
