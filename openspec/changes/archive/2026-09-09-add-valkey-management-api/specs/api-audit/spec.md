## Purpose

Общий аудит сохраняет принятые действия с аккаунтами и Valkey атомарно с изменениями и удерживает историю после удаления ресурса, независимо от будущего API чтения журнала.

## ADDED Requirements

### Requirement: Сервисы записывают аудит через общий контракт

Сервисы пользователей и Valkey SHALL записывать аудит через внутренний сервис аудита. Он SHALL принимать автора, снимок email, действие, service/resource ID, request ID и время операции без загрузки модели пользователя или Valkey. Сервис аудита MUST NOT вызывать сервис Valkey или зависеть от его модели для записи ID. HTTP API чтения и записи аудита SHALL быть вне этой задачи.

#### Scenario: ID новой базы доступен до аудита

- **WHEN** создание инстанса получило ID внутри незавершённой транзакции
- **THEN** сервис аудита сохраняет событие с этим ID в той же транзакции без обратного вызова сервиса Valkey

#### Scenario: Событие аккаунта

- **WHEN** пользователь регистрируется или успешно входит
- **THEN** сервис пользователей вызывает общий аудит с `user.register` или `user.login`, `resource_id=null` и `service=null`

### Requirement: Аудит и бизнес-изменение атомарны

Аудит SHALL участвовать в транзакции вызывающей операции без собственного независимого commit. Успешное изменение SHALL содержать ровно одно событие; повтор по ключу, повтор DELETE, запрос без изменения и отклонённая операция MUST NOT добавлять события. Ошибка аудита SHALL отменять бизнес-изменение. Ошибка другой записи SHALL отменять уже записанный аудит.

#### Scenario: Отказ аудита при регистрации

- **WHEN** запись `user.register` завершается ошибкой
- **THEN** клиент не получает JWT, пользователь, квота и ключ не сохраняются

#### Scenario: Отказ аудита при входе

- **WHEN** пароль верен, но запись `user.login` завершается ошибкой
- **THEN** запрос возвращает ошибку без JWT

#### Scenario: Отказ аудита при изменении базы

- **WHEN** создание, PATCH, resize, whitelist, rotate или DELETE не может записать аудит
- **THEN** откатываются все записи соответствующей операции, включая поколения, периоды и ключ

### Requirement: Журнал сохраняет автора и историю без секретов

Событие SHALL содержать UUIDv7, `user_id`, `user_email`, фиксированное `action`, `service`, `resource_id`, `request_id`, `created_at` UTC. Допустимые действия Valkey SHALL быть `instance.create`, `instance.update`, `instance.resize`, `instance.whitelist.update`, `instance.password.rotate`, `instance.delete`. Пароли, их хеши, JWT, тела запросов и списки CIDR MUST NOT записываться. Email SHALL фиксироваться на момент события. Soft delete ресурса MUST NOT удалять аудит. В v1 автоматическая очистка аудита SHALL отсутствовать; политика длительного хранения, архивирования, удаления и применимых правовых требований SHALL прорабатываться отдельно без заявления о конкретном сроке или обеспеченном соответствии.

#### Scenario: История после удаления

- **WHEN** инстанс получил `deleted_at`
- **THEN** его прежние события доступны в хранилище с прежними resource ID, автором и временем

#### Scenario: Автор не берётся из тела запроса

- **WHEN** аутентифицированный пользователь выполняет действие
- **THEN** аудит содержит автора из проверенной сессии и request ID текущей операции
- **AND** изменение email пользователя впоследствии не меняет прежнее событие
