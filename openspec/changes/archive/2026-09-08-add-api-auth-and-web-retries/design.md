## Context

API сейчас регистрирует только проверки процесса и готовности. В PostgreSQL есть лишь техническая начальная миграция. Консоль уже имеет двухшаговый экран авторизации, защиту маршрутов и общий `apiRequest`, но `auth.ts` хранит аккаунты с открытыми паролями в `localStorage` и выпускает неподписанные демонстрационные токены.

Контракт v1 задаёт bcrypt cost 12, JWT HS256 на 10 лет, проверку `is_blocked` на каждом запросе, один лимит запросов для трёх маршрутов авторизации и `/v1/me` с пользователем, квотой и использованием. API работает в одной реплике, поэтому лимит можно хранить в памяти. Браузер и API используют один origin; отдельная настройка CORS не нужна.

Завершённое изменение `add-valkey-management` ещё не архивировано и содержит дельту `web-auth` про UUIDv7 в `sub`. Эта дельта считается частью текущего состояния: новая спецификация сохраняет `userId` и заменяет только источник данных аккаунта.

## Goals / Non-Goals

**Goals:**

- отделить HTTP, правила авторизации и работу с PostgreSQL так, чтобы криптографию и обработчики можно было проверять независимо;
- исключить хранение открытого пароля аккаунта вне тела текущего запроса;
- сделать повтор сетевого запроса ограниченным, отменяемым и безопасным для изменяющих операций;
- сохранить текущие формы, маршруты и события завершения сессии фронтенда.

**Non-Goals:**

- подтверждение почты, восстановление и смена пароля аккаунта;
- refresh token, отзыв отдельных JWT и серверные сессии;
- распределённый лимит запросов для нескольких реплик API;
- подключение экранов Valkey к серверным маршрутам;
- перенос демонстрационных аккаунтов и данных Valkey из `localStorage` в PostgreSQL.

## Decisions

### 1. Авторизация разделяется между `api`, `auth`, `apierr` и `store`

`api/internal/api` остаётся слоем Gin: декодирует запрос, вызывает предметный сервис и кодирует ответ. `api/internal/auth` нормализует почту, проверяет пароль, выпускает и разбирает JWT и выполняет сценарии регистрации, входа и получения пользователя. `api/internal/store` содержит модели и запросы PostgreSQL. `api/internal/apierr` задаёт коды и один способ превратить известную ошибку в HTTP-ответ.

Зависимости передаются в конструктор маршрутизатора. Глобальные соединения, секреты и часы не используются. `Clock` нужен сервису JWT и ограничителю частоты, поэтому тесты проверяют границы без ожидания реального времени.

Альтернатива с обработчиками, которые напрямую вызывают GORM и криптографические функции, короче в первом коммите, но смешивает HTTP, транзакции и время. Такие тесты потребовали бы поднимать PostgreSQL даже для проверки просроченного токена.

### 2. Первая предметная миграция создаёт четыре таблицы

Миграция создаёт `users`, `user_quotas`, `audit_logs` и `auth_registration_keys`. Основные колонки следуют `SYSTEM-DETAIL.md`. В `auth_registration_keys` ключ является первичным, `user_id` ссылается на созданного пользователя, а `created_at` задаёт срок хранения 24 часа. Регистрация удаляет истёкшие ключи перед вставкой и не считает запись действующей после границы срока, даже если очистка не завершилась.

Отдельных тестов миграции нет. `api just test` применяет её к
`managed_valkey_test`, затем интеграционные тесты отправляют HTTP-запросы через
сервис и хранилище к получившейся схеме. Ошибка SQL останавливает применение
миграций, а несовместимость схемы с кодом проявляется в интеграционных тестах.

Ключ регистрации не хранит тело, пароль, хеш тела или JWT. При успешном повторе API находит связанного пользователя, сверяет нормализованную почту и присланный пароль с bcrypt-хешем и выпускает новый JWT. Совпадение одного ключа без знания пароля недостаточно для получения токена.

Первый запрос создаёт пользователя, квоту, аудит и ключ в одной транзакции. Если параллельный запрос столкнулся с ограничением уникальности, сервис завершает неудачную транзакцию и отдельно проверяет ключ. Тот же ключ и те же данные дают успешный повтор; тот же ключ с другими данными даёт `IDEMPOTENCY_MISMATCH`; другой ключ для занятой почты даёт `CONFLICT`.

Существующую целевую таблицу `idempotency_keys` нельзя использовать без изменения её смысла: она связывает ключ с уже авторизованным `user_id` и хранит публичный ответ операции. Для регистрации пользователь ещё не авторизован, а сохранение JWT в `response_body` превратило бы базу в хранилище действующих bearer-токенов.

### 3. Пароль проверяется bcrypt, JWT подписывается отдельным сервисом

Пароль проверяется по числу символов и длине UTF-8 до вызова bcrypt. Для хеширования используется `golang.org/x/crypto/bcrypt` с cost 12. Вход для неизвестной почты выполняет сравнение с заранее созданным фиктивным хешем, чтобы отсутствие строки не давало заметно более быстрый ответ.

Для JWT используется `github.com/golang-jwt/jwt/v5`. Проверка явно разрешает только HS256, требует `sub` в формате UUID, числовой `exp` и действующий срок. `JWT_SECRET` становится обязательным полем конфигурации API. Middleware после проверки подписи загружает пользователя из базы и проверяет `is_blocked`, затем добавляет `user_id` к контексту и логгеру запроса.

Самописная реализация JWT не выбрана: разбор base64url прост, но строгая проверка алгоритма и зарегистрированных полей уже реализована библиотекой и легче проверяется на известных ошибочных токенах.

### 4. `/v1/me` служит серверной проверкой сессии

Фронтенд разбирает `exp`, чтобы поставить таймер выхода, но не считает разобранное тело доказательством подлинности. При загрузке защищённого маршрута `getSession` читает токен, отклоняет локально истёкший срок и вызывает `/v1/me`. Ответ даёт UUID и почту, поэтому почта не берётся из неподписанного клиентом представления токена.

До появления серверных таблиц Valkey `/v1/me` возвращает нулевое использование вместе с квотой пользователя. Когда ресурсы перейдут с временного клиента на API, расчёт использования заменит нули без изменения DTO.

Проверка только локального `exp` не выбрана, потому что она не замечает блокировку аккаунта и не проверяет подпись. Встраивать почту в JWT тоже не требуется: изменение данных пользователя не должно ждать выпуска нового токена.

### 5. Ограничитель хранит скользящее окно по адресу прямого соединения

Middleware перед обработчиками авторизации хранит для каждого IP упорядоченный список времён принятых запросов. Перед проверкой он удаляет значения не новее границы окна. Первые десять запросов за 60 секунд учитываются независимо от результата обработчика; отклонённые из-за заполненного окна не продлевают блокировку.

Ограничитель использует `RemoteAddr` после разбора host и port. Настройка Gin с `SetTrustedProxies(nil)` сохраняется, поэтому `X-Forwarded-For` и похожие заголовки не меняют ключ. Пустые записи удаляются при последующих обращениях, чтобы карта не росла бесконечно от одноразовых адресов.

Внешний лимит Caddy остаётся отдельным слоем. Клиент умеет разобрать как JSON `RATE_LIMITED` от API, так и пустой `429` от Caddy.

### 6. Регистрация и вход пишут аудит без секретов

Регистрация пишет `user.register` в той же транзакции, что пользователя и квоту. Вход после успешной проверки выполняет короткую транзакцию аудита и выдаёт токен только при успешной записи. Повтор обработанного `login` после потерянного ответа может создать ещё одну строку: это соответствует двум фактически принятым попыткам входа и не меняет состояние аккаунта.

`request_id` берётся из middleware. В аудит и структурированные логи не передаются тела запросов, пароль, bcrypt-хеш, JWT и `Authorization`. Общий обработчик ошибок заменяет текущий ответ Recovery на `500 INTERNAL` в установленном JSON-формате.

### 7. `apiRequest` управляет попытками одного логического запроса

Один вызов создаёт `X-Request-Id`, подготавливает воспроизводимое тело и запускает до трёх попыток. Между второй и третьей попыткой используется экспоненциальная задержка с полным случайным разбросом. Функции времени, ожидания, случайного числа и `fetch` передаются внутреннему исполнителю в тестах; публичный API использует браузерные реализации.

Автоматический повтор включён для `GET`, `HEAD`, `OPTIONS`, явно отмеченных безопасных операций и запросов с `Idempotency-Key`. `check-email` и `login` отмечаются безопасными в модуле авторизации. `register` создаёт UUIDv7 при отправке формы и сохраняет его до завершения всех попыток. Будущие создание инстанса, ресайз и смена пароля используют тот же путь с ключом.

Сетевые ошибки и статусы `408`, `425`, `500`, `502`, `503`, `504` считаются временными. `429` сразу возвращается экрану, потому что скрытое ожидание до минуты удерживало бы форму в состоянии загрузки. Остальные 4xx описывают запрос или права и не исправятся от повтора.

Тело типа `ReadableStream` не повторяется: клиент отклоняет настройку повтора до первой отправки или выполняет одну попытку. Текущие API-запросы используют JSON, поэтому для них тело воспроизводимо.

### 8. Один `AbortSignal` действует на запрос и задержку

Исполнитель проверяет сигнал до попытки, перед задержкой и после неё. Ожидание подписывается на `abort` и удаляет обработчик при завершении. `AbortError` возвращается без преобразования в `ApiError`, без очистки токена и без следующей попытки.

Создание отдельного контроллера на каждую попытку без связи с сигналом вызывающего кода не выбрано: после ухода со страницы запросы продолжили бы работу и могли бы доставить запоздалый ответ.

### 9. Модуль `auth.ts` становится тонким клиентом API

`checkEmail`, `register` и `login` вызывают `apiRequest`; успешные `register` и `login` сохраняют `token` в `mv_token`. `getSession` проверяет форму JWT, локальный `exp` и `/me`. Обработчик кнопки «Выйти» вызывает `logout`, удаляет токен и открывает `/auth`. Удаление `mv_token` передаётся другим вкладкам через стандартное событие `storage`. Запрос к серверу при выходе не отправляется, потому что серверной сессии и отзыва JWT нет.

Код `mv_users`, генерация демонстрационного JWT, искусственная задержка и миграция токена с почтой удаляются. Пометка демонстрационного режима исчезает со страницы. Компонент формы, таблица маршрутов и оболочка сохраняют существующие интерфейсы. Обработчик выхода остаётся в оболочке, но получает отдельную проверку перехода и синхронизации вкладок.

### 10. Интеграционные тесты API входят через настоящий HTTP

Интеграционные сценарии запускают production-маршрутизатор в `httptest.Server`
и обращаются к нему через `http.Client`. Авторизация использует настоящий
`auth.Service`, `store.Store` и PostgreSQL `managed_valkey_test`. Так один тест
проверяет HTTP-заголовки, JSON, middleware, предметные правила и запросы к базе.

Общий помощник создаёт уникальный аккаунт через `POST /v1/auth/register`, получает
JWT через HTTP и ставит очистку связанных строк в `t.Cleanup`. Тесты обращаются к
базе напрямую только для подготовки недоступного через API состояния и проверки
аудита или атомарности. Ошибки внешних зависимостей, которые нельзя безопасно
создать на общем стенде, воспроизводятся подменой соответствующей зависимости,
но запрос к приложению всё равно проходит через TCP HTTP.

Прямые интеграционные вызовы обработчиков, сервиса авторизации и репозитория не
используются. Юнит-тесты отдельных функций и типов сохраняют изолированную
границу и не обязаны поднимать HTTP-сервер.

## Risks / Trade-offs

- [Проверка bcrypt делает маршруты входа дорогими] -> лимит применяется до bcrypt, cost закреплён тестом, а API имеет дополнительное ограничение Caddy.
- [JWT нельзя отозвать отдельно] -> middleware проверяет `is_blocked` в PostgreSQL на каждом запросе; отдельный отзыв остаётся вне v1.
- [Лимит сбрасывается при перезапуске и не делится между репликами] -> v1 запускает одну реплику API, внешний Caddy ограничивает общий поток.
- [Три попытки увеличивают задержку ошибки] -> число попыток и задержка ограничены, `AbortSignal` прекращает запрос сразу, а 429 не ожидается скрыто.
- [Существующий локальный аккаунт исчезнет] -> экран прямо работает с постоянным API; демонстрационные данные не считаются пользовательскими данными сервиса и не переносятся.
- [Завершённая дельта `add-valkey-management` пересекается с `web-auth`] -> перед архивированием текущего изменения сначала архивируется `add-valkey-management`; новая дельта уже содержит итоговый контракт `userId`.

## Migration Plan

1. Применить миграцию с таблицами авторизации до запуска новой версии API.
2. Задать `JWT_SECRET`, затем развернуть API с новыми маршрутами. Старый фронтенд продолжит использовать локальную заглушку и не зависит от них.
3. Собрать и развернуть фронтенд, который использует API. При первом открытии он удалит зависимость от `mv_users`; прежний демонстрационный токен не пройдёт `/v1/me`, после чего пользователь зарегистрируется заново.
4. При откате фронтенд можно вернуть отдельно. Откат API оставляет добавленные таблицы, поскольку production-миграции аддитивны; новая версия фронтенда при таком откате покажет ошибку доступности входа до возврата API.
