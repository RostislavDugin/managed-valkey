## Why

Консоль пока хранит аккаунты и открытые пароли в `localStorage`, а API не предоставляет маршруты авторизации. Перед подключением экранов управления к серверу нужна настоящая учётная запись, проверяемая сессия и общий способ переживать краткие сетевые сбои без повторного выполнения операций.

## What Changes

- Добавить в API регистрацию, вход, проверку почты, получение текущего пользователя и проверку JWT на защищённых маршрутах.
- Хранить пользователей, квоты и журнал действий аккаунта в PostgreSQL; пароли хранить только как bcrypt-хеши.
- Ограничить частоту запросов авторизации по адресу прямого соединения и возвращать единый формат ошибок API.
- Заменить временную авторизацию фронтенда поверх `localStorage` вызовами настоящего API, сохранив текущий двухшаговый экран и поведение сессии.
- Провести все HTTP-запросы фронтенда через общий клиент с ограниченными автоматическими повторами временных ошибок, отменой через `AbortSignal` и сохранением идентификаторов одного логического запроса.
- Защитить повтор регистрации через `Idempotency-Key`; не повторять автоматически ошибки клиента и ограничение частоты запросов.

## Capabilities

### New Capabilities

- `api-auth`: аккаунты в PostgreSQL, маршруты авторизации, JWT, проверка заблокированного пользователя, ограничение частоты запросов и идемпотентная регистрация.
- `web-api-client`: единый HTTP-клиент фронтенда, обработка ответов и безопасные автоматические повторы.

### Modified Capabilities

- `web-auth`: замена временного браузерного хранилища аккаунтов настоящим API и серверная проверка действующей сессии.

## Impact

Изменение затрагивает миграции PostgreSQL, конфигурацию и пакеты `api`, маршрутизацию Gin, `web/src/shared/api`, экран авторизации и проверки маршрутов. В `go.mod` появятся прямые зависимости для bcrypt и JWT. Для запуска API станет обязательным `JWT_SECRET`; тесты API потребуют PostgreSQL, а проверки фронтенда останутся изолированными через подмену `fetch` и времени.
