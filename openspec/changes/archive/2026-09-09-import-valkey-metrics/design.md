## Context

См. [proposal.md](proposal.md). Таблица `valkey_node_metrics`, агрегация, защищённый HTTP-маршрут и экран мониторинга уже работают. Существующий импорт читает типизированный `ValkeyInstance`, проверяет идентичность CR и переносит основное наблюдение в отдельной транзакции. Поле `status.metrics` пока отсутствует в общем Go-типе и сгенерированной схеме CRD, поэтому Kubernetes не может использовать его как надёжный канал до API.

Тесты `api` уже запускают настоящий PostgreSQL и однонодовый k3s. Административный клиент теста может менять `status`, а рабочий клиент API имеет только производственные разрешения. Оператор разрабатывается отдельно и в это изменение не входит.

## Goals / Non-Goals

**Goals:**

- определить точный транспортный формат снимка между CR и API;
- импортировать каждый новый допустимый снимок один раз, независимо от изменений фазы и heartbeat;
- не допускать смешивания процессов или инстансов в истории;
- ограничить рост таблицы настроенным сроком хранения;
- проверить рабочие границы CR, фонового импорта, PostgreSQL и HTTP.

**Non-Goals:**

- собирать `INFO` в операторе или читать `metrics.k8s.io`;
- запускать оператор в тестах API;
- менять агрегацию, HTTP DTO, окна или внешний вид мониторинга;
- восстанавливать снимки, которые успели исчезнуть из CR во время недоступности API;
- добавлять партиционирование или новую миграцию таблицы метрик.

## Decisions

### Общий контракт CRD меняется без логики оператора

В публичный пакет `operator/api/v1alpha1` добавляется тип снимка и поле `Metrics` в `ValkeyInstanceStatus`. Список получает `listType=map`, ключ `ordinal` и предел в три элемента. Строковые идентификаторы обязательны, роль ограничена `primary` и `replica`, числовые поля имеют минимум 0, а CPU остаётся указателем и может отсутствовать.

Для `collectedAt` используется `metav1.MicroTime`. `metav1.Time` сериализуется с точностью до секунды и не выполняет действующий контракт базы, где уникальность и порядок снимков сохраняются до микросекунд. Сгенерированные DeepCopy и CRD обновляются из Go-типа. Если параллельная работа оператора уже добавила поле, реализация сохраняет этот контракт и объединяет совпадающие изменения вместо второй версии типа.

Альтернатива с чтением `status` как `unstructured` не решает задачу: структурная схема Kubernetes удалит неизвестное поле, а API потеряет проверяемый общий контракт.

### Метрики разбираются отдельно от основного наблюдения

После проверки имени, namespace, `spec.instanceId`, меток и UID импорт строит карту `status.nodes` по `ordinal`. Каждый снимок отдельно сверяется с текущей нодой по четырём полям: `ordinal`, `podUID`, `containerID` и `runId`. Совпадение роли не требуется, потому что роль того же процесса может измениться между двумя наблюдениями. Роль снимка описывает состояние в момент сбора.

Допустимые снимки преобразуются в `store.ValkeyNodeMetric`. Снимок с неизвестным ordinal или другой идентичностью отбрасывается; это не лишает истории допустимые снимки остальных нод. Причина записывается без содержимого Secret и без значений, которые не нужны для поиска ошибки.

Разбор метрик и запись основного наблюдения выполняются независимо. Неизменившееся наблюдение, ошибка `ErrValkeyObservationStale` или отсутствие нового `observedAt` не отменяют вставку нового снимка. Повреждение идентичности самого CR по-прежнему останавливает весь импорт из этого объекта. Инстанс с начатым удалением не принимает новые наблюдения и метрики.

Вариант с добавлением метрик в `ValkeyObservation` и одну транзакцию отклонён: ранний выход для совпадающего или устаревшего наблюдения снова сделал бы историю зависимой от heartbeat и фазы.

### Вставка остаётся короткой отдельной транзакцией

Хранилище перечитывает строку инстанса под блокировкой, проверяет, что удаление не начато, получает текущее время PostgreSQL и отбрасывает снимки старше срока хранения. Оставшиеся строки вставляются одним пакетом с `ON CONFLICT DO NOTHING` по существующему уникальному индексу `(instance_id, ordinal, ts)`.

Метрики не используют общую advisory-блокировку пользовательских изменений: они не меняют намерение, квоты или биллинг. Блокировка строки нужна только для согласования с одновременным удалением и удерживается на время вставки не более трёх строк. Отдельная транзакция позволяет следующему опросу повторить вставку после сбоя, не дублируя уже сохранённые строки.

Альтернатива с предварительным запросом существующих времён создаёт лишний обмен с PostgreSQL и всё равно не защищает от конкурирующей вставки.

### Один срок используется при импорте и очистке

Конфигурация API получает `ValkeyMetricsRetention`. Значение `VALKEY_METRICS_RETENTION` разбирается через `time.ParseDuration`, должно быть положительным и по умолчанию равно `168h`. HTTP API сохраняет отдельный жёсткий предел чтения в семь дней; изменение срока хранения не расширяет публичное окно.

Фоновый runner запускает третий независимый проход очистки сразу после старта, затем раз в 24 часа после завершения предыдущего прохода. Очистка выбирает один момент времени PostgreSQL, вычисляет границу и удаляет строки с `ts` строго меньше неё. Ошибка попадает в журнал, не меняет readiness и не запускает параллельный повтор.

Проверка срока при вставке нужна даже при ежедневной очистке: после простоя API в CR может остаться уже просроченный снимок. Вариант с очисткой при каждом секундном импорте создавал бы постоянные полные проходы по таблице. При ожидаемом объёме около 1,5 миллиона строк один проход в сутки не требует отдельного индекса или партиционирования.

### Интеграционный тест подменяет только отсутствующего производителя

Тест создаёт пользователя и инстанс через HTTP, ждёт доставленный CR, затем административным клиентом записывает согласованные `status.nodes` и `status.metrics`. Рабочий фоновый импорт API должен сохранить снимок, после чего запрос владельца к существующему `/metrics` возвращает точку. Повторный проход проверяет уникальность.

Дополнительные случаи меняют только CR и время строк: новый `collectedAt` при прежнем основном наблюдении, неверная идентичность процесса, соседний допустимый снимок, `cpuMillicores=null` и просроченный снимок. Очистка проверяется на настоящей базе с фиксированной границей. Действующая проверка RBAC подтверждает, что рабочий клиент API не может сам записать `status`.

Тесты frontend уже покрывают преобразование DTO, пустые данные, опрос и графики. Их нужно прогнать с остальным набором; изменение кода frontend требуется только при обнаруженной несовместимости с неизменившимся ответом HTTP.

## Risks / Trade-offs

- [Параллельная работа меняет тот же Go-тип CRD] -> Перед реализацией сравнить форму `status.metrics` и объединить изменения в одном публичном типе без копий.
- [API недоступен дольше периода обновления CR] -> Импортируется последний оставшийся снимок; пропуск сохраняется на графике и не заполняется нулём.
- [Повреждённый снимок остаётся в CR и повторяет сообщение при каждом опросе] -> Сообщение содержит инстанс, ordinal и короткую причину; исправление производителя относится к работе оператора.
- [Большой срок хранения увеличивает таблицу, хотя HTTP читает только семь дней] -> Документировать независимость двух пределов; штатное значение остаётся `168h`.
- [Очистка временно не выполнилась] -> Чтение всё равно отсекает данные старше семи дней, а следующий ежедневный проход повторяет физическое удаление.

## Migration Plan

1. Применить обновлённую CRD со структурой `status.metrics`. Изменение аддитивно и не требует остановки существующих CR.
2. Развернуть API с чтением нового поля, импортом и фоновой очисткой. До появления производителя поле может отсутствовать, что считается пустым списком.
3. Проверить запись подготовленного снимка в CR, появление строки в PostgreSQL и ответ существующего маршрута мониторинга.
4. Оператор с производителем снимков можно развернуть позже без повторного изменения API-контракта.

При откате API поле CRD и уже сохранённые строки можно оставить: прежняя версия их не использует. После отката новые строки перестанут появляться и очищаться, но HTTP-контракт существующей версии останется совместимым.
