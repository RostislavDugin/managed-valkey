## Context

`/livez` подтверждает только работу процесса, а `/readyz` проверяет PostgreSQL и намеренно не зависит от Kubernetes. Эту семантику нужно сохранить: потеря управляющего кластера не должна закрывать вход и чтение уже сохранённого состояния.

API уже имеет соединение с PostgreSQL, ограниченный Kubernetes client, настройки `VALKEY_BASE_DOMAIN` и `VALKEY_PUBLIC_PORT` и библиотеку `valkey-go`. В таблице `valkey_instances` уже есть желаемые и наблюдаемые поколения, версии пароля, фаза, отметки наблюдения и удаления, а также признаки восстановления. Новая проверка может использовать эти данные без миграции и без чтения Pod или метрик Kubernetes.

## Goals / Non-Goals

**Goals:**

- Дать Uptime Kuma один HTTP-статус для состояния платформы и полезный JSON для диагностики.
- Проверять пользовательский путь до Valkey, включая DNS, внешний TLS, AUTH и PING.
- Завершать каждый запрос за ограниченное время и не задерживать обычные маршруты API.
- Не раскрывать переданные учётные данные и не превращать `/valkey-health` в произвольный сетевой прокси.

**Non-Goals:**

- Проверка каждой реплики, Pod, Node, Gateway, сертификата или метрики отдельным запросом API.
- Создание постоянного пробного инстанса или запись пробных ключей в пользовательский Valkey.
- Хранение истории проверок и принятие решения об уведомлении внутри API.
- Замена `/livez`, `/readyz`, проверок выпуска или наблюдений оператора.

## Decisions

### `/health` вычисляет снимок во время запроса

Обработчик создаёт контекст со сроком 5 секунд и одновременно запускает проверку PostgreSQL и чтение Namespace `valkey-system` из Kubernetes. Проверка PostgreSQL включает один запрос нужных полей всех строк с `deleted_at IS NULL`; после него операции и состояния вычисляются в памяти. Объём активных строк уже ограничен квотами сервиса, поэтому отдельная таблица, фоновый сборщик и кэш не нужны.

Kubernetes client передаётся в сервис состояния через небольшой интерфейс. Если `KUBERNETES_BACKGROUND_SYNC_ENABLED=false`, вместо клиента передаётся явное состояние `disabled`. Так тесты смогут воспроизводить ошибки без настоящего кластера, а рабочий код использует те же учётные данные, что и фоновые циклы.

Альтернативой был сохранённый результат фоновых проверок. Он добавил бы состояние, таймеры и вопрос о свежести самого результата, хотя запросы выполняются редко и должны показывать текущее состояние.

### Сводка различает ошибку, предупреждение и неизвестный результат

Каждая часть возвращает одно из значений `ok`, `warning`, `fail` или `unknown` и массив проблем. Общий агрегатор применяет порядок `fail`, `warning`, `ok`. `unknown` используется только для зависимых от PostgreSQL частей, когда сам PostgreSQL уже имеет `fail`; оно не создаёт дубликат первичной ошибки.

Проблема имеет `code` и только подходящие к ней поля: `instance_id`, `slug`, `operation`, `phase`, `reason` и `age_seconds`. `reason` берётся только из сохранённой безопасной причины фазы или восстановления. Тексты сетевых ошибок, SQL, имена объектов с учётными данными и конфигурация подключения в ответ не попадают. Массивы сортируются по `slug`, затем по `code`, чтобы ответы и тесты были устойчивыми.

### Операции и состояния используют разные правила

Классификатор сначала исключает строки с `deleted_at`, затем обрабатывает начатое удаление. Для удаления важен только срок от `deletion_requested_at`: предыдущая ошибка инстанса ожидаема и не должна давать второе сообщение.

Для остальных строк активной операцией считается `provisioning`, `updating`, несовпадение поколений или несовпадение версий пароля. Её возраст берётся из `configuration_requested_at`. До 300 секунд это предупреждение, с 300 секунд это ошибка. Явные `error`, `unavailable` и признаки восстановления остаются ошибками сразу, даже во время изменения.

Свежесть `observed_at` проверяется только для строк без активной операции. Это не даёт новому инстансу стать ошибкой через 60 секунд при допустимом времени создания, но обнаруживает остановившийся импорт для уже работающего инстанса. `degraded` остаётся предупреждением, потому что HA-инстанс в этой фазе продолжает обслуживать запросы.

Альтернативой была проверка Pod и внутренних процессов из API. Оператор уже выполняет эти проверки и сохраняет итоговую фазу. Их повтор потребовал бы новых прав Kubernetes и связал бы API с устройством оператора.

### `/valkey-health` получает секреты в заголовках

Uptime Kuma задаёт полные URI в `X-Valkey-Primary` и, для HA, `X-Valkey-Read`. Query string не используется, потому что URL чаще попадает в access log и историю запросов. Read URI необязателен, чтобы тот же маршрут проверял single-инстансы.

До сетевого обращения парсер требует `rediss`, пользователя `app`, непустой пароль, явный настроенный порт, один label перед `VALKEY_BASE_DOMAIN` и отсутствие path, query и fragment. Read label должен быть равен primary label с суффиксом `-ro`. Проверка полного имени, а не простого строкового суффикса домена, исключает адреса вроде `slug.valkey.example.attacker.test`. IP-адреса запрещены.

Это не даёт маршруту обращаться к внутренним адресам и произвольным сервисам. Отдельный токен мониторинга не вводится: пароль Valkey уже имеет высокую энтропию, URI ограничены управляемым доменом, а Caddy ограничивает общий поток проверок до 30 запросов в минуту с одного IP. Если позже маршрут потребуется открыть вне Caddy или защита от распределённого перебора станет существенной, токен можно добавить отдельным изменением контракта.

### Valkey проверяется новым короткоживущим подключением

Для каждого URI создаётся отдельный client `valkey-go` с TLS ServerName из host, системным набором доверенных CA, выключенной очередью и без повторов. Клиент подключается, выполняет AUTH как `app`, посылает PING и закрывается. Оба клиента работают параллельно под общим сроком 5 секунд. Проверка не отправляет SET или GET и не влияет на данные.

Ошибки сводятся к небольшому перечню кодов до журналирования и формирования ответа. В лог попадают роль адреса, код и длительность, но не объект ошибки библиотеки: такой объект может содержать URI. Для тестов фабрика клиента принимает доверенный CA и управляемую реализацию соединения; рабочая конфигурация использует системные CA.

Альтернативой было проверить TCP или только TLS. Такой запрос не замечает неверный пароль и не подтверждает, что Valkey принимает команды. SET/GET дал бы больше уверенности, но потребовал бы управлять временными ключами и правами на запись.

### API не сглаживает краткие сбои

Каждый запрос возвращает фактическое текущее состояние. Для обоих мониторов исходная настройка Uptime Kuma использует интервал 30 секунд и уведомление после шести повторов. Поэтому короткое нарушение видно в истории монитора, но оно не вызывает сообщение. Порог операции в 300 секунд решает другую задачу: отличает штатное создание или изменение от застрявшего процесса.

Сглаживание внутри API потребовало бы разделяемого хранилища при нескольких репликах, усложнило ручную диагностику и скрыло бы время начала отказа от системы мониторинга.

### Caddy использует отдельную общую зону ограничения

В `Caddyfile` добавляется зона для `/health` и `/valkey-health` с ключом `{remote_host}`, 30 событиями и окном в одну минуту. Оба пути добавляются к matcher API до SPA. Настройки access log не расширяются и заголовки URI не журналируются.

Лимит общий для двух маршрутов, чтобы клиент не мог удвоить разрешённую частоту чередованием путей. При штатном интервале Uptime Kuma один монитор расходует два запроса в минуту.

## Risks / Trade-offs

- [Сохранённая фаза отстаёт от реального Valkey] -> наблюдение старше 60 секунд становится ошибкой, а `/valkey-health` отдельно проверяет внешний пользовательский путь.
- [Whitelist инстанса не разрешает исходящий адрес VM с API] -> проверка честно возвращает `connect_failed`; эксплуатационная настройка должна добавить этот адрес в whitelist выбранного проверочного инстанса.
- [Публичный маршрут позволяет проверять пароль управляемого Valkey] -> допустимые host и port жёстко ограничены, ответы не содержат деталей AUTH, Caddy ограничивает частоту, а пароли генерируются случайными.
- [Медленная зависимость занимает обработчик до пяти секунд] -> единый контекст отменяет все незавершённые обращения, а параллельное выполнение не складывает их сроки.
- [Один проблемный пользовательский инстанс делает общую платформу красной] -> это намеренное свойство `/health`; `instance_id` и `slug` позволяют быстро найти причину, а краткие сбои фильтрует Uptime Kuma.

## Migration Plan

1. Добавить сервис состояния, HTTP-контракты и тесты API, не меняя существующие `/livez` и `/readyz`.
2. Добавить маршруты и общую зону ограничения в Caddy, затем проверить итоговую конфигурацию.
3. Развернуть API и Caddy одной ревизией. Проверить `/health` без инстансов, затем `/valkey-health` на single или HA-инстансе с разрешённым исходящим адресом API.
4. Создать в Uptime Kuma HTTP-монитор `/health` и отдельный монитор `/valkey-health` с секретными заголовками, интервалом 30 секунд и шестью повторами до уведомления.
5. При откате вернуть прежние API и Caddy. Новых таблиц, данных и Kubernetes-объектов нет, поэтому отдельный возврат состояния не нужен.
