## Purpose

Даёт внешнему HTTP-монитору один сводный сигнал о состоянии платформы и отдельную проверку пользовательского TLS-подключения к адресам Valkey.

## ADDED Requirements

### Requirement: Сводное состояние доступно без авторизации

API SHALL предоставлять публичный `GET /health` без JWT. Ответ SHALL содержать `status`, время `checked_at` в UTC и объект `checks` с именованными результатами `postgresql`, `kubernetes`, `operations` и `instances`. Каждый результат SHALL иметь собственный `status`; найденные проблемы SHALL содержать машинный `code` и безопасные поля, достаточные для поиска инстанса и оценки возраста состояния. Ответ MUST NOT содержать секреты или исходные тексты ошибок зависимостей.

API SHALL возвращать `200`, когда ни одна проверка не завершилась ошибкой. Общий `status` SHALL быть `warning`, если есть предупреждения без ошибок, и `ok`, если предупреждений нет. Любая ошибка SHALL давать общий `status=fail` и HTTP `503`. Ответ SHALL содержать `Cache-Control: no-store`.

#### Scenario: Все части платформы исправны

- **WHEN** PostgreSQL и Kubernetes отвечают, а активные инстансы не имеют ошибок, устаревших наблюдений и застрявших операций
- **THEN** `GET /health` отвечает `200` с `status=ok` и успешным состоянием всех четырёх проверок

#### Scenario: Есть только предупреждение

- **WHEN** один инстанс имеет допустимое состояние `degraded`, а ошибок нет
- **THEN** `GET /health` отвечает `200` с `status=warning` и указывает этот инстанс в `checks.instances`

#### Scenario: Одна проверка завершилась ошибкой

- **WHEN** любая обязательная проверка имеет состояние `fail`
- **THEN** `GET /health` отвечает `503` с `status=fail` и сохраняет результаты остальных завершившихся проверок

### Requirement: Сводная проверка ограничена общим сроком

Проверки PostgreSQL и Kubernetes SHALL начинаться параллельно и вместе с анализом инстансов SHALL укладываться в общий срок 5 секунд. Истечение срока SHALL завершать незаконченные обращения, отмечать соответствующую проверку кодом `timeout` и возвращать полный ответ по уже завершившимся проверкам.

#### Scenario: Kubernetes не отвечает

- **WHEN** обращение к Kubernetes не завершается до общего срока
- **THEN** `GET /health` отвечает не позднее окончания этого срока с HTTP `503`, `checks.kubernetes.status=fail` и `code=timeout`

#### Scenario: Зависимости отвечают с разной скоростью

- **WHEN** PostgreSQL и Kubernetes отвечают до общего срока
- **THEN** длительность запроса определяется более медленной параллельной проверкой, а не суммой их длительностей

### Requirement: PostgreSQL и Kubernetes проверяются независимо

Проверка PostgreSQL SHALL подтвердить доступность соединения и прочитать одним согласованным запросом поля всех инстансов с `deleted_at IS NULL`, нужные для проверки операций и состояний. Проверка Kubernetes SHALL выполнить разрешённое текущей учётной записи API чтение существующего объекта. Выключенная фоновая синхронизация Kubernetes SHALL считаться ошибкой с кодом `disabled`.

Ошибка PostgreSQL SHALL переводить `operations` и `instances` в `unknown`, но MUST NOT отменять проверку Kubernetes. Ошибка Kubernetes MUST NOT скрывать результаты PostgreSQL, операций и инстансов. `/livez` и `/readyz` SHALL сохранять прежнюю семантику: недоступность Kubernetes не меняет готовность HTTP API.

#### Scenario: PostgreSQL недоступна

- **WHEN** API не может проверить соединение с PostgreSQL или прочитать активные инстансы
- **THEN** `postgresql` имеет состояние `fail`, `operations` и `instances` имеют состояние `unknown`, а Kubernetes всё равно проверяется

#### Scenario: Kubernetes отклонил чтение

- **WHEN** Kubernetes недоступен, вернул ошибку авторизации или не содержит проверяемый объект
- **THEN** `kubernetes` имеет состояние `fail`, а доступные результаты из PostgreSQL остаются в ответе

#### Scenario: Синхронизация выключена

- **WHEN** API запущен с выключенной фоновой синхронизацией Kubernetes
- **THEN** `kubernetes` имеет состояние `fail` и код `disabled`
- **AND** `/readyz` продолжает зависеть только от PostgreSQL

### Requirement: Застрявшие операции определяются по сохранённому намерению

API SHALL считать изменением конфигурации состояние `provisioning` или `updating`, несовпадение `desired_generation` и `observed_generation` либо несовпадение `password_version` и `applied_password_version`. Возраст такого изменения SHALL считаться от `configuration_requested_at`. Возраст удаления SHALL считаться от `deletion_requested_at`, пока `deleted_at` не заполнен.

Незавершённая операция возрастом меньше 300 секунд SHALL давать предупреждение `operation_in_progress`. При возрасте не меньше 300 секунд она SHALL давать ошибку `operation_stalled`. Инстанс с начатым удалением SHALL участвовать только в проверке срока удаления; его прежняя фаза и наблюдение MUST NOT создавать вторую проблему.

#### Scenario: Создание ещё укладывается в срок

- **WHEN** новый инстанс остаётся в `provisioning` 120 секунд
- **THEN** `operations` имеет предупреждение `operation_in_progress`, а сам возраст операции не приводит к HTTP `503`

#### Scenario: Изменение конфигурации застряло

- **WHEN** желаемое и наблюдаемое поколения не совпадают не меньше 300 секунд
- **THEN** `operations` имеет состояние `fail` и проблему `operation_stalled` с ID, slug и возрастом инстанса

#### Scenario: Удаление застряло

- **WHEN** `deletion_requested_at` заполнено не меньше 300 секунд назад, а `deleted_at` отсутствует
- **THEN** `operations` имеет состояние `fail` и проблему `operation_stalled` с видом операции `delete`
- **AND** прежняя фаза удаляемого инстанса не создаёт отдельную проблему в `instances`

### Requirement: Состояния инстансов оцениваются по свежим наблюдениям

Для инстансов без начатого удаления API SHALL считать `error`, `unavailable`, `is_recovery_required=true` и `is_operator_recovery_required=true` ошибками. `degraded` SHALL быть предупреждением. Для инстанса без активного изменения конфигурации отсутствие `observed_at` или возраст наблюдения строго больше 60 секунд SHALL быть ошибкой `observation_stale`. Фазы `provisioning` и `updating` SHALL оцениваться как операции по их сроку, чтобы штатная работа не давала преждевременную ошибку наблюдения.

#### Scenario: Инстанс недоступен

- **WHEN** сохранённая фаза активного инстанса равна `unavailable`
- **THEN** `instances` имеет состояние `fail` и указывает ID, slug, фазу и безопасную причину инстанса

#### Scenario: Требуется восстановление

- **WHEN** один из признаков восстановления активного инстанса равен `true`
- **THEN** `instances` имеет состояние `fail` с отдельным машинным кодом для соответствующего признака

#### Scenario: Наблюдение перестало обновляться

- **WHEN** активный инстанс не меняет конфигурацию и его `observed_at` старше 60 секунд
- **THEN** `instances` имеет состояние `fail` и проблему `observation_stale`

### Requirement: Valkey проверяется через переданные URI

API SHALL предоставлять публичный `GET /valkey-health` без JWT. Запрос SHALL требовать ровно один заголовок `X-Valkey-Primary` с полным URI и SHALL принимать не более одного необязательного заголовка `X-Valkey-Read`. Каждый URI SHALL иметь вид `rediss://app:<password>@<host>:<port>` без path, query и fragment.

Primary host SHALL состоять из одного DNS-label и настроенного `VALKEY_BASE_DOMAIN`. Read host, если он передан, SHALL совпадать с primary host с добавленным суффиксом `-ro` перед базовым доменом. Оба URI SHALL использовать настроенный `VALKEY_PUBLIC_PORT`. IP-адреса, другие схемы, домены, порты, имена пользователей и неполные URI MUST быть отклонены с HTTP `400` и `VALIDATION_FAILED` до сетевого подключения.

#### Scenario: Передан только primary

- **WHEN** запрос содержит допустимый `X-Valkey-Primary` и не содержит `X-Valkey-Read`
- **THEN** API проверяет только primary и возвращает только его результат

#### Scenario: Передана пара адресов HA

- **WHEN** запрос содержит допустимые primary и read URI одного инстанса
- **THEN** API проверяет оба адреса и возвращает отдельный результат для каждого

#### Scenario: Передан посторонний адрес

- **WHEN** URI содержит IP-адрес, другой базовый домен или другой порт
- **THEN** API отвечает `400 VALIDATION_FAILED` и не открывает сетевое соединение

#### Scenario: Read относится к другому инстансу

- **WHEN** DNS-label из `X-Valkey-Read` не равен DNS-label primary с суффиксом `-ro`
- **THEN** API отвечает `400 VALIDATION_FAILED` и не проверяет ни один адрес

### Requirement: Valkey проверяется через TLS, AUTH и PING

Для каждого переданного URI API SHALL открыть новое TLS-соединение с проверкой доверенной цепочки и имени host, выполнить AUTH под пользователем `app`, отправить PING, дождаться PONG и закрыть соединение. Primary и read SHALL проверяться параллельно, без повторного подключения и без команд чтения или записи данных. Общий срок запроса SHALL быть 5 секунд.

Успех всех переданных проверок SHALL давать HTTP `200` и `status=ok`. Ошибка любой проверки SHALL давать HTTP `503` и `status=fail`, не отменяя результат второй проверки. Ответ SHALL содержать `checked_at`, `checks.primary` и, когда адрес передан, `checks.read`; для каждой проверки SHALL возвращаться `status`, `latency_ms` и безопасный код `dns_failed`, `connect_failed`, `tls_failed`, `auth_failed`, `ping_failed` или `timeout`. Ответ SHALL содержать `Cache-Control: no-store`.

#### Scenario: TLS и Valkey отвечают

- **WHEN** сертификаты обоих адресов действительны, AUTH принимает пароль и PING возвращает PONG
- **THEN** `GET /valkey-health` отвечает `200` с успешными результатами primary и read

#### Scenario: Сертификат не подходит имени

- **WHEN** TLS-сертификат primary не подтверждает host из URI
- **THEN** primary получает код `tls_failed`, а `GET /valkey-health` отвечает `503`

#### Scenario: Пароль неверен

- **WHEN** Valkey отклоняет AUTH хотя бы для одного адреса
- **THEN** этот адрес получает код `auth_failed`, а ответ не содержит пароль или исходный текст ошибки

#### Scenario: Один адрес завис

- **WHEN** один адрес отвечает успешно, а второй не завершает подключение за 5 секунд
- **THEN** успешный результат сохраняется, зависший адрес получает код `timeout`, а запрос отвечает `503`

### Requirement: Учётные данные проверки не раскрываются

API и входной прокси MUST NOT записывать значения `X-Valkey-Primary` и `X-Valkey-Read` в логи, метрики или трассировки. Ответы MUST NOT возвращать URI, host, имя пользователя, пароль или исходную ошибку клиента Valkey. Обработчик SHALL использовать переданные учётные данные только в пределах текущего запроса и MUST NOT сохранять или кэшировать их.

#### Scenario: Проверка завершилась ошибкой

- **WHEN** TLS, AUTH или PING завершается ошибкой
- **THEN** журналы и HTTP-ответ содержат только безопасный код и длительность без значения заголовка и без исходной ошибки с URI

### Requirement: Задержка тревоги настраивается во внешнем мониторе

API SHALL отражать текущее состояние без хранения истории сбоев и без задержки ответа. Эксплуатационная документация SHALL задавать для Uptime Kuma интервал 30 секунд и шесть повторов до уведомления как исходную настройку обоих маршрутов.

#### Scenario: Краткий сетевой сбой

- **WHEN** проверка не проходит одну или две минуты, а затем восстанавливается
- **THEN** API возвращает фактические ошибки отдельных запросов, а рекомендуемая настройка Uptime Kuma не отправляет уведомление

#### Scenario: Сбой продолжается

- **WHEN** последовательные проверки не проходят не меньше трёх минут
- **THEN** рекомендуемая настройка Uptime Kuma переводит монитор в состояние ошибки и отправляет уведомление
