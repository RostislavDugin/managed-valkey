## Purpose

Определяет воспроизводимую основу двух Go-приложений, которую можно собирать, запускать, проверять и расширять без смены структуры проекта и набора инструментов.

## ADDED Requirements

### Requirement: Общий Go-модуль

API, оператор и общий серверный код SHALL собираться из одного Go-модуля в корне репозитория. Каталоги приложений MUST NOT содержать вложенные `go.mod` или независимые наборы версий общих зависимостей.

#### Scenario: Загрузка зависимостей из корня

- **WHEN** разработчик загружает зависимости Go из корня репозитория
- **THEN** зависимости API и оператора разрешаются из одного `go.mod` и зафиксированного `go.sum`

### Requirement: Воспроизводимые инструменты Go

Проект SHALL закреплять версии инструментов генерации, тестового Kubernetes-окружения и миграций вместе с Go-модулем. Команды приложений MUST NOT зависеть от произвольной версии одноимённого исполняемого файла в системе разработчика.

#### Scenario: Чистая рабочая среда

- **WHEN** разработчик имеет поддерживаемую версию Go, но не устанавливал серверные инструменты глобально
- **THEN** локальные `Justfile` запускают закреплённые проектом версии инструментов

### Requirement: Локальные команды API

Каталог `api` SHALL содержать `Justfile` только с публичными командами `migration-up`, `migration-down`, `migration-generate name`, `test` и `run`. API MUST NOT делить тесты на быстрый и полный наборы.

#### Scenario: Список команд API

- **WHEN** разработчик запускает `just --list` в `api`
- **THEN** он видит только команды миграций, единую команду тестов и запуск

#### Scenario: Тесты API

- **WHEN** разработчик запускает `just test` в `api` с доступной PostgreSQL
- **THEN** команда создаёт тестовую базу при отсутствии, применяет миграции и выполняет все тесты API без развёртывания Valkey в Kubernetes

### Requirement: Локальные команды оператора

Каталог `operator` SHALL содержать `Justfile` с публичными командами `test-fast`, `test-full` и `run`. Быстрая проверка MUST NOT требовать работающего dev-кластера. `run` SHALL запускать оператор как процесс хоста с отдельным kubeconfig dev k3s. Пока reconciler не создаёт Valkey, `test-full` SHALL сообщать `TODO` и возвращать ненулевой код.

#### Scenario: Быстрые тесты оператора

- **WHEN** разработчик запускает `just test-fast` в `operator`
- **THEN** выполняются тесты логики, CRD и reconcile без ожидания запуска настоящих подов Valkey

#### Scenario: Запуск оператора с dev k3s

- **WHEN** разработчик запускает `just run` в `operator`
- **THEN** команда генерирует CRD и RBAC и запускает manager через `go run` с kubeconfig из `tmp/k3s`

#### Scenario: Полные интеграционные тесты ещё не реализованы

- **WHEN** разработчик запускает `just test-full` в `operator`
- **THEN** команда сообщает, что интеграционные тесты оператора на k3s ещё не добавлены, и завершается с ошибкой

### Requirement: Общие правила линтинга Go

Репозиторий SHALL иметь один корневой `.golangci.yml` формата v2, адаптированный из конфигурации Databasus. Он SHALL включать проверки ошибок, контекста и современного Go, а также `gofumpt`, `golines` с длиной строки 120 и `gci`. Настройка module path SHALL соответствовать общему Go-модулю Managed Valkey. Пре-коммит хук SHALL использовать этот файл для обоих приложений.

#### Scenario: Линтинг API

- **WHEN** staged-изменение затрагивает исходники API
- **THEN** пре-коммит хук форматирует и проверяет API и используемый им общий код по корневому `.golangci.yml`

#### Scenario: Линтинг оператора

- **WHEN** staged-изменение затрагивает исходники оператора
- **THEN** пре-коммит хук форматирует и проверяет оператор и используемый им общий код по корневому `.golangci.yml`

### Requirement: Проверки Go перед коммитом

Корневой `.githooks/pre-commit` SHALL сохранять проверки frontend и запускать форматирование, линтинг и сборку для Go-приложений, затронутых staged-изменениями. Изменение общего Go-кода, `go.mod`, `go.sum` или корневого `.golangci.yml` SHALL затрагивать оба приложения. Хук SHALL проверять чистоту `go mod tidy -diff`. Он MUST добавлять в индекс исправления форматтера только для Go-файлов, которые уже были staged, и MUST NOT добавлять посторонние незакоммиченные файлы. Ошибка форматирования, замечание линтера, расхождение модульных файлов или ошибка сборки SHALL отменять коммит.

#### Scenario: Форматтер исправил staged Go-файл

- **WHEN** staged Go-файл требует только автоматического форматирования, а остальные проверки проходят
- **THEN** hook добавляет исправленную версию этого файла в индекс и разрешает коммит

#### Scenario: Go-файл добавлен в индекс частично

- **WHEN** staged Go-файл содержит незакоммиченные изменения вне индекса
- **THEN** hook отменяет коммит до форматирования и не добавляет эти изменения в индекс

#### Scenario: Проверка нашла проблему

- **WHEN** линтер сообщает замечание, `go mod tidy -diff` находит расхождение или приложение не собирается
- **THEN** hook возвращает ненулевой код и коммит не создаётся

#### Scenario: Изменён общий Go-код

- **WHEN** staged-изменение затрагивает общий Go-пакет или модульные файлы
- **THEN** hook проверяет линтинг и сборку API и оператора

### Requirement: Проверки состояния API

API SHALL предоставлять отдельные HTTP-проверки живого процесса и готовности принимать рабочие запросы. Проверка готовности SHALL завершаться ошибкой, пока API не установил соединение с PostgreSQL; недоступность Kubernetes MUST NOT делать HTTP API неготовым.

#### Scenario: PostgreSQL доступна

- **WHEN** процесс API запущен и соединение с PostgreSQL установлено
- **THEN** проверки живого процесса и готовности отвечают успешно

#### Scenario: PostgreSQL недоступна

- **WHEN** процесс API работает, но соединение с PostgreSQL установить нельзя
- **THEN** проверка живого процесса отвечает успешно, а проверка готовности сообщает ошибку

#### Scenario: Kubernetes недоступен

- **WHEN** PostgreSQL доступна, но API не может обратиться к Kubernetes
- **THEN** проверка готовности API остаётся успешной, а фоновые операции смогут повторить обращение после восстановления связи

### Requirement: Проверки состояния оператора

Оператор SHALL предоставлять проверки живого процесса и готовности manager. Начальный контроллер MUST NOT создавать, изменять или удалять объекты, пока предметное поведение reconcile не реализовано отдельным изменением.

#### Scenario: Manager запущен

- **WHEN** оператор подключился к Kubernetes и запустил manager
- **THEN** проверки живого процесса и готовности отвечают успешно

#### Scenario: Ресурс попал в начальный reconcile

- **WHEN** начальный контроллер получает событие ресурса до реализации управления Valkey
- **THEN** он не изменяет ресурс и не создаёт зависимые объекты

### Requirement: Штатное завершение процессов

API и оператор SHALL обрабатывать завершение процесса через контекст отмены. API SHALL перестать принимать новые соединения и завершить начатые запросы в пределах заданного срока; оператор SHALL остановить manager и активные фоновые задачи. Оба процесса SHALL попытаться отправить накопленные логи перед выходом.

#### Scenario: Получен SIGTERM

- **WHEN** API или оператор получает `SIGTERM`
- **THEN** процесс прекращает новую работу, освобождает ресурсы и завершается с нулевым кодом в пределах срока остановки

### Requirement: Единые структурированные логи

Оба приложения SHALL писать структурированные логи через `slog` в stdout и, когда задан `VL_OTLP_URL`, отправлять их по OTLP/HTTP. Записи SHALL содержать `service.name` и `env`; ключи атрибутов SHALL использовать `snake_case`. Пароли, токены, заголовки авторизации, содержимое Secret и полные тела запросов MUST NOT попадать ни в один обработчик логов.

#### Scenario: Локальный запуск без VictoriaLogs

- **WHEN** `VL_OTLP_URL` не задан
- **THEN** приложение пишет читаемые структурированные записи в stdout и продолжает работу без OTLP-экспортера

#### Scenario: Экспорт логов недоступен

- **WHEN** приложение не может доставить лог в VictoriaLogs
- **THEN** HTTP API или reconcile продолжают работу, а ошибка экспорта не раскрывает содержимое исходной записи

### Requirement: Воспроизводимая генерация Kubernetes-артефактов

Сборка и тесты оператора SHALL использовать закреплённый генератор DeepCopy, CRD и RBAC для Go-маркеров. Повторная генерация из неизменённых исходников MUST NOT менять рабочее дерево.

#### Scenario: Повторная генерация

- **WHEN** разработчик дважды запускает внутренний шаг генерации без изменения Go-типов и маркеров
- **THEN** второй запуск не создаёт различий в отслеживаемых файлах

### Requirement: Будущие проверки отказов записаны рядом с кодом

Репозиторий SHALL содержать краткие `operator/TODO.md` и `e2e/TODO.md`. Первый файл SHALL напоминать о полной проверке восстановления primary оператором; второй SHALL описывать сквозной путь от регистрации пользователя до восстановления запросов Valkey после остановки активного pod.

#### Scenario: Планирование теста восстановления оператора

- **WHEN** разработчик начинает реализацию failover
- **THEN** в `operator/TODO.md` есть сценарий остановки primary и ожидания появления нового работающего primary

#### Scenario: Планирование сквозного теста

- **WHEN** разработчик начинает корневые e2e-тесты
- **THEN** в `e2e/TODO.md` есть сценарий создания пользователя и Valkey через API, запросов каждые 100 мс, наблюдаемого сбоя primary и восстановления успешных запросов
