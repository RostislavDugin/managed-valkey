## MODIFIED Requirements

### Requirement: Кластерный бюджет проверяется в исходном запросе

Общий доступный Valkey бюджет SHALL вычисляться из числа одинаковых Kubernetes-нод и бюджета каждой ноды после резерва инфраструктуры. Создание и увеличивающее резерв изменение размера SHALL дополнительно проверять существование размещения всех резервов по правилам `api-cluster-placement`. В v1 SHALL отсутствовать автоматическое расширение и очередь создания, ожидающая добавления ресурсов. После получения общей блокировки создание и изменение размера SHALL проверять бюджет и предел в 32 неудалённых инстанса. Нехватка SHALL давать `422 NOT_ENOUGH_RESOURCES` в том же HTTP-запросе до записи намерения. API MUST NOT принимать заведомо не помещающийся запрос с `202` и ждать истечения срока состояния `provisioning` или планировщика. Проверка SHALL использовать PostgreSQL и конфигурацию без вызовов Kubernetes.

#### Scenario: Немедленный отказ при нехватке CPU

- **WHEN** при общей квоте 4 CPU / 16 GB уже зарезервированы 3 CPU / 3 GB, а пользователь со свободной личной квотой создаёт `single` 2 CPU / 8 GB
- **THEN** исходный POST возвращает `422 NOT_ENOUGH_RESOURCES` с `reason=cluster_quota` и дефицитом 1 CPU
- **AND** новый инстанс, его аудит, период и ключ отсутствуют, использованная квота не меняется
- **AND** ответ не требует фонового прохода или истечения срока запуска

#### Scenario: Немедленный отказ при нехватке RAM

- **WHEN** CPU достаточно, но резерв кандидата превышает общий RAM-бюджет
- **THEN** исходный POST возвращает `422 NOT_ENOUGH_RESOURCES` с дефицитом RAM и без частичных записей

#### Scenario: Ровно доступный бюджет

- **WHEN** создание доводит CPU и RAM до лимитов без превышения и все резервы размещаются по нодам
- **THEN** API принимает запрос с `202`

#### Scenario: Последнее место по пределу числа инстансов

- **WHEN** существуют 31 неудалённый инстанс и два пользователя одновременно создают ещё по одному при достаточных CPU/RAM
- **THEN** ровно один запрос получает `202`, второй получает `422 NOT_ENOUGH_RESOURCES` с `reason=instance_limit`
- **AND** изменение размера существующего инстанса при 32 записях не отклоняется только из-за их числа

#### Scenario: Конкуренция между владельцами

- **WHEN** два пользователя через разные экземпляры API одновременно запрашивают последний свободный ресурс
- **THEN** ровно один запрос принимается, второй видит уже обновлённый резерв и получает `422`
- **AND** сумма резервов не превышает лимит

### Requirement: Личная квота и общий бюджет дают разные ошибки

Лимиты пользователя SHALL читаться из `user_quotas`; значения по умолчанию остаются 4 CPU / 16 GB. Личная квота SHALL проверяться раньше общей. Ошибка SHALL быть `422 QUOTA_EXCEEDED` с `reason=user_quota`. Для ошибок `user_quota`, `cluster_quota` и `placement_capacity` `details` SHALL содержать `limit`, `used`, `requested`, `missing`, где каждая величина содержит `vcpu` и `ram_gb`, а `requested` означает суммарный резерв после принятия кандидата. Для предела числа `details` SHALL содержать `limit`, `used`, `requested` как целые числа. Для `placement_capacity` `details` SHALL дополнительно содержать сведения из контракта `api-cluster-placement`; нулевой общий `missing` не означает, что размещение возможно. Отказ по квоте или размещению MUST NOT занимать ключ идемпотентности.

#### Scenario: CPU и RAM проверяются независимо

- **WHEN** кандидат превышает только один личный лимит
- **THEN** API отклоняет его и возвращает ненулевой дефицит только соответствующего ресурса

#### Scenario: Два запроса одного пользователя

- **WHEN** каждый из двух конкурентных запросов отдельно помещается в личный остаток, но вместе они превышают квоту
- **THEN** один запрос принимается, другой получает `QUOTA_EXCEEDED`

#### Scenario: Лимит уменьшен ниже занятого объёма

- **WHEN** новое изменение размера не увеличивает резерв ни CPU, ни RAM относительно текущего, но текущий резерв уже выше нового лимита
- **THEN** API допускает уменьшение при выполнении остальных правил готовности
- **AND** увеличение любой превышающей лимит величины отклоняется

### Requirement: Конфигурация квот проверяется при запуске

API SHALL проверять целые положительные лимиты ресурсов и порта, непустую допустимую сетку и корректный домен до приёма HTTP-запросов. Топология и резерв инфраструктуры SHALL браться из обязательных переменных окружения по контракту `api-cluster-placement`; отсутствие или неверный формат MUST NOT заменяться неограниченной квотой. Прежние `MANAGED_K8S_NODE_VCPU` и `MANAGED_K8S_NODE_RAM_GB` MUST NOT интерпретироваться как ёмкость одной ноды. Ставки SHALL быть целыми неотрицательными и не приводить к переполнению расчёта для разрешённых размеров.

#### Scenario: Ошибочная конфигурация

- **WHEN** лимит отсутствует, отрицателен, дробный либо сетка пуста
- **THEN** приложение не начинает обслуживать запросы и сообщает имя ошибочного параметра
