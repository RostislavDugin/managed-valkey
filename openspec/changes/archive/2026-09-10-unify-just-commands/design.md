## Context

Корневой `just test` сейчас запускает API, полный оператор, web и e2e параллельно. У оператора быстрый unit/envtest-набор доступен только как `test-ci`, а API всегда готовит k3s. Сохранённые результаты оператора показывают около 5–6 секунд для unit и 72–77 секунд для envtest. Полная k3s-матрица занимает десятки минут и управляет отдельными кластерами через общий бюджет ресурсов.

API-тесты уже делятся по зависимости от окружения: HTTP- и PostgreSQL-проверки используют общую тестовую обвязку, а Kubernetes-синхронизация требует kubeconfig и административного клиента. E2e имеет собственный `Justfile`, окружение и команды Playwright.

## Goals / Non-Goals

**Goals:**

- Дать одинаковый набор команд приложениям `api`, `operator` и `web`.
- Сделать обычные проверки предсказуемо быстрыми и пригодными для запуска после каждой локальной правки.
- Сохранить все полные проверки и существующую изоляцию окружений.
- Оставить e2e только под отдельными явными командами.

**Non-Goals:**

- Ускорение или повторный прогон полной k3s-матрицы оператора.
- Реализация общего integration-набора API + operator.
- Изменение состава Playwright-сценариев или рабочего dev-окружения.
- Автоматическое создание Git-коммита командой форматирования.

## Decisions

### 1. Одинаковые имена описывают стоимость команды

Каждое приложение предоставляет `run`, `format`, `lint`, `test` и `test-full`. `test` означает быстрый обязательный набор, `test-full` добавляет проверки с тяжёлой инфраструктурой. Предметные команды миграций API сохраняются.

У оператора нынешний `test-ci` становится `test`, а нынешний `test` становится `test-full`. Старое публичное имя `test-ci` удаляется после перевода CI и документации, чтобы не оставлять два имени одного набора.

Альтернатива: сохранить существующие имена и добавить `test-fast`. Она оставляет корневой `test` дорогим и не решает проблему неожиданной длительности.

### 2. Быстрый API сохраняет PostgreSQL, но не создаёт k3s

`api just test` создаёт отдельную базу, применяет миграции и запускает все тесты, которым не нужен Kubernetes. Kubernetes-зависимые тесты получают явный build tag и выполняются командой `test-full` в окружении с однонодовым k3s. Полный запуск выполняет обычные и помеченные тесты одним вызовом Go с включённым tag, чтобы не повторять быстрый набор.

Тестовая обвязка окружения получает режим API без k3s. Он сохраняет существующие правила владения базой, очистки и параллельных запусков.

Альтернатива: запускать Go без переменных окружения и считать пропущенные тесты быстрым набором. Такой результат зависит от внутренних `Skip` и хуже показывает фактический состав проверки.

### 3. Корневые агрегаты делегируют приложениям

Корневые `test` и `test-full` запускают одноимённые команды `api`, `operator` и `web` параллельно, ведут раздельные журналы, ждут все процессы и сохраняют существующую адресную отмену. `test-full` также выводит отдельный статус integration. Пока его `Justfile` отсутствует, статус равен «не реализован» и не называется успешной проверкой.

E2e отсутствует в обоих списках. `test-e2e`, `test-e2e-headed` и `test-e2e-prod` напрямую вызывают `tests/e2e/Justfile`. Отдельное задание CI e2e сохраняется.

Альтернатива: включить e2e только в `test-full`. Пользователь явно выбрал полную независимость e2e от обоих агрегатов.

### 4. Линтинг параллелен, форматирование последовательно

Корневой `lint` запускает `api just lint`, `operator just lint` и `web just lint` параллельно. Команды не меняют файлы и индекс. Go-команды проверяют соответствующие пакеты, общий `internal`, сборку и `go mod tidy -diff`; оператор также проверяет сгенерированные ресурсы. Web проверяет Oxlint, Steiger и TypeScript.

Корневой `format` вызывает локальные форматтеры последовательно, потому что API и оператор оба используют общий `internal`. После форматирования локальная команда добавляет в индекс Git изменения своей области. Корневая команда добавляет области API, оператора, общего Go-кода и web. Команда не создаёт коммит.

Альтернатива: добавлять только файлы, которые уже находились в индексе, как pre-commit hook. Это не выполняет требование подготовить к коммиту все изменения выбранного компонента.

### 5. `run` остаётся единым входом в dev

Корневой `just run` сохраняет нынешний жизненный цикл: инфраструктура, bootstrap, миграции, оператор, API и web. `web just run` становится оболочкой над сервером разработки, а корневой сценарий вызывает дочерние `run` для единообразия. E2e и integration не являются приложениями dev и не входят в `run`.

### 6. CI использует публичный быстрый контракт

Задания API, оператора и web вызывают `just test` в своих каталогах. API больше не поднимает k3s в CI, оператор сохраняет unit/envtest. Полные команды остаются локальными и не добавляются в CI/CD. E2e продолжает выполняться отдельным заданием и отдельной корневой командой.

### 7. Проверка реализации ограничивается быстрым набором

В конце этого изменения запускаются форматирование, линтинг и быстрые тесты затронутых компонентов. `test-full`, e2e и production e2e не запускаются. Корректность маршрутизации полных команд проверяется статически и небольшими тестами обвязки без создания k3s.

## Risks / Trade-offs

- [Семантические правки попадут в индекс вместе с форматированием] → Команды добавляют только область выбранного компонента, а `AGENTS.md` запрещает параллельное форматирование файлов, которыми владеет другой агент.
- [API-тест ошибочно попадёт в быстрый набор и потребует Kubernetes] → Kubernetes-зависимые файлы получают явную метку, а проверка обвязки подтверждает отсутствие k3s в `test` и его наличие в `test-full`.
- [Переименование сломает CI или документацию] → Все вызовы старых имён ищутся по репозиторию; CI и документы обновляются в одном изменении.
- [Параллельный полный запуск превысит доступную RAM] → Сохраняется общий реестр резервов тестовых окружений; наборы ждут освобождения бюджета вместо безусловного запуска новых кластеров.
- [Заглушка integration будет воспринята как успех] → Итоговый отчёт печатает отдельный статус «не реализован» и не создаёт пустой успешный рецепт.

## Migration Plan

1. Добавить новые локальные команды и разделить API-тесты по зависимости от k3s.
2. Перевести корневые агрегаты и CI на новый контракт.
3. Переименовать production e2e-команду и обновить все ссылки.
4. Обновить инструкции и системную документацию.
5. Проверить форматирование, линтинг и только быстрые тесты. Полные и e2e-наборы не запускать.

Откат возвращает прежние рецепты и вызовы CI одним изменением. Прикладные данные и тестовые окружения миграции не требуют.
