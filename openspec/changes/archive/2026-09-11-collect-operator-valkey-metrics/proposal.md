## Why

API уже принимает `status.metrics`, сохраняет снимки в PostgreSQL и отдаёт историю через HTTP, но оператор это поле не заполняет. Поэтому страница мониторинга не получает данные работающих экземпляров Valkey.

## What Changes

- Оператор периодически собирает показатели Valkey из `INFO` для каждого текущего процесса.
- Оператор получает загрузку CPU контейнера `valkey` через `metrics.k8s.io` и допускает отсутствие этого значения.
- Сбор выполняется независимо от основного цикла `Reconcile`, только при активном `LeaseScope`, и не задерживает обновление `status.observedAt`, переключение основного процесса и применение конфигурации.
- Перед записью снимка оператор проверяет `podUID`, `containerID` и `runId` до и после сбора.
- `status.metrics` хранит не больше одного последнего успешного снимка на `ordinal`; снимок прежнего процесса удаляется.
- Тесты клиента Valkey и контроллера проверяют основной путь и отказы. Существующий k3s-сценарий `single` проверяет снимок без создания нового стенда.

## Capabilities

### New Capabilities

- `operator-valkey-metrics`: периодический и изолированный сбор метрик текущих процессов Valkey в `status.metrics`.

### Modified Capabilities

- `api-valkey-sync`: контракт `status.metrics` получает рабочего производителя в операторе вместо оговорки о незаполненном поле.

## Impact

Изменения затронут клиент Valkey, новый контроллер метрик, регистрацию в `ctrl.Manager`, модульные тесты и существующий интеграционный тест оператора. В модуль Go добавится клиент типов `k8s.io/metrics` версии, согласованной с остальными зависимостями Kubernetes. Публичный HTTP API, схема PostgreSQL и форма CRD не меняются. Существующих прав оператора на `pods.metrics.k8s.io` достаточно.
