## Context

Форма `status.metrics`, импорт в API, хранение в PostgreSQL и HTTP-чтение уже реализованы. Основной `ValkeyInstanceReconciler` проверяет процессы каждую секунду и выполняет восстановление, переключение основного процесса и применение конфигурации. Его нельзя задерживать необязательным сбором наблюдаемости.

В `config` уже есть `MetricsInterval`: 10 секунд в рабочей сборке и 1 секунда в интеграционной. RBAC уже разрешает оператору `get` и `list` для `pods.metrics.k8s.io`. Тестовые кластеры используют Kubernetes 1.35 в составе k3s, поэтому клиент должен обращаться к `metrics.k8s.io/v1beta1`.

## Goals / Non-Goals

**Goals:**

- изолировать периодический сбор от основного цикла `Reconcile`;
- публиковать только снимки с проверенной идентичностью процесса;
- сохранить метрики Valkey при недоступном CPU;
- использовать существующий k3s-сценарий для проверки рабочего пути.

**Non-Goals:**

- экспорт внутренних метрик жизненного цикла оператора в Prometheus;
- изменение формы CRD, HTTP API, схемы PostgreSQL или срока хранения;
- восстановление промежуточных снимков, которые API не успел прочитать из CR;
- отдельный интеграционный стенд только для метрик.

## Decisions

### Отдельный контроллер метрик

`ctrl.Manager` зарегистрирует второй контроллер для `ValkeyInstance`. Он будет работать с периодом `config.MetricsInterval`, проверять тот же `LeaseScope` и обновлять только `status.metrics`. Создание или удаление `ValkeyInstance` и смена `podUID`, `containerID` либо `runId` смогут запустить ближайший проход. Изменение остальных полей `status.nodes`, настроек экземпляра или самих метрик не должно создавать немедленный повтор.

Так задержка Valkey или агрегированного API Kubernetes не удерживает основной цикл `Reconcile`. Альтернатива со сбором внутри `reconcileProcess` требует отдельно ограничивать задержки и частоту повторов ошибок, а также связывает наблюдаемость с переключением основного процесса.

### Один проход на ресурс и параллельный сбор узлов

Контроллер получает актуальный `ValkeyInstance` прямым чтением Kubernetes API и собирает до трёх узлов параллельно. После завершения он делает одно обновление `status.metrics`. Это ограничивает число конфликтов с основным контроллером. Медленный узел не задерживает чтение соседних.

Обновление проверяет `resourceVersion` и повторяет чтение при конфликте. На каждой попытке оно заново сверяет результат со свежим `status.nodes`, сохраняет остальные поля `status` и сортирует снимки по `ordinal`.

### Проверка идентичности охватывает весь сбор

Перед сбором контроллер читает Pod и сверяет его UID, состояние контейнера `valkey` и идентификатор контейнера с `status.nodes`. Новая операция клиента Valkey входит под пользователем `operator`, читает один полный `INFO` и возвращает показатели вместе с `run_id` и ролью. После чтения загрузки CPU контроллер повторно читает `run_id` через то же соединение и Pod через Kubernetes API.

Снимок допускается только при совпадении обеих проверок и актуального `status.nodes`. При явной смене идентичности прежний снимок с тем же `ordinal` удаляется до ожидания успешного результата нового процесса. При временной ошибке чтения, которая не доказывает смену процесса, последний успешный снимок сохраняется.

Полный `INFO` выбран вместо нескольких секций: нужные поля разбираются из одного согласованного ответа, а второй короткий `INFO server` нужен только для проверки `run_id`. Отрицательное, отсутствующее или неразбираемое обязательное значение делает весь снимок Valkey недопустимым.

### Загрузка CPU остаётся необязательной частью снимка

Клиент `k8s.io/metrics` создаётся один раз при настройке `ctrl.Manager`. Для совместимости с тестовым Kubernetes 1.35 используется `metrics.k8s.io/v1beta1`. Контроллер выбирает контейнер с именем `valkey` и преобразует его загрузку CPU через `Quantity.MilliValue()`.

Значение считается пригодным, если оно неотрицательно, `PodMetrics.timestamp` не старше одной минуты и не предшествует `containerStatus.state.running.startedAt`. Минутный предел учитывает обычный интервал обновления Metrics Server, но не привязывает свежесть CPU к сокращённому `MetricsInterval` интеграционной сборки. Любая ошибка этого пути даёт `nil`; она не отменяет снимок `INFO`.

### Ошибки данных не управляют очередью основного контроллера

Ошибка `INFO`, чтения CPU или проверки идентичности записывается в журнал без паролей и аргументов команд. Контроллер метрик завершает такой проход обычным ожиданием следующего периода. Ошибка обновления Kubernetes `status` возвращается библиотеке `controller-runtime`, потому что результат сбора не был сохранён. Основной контроллер и его очередь от этого не зависят.

### Проверки сосредоточены на границах ответственности

Тест клиента Valkey проверит успешный разбор полного `INFO`, обязательные поля и смену `run_id`. Тест контроллера с подменёнными читателями проверит период, идентичность, `cpuMillicores=null` и сохранение последнего успешного снимка при ошибке.

Существующий сценарий `single` дождётся снимка после первой готовности, проверит загрузку CPU от настоящего Metrics Server и повторит проверку после уже существующей замены Pod. Отдельный `envtest` не нужен: его `kube-apiserver` не предоставляет агрегированный `metrics.k8s.io`, а конфликты записи `status` уже проверяются общим помощником.

## Risks / Trade-offs

- [Два контроллера одновременно пишут `status`] -> Проверять `resourceVersion`, повторять чтение при конфликте и записывать список один раз за проход.
- [Повтор записи основного контроллера видит уже изменённый `status.Rollout.Process`] -> До записи копировать идентификатор процесса по значению и использовать эту копию на всех попытках.
- [Metrics Server временно недоступен или возвращает старое значение] -> Сохранить показатели Valkey с `cpuMillicores=null` и повторить чтение в следующий период.
- [Процесс меняется во время нескольких сетевых запросов] -> Проверять `podUID`, `containerID` и `runId` до и после сбора, затем сверять свежий `status.nodes` перед записью.
- [Полный `INFO` немного увеличивает нагрузку на Valkey] -> Выполнять его не чаще одного раза за `MetricsInterval`; предел составляет три процесса на экземпляр Valkey и 32 экземпляра на Gateway.
- [API может пропустить заменённый снимок между опросами] -> Сохранить действующую модель последнего снимка в `ValkeyInstance`; гарантированная доставка каждого измерения потребовала бы отдельного хранилища или очереди.

## Migration Plan

1. Добавить клиент `k8s.io/metrics`, чтение снимка Valkey и контроллер метрик без изменения CRD и правил доступа Kubernetes.
2. Развернуть оператор. При недоступном Metrics Server он начнёт публиковать остальные показатели с `cpuMillicores=null`.
3. Проверить появление новых строк через существующий импорт API и HTTP-маршрут метрик.

При откате последний снимок останется в `ValkeyInstance`, и API сможет прочитать его повторно. Новые снимки перестанут появляться; схема Kubernetes и данные PostgreSQL останутся совместимыми.
