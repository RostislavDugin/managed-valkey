## Context

См. [proposal.md](proposal.md). Авторизованная часть уже работает внутри
`ConsoleShell`: слева есть навигация, а `HomePage` занимает весь оставшийся
`main`. Маршрут `/` сейчас показывает только заголовок и кнопку. Временный auth
клиент уже показывает подход к имитации API: асинхронные функции, задержка и
изолированный доступ к `localStorage`. Сейчас он хранит почту в JWT `sub` и не
выдаёт стабильный идентификатор пользователя.

Тарифная сетка, расчёт цены и квота заданы в `SYSTEM.md`. Дизайн консоли,
адаптивная правая панель и форма создания описаны в `web/DESIGN.md`.

Визуальные источники сохранены вне Git:

| Экран | Файл | Что переносим |
|---|---|---|
| Список баз | [h3llo-databases-list.png](/temp/h3llo-databases-list.png) | заголовок с действием, поиск, плотную таблицу, правую панель |
| Пустой список | [h3llo-databases-empty.png](/temp/h3llo-databases-empty.png) | центрированное описание и одну основную кнопку |
| Страница базы | [h3llo-database-detail.png](/temp/h3llo-database-detail.png) | заголовок со статусом, строки свойств и правую панель стоимости |

Сайдбар на снимках не служит источником для этой работы: существующий
`ConsoleShell` уже принят как готовый.

## Goals / Non-Goals

**Goals:**

- сохранить формы будущего API за асинхронным клиентом, чтобы страницы не знали
  о `localStorage`;
- сделать список, создание и страницу базы одним разделом с общими крошками, а вкладки оставить свойством открытой базы;
- считать цену и квоту одной чистой моделью, которую используют список, форма и
  карточка базы;
- связывать сессию и базы через `user_id`, как это сделает будущий API;
- повторить ритм и композицию h3llo cloud через существующие токены обеих цветовых схем.

**Non-Goals:**

- подключение настоящего API, опрос фаз и имитация работы Kubernetes;
- рабочие метрики и журнал аудита;
- показ настоящего пароля, whitelist, смена пароля и maintenance;
- изменение режима существующей базы;
- платёжный сценарий и фактическое начисление денег;
- переделка сайдбара или общих токенов дизайн-системы.

## Decisions

### 1. Вкладка определяется маршрутом внутри базы

Маршруты раздела:

| Путь | Экран |
|---|---|
| `/` | перенаправление на `/valkey/management` |
| `/valkey` | перенаправление на `/valkey/management` |
| `/valkey/management` | список или пустое состояние |
| `/valkey/management/new` | создание базы |
| `/valkey/management/:instanceId` | карточка базы, вкладка «Управление» |
| `/valkey/management/:instanceId/monitoring` | заглушка мониторинга базы |
| `/valkey/management/:instanceId/audit-logs` | заглушка журнала аудита базы |

`ValkeyLayout` рисует хлебные крошки и `Outlet`. Вкладки принадлежат открытой
базе, поэтому их рисует `ValkeyInstanceLayout`: он загружает базу, ставит вторую
крошку с её именем и отдаёт данные вкладкам через контекст. Список и форма
создания вкладок не показывают. История браузера получает обычные переходы.

Вариант с состоянием вкладки в компоненте отброшен: после перезагрузки и при
прямой ссылке он возвращал бы пользователя на первый экран. Параметр `?tab=`
тоже не нужен, потому что три вкладки имеют самостоятельные адреса.

### 1c. Каркас открытой базы не зависит от вкладки

`ValkeyInstanceLayout` держит статус и меню удаления в шапке консоли, а панель
текущей стоимости в правой колонке. Эти элементы остаются смонтированными при
переходе между управлением, мониторингом и журналом аудита. Вкладки и содержимое
занимают доступную ширину с постоянным левым отступом 24px, поэтому смена
маршрута не сдвигает страницу к центру. В основной колонке сначала идут имя и
идентификатор базы, затем вкладки и содержимое выбранного раздела.

### 1a. Имя и DNS-префикс это разные поля

`SYSTEM.md` держит `name` отображаемым, а адрес базы собирает из отдельного
префикса: `slug = <prefix>-<6 случайных символов [a-z0-9]>`, уникальный по всей
установке. Форма создания повторяет это: два поля и предпросмотр будущего
DNS-имени. Slug генерирует временный клиент, как это сделает `api`, поэтому
страницы о правиле сборки не знают. Переименование меняет только `name`.

Вариант «имя и есть адрес» отброшен: он запрещал бы пробелы и заглавные буквы в
отображаемом имени навсегда и не дал бы двум пользователям завести базы с
одинаковым названием.

Документ хранилища переходит на версию 2. Записи версии 1 читаются: префикс
берётся из имени, DNS-имя генерируется при чтении. Неизвестная версия остаётся
ошибкой загрузки.

### 1b. Шапка и правая колонка это слоты каркаса

`web/DESIGN.md` описывает оболочку как `navbar | main 784px | aside`, где шапка
и правая панель прижаты к краям окна. Раздел не может отрисовать их сам: они
живут выше него по дереву. Поэтому `ConsoleShell` держит два пустых узла и
отдаёт их странице через контекст `Outlet`, а страница наполняет их
`createPortal`.

Отброшен вариант «панель внутри контейнера страницы», который был реализован
раньше: он делил 784px между формой и панелью, из-за чего контролы формы
сжимались вдвое против оригинала. Отброшен и вариант с общим состоянием
«панель есть»: пустая колонка схлопывается правилом `:empty`, и лишнего
состояния не нужно.

Домен и порт инстансов приходят отдельным методом временного клиента
`getValkeyDomain`, а не константой в компоненте: на сервере это значения env
(`VALKEY_BASE_DOMAIN`, `VALKEY_PUBLIC_PORT`), и страница о них знать не должна.
Недоступный домен не блокирует форму: подсказка префикса откатывается к
DNS-имени без домена.

### 2. Весь новый код сначала остаётся в одном срезе страницы

Планируемая структура:

```text
src/pages/valkey/
  api/valkey-storage.ts
  model/valkey.ts
  model/valkey-form.ts
  ui/ValkeyLayout.tsx
  ui/ValkeyInstanceLayout.tsx
  ui/ValkeyManagementPage.tsx
  ui/CreateValkeyPage.tsx
  ui/ValkeyInstancePage.tsx
  ui/ValkeyPlaceholderPage.tsx
  ui/*.module.css
  index.ts
```

Все маршруты относятся к одному разделу и пользуются одной моделью. Отдельные
`features` и `entities` пока дали бы одноразовые срезы. Если данные Valkey
понадобятся в другом разделе, транспортный CRUD можно вынести в `shared/api`, а
доменную модель в `entities/valkey` после появления второго независимого
потребителя.

Вариант с новым `widgets` не используется: блоки списка, формы и карточки не
переиспользуются за пределами страницы. Внешние импорты идут только через
`pages/valkey/index.ts`.

### 3. Временный клиент хранит версионированный набор записей

Ключ: `mv_valkey_instances`.

```ts
interface StoredValkeyState {
  version: 1;
  instances: Array<{
    id: string;
    ownerId: string;
    name: string;
    mode: 'single' | 'ha';
    vcpu: 1 | 2 | 4 | 8 | 16;
    ramGb: 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128;
    status: 'running';
    createdAt: string;
    updatedAt: string;
  }>;
}
```

`ownerId` получает `userId` из сессии. Страницы передают его клиенту, а клиент
повторяет фильтрацию по владельцу. Это сохраняет форму будущей проверки по
`user_id` из JWT, хотя `localStorage` не является границей безопасности.

Временный auth добавляет `id` каждой записи `mv_users`. Новый аккаунт получает
UUIDv7, чтобы формат совпадал с будущим `users.id`. JWT хранит идентификатор в
`sub` и срок действия в `exp`. Объект `Session` возвращает `userId` и почту,
которую временный клиент находит в `mv_users`. После подключения API данные
аккаунта придут из `/v1/me`. Владение ресурсами определяет только `userId`.
UUIDv7 создаёт небольшой помощник на `crypto.getRandomValues`, без новой
зависимости; `crypto.randomUUID()` не подходит, потому что возвращает UUIDv4.

При чтении auth мигрирует старые записи `mv_users` без `id`: назначает UUIDv7 и
сохраняет обновлённый список. Старый токен, у которого почта лежит в `sub`,
разрешается через эту запись и заменяется токеном с `sub=user.id` и тем же
`exp`. Если аккаунт найти нельзя, клиент удаляет токен как недействительный.

Клиент предоставляет отдельные операции `listInstances`, `getInstance`,
`createInstance`, `renameInstance`, `resizeInstance` и `deleteInstance`. Такое
разделение соответствует будущим запросам списка, `PATCH`, resize и `DELETE`.
Каждая операция ждёт 400 мс и возвращает копию DTO. Ошибки используют
`ApiError` с кодами `VALIDATION_FAILED`, `CONFLICT`, `NOT_FOUND` и
`QUOTA_EXCEEDED`.

Перед чтением клиент проверяет `version`, поля и допустимые значения каждой
записи. Неизвестная версия или повреждённая запись дают ошибку загрузки.
Хранилище не очищается автоматически, чтобы случайное повреждение не выглядело
как удаление всех баз.

Идентификатор базы создаётся через `crypto.randomUUID()`. Имя по умолчанию имеет вид
`valkey-1474`; четыре цифры выбираются через Web Crypto, а при совпадении
генерируются заново. Временная реализация сразу сохраняет статус `running`:
переходы `provisioning` и `deleting` зависят от оператора и не имитируются.

Вариант с одной общей записью без владельца отброшен, потому что после выхода и
входа под другим аккаунтом базы смешались бы. Отдельный ключ на каждый
`user_id` тоже не используется: один версионированный документ проще проверить
и позднее удалить вместе с временным клиентом.

### 4. Размер и режим образуют тариф, цена хранится в копейках

Временный клиент содержит всю сетку из `SYSTEM.md`:

| vCPU на ноду | Допустимая RAM на ноду, ГБ |
|---:|---|
| 1 | 1, 2, 4, 8, 16 |
| 2 | 2, 4, 8, 16, 32 |
| 4 | 4, 8, 16, 32, 64 |
| 8 | 8, 16, 32, 64, 128 |
| 16 | 16, 32, 64, 128 |

Она получается из наборов vCPU `1, 2, 4, 8, 16` и RAM
`1, 2, 4, 8, 16, 32, 64, 128` по правилам `ramGb >= vcpu` и
`ramGb <= 16 * vcpu`. Ограничения `SIZE_MAX_*` появятся вместе с API; текущая
имитация показывает всю сетку и ограничивает отправку только квотой пользователя.

Модель не хранит готовую цену. Она считает её в целых копейках:

```text
nodes = mode == single ? 1 : 3
hourlyKopecks = (125 * vcpu + 50 * ramGb) * nodes
dayKopecks = hourlyKopecks * 24
monthKopecks = hourlyKopecks * 720
```

Период панели цены относится только к представлению и не сохраняется. Режим
выбирается при создании, а после создания показывается неизменяемым. Изменение
тарифа вызывает только `resizeInstance` с новым размером.

Форма предлагает шесть готовых конфигураций из примеров `SYSTEM.md`: `1/1`,
`1/2`, `1/4`, `2/4`, `2/8` и `4/16`, где первое число это vCPU, второе RAM в
ГБ. Каждая радио-карточка показывает ресурсы и цену за месяц. Режим выбирается
двумя отдельными радио-карточками. Форма на `useForm` работает в
controlled-режиме: выбор режима и конфигурации сразу меняет цену и проверку
квоты. Имя, префикс и белый список проверяются при потере фокуса и отправке.

### 5. Доступность тарифа вычисляется из общей квоты

Квота фиксирована для временного клиента: 4 vCPU и 16 ГБ RAM. Использование:

```text
usedVcpu = sum(nodes(instance.mode) * instance.vcpu)
usedRamGb = sum(nodes(instance.mode) * instance.ramGb)
```

При создании кандидат прибавляется к полному использованию. При resize клиент
сначала вычитает текущие ресурсы изменяемой базы, затем прибавляет кандидата.
Проверку выполняют и форма, и клиент перед записью. Клиент остаётся источником
окончательного ответа, как будущий сервер.

Все значения тарифной сетки остаются на слайдерах. Пользователь может выбрать
размер сверх квоты, чтобы увидеть его цену, но не может отправить форму. Под
контролами показываются занятый и требуемый ресурс, а также ссылка
`https://t.me/rostislav_dugin`. Если доступного размера нет, значение тарифа
остаётся выбранным для расчёта, кнопка отправки блокируется, а форма показывает
отдельный блок «Напишите в поддержку для увеличения квоты».

Панель квоты на списке показывается только при непустом наборе баз. Она содержит
две строки прогресса: vCPU и RAM, в формате «занято / доступно». У пустого
состояния панели нет.

### 6. Композиция меняется по состоянию страницы

Список с данными:

```text
+------------------------------+----------------+
| Базы данных                  | Использование  |
| Базы данных     [Создать]    | vCPU  2 / 4    |
|                              | RAM   6 / 16 GB|
| [Поиск....................]  |                |
| +--------------------------+ |                |
| | Имя | Статус | ... | ... | |                |
| +--------------------------+ |                |
+------------------------------+----------------+
```

Главная область списка работает в широком режиме, потому что таблица должна
сохранить столбцы из спецификации. Поиск стоит над таблицей. Меню строки
содержит «Открыть», «Переименовать» и «Удалить».

Пустое состояние:

```text
+------------------------------------------------+
| Базы данных                                    |
|                                                |
|                    VALKEY                      |
|            Управляемые базы Valkey             |
|       Краткое описание без рекламных обещаний  |
|                 [Создать базу]                 |
+------------------------------------------------+
```

Карточка базы переносит со снимка имя с кнопкой переименования, строку типа и
копируемого идентификатора, примеры подключения и плотную сетку свойств. В
примерах есть JavaScript, TypeScript, Python и Go. Они используют адрес базы,
пользователя `app`, TLS с именем сервера и заполнитель `<PASSWORD>` вместо
секрета. Статус и удаление находятся в шапке, текущая стоимость находится
справа. Изменение тарифа открывает отдельное короткое окно с радио-карточками
допустимых конфигураций, новой стоимостью и предупреждением о последствиях
ресайза. Для `single` это простой и очистка
кеша. Для `ha` уменьшение RAM очищает кеш, остальные изменения могут потерять
последние записи при смене primary. Окно также сообщает, что ресайз нельзя
отменить, а новый тариф действует с момента принятия запроса. Удаление
открывает подтверждение с точным именем.

Форма создания занимает самостоятельный маршрут. Порядок полей: режим, тариф,
имя. Справа находится панель стоимости с переключателем «Месяц», «День», «Час».
На узком экране она открывается как выдвижная панель по правилам
`web/DESIGN.md`.

На ширине меньше 1024px правая панель становится выдвижной, таблица получает
горизонтальную прокрутку внутри `ScrollArea`, а пустое состояние сохраняет
центрирование. На 375px кнопка создания и заголовок могут занимать разные
строки.

### 7. Каждая операция сообщает результат в двух местах

Кнопка отправки показывает загрузку и блокирует повторное нажатие. После ответа
уведомление сообщает об успехе или ошибке, а список или карточка сразу отражают
новые данные. Ошибка имени остаётся у поля. Ошибка квоты показывает требуемый
ресурс и ссылку на поддержку.

Загрузка списка и карточки использует скелетоны известной формы. Сбой загрузки
показывает действие «Повторить». Неизвестный `instanceId` показывает отдельное
состояние «База не найдена» со ссылкой к списку. «Ничего не найдено» при поиске
не использует пустой экран аккаунта.

Опасное действие подтверждается модальным окном. После удаления карточка ведёт
к списку. Если удалена последняя база, список переключается в пустое состояние.

### 8. Снимки задают композицию, а токены проекта задают оформление

Из оригинального h3llo cloud не копируются пиксельные значения и светлая тема
как единственный вариант. Компоненты используют Mantine 9, семантические токены
`h3_*`, варианты кнопок из `shared/config` и Lucide. Экран проверяется в обеих
цветовых схемах и на ширинах 375, 768, 1024 и 1440px.

## Risks / Trade-offs

- [Пользователь может изменить `localStorage` вручную] -> клиент проверяет
  структуру и повторяет квоты, но временное хранилище не считается защитой.
- [Имитация не воспроизводит фазы и конфликты настоящего оператора] -> формы методов,
  DTO и коды ошибок соответствуют будущему API, а статус явно ограничен
  `running`.
- [Два таба пока ведут на пустые страницы] -> заглушки имеют отдельные маршруты,
  поэтому их можно заменить без переделки навигации.
- [Файлы в `/temp` могут исчезнуть после очистки машины] -> решения, нужные для
  реализации, описаны в этом документе; снимки служат только визуальной сверкой.
- [Широкая таблица тесна на телефоне] -> прокрутка ограничена областью таблицы и
  не создаёт горизонтальную прокрутку всей страницы.

## Migration Plan

1. При первом чтении auth назначает UUIDv7 записям `mv_users` без `id`. Старый
   токен с почтой в `sub` заменяется токеном с `user_id` и прежним сроком
   действия.
2. При первом чтении отсутствие `mv_valkey_instances` означает пустой список;
   клиент создаёт документ только при первой записи.
3. Маршрут `/` начинает перенаправлять на `/valkey/management`; сохранённый
   возврат после входа продолжает работать через React Router.
4. При подключении API меняется реализация операций в `api/valkey-storage.ts`.
   Страницы и модель форм сохраняют формы запросов и ответов.
