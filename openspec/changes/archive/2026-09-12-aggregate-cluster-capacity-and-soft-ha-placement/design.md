## Context

См. `proposal.md`. Сейчас API получает число одинаковых worker-нод, их размер и понодовый резерв. Он хранит эту топологию в `ClusterTopology`, вычисляет общий лимит и перед каждой увеличивающей мутацией запускает ограниченный по времени поиск раскладки всех резервов. HA требует три разные ноды как в API, так и в обязательном `podAntiAffinity` оператора.

Квота и фактическое планирование решают разные задачи. Квота ограничивает суммарный продаваемый объём, а Kubernetes учитывает `allocatable`, уже размещённые Pod, taints, cordon и форму каждой ноды. Новые требования разделяют эти уровни в `api-cluster-capacity`, `api-valkey-quotas` и операторских спецификациях этого изменения.

Рабочий кластер состоит из трёх нод 4 vCPU / 16 GiB, но конфигурация API должна содержать только общие 12 vCPU / 48 GiB. Подготовка выпуска и состояние межнодовой сети рассматриваются отдельно.

## Goals / Non-Goals

**Goals:**

- отделить суммарный учёт ресурсов от формы и количества worker-нод;
- разрешить полному HA работать на одной или двух нодах при достаточных жёстких ресурсах;
- сохранить атомарный учёт личной и общей квоты, включая незавершённые resize и удаления;
- не выдавать суммарный лимит за гарантию физического размещения;
- быстро проверять новую семантику целевыми тестами во время реализации и завершить работу только после полного локального прогона.

**Non-Goals:**

- динамически читать `allocatable` или фактическую загрузку Kubernetes из HTTP API;
- автоматически менять суммарную квоту при добавлении или удалении нод;
- гарантировать перераспределение уже работающих Pod после появления новой ноды;
- делать весь production-стек однонодовым: текущие cert-manager webhook, Envoy, DNS и PDB сохраняют отдельные требования;
- использовать совместное размещение как обход неисправной межнодовой сети;
- автоматически переводить существующие рабочие HA Pod со старого обязательного anti-affinity.

## Decisions

### 1. Полная ёмкость задаётся двумя целыми параметрами

API читает `MANAGED_K8S_CLUSTER_VCPU` и `MANAGED_K8S_CLUSTER_RAM_GB`. RAM сохраняет принятую в API семантику GiB, несмотря на суффикс `_GB`. Конфигурация переводится в тысячные доли CPU и MiB с проверкой переполнения.

Все семь прежних параметров топологии считаются ошибкой запуска. Молчаливое игнорирование опасно: при частично обновлённом production-окружении оператор получил бы другую квоту без явного сигнала.

Альтернативой было сохранить необязательные сведения о нодах только для диагностики. Она отклонена, потому что оставила бы два источника конфигурации и соблазн снова использовать топологию при принятии запроса.

### 2. Резерв равен 15% CPU и 10% RAM

Внутренний бюджет вычисляется целочисленно:

```text
cpu_milli = floor(cluster_vcpu * 1000 * 85 / 100)
ram_mib   = floor(cluster_ram_gb * 1024 * 90 / 100)
```

Для 12/48 получаются 10200m и 44236 MiB. Публичный DTO и размеры резервов выражены целыми vCPU/GiB, поэтому `/capacity` сообщает 10/43, а оставшиеся дробные части не позволяют принять ещё один целый ресурс каталога.

Для 4/16 внутренний бюджет равен 3400m и 14745 MiB, а `/capacity` сообщает 3/14. Поэтому процесс 4/16 превышает суммарный бюджет уже на пустом кластере. Если личной квоты пользователя хватает, интерфейс блокирует отправку по данным `/capacity` с причиной нехватки ресурсов Managed Kubernetes, а повторная проверка API возвращает `cluster_quota` до записи намерения. При одновременной нехватке личной квоты сохраняется её существующий приоритет.

Проценты являются именованными константами, а не дополнительными переменными окружения. Это сохраняет запрошенный контракт из двух параметров. Резерв выбран как исходная эксплуатационная граница, а не доказательство достаточности: перед его дальнейшим уменьшением нужны фактические `allocatable`, requests и пики системных компонентов.

Альтернативный резерв 25% CPU / 12,5% RAM сохранял прежний общий лимит 9/42, но смешивал инфраструктурный запас с потерями от понодовой раскладки. Единый процент также отклонён: CPU и память системных компонентов имеют разный профиль.

### 3. API проверяет только суммарные резервы

`ClusterTopology` заменяется объектом суммарной ёмкости. `Capacity()` и `checkQuota()` используют один доступный CPU/RAM-бюджет. Существующий `ValkeyUsage` и общая advisory-блокировка остаются: они уже атомарно учитывают `single` с множителем 1, HA с множителем 3 и покомпонентный максимум желаемого и применённого размера.

Из сервиса и хранилища удаляются `placementCandidate`, поиск раскладки, его deadline, чтение всех `ValkeyReservations` и построение `placement_capacity`. Ошибка `cluster_quota` остаётся прежней по форме. Удаление placement-проверки не требует миграции PostgreSQL и не меняет успешный DTO `/capacity`.

Альтернатива с синхронным чтением Kubernetes отклонена. Она добавила бы сетевую зависимость внутрь транзакции HTTP, не устранила бы гонку с scheduler и усложнила бы работу нескольких экземпляров API.

### 4. Суммарная квота допускает недоступную физическую комбинацию

API принимает намерение, если хватает личной квоты, суммарного бюджета и места в лимите 32 инстансов. После доставки CR Kubernetes может оставить Pod в `Pending`. Резерв продолжает занимать квоту, потому что намерение не удалено и пользователь всё ещё ожидает ресурс.

Интерфейс использует `/capacity` для предварительного ограничения только по сумме. Тексты документации и интерфейса не должны называть `cluster.limit` свободным местом Kubernetes или гарантией запуска.

Рабочий `VALKEY_INSTANCE_MAX_VCPU/RAM_GB` остаётся равен 4/16. Каталог описывает поддерживаемые размеры, а `/capacity` определяет, доступен ли выбранный размер при текущем суммарном бюджете. API повторяет эту проверку внутри транзакции, поэтому устаревший снимок интерфейса не позволяет превысить бюджет.

### 5. HA использует мягкое топологическое распределение

Обязательный `PodAntiAffinity` заменяется одним `TopologySpreadConstraint` для HA:

```yaml
maxSkew: 1
topologyKey: kubernetes.io/hostname
whenUnsatisfiable: ScheduleAnyway
labelSelector: <метки процессов одного инстанса>
```

`minDomains` не задаётся. `single` не получает это ограничение. Selector использует те же устойчивые метки инстанса, что PDB и текущий anti-affinity.

`ScheduleAnyway` выражает нужную семантику лучше мягкого `PodAntiAffinity`: scheduler оценивает перекос по всем доступным hostname, но не блокирует третий Pod при одной или двух нодах. Это предпочтение не гарантирует 1+1+1, если другие scheduler scores выбирают другую ноду.

### 6. Фаза зависит от состава процессов, а не от числа нод

Текущий расчёт доступности уже использует готовый primary и число готовых реплик. Его не нужно связывать с уникальными UID нод. `running` требует primary и две синхронизированные реплики; `degraded` сохраняется при одной готовой реплике, а `unavailable` при потере primary по существующим правилам.

PDB `minAvailable: 2` сохраняется. На однонодовом HA он не защищает от аварии ноды и может блокировать добровольный drain, пока нет другого подходящего хоста. Это ожидаемое ограничение, которое нужно описать в эксплуатационной документации.

### 7. Тесты разделяют состав и распределение

Общий helper HA больше не требует три уникальные ноды. Он проверяет три процесса, роли, идентичности и репликацию. Отдельные helpers проверяют число занятых hostname только в сценариях распределения и отказа, где оно является предусловием действия.

Новые k3s-сценарии создают HA на одной, двух и трёх нодах. Двухнодовые fault-сценарии покрывают потерю ноды с двумя процессами в вариантах, где на выжившей ноде остаётся primary или replica. Сценарии resize и смены пароля проверяются на совместно размещённом составе. Отдельный сценарий создаёт настоящую жёсткую нехватку через cordon или requests, чтобы `Pending` не зависел от удалённого anti-affinity.

Во время реализации запускаются затронутые Go-тесты, новые целевые k3s-сценарии и изменённые Playwright-сценарии `cluster-capacity` и `worker-node-loss`. Это сокращает обратную связь, но не заменяет финальную проверку.

После завершения кода и документации последовательно выполняются `just lint`, `just test`, `just test-full`, `just test-integrations` и `just test-e2e`. `just test-full` уже включает общую интеграцию; отдельный `just test-integrations` дополнительно проверяет самостоятельную точку запуска. Перед тяжёлыми наборами, во время их работы и после завершения проверяются ресурсы хоста и принадлежность оставшихся процессов и контейнеров.

Каждый сбой разбирается и исправляется в коде, тесте или локальной тестовой обвязке. Сначала повторяется упавший сценарий, затем команда, в которой он упал. Изменение нельзя считать завершённым, пока все пять команд не пройдут. Нельзя добиваться успеха отключением теста, ослаблением проверки или исключением сценария из каталога.

`just test-e2e-headed` запускает тот же локальный Playwright-набор в другом режиме и отдельного покрытия не добавляет. `just test-e2e-prod` проверяет уже развёрнутое production-окружение и остаётся для отдельной работы по выпуску.

## Risks / Trade-offs

- [API может принять физически неразмещаемый набор из-за фрагментации или формы нод] -> сохранять резерв у `Pending` намерения и прямо описать смысл суммарного лимита. Кандидат, превышающий бюджет после инфраструктурного резерва, отклоняется с `cluster_quota` и до Kubernetes не доходит.
- [Фиксированный процент перестанет соответствовать инфраструктуре] -> проверять фактические requests и `allocatable` при изменении состава production; изменение процентов проводить отдельным решением с нагрузочной проверкой.
- [Scheduler не гарантирует равномерный результат] -> проверять точную конфигурацию constraint в unit/envtest, а 1+1+1 и 2+1 только на контролируемых одинаковых стендах.
- [После добавления ноды Pod не переедут сами] -> не обещать автоматический rebalance; использовать штатную замену процесса, если перенос нужен операционно.
- [Совместное размещение снижает node-level HA] -> сохранять сведения о нодах в status и документации, не считать `running` обещанием пережить потерю единственного хоста.
- [Старые Pod сохранят обязательный anti-affinity] -> выпускать изменение только при подтверждённом отсутствии активных production-инстансов; для непустого окружения сначала спроектировать безопасную последовательную замену.
- [Полный локальный прогон требует много времени и ресурсов] -> сначала устранять ошибки точечными командами, затем запускать обязательные полные наборы с контролем ресурсов и адресной очисткой только своих стендов.

## Migration Plan

1. Повторно проверить отсутствие активных production-инстансов. При наличии хотя бы одного остановить выпуск и не удалять его Pod автоматически.
2. Обновить API, production Compose, примеры окружения и runner-скрипты одним изменением, чтобы новые обязательные параметры появились одновременно с удалением старых.
3. Сохранить production `VALKEY_INSTANCE_MAX_VCPU=4` и `VALKEY_INSTANCE_MAX_RAM_GB=16`; доступность каждого размера ограничивать результатом `/capacity` и повторной проверкой API.
4. Обновить оператор с мягким topology spread. Одноразовые dev и тестовые инстансы пересоздать штатной очисткой их окружений.
5. Выполнить обязательный полный локальный прогон, исправить все сбои и передать изменение только после успеха каждого набора.

Откат до создания новых HA возвращает прежние образы и пять действующих переменных топологии; два более старых имени остаются запрещёнными. После создания совместно размещённого HA безопасный откат требует сначала обеспечить три подходящие ноды и пересоздать процессы под старым обязательным anti-affinity. В таком состоянии предпочтительнее исправление вперёд.
