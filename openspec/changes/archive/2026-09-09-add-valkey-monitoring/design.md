## Context

В `api` уже есть таблица `valkey_instances`, JWT-аутентификация и общая проверка владельца для маршрутов `/v1/managed/valkey/instances/{id}`. Таблицы и кода чтения метрик пока нет.

Во фронтенде маршрут мониторинга вложен в `ValkeyInstanceLayout`, но `ValkeyMonitoringPage` показывает заглушку. Полная версия экрана с графиками и тестами есть в истории репозитория в коммите `8fc92f9`; серверный клиент из неё был удалён при подключении API управления. Цветовые токены графиков и общие функции форматирования времени остались в текущем коде.

Целевые поля таблицы и правила агрегации описаны в `SYSTEM.md` и `SYSTEM-DETAIL.md`. Этот change создаёт читаемый путь от PostgreSQL до фронтенда. Источник строк в таблице появится в отдельном change.

## Goals / Non-Goals

**Goals:**

- закрепить схему снимка метрик, пригодную для будущего импорта из `status.metrics`;
- выполнять агрегацию в PostgreSQL и ограничить размер HTTP-ответа;
- вернуть готовый экран мониторинга, заменив демонстрационный источник на HTTP API;
- проверять маршрут через настоящий HTTP и PostgreSQL, заполняя таблицу напрямую в тестах.

**Non-Goals:**

- чтение ресурсов Kubernetes и `status.metrics`;
- изменение оператора или CRD;
- автоматическая очистка строк старше срока хранения;
- таблица `valkey_instance_nodes`, API аудита и восстановление экрана аудита;
- выбор произвольных `from` и `to` в интерфейсе.

## Decisions

### Таблица следует целевой схеме без суррогатного идентификатора

Новая миграция создаёт `valkey_node_metrics` с полями из `SYSTEM-DETAIL.md`. Естественная пара `(instance_id, ordinal, ts)` определяет снимок и получает ограничение уникальности. Отдельный UUID не нужен, потому что строки не адресуются по одной через API и никогда не изменяются после вставки.

`instance_id` ссылается на `valkey_instances` с `ON DELETE RESTRICT`. Сейчас базы удаляются мягко, а история остаётся связанной с исходной записью. `ordinal` неотрицательный, роль ограничена значениями `primary`, `replica`, `unknown`, все счётчики и показатели неотрицательны. Только `cpu_millicores` допускает `null`.

Индекс `(instance_id, ts DESC)` отбирает окно одной базы. Уникальный индекс `(instance_id, ordinal, ts)` одновременно защищает будущий повторный импорт. В этой задаче нет писателя приложения; интеграционные тесты создают строки напрямую.

Альтернатива с JSONB для снимка сократила бы число колонок, но усложнила бы проверки типов и агрегацию. Отдельная таблица на каждую метрику увеличила бы число строк и соединений без пользы для фиксированного набора показателей.

### HTTP API имеет один контракт для готовых и произвольных окон

Маршрут добавляется в существующую группу `owned`, поэтому получает ту же проверку JWT и владельца, что карточка и credentials. Параметры разбираются в HTTP-слое, а нормализованное окно передаётся в сервис Valkey.

Клиент выбирает один из двух вариантов:

- `range=5m|1h|24h|7d`;
- оба параметра `from` и `to` в RFC 3339.

Без параметров используется `1h`, как задано в `SYSTEM.md`. Одновременный `range` и `from`/`to`, неполная пара, неизвестные параметры, обратный порядок времени и окно шире семи дней возвращают `400 VALIDATION_FAILED`.

Ответ имеет одну форму:

```json
{
  "from": "2026-09-09T09:00:00Z",
  "to": "2026-09-09T09:05:00Z",
  "step_seconds": 10,
  "nodes": [
    {
      "ordinal": 0,
      "name": "cache-a1b2c3-0",
      "role": "primary",
      "points": [
        {
          "collected_at": "2026-09-09T09:00:00Z",
          "used_memory_bytes": 805306368,
          "cpu_millicores": 125.5,
          "connected_clients": 12,
          "ops_per_sec": 740.5,
          "keyspace_hits": 680,
          "keyspace_misses": 9,
          "evicted_keys": 0
        }
      ]
    }
  ]
}
```

`name` вычисляется из текущего `slug` базы и `ordinal`. `run_id` и `maxmemory_bytes` нужны для хранения и расчётов, но фронтенд их не использует, поэтому API их не возвращает. Пустой результат имеет `nodes: []`; API не создаёт ноды или значения из режима базы.

Альтернатива с плоским массивом точек заставила бы каждый клиент самостоятельно группировать и подписывать ноды. Ряды по нодам совпадают с уже спроектированной моделью фронтенда.

### PostgreSQL строит корзины и пропуски

Хранилище выполняет один запрос для выбранной базы и окна. `date_bin` относит снимки к корзинам, а `generate_series` создаёт недостающие позиции для каждой ноды, у которой есть хотя бы один снимок в окне. Поэтому ответ ограничен числом нод и корзин, а пропуски представлены `null`.

Средние показатели считаются функцией `AVG`, которая не учитывает `null`. Для счётчиков запрос сначала получает разницу с предыдущим снимком той же ноды через `LAG`. Если `run_id` изменился, вклад нового снимка равен его текущему значению. Запрос читает один предшествующий снимок на ноду, чтобы корректно посчитать первую корзину окна.

Роль ряда берётся из последнего снимка ноды внутри окна. Ноды и точки сортируются сервером, чтобы клиент не зависел от порядка строк PostgreSQL. Дополнительный фильтр по текущему времени базы не позволяет читать строки старше семи дней, пока отдельная задача очистки ещё не реализована.

Агрегация в Go потребовала бы читать до десятков тысяч сырых строк на ноду при каждом пятисекундном обновлении. Агрегация в PostgreSQL возвращает не более 336 точек на ноду для готовых окон.

### Код метрик остаётся внутри существующего среза Valkey

В `api` модель таблицы размещается в отдельном файле `internal/store/valkey_node_metric.go`, запрос агрегации рядом с репозиторием Valkey, а разбор окна и DTO в `internal/valkey`. HTTP-обработчик расширяет текущий маршрут Valkey. Новый пакет для одной операции не нужен.

Во фронтенде восстанавливаются `pages/valkey/api/valkey-metrics.ts`, `pages/valkey/model/valkey-observability.ts`, `MetricChart`, `ValkeyMonitoringPage` и их стили и тесты из коммита `8fc92f9`. Это соответствует pages-first структуре FSD: запрос и модель пока нужны одной группе маршрутов. Клиент использует общий `apiRequest`, преобразует поля ответа из `snake_case` в текущую модель и больше не принимает `ownerId` и `source: demo`.

Экран явно отправляет `range=5m` при первом открытии, обновляется раз в пять секунд без параллельных запросов и отменяет запрос при смене базы или окна. Роль `unknown` получает подпись «роль неизвестна». Если `nodes` пуст, экран сохраняет выбор окна и показывает «Метрик пока нет».

### Проверки используют рабочие границы системы

Интеграционные тесты API регистрируют пользователей через HTTP, создают базу через рабочий маршрут, вставляют снимки напрямую для подготовки состояния и запрашивают метрики через `httptest.Server` и `http.Client`. Они проверяют владельца, параметры окна, сортировку, агрегацию, смену `run_id`, пропуски и `null` CPU. Отдельный тест миграции не нужен: `api just test` применяет всю схему до запуска тестов.

Тесты фронтенда подменяют только HTTP-ответ. Они проверяют преобразование DTO, четыре окна, обновление без параллельных запросов, отмену, выбор нод, состояния загрузки, ошибки и пустого ответа, а также доступность графиков с клавиатуры.

## Risks / Trade-offs

- [После выкладки таблица остаётся пустой до появления импортера] → Пустой ответ и текст «Метрик пока нет» являются штатным состоянием; API не создаёт демонстрационные строки.
- [Текущая корзина может меняться между соседними запросами] → Точка привязана к началу корзины и обновляется на месте, а предыдущие точки сохраняют те же временные ключи.
- [Сложный SQL для приростов легко ошибиться на границе окна] → Запрос включает предшествующий снимок, а интеграционные тесты покрывают обычный прирост и смену `run_id`.
- [Старые строки пока не удаляются] → API скрывает данные старше семи дней; физическую очистку добавит change фоновой синхронизации.

## Migration Plan

1. Применить аддитивную миграцию с `valkey_node_metrics`.
2. Развернуть API с новым маршрутом чтения.
3. Развернуть фронтенд, который начинает опрашивать маршрут.

При откате API и фронтенда таблица может остаться в PostgreSQL: прежний код её не читает. Миграцию вниз используют только в локальном окружении, где потеря тестовых метрик допустима.
