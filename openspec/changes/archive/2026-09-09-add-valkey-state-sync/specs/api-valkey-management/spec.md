## MODIFIED Requirements

### Requirement: Чтение различает намерение и наблюдения

Список SHALL возвращать `{items: [...]}` только для текущего владельца и строк с `deleted_at IS NULL`, включая `deleting`, в порядке `created_at DESC, id DESC`. Карточка SHALL возвращать публичные настройки, адреса, маску, желаемые и применённые размеры и режим, поколения, версии, временные отметки, признаки восстановления и проверки сети. Вычисляемый `status` SHALL учитывать сначала подтверждённое удаление, затем запрос удаления, затем фазу. `is_stale` SHALL быть `true` при отсутствии `observed_at` или возрасте строго больше 60 секунд; `is_updating` SHALL означать неравенство поколений. HTTP API SHALL читать наблюдения, сохранённые фоновым импортом из `status` CR, и MUST NOT имитировать наблюдения, готовность или подтверждённое удаление. Доставка `spec` сама по себе MUST NOT менять подтверждённые значения.

#### Scenario: Синхронизация ещё не реализована

- **WHEN** фоновые циклы отсутствуют в запущенной версии API или ещё не запущены и после создания выполняются повторные `GET`-запросы
- **THEN** база остаётся `provisioning` с неприменённым поколением и без свежего наблюдения
- **AND** чтение не меняет строку инстанса

#### Scenario: Оператор ещё не подтвердил конфигурацию

- **WHEN** после создания доставка записала `spec`, но `status` ещё не содержит наблюдения оператора
- **THEN** база остаётся `provisioning` с неприменённым поколением и без свежего наблюдения
- **AND** повторные `GET`-запросы не меняют строку инстанса

#### Scenario: Импортировано подтверждение

- **WHEN** фоновый импорт сохранил допустимые поля применённой конфигурации, фазу и `observedAt` из CR
- **THEN** следующий `GET` возвращает сохранённое подтверждение и вычисляет `is_stale` по исходному `observedAt`

#### Scenario: Запоздалое наблюдение после запроса удаления

- **WHEN** у инстанса есть `deletion_requested_at`, но сохранённая фаза равна `running`
- **THEN** список и карточка показывают `deleting`
