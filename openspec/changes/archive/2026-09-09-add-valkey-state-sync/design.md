## Context

Причина изменения описана в `proposal.md`. HTTP уже записывает намерение и версии в `valkey_instances`. API использует уровень изоляции `READ COMMITTED`, общую рекомендательную блокировку PostgreSQL для пользовательских мутаций и блокировку строки существующего инстанса. В сетевых операциях эти транзакции участвовать не должны.

В `api/internal/config` уже есть `SyncInterval=5s`, но фоновые циклы не подключены. Общий контракт CR содержит `spec`, поля наблюдаемой и применённой конфигурации, `nodes` и `network`. `Secret` использует ключи `app-password-hash.<version>` из публичного пакета оператора. Условие восстановления называется `RecoveryRequired`; `RECOVERY_REQUIRED` в ТЗ обозначает смысл состояния, а не буквальное имя условия в коде.

Тестовое окружение API создаёт отдельную базу и однонодовый k3s с CRD и RBAC. API получает файл подключения к Kubernetes с ограниченными правами, файл подключения с административными правами принадлежит обвязке тестов. Оператор в этом окружении отсутствует.

## Goals / Non-Goals

Доставка должна сходиться к последнему принятому намерению после прерывания на любой границе PostgreSQL/Kubernetes. Импорт должен сохранять согласованный снимок подтверждений, не вмешиваясь в принятие HTTP-операций. Для удаления требуется сохраняемое различие между ожидаемым завершением CR и неожиданной потерей его истории.

В этой версии работает одна реплика API. Не вводим распределённое владение циклами и не заявляем поддержку нескольких одновременно пишущих экземпляров. Изменение числа реплик потребует отдельного решения. Поля HA доставляются по общему контракту, но выполнение HA текущим оператором не добавляется. Метрики, сбор данных из Valkey и планировщик `maintenance` остаются за пределами реализации.

## Decisions

### Два цикла внутри API

Новый пакет `api/internal/sync` получает через зависимости репозиторий, клиент Kubernetes, часы и средство записи логов. Он предоставляет отдельные операции одного прохода доставки и импорта и запуск обоих циклов. Точка входа API связывает их с общим контекстом процесса и ждёт остановки до закрытия базы.

`config.SyncInterval` меняется на `time.Second`. Первый проход выполняется сразу. Последующие запускает таймер с периодом в секунду; пока проход работает, второй проход этого цикла не начинается, пропущенные интервалы не превращаются в очередь. При медленной инфраструктуре интервал планирования не означает гарантированное применение за секунду. Тестовые часы управляют интервалом без реального ожидания.

Оба цикла независимы. Обращения имеют ограниченное время ожидания и замечают отмену контекста. Число одновременно обрабатываемых инстансов ограничено небольшим пулом, например четырьмя работниками, без параллельной доставки одного инстанса. Это не позволяет одному зависшему объекту задержать все остальные на сумму предельных сроков ожидания. Предельное время ожидания и размер пула фиксируются константами и проверяются при реализации на существующем лимите 32 инстанса.

Альтернатива с очередью и отдельным процессом добавила бы второй источник состояния выполнения. Для принятого объёма достаточно повторно читать PostgreSQL. Подписка на события Kubernetes тоже не заменяет сверку намерений БД; секундный опрос позволяет начать с одного механизма восстановления.

Ошибка подключения к Kubernetes отражается в логах и повторах, но не на готовности HTTP API. Невалидный локальный файл подключения к Kubernetes считается ошибкой конфигурации запуска; недоступный адрес корректно настроенного Kubernetes не блокирует запуск HTTP. Проверка доступности кластера не входит в конструктор маршрутизатора. При неизменном состоянии выполняются чтения без записи; ошибки журналируются без дампа объектов и секретных значений.

### Явное владение полями и идентичностью

Репозиторий получает отдельные операции для чтения всех неудалённых инстансов, свежего чтения одного намерения и записи наблюдений/служебных этапов. Запись всей GORM-модели через `Save` не используется. Фоновая запись не обновляет `updated_at` автоматически.

В `valkey_instances` добавляются поля, допускающие `NULL`: `kubernetes_namespace_uid`, `kubernetes_cr_uid` и `deletion_stage`. Существующие записи начинают без этих значений. После создания или проверки существующего объекта API сохраняет его UID; при принятии объекта проверяет имена, `slug`, `spec.instanceId`, метки `Namespace` и доступные отметки владельца. Совпадение имени без совпадения сохранённого UID недостаточно. В `Namespace` и входные объекты API записывает идентификаторы инстанса/владельца для проверки принадлежности.

UID привязывается под блокировкой строки: другая уже сохранённая идентичность вызывает восстановление, а не перезапись. После потерянного ответа `Create` повторный проход читает объект и проверяет принадлежность. Отсутствие ещё не сохранённого UID само по себе не разрешает принять произвольный объект.

Импорт использует строковую блокировку и явный список наблюдаемых колонок. Изменения применённых размеров и `deleted_at`, влияющие на резерв, выполняются с тем же порядком блокировок, что HTTP: сначала общая рекомендательная блокировка PostgreSQL, затем блокировка строки. Kubernetes читается до транзакции; внутри неё перечитывается БД и проверяется допустимость снимка. Такой порядок сохраняет общий расчёт квот и исключает инверсию блокировок. Записи, не влияющие на квоту, могут использовать только строковую блокировку.

### Доставка конфигурации

Проход выбирает `deleted_at IS NULL`, но перед каждым изменением перечитывает инстанс. Запрос удаления переводит обработку в протокол удаления. Сетевой вызов уже мог уйти до конкурентного HTTP `DELETE`; его результат остаётся под защитой отметки удаления, и следующий шаг обязан обработать удаление. Транзакция PostgreSQL не удерживается в ожидании Kubernetes.

При создании порядок такой: `Namespace` с метками, `Secret` с хешем `app`, CR с защитной отметкой удаления. Поля `spec` проецируются из строки: `instanceId`, `slug`, `mode`, `vcpu`, `ramGb`, `publicPort`, `whitelist`, `passwordVersion`, `desiredGeneration`. Публичный порт берётся из сохранённой строки, а не заново из переменных окружения. `name` и `maintenance` не входят в эту проекцию.

Для существующих объектов используем обновление с проверкой `resourceVersion` по прочитанному объекту, сохраняя `status`, `finalizers`, `annotations`, `ownerReferences` и чужие поля. На конфликте повторяем свежую сверку, включая чтение PostgreSQL. Число немедленных повторов ограничено; затем работу подхватывает следующий проход. При равных значениях записи нет. Обнаруженное поколение или версия пароля больше текущей БД не откатывается и требует разбора. Расхождение полей того же поколения исправляется из PostgreSQL только для принадлежащих API полей и при совпавшей идентичности.

Хеш новой версии сначала добавляется в `Secret`. Обновление CR разрешено после подтверждения наличия именно этого хеша в `Secret`. Существующий ключ той же версии с другим хешем считается повреждением, а не поводом молча заменить его. Служебные ключи и старые версии API не очищает. Если оператор уже удалил предыдущий хеш после ротации, устаревший проход не возвращает его: перед записью сверяет текущую версию БД, CR и `appliedPasswordVersion`.

Имя защитной отметки удаления и ключи маркировки, которые нужны обоим приложениям, выносятся в публичный пакет контракта, если сейчас объявлены только внутри оператора. API не импортирует `operator/internal`.

### Потеря объектов

Если CR существует, а `Secret` отсутствует, API отмечает восстановление и не создаёт пустую замену. При `credentialsInitialized=true` проверяется наличие полного служебного комплекта. API не генерирует служебные пароли.

Если CR отсутствует без подготовленного удаления, проверяем сохранённый UID, импортированные наблюдения и служебные поля `Secret`. Любой признак начавшейся обработки блокирует новое создание. Если прежнего CR не было, а `Secret` содержит только хеши `app`, продолжаем прерванное создание. `Namespace` в состоянии `Terminating` не восстанавливаем.

`is_recovery_required` объединяет подтверждённые причины доставки и условие `RecoveryRequired=True` из CR. Для этого служебная причина доставки сохраняется отдельно в поле, допускающем `NULL`: `sync_recovery_reason`; импорт не снимает её лишь потому, что оператор не установил условие. Доставка очищает свою причину после проверки восстановления исходной идентичности и необходимых полей; импорт очищает причину оператора только по допустимому снимку. Итоговый флаг пересчитывается под строковой блокировкой с учётом обеих причин. Для независимости записей сохраняется также `is_operator_recovery_required`.

`Namespace` с нашей маркировкой без строки БД обнаруживается при сверке списка `Namespace` и журналируется. Ошибка чтения БД прекращает такую проверку: отсутствие результата не означает отсутствие владельца. Автоматической уборки этих `Namespace` нет.

### Импорт наблюдений

Импорт проверяет принадлежность CR и `Namespace`, затем валидирует снимок до записи. `metadata.generation` не подменяет `spec.desiredGeneration` и `status.observedGeneration`. Подтверждённые версии не превышают соответствующие значения `spec` и свежей строки PostgreSQL. Более старое `observedAt`, меньшее `observedGeneration` или `appliedPasswordVersion` отклоняют снимок целиком; нельзя брать максимум поколений и при этом записывать старый применённый размер.

Пустой первоначальный `status` не является наблюдением. При одинаковом `observedAt` допускается согласованное изменение сети или других наблюдаемых полей, но время не освежается. Дополнительный курсор `resourceVersion` для порядка не вводим: версии Kubernetes считаются непрозрачными; проходы импорта не перекрываются и читают API напрямую. Снимок удаляемого CR не подтверждает новую рабочую конфигурацию. Импорт не изменяет `deleted_at`; уже удалённые строки пропускаются.

Добавляется таблица `valkey_instance_nodes` с уникальностью `(instance_id, ordinal)`, ролью, именем пода, `podUID`, `containerID`, `runId`, именем и UID ноды, `readiness` и временем наблюдения. Имя пода вычисляется по текущему контракту создаваемых оператором ресурсов из `slug` и `ordinal`. В одном снимке `ordinal` уникальны; допустимо до одного узла `single` или до трёх узлов HA. Принятый список заменяет прежний состав в той же транзакции. Пустой список в полноценном наблюдении очищает прежние ноды.

Таблица `valkey_instance_phase_events` хранит UUIDv7, `instance_id`, `from_phase`, `to_phase`, `reason` и `created_at`. Для перехода берём время `observedAt`; для `deleted` время PostgreSQL при подтверждении удаления. Событие создаётся только при смене фазы под блокировкой строки, без дубликатов при повторе. Первоначальная запись `provisioning` уже существует в инстансе: её повторное наблюдение не создаёт искусственный переход. Изменение `reason` при прежней фазе обновляет наблюдение без нового перехода. Пропущенные фазы не восстанавливаем.

Существующие структуры HTTP-ответов показывают импортированные поля без новых маршрутов. Ноды и история сохраняются для дальнейшего использования; их проверка напрямую в PostgreSQL разрешена, поскольку HTTP пока их не возвращает. Биллинг и пользовательский аудит остаются в существующих HTTP-транзакциях: импорт не создаёт повторного события принятия операции.

### Сохраняемый протокол удаления

Используем два этапа `cr_delete_prepared` и `namespace_delete_prepared`; завершение выражается `deleted_at`. Этапы изменяются только вперёд, при существующем `deletion_requested_at` и совпадающих UID.

1. При запросе удаления читаем существующий CR и `Namespace`. Проверяем принадлежность, UID и наличие защитной отметки удаления. Сохраняем UID и `cr_delete_prepared` до отправки `DELETE`. Затем повторно сверяем объекты и намерение и отправляем удаление с условиями совпадения `metadata.uid` и `metadata.resourceVersion`. Если CR уже штатно удаляется и содержит защитную отметку удаления, фиксируем тот же этап и ожидаем завершения.
2. Пока CR существует, `Namespace` и `Secret` сохраняются. API не снимает защиту удаления. Конфликты и потерянный ответ `DELETE` приводят к повторному чтению; повторное удаление того же UID допустимо.
3. `NotFound` CR при `cr_delete_prepared` означает завершение удаления ранее проверенного защищённого объекта. Проверяем исходный `Namespace`, сохраняем `namespace_delete_prepared` и удаляем `Namespace` с условием совпадения UID. Без подготовленного этапа пропавший CR с историей не даёт этого разрешения.
4. При `namespace_delete_prepared` ждём `NotFound` `Namespace` и в одной транзакции под общей блокировкой квот записываем `deleted_at` и событие `deleted`. Повторный проход ничего не добавляет. Объект с тем же именем и другим UID не считается подтверждением удаления и не удаляется.

Если создание отменено до первого CR и нет UID/наблюдений CR или служебных полей `Secret`, разрешён переход сразу в `namespace_delete_prepared` для проверенного `Namespace`. Когда ни `Namespace`, ни следов запуска не было, тот же путь завершает запись после подтверждённого `NotFound`. Если `Namespace` пропал у ранее работавшего инстанса вне подготовленного удаления, автоматически освобождать квоту по одному отсутствию нельзя.

Подготовленный этап записывается до `DELETE`, поэтому падение после отправленного запроса не теряет намерение. Сбой между подготовкой и отправкой разрешается повторным `DELETE`. Защитная отметка удаления ранее проверенного CR обеспечивает остановку процессов независимо от того, API или иной штатный клиент отправил запрос удаления. Принудительное снятие защиты удаления или обход этого протокола администратором не даёт доказательства остановки и не поддерживается как автоматическое восстановление. Отдельная таблица заданий не решила бы атомарность двух систем; сохраняем этапы непосредственно рядом с инстансом.

### Проверки на k3s

Окружение готовит существующий `scripts/test_environment.sh`. Он выделяет сетевой диапазон, сохраняет `K3S_DOCKER_GATEWAY` в `environment.env` и передаёт его в `docker-compose.test.yml` и `scripts/k3s_bootstrap.sh`. Подготовка k3s берёт заданный шлюз; чтение шлюза через `docker network inspect` остаётся запасным способом только для окружений без этой переменной. Новая тестовая обвязка использует подготовленные файлы подключения и адреса своего запуска, без собственных постоянных адресов или повторного определения шлюза.

Сценарии синхронизации располагаются в HTTP-наборе API и запускают реальные циклы с файлом подключения к Kubernetes с ограниченными правами. Пользователь регистрируется, а инстанс и изменения создаются через `httptest.Server` и `http.Client`. Обвязка проверяет `Namespace`/`Secret`/`spec` административным клиентом, подготавливает `status` и проверяет результат через HTTP. Прямые SQL-запросы используются для очистки, подготовки специальных гонок и проверки скрытой истории/нод.

Асинхронные результаты проверяются повторным чтением до ожидаемого состояния с ограниченным сроком ожидания. Успешный HTTP-ответ, создание CR или первое чтение карточки не заменяют ожидание требуемых полей. Это относится и к удалению: отдельно ждём исчезновения CR, затем `Namespace` и подтверждения в PostgreSQL. Проверка интервала планировщика управляемыми часами остаётся отдельной от ожидания реальных сетевых операций.

Административный клиент снимает защиту удаления только как явно заданный шаг имитации успешно закончившего оператора после проверки, что API оставил `Namespace` и `Secret`. Он не используется для скрытого обхода зависшего сценария. Секретные данные не печатаются даже при сравнении в упавшем тесте. Каждый сценарий останавливает свои циклы перед очисткой и удаляет только свои данные. Наборы с общей квотой одной БД идут последовательно.

Проверяем создание, увеличение и уменьшение размера, смену пароля, список разрешённых адресов, свежесть наблюдений, состояние сети и необходимость восстановления, ноды и переходы фаз; повторные проходы без лишних записей; прерывания до/после каждой сохраняемой стадии; конфликты `resourceVersion`; `DELETE` одновременно с доставкой и импортом; потерю CR/`Secret`; RBAC и недоступность Kubernetes. Ошибки транспорта воспроизводятся локально для конкретного тестового клиента, без остановки общего стенда; успешные запросы продолжают доходить до настоящего k3s. Гонки задаются управляемыми барьерами, время и интервалы проверяются через часы. Небольшой сценарий с реальным планировщиком проверяет подключение циклов при запуске; основные проверки не используют реальные секундные паузы.

Общий контракт получает дополнительные допустимые фазы и публичные константы, генерация обновляется из Go-маркеров. Регрессионные тесты оператора подтверждают, что первоначальная конфигурация, `UnsupportedChange` и удаление сохранили поведение. Тесты с подготовленным `status` доказывают только сторону API; применение изменения процессами Valkey ими не считается проверенным.

## Risks / Trade-offs

- Опрос раз в секунду увеличивает число чтений. Ограниченный пул, отсутствие записей при совпадении и ограничение времени ожидания удерживают нагрузку; интервал не является обещанием полной готовности за секунду.
- Статус оператора обновляется реже, чем API читает CR. Исходный `observedAt` сохраняет смысл свежести; частота свежих проверок оператором в рамках этого изменения не меняется.
- PostgreSQL и Kubernetes не имеют общей транзакции. Повторная сверка, проверки UID и сохраняемые этапы закрывают штатные прерывания, но не восстанавливают историю после административного удаления защищённых объектов.
- Новый API доставит изменения, которые текущий оператор не выполняет. Они останутся незавершёнными с `UnsupportedChange` до следующего этапа оператора; API не подтверждает их самостоятельно.

## Migration Plan

1. Добавить миграцию `goose`, которая расширяет схему с допускающими `NULL` полями UID и этапа, причинами восстановления и новыми таблицами. Булевы поля получают значение `false` по умолчанию; существующий `is_recovery_required` при миграции сохраняется как действующая причина до проверки, а не обнуляется. Таблицы создаются до отдельно объявленных внешних ключей и индексов; `AutoMigrate` не используется. Применение выполняется с `-allow-missing`.
2. Расширить Go-контракт фаз и общих констант, сгенерировать CRD/`DeepCopy` и установить CRD до запуска использующего его API. Права API не расширяются на `status` или поды. Старый оператор остаётся совместимым.
3. Подключить циклы к API, проверить существующие файлы подключения к Kubernetes для разработки и рабочего окружения и зависимости остановки. Обновить значение `SyncInterval` и соответствующие фрагменты `SYSTEM.md` и `SYSTEM-DETAIL.md` на 1 секунду без переноса в это изменение других запланированных подсистем.
4. Выполнить `just test` в каталоге `api`, проверки генерации и полный набор `just test` в каталоге `operator` при изменении общего контракта, а также применимые линтинг и сборку. Новые сценарии автоматически входят в корневой `just test` и действующее задание CI `test-api`; проверки общего контракта также проходят через `test-operator`. Существующие сроки ожидания заданий составляют 20 минут для API и 30 минут для оператора, включая подготовку окружения.
5. При откате вернуть предыдущий бинарник API, оставив аддитивную схему и CRD. Оператор продолжит уже доставленные операции; новые намерения дождутся восстановления версии с синхронизацией. Обратная миграция после появления истории не используется для рабочего отката.
