## Context

См. [proposal.md](proposal.md). Оператор уже запрашивает `metrics.k8s.io/v1beta1` и считает CPU необязательным полем снимка. Его RBAC разрешает `get` и `list` для `pods.metrics.k8s.io`. Production-развёртывание устанавливает Gateway API, Envoy Gateway и cert-manager, но не создаёт Metrics Server и не проверяет агрегированный API.

API возвращает равномерные интервалы: 10 секунд для окна 5 минут, 1 минуту для часа, 5 минут для суток и 30 минут для недели. Пустой интервал содержит `null`. `MetricChart` передаёт эти значения в Mantine `AreaChart` с `connectNulls={false}`, поэтому любой пустой интервал разрывает ряд.

## Goals / Non-Goals

**Goals:**

- сделать получение CPU обязательной проверкой production-развёртывания;
- сохранить повторяемость развёртывания в новом и уже работающем кластере;
- соединять пропуск между измерениями длительностью не больше одной минуты только на уровне отрисовки всех четырёх графиков;
- сохранить различие между полученным и отсутствующим измерением во всех текстовых представлениях.

**Non-Goals:**

- делать доступность Metrics Server условием работы оператора после завершения выпуска;
- менять частоту сбора, серверную агрегацию, HTTP-ответ или данные PostgreSQL;
- заполнять пропуски, между границами которых прошло больше одной минуты;
- добавлять в интерфейс отдельное обозначение вычисленного участка.

## Decisions

### Metrics Server устанавливается официальным Helm chart

Сценарий `scripts/deploy_kubernetes.sh` установит официальный chart `metrics-server` версии `3.14.0` с Metrics Server `v0.9.0`. Эта версия поддерживает используемый production-кластер Kubernetes 1.34. Релиз размещается в `kube-system` и использует один экземпляр, поскольку текущий кластер однонодовый. Версия chart задаётся рядом с версиями Gateway API, Envoy Gateway и cert-manager.

`helm upgrade --install` сохраняет повторяемость первого и последующих выпусков. Отдельный манифест, скопированный из выпуска Metrics Server, потребовал бы вручную переносить исправления chart. Ссылка `releases/latest` не подходит, потому что один и тот же SHA приложения мог бы разворачивать разные версии инфраструктуры.

Metrics Server работает с `hostNetwork` и `containerPort: 4443`: управляемый control plane не достигает Service CIDR, а стандартный порт `10250` на ноде занят kubelet. Единственный экземпляр обновляется с `maxSurge: 0` и `maxUnavailable: 1`. Старый Pod освобождает порт ноды до запуска нового, поэтому изменение CA или шаблона не блокирует rollout из-за занятого `4443`. `APIService` направляется в Service `metrics-server-control-plane` типа `ExternalName` с адресом `cert-manager-webhook.valkey.h3llo-demo.com` и портом `4443`. Перед развёртыванием этот адрес уже проверяется на точное совпадение с внутренними адресами всех Node. Поэтому control plane подключается к Metrics Server через достижимый адрес ноды.

Для обращения Metrics Server к kubelet выбирается тип адреса `Hostname`. Сценарий строит `hostAliases` из имён и внутренних адресов текущих Node, поэтому имя совпадает с DNS SAN сертификата kubelet без зависимости от кластерного DNS.

Проверка TLS kubelet не отключается. CA не хранится в репозитории: набор PEM-сертификатов поступает из обновляемого секрета окружения GitHub `PRODUCTION_KUBELET_CA`. Сценарий до обращения к Kubernetes отклоняет посторонние данные и проверяет цепочку, признак CA и запас срока действия каждого сертификата не менее 30 дней. Затем он создаёт ConfigMap `metrics-server-kubelet-ca` и добавляет SHA-256 всего набора в аннотацию шаблона `Pod`. Новое значение секрета меняет аннотацию и запускает замену `Pod`, поэтому ротация не зависит от изменения chart или исходного кода.

Перед поэтапной ротацией CA или заменой ноды оператор production добавляет новый CA к прежнему в `PRODUCTION_KUBELET_CA`, обновляет служебную DNS-запись и запускает выпуск. После перевода всех нод старый CA удаляется из набора следующим выпуском. Готовность Deployment, `APIService` и запрос свежего CPU проверяют соответствие набора живому kubelet. Повреждённый, просроченный или не совпадающий с kubelet набор завершает выпуск с диагностикой и не допускает запись успешного SHA. Параметр `--kubelet-insecure-tls` такую ошибку не скрывает.

### Развёртывание проверяет не только готовность Pod Metrics Server

После установки процесс ждёт условие `Available` у `APIService` `v1beta1.metrics.k8s.io`. После готовности оператора он от имени его учётной записи запрашивает `PodMetrics` работающего `operator-0` и принимает ответ только со свежей отметкой времени и неотрицательным CPU контейнера. Проверка повторяется до отдельного конечного срока, потому что первая метрика появляется позже готовности Deployment.

Так проверяется вся цепочка: регистрация агрегированного API, доступ Metrics Server к kubelet и RBAC оператора. Проверка только Deployment могла бы пройти при ошибке сбора с ноды, а отдельный `kubectl auth can-i` не подтвердил бы получение данных.

Сценарий развёртывания выполняет эту проверку до подготовки файла подключения API и до записи успешного SHA. Его автоматический тест проверяет команду установки, закреплённую версию, сетевой маршрут, ожидание APIService, запрос от имени оператора, отказ при истечении срока и замену контрольной суммы при ротации CA.

### Короткий пропуск заполняется отдельным значением только для отрисовки

Чистая функция подготовки графика обрабатывает каждый набор «нода + метрика» независимо и находит последовательности `null`. Для последовательности с известными значениями с обеих сторон функция вычитает `collectedAt` предыдущего фактического измерения из `collectedAt` следующего фактического измерения. Если разница положительна и не превышает 60 секунд, функция рассчитывает для каждой пустой точки линейное значение между известными границами с учётом её метки времени. Во всех остальных случаях значение для отрисовки остаётся `null`. Одна функция применяется к памяти, CPU, подключениям и операциям.

Исходное поле ряда сохраняется. График получает отдельный ключ со значением для отрисовки, а подсказка, сводка и клавиатурная навигация продолжают читать исходный ключ. Поэтому линия проходит через короткий пропуск, но интерфейс не сообщает вычисленное число как измеренное. `connectNulls` остаётся выключенным: интервалы между известными измерениями дольше одной минуты и незамкнутые пропуски по-прежнему разрывают площадь и линию.

Глобальный `connectNulls={true}` не подходит, поскольку он соединил бы и многоминутное отсутствие данных. Заполнение на стороне API тоже не подходит: оно изменило бы контракт для всех клиентов и скрыло бы происхождение значения.

### Порог равен одной минуте между измерениями для любого окна

Порог сравнивается с `collectedAt` известных значений по обе стороны пропуска, а не с количеством пустых точек и не с `stepSeconds`. Например, предыдущее измерение в `12:00:00` и следующее в `12:01:00` соединяются. Если следующее измерение имеет метку `12:01:00.001`, пропуск остаётся разрывом. Граница 60 секунд включается в короткий пропуск.

В окне 5 минут с шагом 10 секунд могут соединиться несколько пустых точек, если известные границы находятся не дальше минуты друг от друга. В окне с шагом 1 минута пропуск одной точки размещает известные границы в 120 секундах друг от друга и остаётся разрывом. Более крупный масштаб также не расширяет допустимый интервал между фактическими измерениями.

Неразбираемая или не возрастающая метка времени не используется для интерполяции. Такой участок остаётся разрывом, чтобы повреждённые данные не превращались в правдоподобную линию.

## Risks / Trade-offs

- [Первая метрика Metrics Server появляется не сразу] → Использовать ограниченное ожидание наблюдаемого `PodMetrics`, а не фиксированную паузу.
- [CA kubelet повреждён, близок к окончанию срока или не соответствует новой ноде] → Проверять файл до изменения кластера, хранить его в обновляемом параметре production, перезапускать Metrics Server по контрольной сумме и подтверждать новый CA запросом живой метрики.
- [Управляемый control plane не достигает ClusterIP Metrics Server] → Использовать `hostNetwork` с незанятым портом `4443` и направлять `APIService` через проверенную служебную DNS-запись на внутренний адрес ноды.
- [Установка новой зависимости увеличивает потребление однонодового кластера] → Оставить один экземпляр с ресурсами официального chart и учитывать его при проверке доступной ёмкости кластера.
- [Вычисленное значение может попасть в подсказку библиотеки графиков] → Хранить исходные и отрисовочные ключи раздельно и проверять подсказку и клавиатурную навигацию компонентными тестами.
- [Ошибочная метка времени может неверно сократить интервал между измерениями] → Интерполировать только при разобранных строго возрастающих метках обеих границ и пустых точек.
- [Сглаженная кривая создаёт выброс возле вычисленной точки] → Использовать линейную интерполяцию между соседними значениями и сохранить существующую проверку отсутствия дополнительных пиков.

## Migration Plan

1. Настроить `PRODUCTION_KUBELET_CA`, добавить установку Metrics Server, маршрут `metrics-server-control-plane` и проверки `metrics.k8s.io` в production-сценарий, затем обновить его автоматический тест.
2. Добавить подготовку значений для отрисовки всех четырёх графиков и тесты порога 60 секунд, более долгих, краевых и временно некорректных пропусков.
3. Запустить затронутые проверки сценария развёртывания и клиентского приложения.
4. Отправить изменение в `main`. Обычное production-развёртывание установит Metrics Server в текущий кластер и дождётся первой метрики до запуска серверной части выпуска.

При откате приложения Metrics Server можно оставить в кластере: прежний оператор совместим с доступным `metrics.k8s.io`. Откат клиентского приложения вернёт разрывы на всех `null`, не меняя сохранённые данные. Если требуется удалить Metrics Server, оператор продолжит работу с `cpuMillicores=null`.
