## Context

Мотивация и область изменения описаны в proposal.md. Источники требований: SYSTEM.md, разделы 3, 6, 7, 9, 13 и 14, и SYSTEM-DETAIL.md, разделы «Контракт и объекты оператора», «Три цикла», «Readiness и публичная готовность», «Первый запуск» и «Поды на недоступной ноде».

В репозитории есть manager с Lease, пустой reconciler, минимальная CRD, envtest и dev k3s с двумя Envoy. Полноценного контракта Secret и клиента Valkey ещё нет. Design необходим из-за расширения публичного контракта и требований к безопасной остановке.

## Goals / Non-Goals

Реализуем первоначальную конфигурацию single, её наблюдение и удаление. Операции переживают рестарт без состояния, существующего только в памяти. Настоящие тесты подают намерение напрямую через Kubernetes.

Автоматическая замена входит только после доказанной остановки прежнего процесса. Автоматическое лечение BUSY, SIGSTOP и иных зависаний откладывается; явное удаление инстанса при этом обязано работать по общей процедуре остановки. Не реализуем полный алгоритм HA или перенос оператора при потере worker-ноды. Проверки этих областей из SYSTEM.md остаются будущими требованиями v1.

## Decisions

### Контракт и снимок принятой конфигурации

Добавляем поля spec из SYSTEM-DETAIL.md: instanceId, slug, mode, vcpu, ramGb, publicPort, whitelist, passwordVersion, desiredGeneration. Валидация использует сетку размеров и ограничения SYSTEM.md. Идентификаторы остаются неизменяемыми; имя CR равно slug, namespace равен `valkey-<slug>`. CRD допускает известные режимы single/ha, но контроллер диагностирует ha как неподдерживаемый без создания ресурсов.

До первого изменения дочерних ресурсов контроллер сохраняет в status снимок принятой первоначальной конфигурации и её desiredGeneration. Снимок не содержит хешей или паролей. Он нужен, чтобы продолжить создание и обслуживать исходную конфигурацию, если spec изменился до готовности или после неё. Альтернатива с запретом обновления всей spec в CRD затруднила бы дальнейшее развитие API.

При отличии spec от снимка condition `UnsupportedChange` описывает неподдерживаемое изменение; контроллер продолжает наблюдение и безопасное восстановление исходной конфигурации, не меняет размер, пароль или сеть и не подтверждает новое поколение. Возврат исходных настроек позволяет убрать condition. Удаление имеет приоритет даже при таком несовпадении.

`status.observedGeneration` относится к `spec.desiredGeneration`, а не к `metadata.generation`. Для conditions объектов Kubernetes проверяется их собственная metadata.generation. Эти два счётчика тестируются с намеренно разными значениями. `applied`, `appliedPasswordVersion`, флаги инициализации, nodes, network и deletion добавляются по мере реализованного поведения.

### Secret

Имя Secret: `<slug>-auth`, тип Opaque. Логическая коллекция appPasswordHashes из SYSTEM-DETAIL.md хранится в `data` как отдельные ключи `app-password-hash.<version>` с SHA-256 в виде 64 строчных hex-символов. Служебные ключи: `operator-password`, `replica-password`, `health-password`, `users.acl`. Формат описывается в публичном контракте, чтобы API не импортировал внутренности оператора.

API или тест создаёт namespace с метками инстанса и пользователя, Secret с хешем, затем CR с finalizer. Оператор не создаёт отсутствующий Secret. Он добавляет ownerReference на CR, независимо генерирует каждый служебный пароль из 24 случайных байт в base64url без padding, сохраняет весь комплект и ACL одной записью, затем ставит credentialsInitialized. Все обновления проверяют resourceVersion и сохраняют неизвестные поля и доставленные версии хешей. При конфликте заново читаются CR и Secret.

При рестарте до записи status полный сохранённый комплект переиспользуется. Частичный комплект служебных полей считается повреждением и требует восстановления; оператор не достраивает его догадками. После credentialsInitialized потеря Secret или любого обязательного поля даёт RECOVERY_REQUIRED. Для принятой конфигурации требуется её версия хеша; наличие более новой версии не переключает ACL. В этом изменении старые хеши не очищаются, поскольку ротация не реализована.

### Управление процессом

Предметная логика остаётся в `operator/internal/operator`, протокол Valkey в `operator/internal/valkey`. Клиент valkey-go имеет ограниченные таймауты и отключённые автоматические повторы изменяющих команд. После получения Lease и перед использованием каждого процесса оператор завершает AUTH, выполняет CLIENT KILL USER operator SKIPME YES и перечитывает состояние. AUTH и изменения не объединяются в pipeline. Потеря Lease отменяет задачи, закрывает соединения и завершает процесс.

Создаём неизменяемую ConfigMap с digest содержимого в имени, StatefulSet OnDelete с одной репликой, headless и primary Services, NetworkPolicy. Шаблон и настройки памяти, readiness, emptyDir в памяти и контейнерный restartPolicy Never соответствуют SYSTEM-DETAIL.md. Liveness не добавляется. Изменение VALKEY_IMAGE у существующего StatefulSet даёт RECOVERY_REQUIRED и не запускает обновление образа.

Новый процесс запускается master с app off. До включения app сохраняем Pod UID, container ID, run_id, имя и UID Node и ставим Pod finalizer process-stopped. Метка primary выдаётся только проверенному процессу. Если результат ACL-команды неизвестен, следующий проход читает реальное состояние после очистки старых административных соединений.

Обычное завершение контейнера сохраняется в CR как доказательство остановки конкретного процесса до снятия Pod finalizer и замены Pod. Неожиданная смена контейнера без доказательства старого завершения блокирует клиентский доступ нового процесса. NotReady, исчезновение Pod и таймаут не считаются доказательством. Отсутствие Node с сохранённым UID принимается только по правилу v1 из SYSTEM-DETAIL.md; проверка UID защищает от повторного использования имени. Недоступный Kubernetes не равен NotFound.

### Сеть и допуск клиента

Для single создаётся только primary listener/TCPRoute; адрес -ro и PDB отсутствуют. Изменение общего Gateway использует проверку resourceVersion и сохраняет listeners соседей. Whitelist выключен: SecurityPolicy отсутствует. Включён: defaultAction Deny; пустой список запрещает всех. Listener ограничивает namespace через метку инстанса.

Проверяем актуальные conditions Gateway, TCPRoute, SecurityPolicy и общей ClientTrafficPolicy, сертификат и соответствие домена. На prod требуется Ready у Certificate; на dev используется mkcert. Затем через port-forward читаем активные config_dump и certs обеих реплик Envoy: SNI, backend, RBAC, сертификат, idle timeout. Warming, неизвестный формат, один успешный ответ или неоднозначный состав дают pending/unknown, не verified.

Отпечаток содержит только настройки инстанса, не всё поколение Gateway и не Pod IP Valkey. Проверка повторно сверяет состав Envoy и целевые настройки перед сохранением успеха. Дамп не попадает в логи или CR. Снимок Envoy переиспользуется в одном цикле между инстансами.

После verified включаем app с нужным ACL, назначаем роль и проверяем актуальные EndpointSlice на текущий Pod UID/IP. Только затем ставим initialized, running и подтверждения конфигурации. Отдельный внешний тест проверяет TLS/SNI/AUTH; оператор не обещает измерение доступности из интернета.

### Фазы и удаление

Время зависит от Clock; интервалы берутся из закреплённых констант. До первой публичной готовности provisioning, после ProvisionTimeout от создания CR терминальный error; объекты сохраняются для разбора и удаления. Рестарт таймер не обнуляет. После первого успеха потеря primary или подтверждённая поломка сети даёт unavailable; восстановление проверок возвращает running. Неудача admin API при неизменном ранее подтверждённом составе и сети сохраняет последнее подтверждение с unknown по правилам SYSTEM-DETAIL.md. Heartbeat обновляется по свежим наблюдениям, отдельно от сверки Envoy. Метрики не собираются.

При deletionTimestamp сначала сохраняется стадия удаления. Оператор убирает свой listener, маршруты и политики, выключает app и закрывает его существующие соединения на доступных процессах, переводит StatefulSet в ноль и ждёт доказательства остановки всех известных процессов. Недоступность Valkey не мешает запросить штатную остановку через Kubernetes, но не разрешает снять finalizer без доказательства. Secret сохраняется до конца. Стадии и подтверждения привязаны к идентичностям и переживают рестарт; повтор не создаёт ресурсы заново. После остановки снимаются Pod finalizers и finalizer CR. Namespace удаляет API или тест после NotFound CR и проверки удаления дочерних объектов.

### Проверки

Unit-тесты проверяют переходы, расчёты и разбор обезличенных ответов. Envtest проверяет настоящий resourceVersion, status subresource, конфликты, watchers и идемпотентность; неизменный проход вне срока heartbeat не пишет status. Watch Secret и дочерних объектов дополняется периодической проверкой внешнего состояния.

`just test-full` использует k3s и запускает только одну копию оператора. Тестовая сторона подаёт входные объекты с правами API, наблюдает кластер с тестовыми правами и подключается снаружи по TLS/SNI с проверкой CA. Два клиента с различимыми адресами проверяют whitelist; port-forward к Valkey не заменяет эту проверку. Тестовые пароли создаются в памяти. Очистка ограничена namespace и ресурсами текущего запуска, проходит через штатное удаление CR. При неудаче сохраняются обезличенная диагностика и явная ошибка, а не принудительное снятие finalizers.

## Risks / Trade-offs

- Недоступность ContainerRestartRules ломает подтверждение остановки: до основной реализации проверяем приём шаблона и отсутствие перезапуска контейнера при остановленном операторе. Отрицательный результат блокирует запуск этого изменения.
- Формат Envoy зависит от закреплённой версии: первым этапом фиксируем обезличенные ответы и точные проверки активных полей; неизвестный формат не считается успехом.
- Host-процесс оператора должен обращаться к Pod IP и соблюдать принятую NetworkPolicy: проверяем dev-сетевой путь на стенде, не ослабляя изоляцию ради теста.
- Снимок конфигурации расширяет status, зато позволяет пережить преждевременное обновление spec. Его назначение и жизненный цикл фиксируются до реализации дальнейших операций.
- Автоматическое лечение зависаний отложено: такой single может оставаться unavailable до восстановления процесса или явного удаления. Это ограничение этапа указывается в тестовом отчёте.

## Migration Plan

Сначала генерируются и устанавливаются CRD/RBAC, затем оператор, затем будущий код API. Минимальные CR старого каркаса не должны получить случайные рабочие значения по умолчанию: используем явную валидацию полноты в контроллере и совместимую аддитивную схему. Старые объекты остаются без workload до доставки полного намерения.

Откат к пустому оператору не является штатным откатом при активных инстансах: он перестанет обслуживать finalizers. До такого отката нужно штатно удалить тестовые инстансы совместимой версией. Production-готовность всего сервиса этим изменением не подтверждается.
