## Проверка 9 сентября 2026 года

### Локальный стенд

Замер выполнен на машине с 32 логическими CPU и 63 921 MiB RAM. Dev и четыре
test-окружения готовились одновременно. В них работали 13 нод k3s и 14 внешних
Docker-контейнеров. `docker stats` опрашивался раз в секунду от начала
подготовки до готовности последнего кластера.

| Окружение | Ноды | Время подготовки |
| --- | ---: | ---: |
| api | 1 | 14,5 с |
| operator | 3 | 158,3 с |
| integration | 3 | 100,3 с |
| e2e | 3 | 138,1 с |

Пиковое суммарное потребление внешних контейнеров составило 5 797,3 MiB RAM и
348,5% CPU, то есть около 3,5 логического CPU. После готовности во всех четырёх
test-кластерах было `unscheduled_or_not_running=0`.

У контейнера Envoy задано `100m/512Mi`, у Envoy Gateway `100m/256Mi`, у
shutdown-manager `10m/32Mi`. CoreDNS и metrics-server запрашивают по
`100m/70Mi`. Все pod с этими requests получили ноду. После замера test-кластеры,
их тома, сети и три test-базы удалены; dev-кластер и dev-база сохранились.

Корневой `just test` при работающем `just run` завершился успешно и не изменил
контрольный объект или строки dev-базы. Повторный запуск после сетевых правок
тоже прошёл: по времени изменения журналов web занял около 2,8 с, API 62,3 с,
operator 292,3 с. В operator вошли envtest и `TestSingleLifecycle`; сам
lifecycle занял 109 с. Разница между полным временем и временем Go-тестов
приходится на подготовку k3s, Helm и загрузку образов.

### GitHub Actions

Замер текущей реализации на GitHub Actions ещё не выполнен: изменения находятся
только в рабочем дереве и не запускались GitHub runner. Теоретическую оценку
runner нельзя подставлять вместо фактических RAM, CPU и времени jobs. После
первого `push` сюда нужно добавить длительность `test-api`, `test-operator` и
`test-web`, пиковые ресурсы соответствующих стендов и результат размещения pod.
