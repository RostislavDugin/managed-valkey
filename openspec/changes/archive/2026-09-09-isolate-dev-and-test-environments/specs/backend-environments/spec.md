## MODIFIED Requirements

### Requirement: Dev-сервисы доступны только с хоста

PostgreSQL SHALL использовать порт `5432` внутри контейнера и публиковаться на `127.0.0.1:${POSTGRES_PORT}`. Kubernetes API `6443` и NodePort шлюза `31379` SHALL публиковаться только на `127.0.0.1`. Dev SHALL сохранять стабильные порты; тестовые окружения SHALL получать собственные свободные порты и передавать фактические адреса потребителям.

#### Scenario: Подключение локального API

- **WHEN** API запускается на хосте с `DATABASE_URL`, указывающим на `127.0.0.1:${POSTGRES_PORT}`
- **THEN** API подключается к PostgreSQL без адреса внутренней сети compose

#### Scenario: Одновременный запуск окружений

- **WHEN** dev и тестовые кластеры запущены одновременно
- **THEN** их опубликованные порты не конфликтуют, а тесты используют адрес своего окружения

### Requirement: Dev-кластер готовится на хосте

`scripts/k3s_bootstrap.sh` SHALL запускать системные `kubectl`, `helm` и `mkcert` на хосте для выбранного окружения. Для полного стенда скрипт SHALL получить административный kubeconfig из выбранного `k3s-server`, установить Gateway API `v1.5.1`, Envoy Gateway `v1.8.4`, CRD и RBAC Managed Valkey, инфраструктуру, TLS Secret и NodePort `31379`. Облегчённый стенд API SHALL устанавливать CRD и RBAC без оператора, Envoy и сертификатов публичного доступа. Подготовка MUST NOT менять соседний кластер или его маршруты.

#### Scenario: Повторный bootstrap

- **WHEN** разработчик дважды запускает `scripts/k3s_bootstrap.sh` для dev
- **THEN** оба запуска завершаются успешно и не удаляют прикладные ресурсы

#### Scenario: Незавершённая операция Helm

- **WHEN** релиз Envoy Gateway выбранного окружения имеет состояние `pending-install`, `pending-upgrade` или `pending-rollback`
- **THEN** bootstrap удаляет незавершённую установку либо откатывает релиз к последней готовой ревизии и продолжает обновление только в этом окружении

#### Scenario: Подготовка API-тестов

- **WHEN** готовится однонодовый API-стенд
- **THEN** Kubernetes принимает Namespace, Secret и ValkeyInstance без запуска оператора и подов Valkey

### Requirement: Приложения получают отдельные kubeconfig

Bootstrap SHALL создать отдельные kubeconfig API и оператора с режимом `0600` и фактическим адресом выбранного кластера. Файлы SHALL лежать в отдельном каталоге окружения под `tmp/k3s`; тестовые файлы SHALL также различаться по запуску. Административный kubeconfig MUST NOT использоваться приложениями. API MUST NOT иметь прав на `ValkeyInstance/status` и поды. Тестовый административный клиент SHALL использоваться только обвязкой для подготовки, проверки и очистки своего окружения.

#### Scenario: Проверка прав API

- **WHEN** разработчик выполняет `kubectl auth can-i` с kubeconfig API
- **THEN** API может создавать ValkeyInstance, но не может обновлять подресурс status или читать поды

#### Scenario: Независимые подключения

- **WHEN** одновременно готовятся dev и тесты
- **THEN** их kubeconfig не перезаписывают друг друга и каждый указывает на свой кластер

### Requirement: API и оператор запускаются на хосте

`api/Justfile` SHALL загружать корневой `.env`, применять миграции перед `just run` и запускать API через `go run`. `operator/Justfile` SHALL загружать `.env`, готовить CRD и RBAC и запускать оператор через `go run` с отдельным kubeconfig выбранного dev-кластера. Явно переданные параметры тестового окружения MUST иметь приоритет над dev-настройками. Локальные процессы SHALL писать логи в stdout без обязательного `VL_OTLP_URL`.

#### Scenario: Локальная разработка backend

- **WHEN** инфраструктура и bootstrap готовы, а разработчик запускает `just run` в каталогах `api` и `operator`
- **THEN** оба процесса работают на хосте и отвечают на свои проверки состояния

#### Scenario: Тестовые параметры

- **WHEN** тестовый запуск передаёт свои DATABASE_URL и kubeconfig
- **THEN** загрузка корневого `.env` не переключает процессы на dev

### Requirement: Тестовая база создаётся по требованию

`api just test` SHALL подготовить PostgreSQL, создать выделенную базу запуска, применить миграции с `goose -allow-missing` и запустить тесты. API, общие интеграционные и e2e-наборы MUST NOT использовать одну базу между собой или dev-базу. Локально эти базы SHALL поддерживаться одним сервером PostgreSQL. Dev compose MUST NOT монтировать init-скрипт PostgreSQL.

#### Scenario: Первый запуск тестов

- **WHEN** разработчик выполняет `api just test` без подготовленной тестовой базы
- **THEN** команда готовит сервер и базу, применяет миграции и выполняет тесты без ручной подготовки

#### Scenario: Параллельная проверка квот

- **WHEN** API-тесты проверяют общую квоту одновременно с интеграционными или e2e-тестами
- **THEN** записи соседнего набора не участвуют в расчёте квоты и не удаляются при очистке

### Requirement: Локальная разработка запускается через корневой Justfile

Корневой `just run` SHALL запускать dev-инфраструктуру, ждать её готовности, выполнять bootstrap и миграции, затем запускать оператор, API и фронтенд на хосте. Повторный запуск SHALL сохранять dev-данные. Завершение команды SHALL останавливать принадлежащие ей процессы приложений и сохранять инфраструктуру. Корневой `just down` SHALL останавливать dev-инфраструктуру без удаления её данных и без воздействия на тестовые окружения.

#### Scenario: Запуск локальной разработки

- **WHEN** разработчик с установленными инструментами и локальной конфигурацией выполняет `just run`
- **THEN** команда сама готовит dev-кластер и базу и запускает все приложения без отдельного ручного bootstrap

#### Scenario: Остановка и повторный запуск

- **WHEN** разработчик завершает `just run` через Ctrl+C и запускает его снова
- **THEN** прежние процессы приложения завершены, dev-данные сохранены, новая копия оператора не работает одновременно с прежней

#### Scenario: Ошибка приложения

- **WHEN** один из запущенных процессов неожиданно завершается
- **THEN** команда завершает остальные принадлежащие ей процессы и сообщает ошибку, сохраняя dev-инфраструктуру

## ADDED Requirements

### Requirement: Пять независимых окружений Kubernetes

Проект SHALL поддерживать постоянный трёхнодовый dev-кластер и отдельные кластеры для API-тестов (одна нода), оператора (три ноды), API + operator (три ноды) и Playwright e2e (три ноды). Трёхнодовый кластер SHALL состоять из одного server и двух agents. Подготовка SHALL использовать общий параметризованный шаблон. Окружения SHALL иметь независимые Compose projects, тома, токены и сетевые диапазоны; маршруты к Pod IP MUST NOT пересекаться при одновременной работе на одном хосте.

#### Scenario: Полный локальный запуск

- **WHEN** dev и четыре тестовых окружения подняты одновременно
- **THEN** работают пять независимых Kubernetes API и 13 нод, а оператор каждого полного стенда обрабатывает только CR своего кластера

#### Scenario: Очистка тестового кластера

- **WHEN** тестовый запуск удаляет свой кластер и тома
- **THEN** dev-инстансы, dev-база и соседние тестовые окружения сохраняются
