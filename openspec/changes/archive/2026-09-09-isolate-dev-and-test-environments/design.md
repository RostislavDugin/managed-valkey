## Context

Мотивация описана в proposal.md. Сейчас `docker-compose.dev.yml` задаёт один project, PostgreSQL и три ноды k3s. Bootstrap использует фиксированную Docker-сеть, устанавливает host-маршруты к Pod CIDR и сохраняет kubeconfig в `tmp/k3s`. Корневой `just run` запускает API и Vite, но не оператор.

`operator/just test-full` использует dev-кластер, общий Gateway и тестовый manager с отключённым leader election. Manager наблюдает CR всего кластера. Его тесты используют фиксированные адреса Docker-клиентов и порт Envoy. `_generate` переписывает отслеживаемые файлы перед запуском тестов.

API-тесты используют `managed_valkey_test`; общие квоты делают параллельные независимые запуски в одной базе некорректными. Синхронизации PostgreSQL ↔ CR и сквозных API + operator / Playwright-тестов пока нет.

## Goals / Non-Goals

Цель: запускать работу разработчика и независимые наборы тестов одновременно, сохраняя обычную кластерную область действия оператора. Все созданные тестовым запуском ресурсы должны иметь определённого владельца, чтобы очистка не зависела от широких масок имён.

В change входят инфраструктура пяти окружений, перенос существующих тестов, команды и CI. Реализация синхронизации, новых операций Valkey и отсутствующих сквозных пользовательских сценариев остаётся следующим изменениям. Подготовленный e2e-кластер сам по себе не считается e2e-проверкой.

## Decisions

### Окружения из одного шаблона

| Назначение | Топология | Прикладные компоненты | PostgreSQL |
| --- | --- | --- | --- |
| dev | server + 2 agents | оператор, API и Vite на хосте; Envoy в k3s | постоянная dev-база |
| api | server | CRD и RBAC; тестируемый API; административный клиент обвязки | база запуска |
| operator | server + 2 agents | тестовый manager, Envoy, Valkey | не нужна |
| integration | server + 2 agents | API с синхронизацией, оператор, Envoy, Valkey после подключения набора | база запуска |
| e2e | server + 2 agents | полный стек с Caddy и собранным web, Playwright после подключения набора | база запуска |

Сохраняем dev Compose как точку прямого запуска инфраструктуры. Общие определения k3s и скрипты подготовки переиспользуются тестовыми конфигурациями; полные копии bootstrap для каждого набора не создаются. Трёхнодовый стенд имеет один control plane, а не три server. Для API не устанавливаем Envoy и Gateway API, не настраиваем прямые host-маршруты к Pod IP. Необязательные встроенные компоненты k3s в этом профиле можно выключить при сохранении Namespace lifecycle и поведения Kubernetes API.

Разделение одного кластера метками отвергнуто: оно требует изменения manager и проверки области действия в Reconcile, не изолирует CRD, Nodes и общий шлюз. Отдельные кластеры позволяют устанавливать схему и проверять отказы независимо. Они делят CPU, RAM и диск хоста, поэтому изоляция ресурсов не равна изоляции производительности.

### Имена, адреса и маршруты

Для dev сохраняем существующий Compose project и тома, чтобы смена обвязки не выглядела потерей базы. Тестовый запуск получает run ID; его Compose project, имена баз и каталоги включают назначение и run ID. Состояние подключения хранится в `tmp/k3s/dev/` и `tmp/k3s/<suite>/<run-id>/`; старый каталог dev автоматически не удаляется.

Dev сохраняет стабильные опубликованные порты. Тестовым Kubernetes API, HTTP и Envoy назначаем свободные localhost-порты средствами Docker или ОС, затем читаем фактические назначения. Внутренние порты Kubernetes и NodePort остаются постоянными. Публичный адрес тестового клиента, `spec.publicPort` и порт listener внутри Envoy не смешиваем: текущие тесты уже используют внешнее отображение NodePort. Для будущих сквозных тестов адрес, показываемый API пользователю, должен действительно вести в Envoy выбранного стенда.

Каждый одновременно работающий кластер получает непересекающиеся Docker subnet, Pod CIDR и Service CIDR, согласованный `cluster-dns`. Настройки выбираются из проверяемого пула с блокировкой выделения; учитываются существующие Docker-сети и маршруты хоста. Если свободный диапазон недоступен, подготовка завершается до изменения сетей. Фиксированные адреса `172.27.0.101` и соседние адреса тестовых клиентов заменяются адресами из сети выбранного стенда, вместе с CIDR в whitelist-проверках.

Bootstrap получает project, пути kubeconfig и параметры сети явно. Его команды получения нод, Helm, CRD и настройки маршрутов используют только выбранный кластер. Очистка маршрутов проверяет сохранённые destination и gateway, чтобы не удалить запись, которую уже изменил другой процесс. Выделение сети требует краткой общей блокировки, но сами наборы тестов работают параллельно.

Каждый кластер получает свой K3S_TOKEN. API и оператор используют разные ServiceAccount и kubeconfig с текущими production-подобными правами. Сам Namespace в kubeconfig не служит изоляцией; её обеспечивает отдельный Kubernetes API.

### PostgreSQL и сроки жизни

На локальной машине переиспользуем один сервер PostgreSQL из dev-инфраструктуры, даже когда `just run` не запущен. Его первоначальный запуск сериализуем отдельно от подготовки k3s. Команды тестов могут запустить сервер, но не получают право удалять его или dev-том при завершении.

Создаём отдельную базу на каждый запуск api, integration и e2e; применяем миграции с `goose -allow-missing`. DB URL передаём явно, поверх `.env`. Обвязка отклоняет dev-базу как цель тестовой очистки. Перед удалением базы останавливаем процессы и закрываем соединения своего набора. Существующая очистка тестовых аккаунтов сохраняется; общий сервер не очищается через TRUNCATE.

Внутри API-набора проверки глобальной квоты остаются последовательными. Конкурентность, которая проверяется самим тестом, сохраняется. Для нескольких пакетов с такими проверками задаём последовательность пакетов либо выделяем им разные базы.

### Жизненный цикл команд

`just run` выполняет проверки инструментов и локальной конфигурации, старт инфраструктуры, ожидание readiness, bootstrap и миграции. Затем запускает приложения в управляемых группах процессов. Выбор лидера не заменяет контроль повторного dev-запуска: второй корневой run отклоняется, пока первый владеет dev-процессами. При Ctrl+C завершаем свои приложения, сохраняем k3s и PostgreSQL. При неожиданном выходе приложения завершаем остальные и возвращаем ошибку. `just down` останавливает dev-инфраструктуру без удаления томов; при активном run сообщает конфликт, не убивает посторонние процессы.

`api/just test` и `operator/just test` становятся самостоятельными полными командами. Команды `test-fast` / `test-full` удаляются вместе со ссылками из инструкций и CI. Build tags envtest/integration остаются внутренним способом выбора этапов и не исчезают из Go. Результаты инфраструктурных Go-тестов не берём из кэша: используем `-count=1`. `web/just test` вызывает существующий pnpm test.

Корневой `just test` создаёт run ID, запускает независимые команды, хранит PID и результаты, ждёт все начатые наборы. Ошибка одного набора не вызывает fail-fast для остальных. Каждый набор пишет отдельный журнал; после завершения корень показывает сводку и пути. Необходимые readiness-проверки ограничены deadline. Подключённый набор с нулём обнаруженных тестов или отсутствующей инфраструктурой считается ошибкой, а не пропуском.

При прерывании сначала останавливаем процессы, собираем доступную диагностику, затем освобождаем свои ресурсы. Удаление целого одноразового тестового кластера допустимо при cleanup; принудительное снятие finalizers ради успешного lifecycle-теста не допускается. Исключение для административной имитации завершения удаления в API-тесте остаётся частью его проверяемого сценария. Ошибка cleanup отражается в результате и оставляет точные данные о ресурсах для повторной очистки.

### Генерация без гонок

Тестовые команды используют проверку генерации во временном каталоге на основе `scripts/check_operator_generated.sh`; устанавливают проверенные CRD из текущей ревизии. Явная генерация при разработке остаётся отдельным шагом. Перед компиляцией не запускается команда, перезаписывающая публичный пакет `operator/api/v1alpha1`. Проверка работает и при dirty worktree и не требует отсутствия пользовательских изменений.

### Поэтапное подключение сквозных наборов

В этом change создаём конфигурации и проверяем подготовку/очистку всех четырёх тестовых стендов. Регистрация исполняемых наборов содержит существующие API, operator и web. Отсутствующие integration/e2e показываем отдельно как не реализованные; для них нет пустых успешных команд. Окружения создаются по требованию, поэтому обычный test не держит неиспользуемый трёхнодовый кластер без сценариев.

Изменение синхронизации добавляет её тесты в `api/just test`. Последующие изменения добавляют общие integration и e2e-сценарии и сразу включают их в корневую команду и CI. Для тестов API оператор не нужен: сценарий идёт через настоящий HTTP, затем обвязка проверяет Namespace/Secret/spec, записывает status административным клиентом и проверяет результат через HTTP. Фоновая синхронизация использует реальный ограниченный клиент. Интервал синхронизации около секунды фиксируется в отдельном change синхронизации, а ожидания тестов проверяют условие с deadline вместо фиксированного sleep.

### CI и проверка ресурсов

GitHub Actions выполняет те же команды в отдельных jobs после lint; build зависит от всех подключённых наборов. CI не запускает корневой параллельный test внутри каждого job. Образы и инструменты закреплены; кэширование загрузок не подменяет результаты тестов. Диагностика сохраняется даже при ошибке, без kubeconfig и Secret. Для будущего Playwright учитываем, что trace и network log могут содержать пароли: сбор и публикация должны исключать такие данные.

При реализации измеряем пиковую RAM, CPU, время подготовки и длительность наборов на реальном runner. Прежний замер простаивающего dev-стенда не служит бюджетом. Проверяем также requests подов и доступность их размещения: отсутствие нагрузки не отменяет решений scheduler. Изменение класса runner при необходимости не должно отключать тесты или ослаблять размещение ради прохождения CI.

## Risks / Trade-offs

- Коллизии сетей и host-маршрутов: выделение диапазонов с блокировкой, проверка пересечений, точечная очистка по сохранённым параметрам.
- Цена четырёх control plane и браузера: окружения поднимаются по требованию; CI разносит наборы по jobs; пиковые ресурсы измеряются до завершения реализации.
- Общий локальный PostgreSQL остаётся общей точкой отказа: тесты не перезапускают и не удаляют сервер; тесты намеренного отказа всего PostgreSQL требуют отдельного сервера.
- Аварийное завершение процесса может оставить ресурсы: журнал владения записывается при создании; повторная очистка работает по точному run ID, без удаления по общему префиксу.
- Новые команды несовместимы с прежними test-fast/test-full: ссылки в CI, AGENTS и документации меняются в той же реализации.

## Migration Plan

1. Ввести параметры окружений и владение ресурсами, сохранив dev-project, тома и стабильные адреса.
2. Добавить изолированные тестовые профили и проверить подготовку всех топологий.
3. Перенести существующий operator lifecycle на свой стенд; обновить тестовую БД API и убрать генерацию из тестового рабочего дерева.
4. Ввести единые команды, корневой запуск и CI. Обновить краткое объяснение в SYSTEM.md и подробности в SYSTEM-DETAIL.md, синхронизировать инструкции приложений.
5. Проверить параллельную работу с dev, cleanup, диагностику отказов и ресурсный бюджет. При откате команд сохранить dev-тома и убрать только тестовые ресурсы этого изменения.
