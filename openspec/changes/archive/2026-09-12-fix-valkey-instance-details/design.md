## Context

API сейчас хранит `host_ro` только для `ha`, оператор не создаёт объекты `-ro` для `single`, а web и e2e прямо ожидают отсутствие адреса чтения у `single`. Окно обслуживания уже хранится в PostgreSQL и меняется через PATCH, но POST создания его не принимает; web спрятал эту настройку в общем окне переименования. Выполненные планы в `operator/TODO.md` всё ещё упомянуты в действующей спецификации, `operator/AGENTS.md` и дереве `SYSTEM-DETAIL.md`.

## Goals / Non-Goals

**Goals:**

- дать клиентам одинаковую пару стабильных DNS-адресов в обоих режимах;
- сохранить окно обслуживания атомарно с созданием и сделать его изменение очевидным;
- согласовать пользовательские подписи и активную документацию с текущим поведением;
- подтвердить изменения на каждом уровне, где контракт наблюдаем пользователем или другим компонентом.
- ограничить проверку изменёнными тестами и сценариями, чтобы не запускать многочасовые полные наборы.

**Non-Goals:**

- добавлять второй процесс или физическую реплику в `single`;
- запрещать команды записи через адрес чтения `single`;
- менять внутренний термин `whitelist`, имена полей HTTP API или событий аудита;
- придавать окну обслуживания влияние на планирование операций в v1;
- переписывать архивные изменения OpenSpec.
- запускать агрегатные `test-full` или полные наборы неизменённых компонентов.

## Decisions

### 1. API хранит `host_ro` для каждого инстанса

Новые строки получают `<slug>-ro.<domain>` одновременно с основным адресом. Существующие строки `single` заполняются миграцией на основе сохранённых `slug` и `host`, а не текущей настройки домена. Поэтому смена домена сервера не меняет адреса уже созданных баз.

Поле в Go и TypeScript можно временно оставить допускающим `null`, чтобы безопасно прочитать строку во время развёртывания, но публичный контракт после миграции требует непустое значение. Защитная проверка должна сообщать о повреждённой старой строке, а не молча собирать адрес из текущей конфигурации.

Альтернатива: вычислять `host_ro` при каждом ответе. Она отвергнута, потому что адрес изменился бы после смены домена и перестал бы быть сохранённой частью контракта.

### 2. Адрес чтения `single` использует тот же primary

Оператор создаёт второй SNI-маршрут `<slug>-ro.<base-domain>` с теми же TLS, whitelist, idle timeout и backend основного процесса. Отдельный процесс и отдельный резерв ресурсов не появляются. Оператор включает пользователя `app` и подтверждает `running` только после проверки обоих маршрутов на обеих штатных репликах Envoy.

Такой адрес даёт приложению постоянную схему настройки при переходе между `single` и `ha`, но не является границей прав. В `single` запись через него может завершиться успешно. В `ha` существующий `-ro` продолжает выбирать готовую реплику и возвращает `READONLY` для записи.

Альтернатива: показать два одинаковых текста адреса без нового SNI. Она отвергнута, потому что это не два стабильных адреса и клиенту пришлось бы менять конфигурацию при переходе на HA.

### 3. Окно обслуживания входит в первоначальную транзакцию

POST принимает необязательный `maintenance` с тем же форматом и проверкой границ, что PATCH. Отсутствие и `null` нормализуются в одно состояние без окна и одинаковый идемпотентный отпечаток. Допустимый объект входит в отпечаток запроса и сохраняется в строке инстанса до записи аудита, биллингового периода и ответа.

Окно не входит в `ValkeyInstance.spec`, не увеличивает `desired_generation` и не меняет `configuration_requested_at`. Оно остаётся пользовательской метаинформацией до отдельного изменения, которое определит выполнение обслуживания.

Альтернатива: создать базу и сразу отправить PATCH. Она отвергнута из-за частичного результата при сбое второго запроса и двух отдельных пользовательских действий в аудите.

### 4. Web разделяет переименование и окно обслуживания

Форма создания получает необязательные поля дня, часа UTC и длительности. Карточка всегда показывает строки «Primary» и «Для чтения». Значения на странице и в буфере обмена форматируются как `redis://<host>:<port>`, но API продолжает хранить и возвращать host без схемы. Примеры подключения содержат обе роли адресов, чтобы копирование примера не скрывало второй адрес.

Окно переименования отвечает только за имя. Отдельное окно обслуживания открывается действием из одноимённой строки, загружает текущие значения и отправляет PATCH только с `maintenance`. Это сохраняет независимость метаданных и позволяет менять окно во время операции конфигурации до начала удаления.

Для сетевой настройки весь видимый текст использует «Белый список». Внутренние типы, функции, маршруты и поля сохраняют `whitelist`, поэтому изменение не затрагивает совместимость HTTP API и CR.

### 5. Проверки запускаются точечно

Во время реализации запускаются только изменённые unit- и компонентные тесты, конкретный k3s-сценарий оператора, затронутый сценарий общей интеграции и выбранный файл Playwright. Для приложения выполняются его линтер, проверка типов или сборка, если изменённый код проходит через эту проверку. Корневой `just test-full`, компонентные `test-full` и полный каталог Playwright не запускаются.

Альтернатива: выполнить все полные наборы перед завершением. Она отвергнута, потому что независимые k3s и e2e-стенды делают такую проверку несоразмерно долгой для локального изменения, а изменённые контракты имеют именованные сценарии.

### 6. Выполненные планы удаляются из активной документации

После сверки каждого пункта с текущими тестами и рабочим выпуском из
`operator/TODO.md` удаляются только подтверждённо выполненные разделы. Если в
файле остаются подтверждённо незавершённые сценарии, файл сохраняется с ними и
не объявляется выполненным планом. Сам файл удаляется только после удаления всех
разделов. Активные ссылки в `operator/AGENTS.md`, `SYSTEM-DETAIL.md` и основной
спецификации, которые требуют завершённые списки будущих тестов, заменяются
описанием фактических наборов либо удаляются. Архив OpenSpec остаётся
историческим снимком.

Если сверка найдёт действительно невыполненный пункт, его нельзя удалять под
видом очистки. Он остаётся в `operator/TODO.md`; отдельное изменение OpenSpec
для его реализации создаётся после согласования и не расширяет эту реализацию.

## Risks / Trade-offs

- [Адрес чтения `single` выглядит как реплика] -> В интерфейсе использовать нейтральную подпись «Для чтения», а в документации и тестах явно указать общий процесс и отсутствие запрета записи.
- [API начнёт возвращать адрес до готовности маршрута] -> Сначала разворачивать поддержку оператора и дождаться сверки существующих CR, затем применять миграцию и включать новый контракт API; production e2e проверяет оба адреса.
- [Новый маршрут увеличит время provisioning] -> Проверять оба маршрута в одном цикле сверки Envoy и сохранять существующий конечный срок операции.
- [Изменение идемпотентного отпечатка сломает повтор старого POST] -> Не включать отсутствующее или равное `null` окно в каноническое представление; старое тело сохраняет прежний отпечаток.
- [Миграция соберёт адрес из нового домена] -> Выводить суффикс домена из сохранённого `host` каждой строки и проверять ожидаемый префикс slug.
- [Очистка TODO удалит настоящую будущую работу] -> Перед удалением сопоставить каждый активный пункт с именованным тестом, сценарием выпуска или действующей спецификацией и сохранить несопоставленный пункт в `operator/TODO.md` до согласования.
- [Точечная проверка пропустит побочное влияние] -> Выбирать тесты по изменённым контрактам между компонентами, запускать линтер и сборку затронутых приложений и перечислять границы проверки в отчёте.

## Migration Plan

1. Добавить маршрут чтения `single`, проверки готовности и operator k3s-тесты, не меняя публичный ответ API.
2. Добавить миграцию `host_ro` для существующих строк, генерацию двух адресов для новых строк и поддержку окна обслуживания в POST. Проверить миграцию на новой базе и на базе с уже применёнными более поздними версиями через `goose -allow-missing`.
3. Обновить web, общую интеграцию и Playwright e2e. Проверить изменённые сценарии точечными командами без запуска полных `test-full`.
4. Удалить из `operator/TODO.md` подтверждённо выполненные разделы и активные ссылки, которые называют их будущей работой. Если после сверки остаются незавершённые сценарии, сохранить файл с этими сценариями; удалить файл только когда он пуст.
5. При откате web может безопасно игнорировать `host_ro` у `single` и поле окна в POST. Оператор нельзя откатывать до версии, удаляющей `-ro`, пока API продолжает публиковать этот адрес; полный откат требует согласованного отката API и миграции данных.
