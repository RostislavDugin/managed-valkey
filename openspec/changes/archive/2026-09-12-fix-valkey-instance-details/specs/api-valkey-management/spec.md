## MODIFIED Requirements

### Requirement: Создание атомарно сохраняет намерение

`POST /instances` SHALL принимать `{name, prefix, mode, vcpu, ram_gb, password, is_whitelist_enabled?, whitelist_cidrs?, maintenance?}` и обязательный UUID `Idempotency-Key`. Неуказанный whitelist SHALL означать `false` и `[]`. `maintenance` SHALL отсутствовать, быть `null` либо быть полным объектом `{dow, hour_utc, duration_min}` с теми же границами значений, что и PATCH. Отсутствующее или равное `null` окно SHALL означать, что окно не задано. Имя SHALL содержать от 1 до 40 символов, префикс от 3 до 20; оба допускают `[a-z0-9-]`, начинаются и заканчиваются буквой либо цифрой. Имя SHALL быть уникальным у владельца среди строк с `deleted_at IS NULL`. Режим SHALL быть `single` либо `ha`. Пароль SHALL содержать ровно 32 символа `[A-Za-z0-9_-]`. Создание SHALL сохранять инстанс, начальное окно обслуживания, аудит, открытый биллинговый период и идемпотентный ответ одной транзакцией, затем возвращать `202` с DTO инстанса.

#### Scenario: Начальные значения

- **WHEN** API принимает допустимое создание в пределах квот
- **THEN** ответ содержит UUIDv7, `status=provisioning`, `desired_generation=1`, `observed_generation=0`, `password_version=1`, `applied_password_version=0`, `applied_vcpu=0`, `applied_ram_gb=0`, `observed_at=null`, `is_stale=true`, `is_updating=true`
- **AND** `created_at`, `updated_at` и `configuration_requested_at` имеют одну временную отметку принятия
- **AND** повторное чтение после перезапуска API возвращает сохранённый инстанс

#### Scenario: Whitelist задаётся при создании

- **WHEN** клиент передаёт включённый whitelist с допустимыми CIDR
- **THEN** API сохраняет нормализованный список в первоначальном поколении
- **AND** не выполняет вторую операцию настройки и не создаёт второе событие аудита

#### Scenario: Окно обслуживания задаётся при создании

- **WHEN** клиент передаёт допустимый объект `maintenance`
- **THEN** API сохраняет окно в строке создаваемого инстанса и возвращает его в первоначальном ответе
- **AND** не выполняет последующий PATCH, не увеличивает поколение и не создаёт отдельное событие изменения настроек

#### Scenario: Окно обслуживания отсутствует

- **WHEN** поле `maintenance` отсутствует или равно `null`
- **THEN** API создаёт инстанс с `maintenance=null`
- **AND** оба представления входят в одинаковую идемпотентную семантику запроса

#### Scenario: Занятое имя

- **WHEN** у владельца есть неудалённый инстанс с таким именем, в том числе `deleting`
- **THEN** API отвечает `409 CONFLICT` с `details.reason=name_taken` и `details.field=name`
- **AND** такое же имя у другого владельца не мешает созданию

#### Scenario: Ошибка одной из связанных записей

- **WHEN** запись инстанса, окна обслуживания, аудита, периода или идемпотентного ответа завершается ошибкой
- **THEN** API не возвращает `202`, а все записи этой попытки откатываются

### Requirement: Адреса и секреты имеют постоянный контракт

API SHALL создавать глобально уникальный slug `<prefix>-<6 случайных символов [a-z0-9]>` и повторять подбор при коллизии. `prefix` SHALL использоваться только как вход создания, не сохраняться отдельно и не возвращаться в DTO. Slug SHALL оставаться занятым после soft delete. Основной адрес `<slug>.<domain>`, адрес чтения `<slug>-ro.<domain>` и порт SHALL фиксироваться при создании из конфигурации сервера для `single` и `ha`; `host_ro` MUST NOT быть `null` у созданного инстанса. В `single` адрес чтения ведёт на тот же единственный процесс, что и основной адрес, и не обещает отдельную копию данных или запрет записи. `mode`, `slug`, адреса, владелец и ID MUST NOT изменяться через публичные мутации. Credentials SHALL содержать `{host, host_ro, port, username, password_hint, password_version, applied_password_version}`, где `username=app`. API SHALL хранить только SHA-256 пароля и первые четыре символа; полный пароль и хеш MUST NOT появляться в DTO, аудитах, логах или сохранённых ответах.

#### Scenario: Коллизия slug

- **WHEN** генератор сначала возвращает занятый slug, затем свободный
- **THEN** создание завершается с новым slug и ровно одним набором связанных записей

#### Scenario: Два адреса single

- **WHEN** API создаёт или читает `single` со slug `shop-a1b2c3`
- **THEN** DTO и credentials содержат `host=shop-a1b2c3.<domain>` и `host_ro=shop-a1b2c3-ro.<domain>` с одним портом

#### Scenario: Смена настроек домена

- **WHEN** сервер перезапущен с новым доменом или портом
- **THEN** существующий инстанс сохраняет оба адреса и порт, новые инстансы используют новую конфигурацию

#### Scenario: Проверка секретов

- **WHEN** клиент создаёт инстанс, читает список, карточку, credentials или повторяет создание
- **THEN** ответы содержат только маску и версии пароля
- **AND** исходный пароль отсутствует в хранимых данных и логах, а ACL-хеш доступен только во внутренней записи инстанса
