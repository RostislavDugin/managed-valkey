## ADDED Requirements

### Requirement: Общий интеграционный стенд использует одну копию каждого компонента

Общий интеграционный стенд SHALL запускать одну копию API с его штатными фоновыми обработчиками, одну копию оператора и одну копию Envoy. API и оператор SHALL получать отдельные kubeconfig с рабочими правами, указывать на один тестовый кластер и использовать одну выделенную базу запуска. Четыре параллельных сценария SHALL совместно использовать эти процессы, базу и кластер, но SHALL создавать четыре отдельных аккаунта, Valkey-инстанса и Namespace. Тест MUST NOT запускать отдельные API, фоновые обработчики, операторы, базы, кластеры или Envoy для каждого сценария.

#### Scenario: Подготовлен общий стенд

- **WHEN** интеграционная команда завершила подготовку
- **THEN** один API принимает HTTP-запросы, его фоновые обработчики работают, один оператор управляет CR тестового кластера, а одна копия Envoy предоставляет TLS-доступ к Valkey

#### Scenario: Параллельные сценарии используют общий стенд

- **WHEN** создание, изменение ресурсов, ротация пароля и удаление выполняются одновременно
- **THEN** четыре сценария обращаются к одним процессам API и оператора, одной базе и одному кластеру и различаются своими аккаунтами, Valkey-инстансами и Namespace

## MODIFIED Requirements

### Requirement: Тестовая база создаётся по требованию

`api just test`, `api just test-full` и общий интеграционный набор SHALL подготовить PostgreSQL, создать выделенную базу запуска и применить миграции с `goose -allow-missing`. `api just test` SHALL выполнять все тесты без k3s. `api just test-full` SHALL дополнительно подготовить отдельный однонодовый k3s и выполнить Kubernetes-зависимые тесты без оператора. Общий интеграционный набор SHALL использовать собственную базу, общую только для сценариев одного запуска. API, общие интеграционные и e2e-наборы MUST NOT использовать одну базу между собой или dev-базу. Локально эти базы SHALL поддерживаться одним сервером PostgreSQL. Dev compose MUST NOT монтировать init-скрипт PostgreSQL.

#### Scenario: Первый запуск тестов

- **WHEN** разработчик выполняет `api just test` без подготовленной тестовой базы
- **THEN** команда готовит сервер и базу, применяет миграции и выполняет все тесты без запуска k3s

#### Scenario: Первый полный запуск тестов

- **WHEN** разработчик выполняет `api just test-full` без подготовленного тестового окружения
- **THEN** команда готовит отдельные базу и однонодовый k3s, применяет миграции и выполняет весь набор API

#### Scenario: Первый общий интеграционный запуск

- **WHEN** разработчик выполняет `just test-integrations` без подготовленной базы запуска
- **THEN** команда создаёт отдельную базу, применяет миграции до запуска API и удаляет базу при штатной очистке

#### Scenario: Параллельная проверка квот

- **WHEN** API-тесты проверяют общую квоту одновременно с интеграционными или e2e-тестами
- **THEN** записи соседнего набора не участвуют в расчёте квоты и не удаляются при очистке

### Requirement: Изолированные окружения Kubernetes

Проект SHALL поддерживать постоянный трёхнодовый dev-кластер и отдельные кластеры для API-тестов (одна нода), API + operator (одна нода) и Playwright e2e (три ноды). Каждый сценарий оператора SHALL получать независимый кластер из одной, двух, трёх или четырёх нод. Трёхнодовый кластер SHALL состоять из одного server и двух agents; четвёртая нода SHALL быть дополнительным agent того же тестового запуска. Набор оператора SHALL проверять восстановление как без запасного хоста, так и с ним. Дополнительная нода тестового окружения оператора MUST NOT добавляться в постоянный dev или соседние кластеры.

Подготовка SHALL использовать общий параметризованный шаблон. Окружения SHALL иметь независимые Compose projects, тома, токены и сетевые диапазоны; маршруты к Pod IP MUST NOT пересекаться при одновременной работе на одном хосте. Дополнительный agent SHALL участвовать в выделении адресов, bootstrap, подготовке образов, маршрутах, диагностике и очистке своего запуска. Явный gateway тестовой Docker-сети SHALL сохраняться при добавлении и замене agent; его адрес MUST NOT совпадать с адресами нод или тестовых клиентов.

#### Scenario: Полный локальный запуск

- **WHEN** dev и несколько тестовых окружений подняты одновременно
- **THEN** каждый кластер имеет независимый Kubernetes API, число стендов и нод ограничено общим бюджетом, а оператор обрабатывает только CR своего кластера

#### Scenario: Однонодовая интеграция API и оператора

- **WHEN** готовится окружение общего интеграционного набора
- **THEN** кластер содержит одну server-ноду, а все штатные операции `single` выполняются на ней через один общий API и один оператор

#### Scenario: Дополнительная нода оператора

- **WHEN** сценарий оператора получает запасной agent
- **THEN** его кластер содержит четыре ноды, dev сохраняет три ноды, а дополнительный agent использует сеть и ресурсы только своего тестового запуска

#### Scenario: Восстановление без запасного хоста

- **WHEN** оператор проверяет потерю worker-ноды на исходном трёхнодовом стенде
- **THEN** остаются две ноды, HA восстанавливает запись в degraded с третьим Pod в Pending; добавление чистого agent позволяет восстановить три копии

#### Scenario: Очистка тестового кластера

- **WHEN** тестовый запуск удаляет свой кластер и тома
- **THEN** он освобождает также дополнительный и заменяющие agents, их маршруты и сетевые ограничения, а dev-инстансы, dev-база и соседние тестовые окружения сохраняются
