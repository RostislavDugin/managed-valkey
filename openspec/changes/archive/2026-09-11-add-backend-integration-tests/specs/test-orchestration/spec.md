## ADDED Requirements

### Requirement: Общий интеграционный набор проверяет совместную работу backend

Общий интеграционный набор SHALL управлять инстансами только через настоящий TCP HTTP API и SHALL запускать рабочие фоновые обработчики API вместе с настоящим оператором. Он SHALL подтверждать результат по сохранённому состоянию HTTP API, объектам Kubernetes и настоящему TLS-подключению к Valkey. Административный клиент Kubernetes SHALL использоваться только для чтения, ожидания, диагностики и очистки ресурсов своего запуска. Тесты MUST NOT создавать или изменять CR напрямую, записывать `status`, снимать `finalizers`, вызывать фоновые обработчики как функции либо менять PostgreSQL для имитации результата.

#### Scenario: Создание single-инстанса

- **WHEN** тест регистрирует отдельный аккаунт и создаёт `single`-инстанс через HTTP API
- **THEN** фоновые обработчики доставляют Namespace, Secret и CR, оператор запускает Valkey, а импорт возвращает в API `status=running`, совпавшие поколения, применённые ресурсы и версию пароля
- **AND** TLS-подключение через публичный адрес принимает `AUTH`, `PING`, `SET` и `GET` с заданным паролем

#### Scenario: Изменение ресурсов single-инстанса

- **WHEN** готовый `single`-инстанс получает новый допустимый размер через HTTP API
- **THEN** оператор заменяет рабочий процесс, Kubernetes показывает запрошенные ресурсы, а API возвращает совпавшие поколения и новые `applied_vcpu` и `applied_ram_gb`
- **AND** Valkey снова принимает TLS-подключение с действующим паролем

#### Scenario: Ротация пароля single-инстанса

- **WHEN** тест записал значение в готовый `single`-инстанс и меняет пароль через HTTP API
- **THEN** API после работы оператора и фонового импорта возвращает совпавшие `password_version` и `applied_password_version`
- **AND** старый пароль отклоняется, новый пароль читает записанное до ротации значение

#### Scenario: Удаление single-инстанса

- **WHEN** тест удаляет готовый `single`-инстанс через HTTP API
- **THEN** оператор завершает удаление, фоновая синхронизация удаляет Namespace, а API исключает инстанс из карточки и списка и освобождает его резерв пользовательской квоты

### Requirement: Общий интеграционный набор имеет ориентир длительности для CI

Штатный запуск общего интеграционного набора SHOULD завершать подготовку окружения, выполнение обязательных сценариев и обычную очистку примерно за пять минут. Запуск SHALL измерять и сообщать полную длительность. Превышение ориентира MUST NOT само по себе менять успешный результат тестов. Отсутствие обязательной инфраструктуры или обязательного теста и недостижение требуемого состояния до срока конкретного ожидания MUST завершать набор ошибкой. Сбор диагностики и аварийная очистка SHALL иметь собственные конечные сроки.

Сценарии создания, изменения ресурсов, ротации пароля и удаления SHALL начинаться параллельно и использовать общий стенд. Каждый сценарий SHALL владеть отдельными аккаунтом, Valkey-инстансом и Namespace. Зависимые операции внутри одного сценария SHALL выполняться последовательно. Первая версия набора MUST NOT ограничивать число одновременно работающих сценариев ниже четырёх; невозможность разместить четыре минимальных `single`-инстанса на тестовой ноде SHALL завершать набор ошибкой.

#### Scenario: Штатный запуск в CI

- **WHEN** общий интеграционный набор запускается на поддерживаемом CI runner с доступными зависимостями и образами
- **THEN** отчёт содержит полную длительность подготовки, обязательных сценариев и обычной очистки и позволяет сравнить её с ориентиром в пять минут

#### Scenario: Превышение ориентира длительности

- **WHEN** все обязательные проверки и очистка завершились успешно, но заняли больше пяти минут
- **THEN** набор сообщает фактическую длительность и остаётся успешным

#### Scenario: Параллельные цепочки

- **WHEN** сценарии создания, изменения ресурсов, ротации пароля и удаления выполняются на общем стенде
- **THEN** все четыре сценария запускаются параллельно через один API и один оператор, используя четыре отдельных аккаунта, Valkey-инстанса и Namespace
- **AND** состояние и очистка одного сценария не затрагивают остальные сценарии

#### Scenario: Четыре инстанса не поместились на ноде

- **WHEN** однонодовый стенд не может одновременно разместить четыре минимальных `single`-инстанса
- **THEN** набор завершается ошибкой и не уменьшает параллелизм автоматически

#### Scenario: Отдельное ожидание превысило срок

- **WHEN** API, оператор, Kubernetes или Valkey не достигает требуемого состояния до срока этой операции
- **THEN** набор завершается ошибкой, сохраняет безопасную диагностику и адресно очищает свои ресурсы

## MODIFIED Requirements

### Requirement: Корневая команда запускает все подключённые наборы

Корневой `just test` SHALL параллельно запускать быстрые наборы `api`, `operator` и `web`. Он SHALL завершаться примерно за пять минут на поддерживаемой рабочей машине при установленных зависимостях и MUST NOT запускать k3s-сценарии. Корневой `just test-full` SHALL параллельно запускать полные наборы этих приложений и обязательный общий интеграционный набор. Ни `test`, ни `test-full` MUST NOT запускать Playwright e2e. Отдельная корневая команда `just test-integrations` SHALL запускать только общий интеграционный набор. Каждый подключённый набор SHALL сам готовить своё окружение и выполнять необходимые этапы по порядку. Наборы, использующие общую кластерную квоту в PostgreSQL, MUST NOT конкурентно изменять одну тестовую базу.

#### Scenario: Быстрая проверка

- **WHEN** разработчик запускает `just test` из корня
- **THEN** быстрые наборы API, оператора и web выполняются параллельно без создания k3s

#### Scenario: Полная проверка

- **WHEN** разработчик запускает `just test-full` из корня
- **THEN** полные наборы API, оператора и web и общий интеграционный набор выполняются параллельно

#### Scenario: Только общая интеграция

- **WHEN** разработчик запускает `just test-integrations` из корня
- **THEN** выполняется общий интеграционный набор без запуска полных наборов приложений и Playwright e2e

#### Scenario: E2e запускается отдельно

- **WHEN** разработчик запускает `just test`, `just test-full` или `just test-integrations`
- **THEN** ни один Playwright-сценарий не запускается

### Requirement: Результат отражает фактически выполненные проверки

Корневые `just test`, `just test-full` и `just test-integrations` SHALL дождаться каждого начатого набора, вывести отдельные результаты и вернуть ненулевой код при ошибке подготовки, тестов или обязательной очистки. Неудача одного набора MUST NOT прерывать независимые наборы. Реализованный обязательный набор MUST NOT пропускаться из-за отсутствия инфраструктуры, переменной окружения или найденных тестов. Общий интеграционный набор SHALL считаться выполненным только после прохождения всех обязательных сценариев. Пустая команда, отсутствие найденных тестов или пропуск из-за недоступного k3s MUST NOT считаться успешной проверкой.

#### Scenario: Ошибка подготовки

- **WHEN** k3s не достиг готовности до срока ожидания во время `test-full` или `test-integrations`
- **THEN** соответствующий набор получает ошибку, остальные начатые наборы продолжают работу, а корневая команда возвращает ненулевой код

#### Scenario: Общий интеграционный сценарий не выполнен

- **WHEN** обязательный сценарий отсутствует в запуске, пропущен или завершился ошибкой
- **THEN** отчёт указывает непроверенный сценарий и общий интеграционный набор завершается неуспешно

#### Scenario: Общий integration-набор ещё не существует

- **WHEN** корневая команда не находит исполняемый общий integration-набор или его обязательные сценарии
- **THEN** запуск завершается ошибкой и не использует прежнюю успешную заглушку

### Requirement: Границы наборов сохраняются при подключении синхронизации

Быстрые API-тесты SHALL проверять HTTP и PostgreSQL без Kubernetes. Полные API-тесты SHALL дополнительно проверять доставку Namespace/Secret/spec и импорт status через настоящий Kubernetes API без оператора. Набор оператора SHALL начинаться с прямого создания CR без HTTP и PostgreSQL. Общий интеграционный набор SHALL проверять HTTP → PostgreSQL → CR → оператор → status → PostgreSQL → HTTP без подмены фоновых обработчиков. Playwright e2e SHALL выполнять пользовательский путь через браузер и полный стек без подмены backend. Общий интеграционный набор SHALL входить в корневой `test-full` и CI/CD, но MUST NOT входить в быстрый `test` или Playwright e2e. Полные Kubernetes-зависимые наборы API и аварийная матрица оператора SHALL оставаться локальными и MUST NOT включаться в CI/CD.

#### Scenario: Имитация наблюдений в API-тесте

- **WHEN** полный тест API проверяет импорт наблюдений или ожидание удаления CR с finalizer
- **THEN** тестовая обвязка меняет status или снимает finalizer своим административным клиентом, а приложение продолжает работать с ограниченным kubeconfig API

#### Scenario: Настоящее наблюдение в общем интеграционном тесте

- **WHEN** общий интеграционный тест ожидает создание, изменение ресурсов, ротацию пароля или удаление
- **THEN** только настоящий оператор меняет рабочие ресурсы и `status`, а API получает результат через свои фоновые обработчики

#### Scenario: Подключение сквозного сценария

- **WHEN** общий интеграционный набор проверяет создание инстанса через API с настоящим оператором
- **THEN** проверка использует однонодовое integration-окружение и входит в корневой `just test-full` и CI, но не в `just test` и не в Playwright e2e

#### Scenario: Тяжёлая аварийная матрица остаётся локальной

- **WHEN** CI запускает общий интеграционный набор
- **THEN** он проверяет штатные операции на одной ноде и не запускает сценарии HA, потери нод, сетевого разделения или восстановления после аварий
