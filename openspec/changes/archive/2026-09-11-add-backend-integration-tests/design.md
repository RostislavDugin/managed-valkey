## Context

См. мотивацию в `proposal.md`. Сейчас `tests/integrations` пуст, а `scripts/run_all_tests.sh` выводит для общего integration-набора заглушку. `scripts/test_environment.sh` уже умеет выделять для профиля `integration` отдельные PostgreSQL, Compose project, сеть, kubeconfig и k3s, но по умолчанию поднимает три ноды и две реплики Envoy.

Один процесс API сам запускает циклы доставки, импорта и очистки метрик. Доставка и импорт обрабатывают до четырёх инстансов одновременно. Оператор также допускает четыре параллельных reconcile. Это позволяет проверить четыре независимых пользовательских сценария на одном процессе API и одном процессе оператора.

Минимальный `single` запрашивает 1 CPU и 1 GB RAM. Четыре сценария вместе создадут четыре таких инстанса. Сценарий resize меняет только память с 1 до 2 GB, поэтому суммарный запрос CPU не превышает четыре. Первая версия намеренно не вводит очередь или семафор: нехватка ресурсов на CI должна проявиться как ошибка, после чего топологию или размеры runner можно будет пересмотреть отдельно.

## Goals / Non-Goals

**Goals:**

- Запускать четыре самостоятельных Go-сценария параллельно на одном общем backend-стенде.
- Проверять реальную доставку намерений и импорт наблюдений, а не вызывать фоновые функции из теста.
- Получать понятный результат каждого сценария и безопасную диагностику при сбое.
- Измерять полный штатный путь от начала подготовки до завершения очистки и стремиться удерживать его около пяти минут без ошибки только из-за длительности.

**Non-Goals:**

- Проверять HA, отказ ноды или процесса, сетевое разделение и продолжение незавершённых операций после рестарта. Эти случаи остаются в полном наборе оператора.
- Повторять подробные проверки валидации, квот, идемпотентности и ошибок PostgreSQL из API-тестов.
- Проверять браузер, клиентское приложение или рабочее окружение.
- Покрывать whitelist и импорт метрик в первой версии набора.

## Decisions

### Один стенд на весь запуск

В `tests/integrations` появятся `Justfile` и Go-пакет с тестами. Команда каталога сначала проверит каталог обязательных тестов, затем вызовет `scripts/test_environment.sh exec integration -- scripts/test_integrations.sh`. Профиль `integration` будет по умолчанию задавать одну k3s server-ноду и одну реплику Envoy; профили API, оператора и e2e не изменятся.

`scripts/test_integrations.sh` применит миграции, выберет свободные loopback-порты и запустит один API и один оператор отдельными группами процессов. API получит `HTTP_ADDR`, выделенную базу и свой kubeconfig. Его обычная точка входа запустит штатные фоновые циклы. Оператор получит собственный kubeconfig и настройки из `operator.env`.

Оператор собирается с существующим build tag `integration`: он сокращает ожидания длительных операций и разрешает `VALKEY_ENVOY_PROCESSES=1`, но использует тот же manager и reconciler, что рабочая сборка. API запускается без тестовой реализации фоновых обработчиков. Для одновременного dev и integration-запуска адрес health probe оператора станет настраиваемым через переменную окружения с прежним `:8081` по умолчанию; тест передаст свободный loopback-порт.

Альтернатива с отдельным API, оператором и кластером для каждого теста отвергнута из-за времени подготовки. Один Valkey на четыре теста тоже не подходит: resize, ротация и удаление меняют общее состояние и делают результаты зависимыми от порядка запросов.

### Четыре параллельных сценария и четыре Valkey-инстанса

Набор содержит четыре обязательные функции:

- `Test_CreateSingleValkey_WithRealApiAndOperator_BecomesReachableAndRunning`
- `Test_ResizeSingleValkey_WithRealApiAndOperator_AppliesRequestedResources`
- `Test_RotateSingleValkeyPassword_WithRealApiAndOperator_ReplacesApplicationCredential`
- `Test_DeleteSingleValkey_WithRealApiAndOperator_RemovesKubernetesResourcesAndApiState`

Каждая функция вызывает `t.Parallel`, регистрирует собственный аккаунт через `POST /v1/auth/register` и создаёт отдельный `single` размером 1 CPU / 1 GB. Уникальный суффикс запуска входит в email, имя и prefix, поэтому четыре теста получают разные строки PostgreSQL, slug и Namespace. `go test` запускается с `-parallel=4`. Общий барьер после регистрации аккаунтов выпускает четыре запроса создания вместе; у барьера есть срок ожидания и отмена при ранней ошибке.

Сценарий resize меняет размер на 1 CPU / 2 GB. Сценарии создания, resize и ротации удаляют свой инстанс в `t.Cleanup` через HTTP и ждут подтверждённого удаления. Сценарий удаления выполняет тот же путь как основную проверку. Полная очистка выделенного окружения остаётся последней страховкой, если API или оператор сломан.

Каталог перед запуском k3s сравнивает найденные `Test_`-функции с четырьмя обязательными именами. Удалённый, переименованный или случайно исключённый сценарий останавливает команду, а не превращается в успешный запуск с неполным покрытием.

Альтернатива с двумя длинными цепочками потребовала бы меньше Valkey, но хуже отделяла бы результаты операций и не проверяла бы одновременную работу фоновых обработчиков с четырьмя аккаунтами.

### Управление только через HTTP, проверка на трёх границах

Тестовый HTTP-клиент обращается к реальному TCP-порту API. Все мутации проходят через рабочий router, middleware, сервисы и PostgreSQL. Тест не импортирует внутренние пакеты API и не меняет базу после миграций.

Для каждой операции тест ждёт согласованного ответа `GET /v1/managed/valkey/instances/{id}`. Готовое состояние требует `status=running`, свежего наблюдения, равных `desired_generation` и `observed_generation`, ожидаемых применённых ресурсов и равных версий пароля. Это подтверждает обратный путь от `status` CR через фоновый импорт в PostgreSQL и HTTP.

Административный Kubernetes-клиент только читает CR, Pod и их метаданные. Создание проверяет наличие Namespace, CR и готового Pod. Resize дополнительно сравнивает UID Pod до и после замены и проверяет его resource requests. Удаление ждёт `NotFound` для Namespace. Клиент не пишет `spec`, `status` или `finalizers`.

Проверка Valkey подключается к опубликованному NodePort, но передаёт hostname из ответа API как TLS SNI. Она использует пользователя `app` и пароль, который сам тест отправил в API. Создание проверяет `PING`, `SET` и `GET`; resize проверяет новое подключение после замены Pod; ротация проверяет отказ старого пароля и чтение прежнего значения с новым. Удаление также проверяет отсутствие инстанса в карточке и списке и нулевое использование ресурсов в `GET /v1/me` для отдельного аккаунта.

Одних HTTP-проверок недостаточно: ошибочная имитация наблюдений могла бы вернуть `running` без работающего Valkey. Только Kubernetes-проверки тоже не доказывают, что API импортировал `status`. Поэтому набор сохраняет обе границы и настоящее клиентское подключение.

### Ориентир длительности и ожидание условий

Обёртка запуска измеряет время до подготовки окружения и заканчивает измерение после штатной очистки базы, k3s и процессов. Пять минут используются как ориентир для штатного запуска, а не как timeout или критерий успеха. Если все проверки и очистка прошли, команда остаётся успешной независимо от полной длительности.

Каждая операция сохраняет собственный конечный срок ожидания: готовность API и оператора, применение конфигурации, подключение к Valkey и удаление ресурсов не могут ждать бесконечно. Эти сроки защищают от зависания и означают функциональную ошибку конкретного шага. Они не вычисляются из общего пятиминутного бюджета. Циклы проверяют наблюдаемое состояние с коротким интервалом и сразу замечают завершение API или оператора. Фиксированные паузы вместо проверки условия не используются.

Скрипт записывает длительность подготовки, старта процессов, каждого теста и очистки. Отчёт отдельно показывает превышение пяти минут, но не меняет код завершения. `timeout-minutes` задания CI остаётся значительно больше ориентира и защищает runner только от зависшего процесса или сломанной очистки.

### Подключение к локальным командам и CI

Корневой `just test-integrations` вызывает только новый набор. В `scripts/run_all_tests.sh` профиль `test-full` заменяет строку-заглушку настоящим integration-набором и запускает его параллельно с полными наборами API, оператора и web. Быстрый `just test` не меняется.

GitHub Actions получает отдельный job `test-integrations` после трёх lint jobs. Он устанавливает Go и `just`, запускает корневой `just test-integrations` и при ошибке публикует диагностику. `build-api` и `build-web` зависят от него вместе с остальными обязательными тестами, поэтому deploy не сможет обойти сбой интеграции. Полные тесты API и сорокаминутный набор оператора в этот job не входят.

Отдельный job выбран вместо вызова корневого `just test-full`: последний содержит полную матрицу оператора и не подходит для CI. Добавлять integration к быстрому `just test` тоже нельзя, потому что эта команда должна работать без k3s.

### Процессы и безопасная диагностика

Скрипт хранит PID и время старта API и оператора, останавливает их группы по `TERM` и дожидается завершения до удаления окружения. Журналы процессов с самого начала пишутся в каталог диагностики запуска. При ошибке `scripts/test_environment.sh` добавляет состояния Kubernetes и Events, не запрашивая Secret.

Проверка артефактов будет расширена с существующего сканера e2e. Она ищет тела запросов с полем `password`, точные тестовые пароли, JWT аккаунтов и ключ подписи JWT во всех публикуемых файлах. Значения для проверки лежат вне каталога выгрузки. Если найден секрет, CI не публикует артефакт и завершает job ошибкой.

## Risks / Trade-offs

- [Четыре Pod по 1 CPU не помещаются в allocatable CPU runner] → Первая версия падает с диагностикой `Pending` и не скрывает проблему ограничением параллелизма. После первых запусков можно отдельно увеличить runner или согласовать меньший параллелизм.
- [Холодная загрузка k3s, Helm chart или образов превышает пять минут] → Запуск остаётся успешным при пройденных проверках, длительности этапов сохраняются для последующей оптимизации. При необходимости добавляется кэш CI.
- [Асинхронная сходимость делает тест нестабильным] → Каждая проверка ждёт наблюдаемое условие до срока своей операции и при ошибке сохраняет последнее HTTP-состояние, ресурсы Kubernetes и журналы обоих процессов.
- [Тестовый build tag расходится с рабочим оператором] → Tag меняет только уже существующие интервалы, точки управления тестом и допустимое число процессов Envoy. Release-образ по-прежнему собирается без него и проверяется существующим тестом конфигурации.
- [Параллельный сценарий удаляет чужие данные] → Все операции используют UUID и slug, полученные через отдельный аккаунт. Обычная очистка идёт через HTTP, а удаление всего кластера и базы выполняется только для идентификатора текущего запуска.
- [Пароль или токен попадает в журнал или артефакт] → HTTP-клиент не печатает тела запросов, Kubernetes-диагностика не читает Secret, а сканер блокирует публикацию при совпадении с тестовыми паролями или JWT аккаунтов.

## Migration Plan

1. Добавить каталог обязательных сценариев, тестовый HTTP-клиент и проверки Kubernetes и Valkey.
2. Добавить запуск API и оператора, случайные порты, однонодовый профиль integration и измерение полной длительности относительно ориентира в пять минут.
3. Подключить `just test-integrations`, заменить заглушку в `test-full` и обновить `AGENTS.md`.
4. Запустить набор локально несколько раз, проверить одновременное наличие четырёх Valkey и измерить полный штатный запуск с очисткой.
5. Добавить обязательный job CI и зависимости сборки после подтверждения функциональной стабильности и корректного отчёта о длительности на runner.

Откат удаляет job и новые команды, возвращает заглушку `integration` в `test-full` и прежний профиль из трёх нод и двух реплик Envoy. Изменений рабочей схемы или пользовательских данных нет.
