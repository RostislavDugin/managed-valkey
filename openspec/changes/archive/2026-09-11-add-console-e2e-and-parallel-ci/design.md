## Context

См. `proposal.md` для причин изменения. Подготовщик `e2e` уже создаёт отдельную базу, трёхнодовый k3s, две реплики Envoy, сертификат и свободные порты. Текущий запуск поднимает только API и Vite, а Playwright содержит один сценарий регистрации с одним worker. Общая интеграция уже показывает подход к запуску API и оператора, регистрации процессов, конечным срокам ожидания и безопасной диагностике.

Активные спецификации описывают прежнее состояние: e2e не требует оператора, production-проверка не создаёт Valkey, а CI выполняет lint, test и build последовательно. Их нужно синхронно изменить вместе с реализацией.

## Goals / Non-Goals

**Goals:**

- Переиспользовать один полный e2e-стенд для последовательного каталога Playwright.
- Проверить пользовательский путь через браузер и настоящий TLS-доступ к Valkey.
- Внести два ограниченных отказа Kubernetes без подмены пользовательских операций.
- Сохранить понятный headed-запуск без замедления headless и проверок состояния.
- Сократить критический путь CI параллельным запуском независимых jobs.

**Non-Goals:**

- Не переносить e2e в корневые `just test` или `just test-full`.
- Не повторять полную аварийную матрицу оператора в Playwright.
- Не запускать production-проверку автоматически.
- Не менять публичные HTTP API, схему PostgreSQL или поведение продукта ради тестов.

## Decisions

### Один стенд и последовательные независимые сценарии

`scripts/test_environment.sh exec e2e` создаёт окружение один раз. `scripts/test_e2e.sh` применяет миграции, запускает один API, один оператор с интеграционными временными порогами и один Vite, ждёт три readiness endpoint и затем один раз вызывает Playwright. Процессы регистрируются в состоянии запуска и завершаются группами с конечным сроком.

У стандартной виртуальной машины CI две vCPU и около 7 GiB RAM, поэтому её объект Kubernetes `Node` не размещает обязательный тариф `4 vCPU / 16 GB`. Только в CI сборка оператора с тегом `integration` задаёт поля `resources.requests` Valkey равными `100m` CPU и `128Mi` RAM. Поля `resources.limits`, `maxmemory`, принятый тариф и статус применённой конфигурации остаются исходными. Рабочая сборка не читает эти переменные.

Playwright сохраняет `workers: 1`, `fullyParallel: false` и отсутствие retries. Сценарии не объединяются в `serial`: после ошибки Playwright сможет выполнить остальные тесты, а обязательный каталог не превратится в цепочку пропущенных случаев. Каждый тест получает новый browser context и отдельный аккаунт, но использует общие процессы, базу и кластер.

Альтернатива с отдельным стендом на сценарий лучше изолирует отказы, но противоречит требованию переиспользования и заметно увеличивает время bootstrap. Параллельные сценарии на одном стенде усложнят квоты и сделают headed-наблюдение нечитаемым.

### Каталог сценариев проверяется до bootstrap

Лёгкая проверка вызывает список Playwright-тестов и сверяет обязательные русские названия и теги. Отсутствующий, переименованный, пропущенный или неверно помеченный сценарий завершает команду до создания k3s. Теги хранятся в метаданных: `@prod` для регистрации и штатных lifecycle, `@local` для квот, `@local-k8s` для отказов.

### Общие помощники описывают пользовательские операции

Тесты используют небольшие помощники регистрации, входа, создания, ожидания состояния, изменения размера, смены пароля и удаления. Локаторы опираются на роли, подписи и видимый текст. Размеры читаются из интерфейса: тест выбирает минимальный доступный, следующий больший и первый вариант, который не помещается в квоту.

Данные подключения, включая host, port и одноразовый пароль, берутся только со страницы. TypeScript-клиент Valkey подключается по TLS с SNI и пользователем `app`; локально он доверяет CA текущего стенда, а production использует системное доверие. `INFO memory` проверяет `maxmemory`, равный 75% RAM одного процесса.

### Задержка применяется перед следующим пользовательским действием

Фикстура хранит время последнего завершённого пользовательского действия. Перед следующим действием она ждёт только недостающую часть интервала. Runner передаёт 0 мс для headless и 3000 мс для headed и production.

Задержка не ставится после действия, потому что тогда она отложит ближайшую проверку. `expect`, ожидания HTTP-ответов, опрос состояния, команды Valkey, Kubernetes и teardown вызываются напрямую. Playwright `slowMo` не используется, так как он замедляет больше операций, чем требуется.

### Ожидания основаны на наблюдаемом состоянии

Тесты не используют фиксированный `sleep`, кроме интервала демонстрации пользовательских действий и 100-миллисекундного периода фоновых проб отказа. Создание, изменение размера, смена пароля, удаление, failover и восстановление ноды ожидаются до собственных конечных сроков. Сценарий фиксирует последнее увиденное состояние в сообщении ошибки.

Обычные операции получают срок до пяти минут. Запись после отказа должна восстановиться за две минуты; максимальный промежуток между успешными RO-чтениями равен пяти секундам. Общий timeout Playwright и CI устанавливается выше суммы последовательных сценариев и уточняется после первого измеренного headless-запуска.

### E2E использует стабильный NodePort сервера

Для e2e Service Envoy использует межнодовую передачу трафика, а публичный host port берётся у `k3s-server`. API публикует этот случайный внешний порт. Оператор использует собственный `VALKEY_PUBLIC_PORT=41379` как общий порт listener Envoy, который закреплён за NodePort `31379`; Docker перенаправляет случайный внешний порт на этот NodePort. Поэтому адрес, который API отдаёт личному кабинету, работает через настоящий SNI-маршрут и не зависит от выбранного worker. Остановка agent с primary оставляет server и хотя бы один Envoy доступными. Профили operator и integration сохраняют свои текущие правила NodePort.

Перед потерей worker-ноды тест по свежему CR находит primary. Если primary расположен на server, тест удаляет только его Pod и ждёт штатного failover на agent. Затем он останавливает только контейнер agent текущего Compose project, проверяет остановку и удаляет соответствующий Node. После повторной регистрации agent k3s может выделить новый Pod CIDR, поэтому Kubernetes-помощник добавляет его маршрут в таблицу хоста и в список ресурсов запуска. Затем HA достигает `running` с тремя процессами. Teardown удаляет старый и новый маршруты.

Альтернатива с переключением host port после отказа не проверит восстановление через прежний адрес из интерфейса. Отдельный тестовый TCP-прокси добавит компонент, которого нет в пользовательском пути.

### Очистка остаётся пользовательским действием

Фикстура регистрирует аккаунт до отправки формы и ведёт список созданных имён и slug. После теста отдельный context входит в каждый аккаунт, удаляет все видимые инстансы через интерфейс и ждёт пустого списка и нулевой квоты. Это выполняется и после ошибки. Для сценария общей ёмкости аккаунты обходятся последовательно.

Восстановление остановленного agent и остановка фоновых проб выполняются раньше пользовательской очистки. Если UI-очистка не удалась, тест не удаляет CR или строки базы в обход продукта: запуск падает, сохраняет безопасные идентификаторы и затем уничтожает весь принадлежащий ему временный стенд штатной обвязкой.

### Секреты регистрируются до формирования отчёта

Runner создаёт закрытый файл контрольных секретов в каталоге состояния. В него входят `testpassword`, JWT-секрет процесса и каждый одноразовый пароль Valkey сразу после чтения из интерфейса. HTML-отчёт проходит очистку по всем значениям, затем общий сканер проверяет отчёт и диагностику, включая ZIP и встроенные данные.

Автоматические снимки Playwright отключаются. Фикстура ошибки делает снимок сама и маскирует поля `Пароль базы` и `Новый пароль`. Trace остаётся выключенным. Диагностика Kubernetes не содержит Secret, а журнал host-оператора хранится отдельно от попытки собрать журнал оператора внутри кластера.

### CI использует fan-out и единый fan-in

У `lint-api`, `lint-operator`, `lint-web`, `test-api`, `test-operator`, `test-web`, `test-integrations`, `test-e2e`, `build-api` и `build-web` нет `needs`. GitHub Actions может запускать их сразу; ограничение фактического параллелизма остаётся за числом доступных runners.

Новое итоговое задание зависит от всех десяти jobs, запускается с `if: always()` и принимает только результат `success` каждого обязательного задания. `deploy` зависит от этого барьера и по-прежнему запускается только для `push` в `main`. Образы собираются и публикуются независимо, но не используются при провале любой проверки.

Альтернатива с прямым списком всех проверок в `deploy.needs` не даёт одного стабильного обязательного результата для branch protection. Ожидание lint перед тестами экономит runner time на плохом коммите, но увеличивает критический путь и противоречит выбранному приоритету скорости.

## Risks / Trade-offs

- [Общий стенд может остаться загрязнённым после ошибки] → Каждый тест выполняет UI-teardown, а следующий сценарий начинает с нового аккаунта; ошибка очистки остаётся видимой и делает запуск неуспешным.
- [Полный e2e не уложится в лимит CI] → Headless не получает демонстрационных пауз, образы Valkey заранее загружаются на три ноды, а предел задания равен 60 минутам по измеренному запуску на CI.
- [Одноразовый пароль попадёт в снимок или HTML] → Снимки создаются только общей фикстурой с маскированием, известные значения очищаются и затем ищутся отдельным сканером.
- [Восстановление worker повредит чужое окружение] → Docker и Kubernetes цели сверяются с Compose project, именем agent, container ID и Node UID текущего запуска.
- [Параллельные сборки потратят ресурсы при ранней ошибке lint] → Это принятая цена сокращения критического пути; итоговый барьер всё равно запрещает deploy.
- [Production lifecycle оставит инстанс после ошибки] → `test-e2e-prod` остаётся ручным, выполняет повторную UI-очистку и сообщает безопасные идентификаторы для ручного удаления, если интерфейс недоступен.

## Migration Plan

1. Добавить помощники Playwright, проверку каталога, очистку, TLS-клиент и безопасные диагностические файлы.
2. Расширить e2e-runner оператором, стабильным публичным адресом и учётом процессов.
3. Реализовать сценарии по группам `@prod`, `@local` и `@local-k8s`, затем измерить полный headless-запуск.
4. Поднять конечные сроки Playwright и CI по измерению, не сокращая отрицательные проверки.
5. Перевести workflow на независимый fan-out и итоговый barrier, обновить его автоматическую проверку.
6. Обновить `tests/e2e` и системную документацию, удалить устаревший корневой `e2e/TODO.md`.

Откат выполняется возвратом прежнего задания регистрации и последовательного графа CI. Миграции данных и совместимость публичного API не требуются.
