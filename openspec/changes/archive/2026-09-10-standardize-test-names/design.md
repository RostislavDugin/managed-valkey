## Context

См. мотивацию в `proposal.md` и требования в `specs/test-orchestration/spec.md`.

В проекте есть 331 самостоятельная Go-функция тестов и 69 мест объявления `t.Run`. Vitest содержит 100 объявлений тестовых сценариев: 96 прямых вызовов `it` или `test` и четыре вызова `.each`. В нём также есть 28 групп `describe`. Playwright содержит один e2e-сценарий. Ещё семь shell-файлов проверяют тестовую инфраструктуру без отдельного фреймворка сценариев.

Все 62 k3s-сценария оператора перечислены по точному имени в `scripts/operator_test_scenarios.tsv`. Скрипты подготовки и CI выбирают envtest по префиксу `TestEnvtest`, а проверки запуска используют искусственные имена Go-тестов как входные данные. Эти ссылки входят в миграцию имён.

## Goals / Non-Goals

**Goals:**

- Сделать имя каждого самостоятельного теста понятным без чтения его тела.
- Использовать естественный русский текст там, где фреймворк допускает строковое описание.
- Сохранить машинную надёжность Go-идентификаторов, фильтров и каталога оператора.
- Провести переименование параллельно по непересекающимся областям репозитория.

**Non-Goals:**

- Не менять подготовку, действия и проверки существующих тестов.
- Не разделять крупные тесты и не объединять мелкие, даже если новое имя получается длинным.
- Не переименовывать тестовые файлы, вспомогательные функции и переменные только ради единообразия.
- Не переписывать архивные OpenSpec-артефакты, старые отчёты и журналы с прежними именами.
- Не запускать корневой или дочерние `just test-full`, отдельные e2e-команды и другие наборы, которые выполняют тестовые сценарии.

## Decisions

### Go-функции используют структурированное английское имя

Самостоятельная функция получает одну из форм:

```text
Test_<WhatWeDo>_<WhatWeExpect>
Test_<WhatWeDo>_<WhichConditions>_<WhatWeExpect>
```

Условие начинается с подходящего слова `When`, `With`, `Without`, `After` или `Before`. Сегменты пишутся в `PascalCase`; между смысловыми частями ставится `_`. Предпочтительно длинное точное имя, а не сокращение, понятное только автору теста.

Альтернатива состояла в добавлении одного `_` после существующего префикса `Test`. Она отклонена: многие текущие имена одновременно называют несколько действий и результатов, поэтому механическая вставка разделителя не делает их понятнее.

### Идентификаторы матрицы сохраняются отдельным сегментом

Integration-тесты оператора сохраняют обозначения `HA`, `FP`, `ND`, `NT`, `OP`, `RZ`, `PW`, `DL` и `CT` сразу после `Test_`, например:

```text
Test_CT14HA03_ReconcilePendingReplica_WhenCapacityReturns_MarksReplicaRunning
```

Так отчёты продолжают связывать тест с обязательной матрицей, а смысловая часть имени остаётся читаемой. Перенос идентификаторов в комментарии отклонён, потому что отчёт извлекает их из имён тестов и комментарии в проекте допускаются только для невыразимой кодом причины.

### Строковые сценарии пишутся по-русски

Самостоятельные сценарии `t.Run`, `it` и `test` получают длинную русскую формулировку без точки в конце. Название сообщает наблюдаемое действие, существенное условие и результат. Оно не обязано повторять имя родительской Go-функции.

Исключение действует для запускателя, который вызывает бывшие самостоятельные Go-функции как подтесты: строка `t.Run` сохраняет полное имя функции дословно. Это позволяет сопоставлять прежний самостоятельный тест с отчётом без второго словаря имён.

`describe` остаётся названием группы. Значения табличных вариантов вроде `level=debug`, `status=503`, имени стадии или конфигурации сохраняются короткими, если действие и результат уже заданы родительским тестом. Полноценная фраза нужна, когда значение `testCase.name` само различает поведение и ожидание.

Альтернатива с `Test_...` во всех строках отклонена: свободный текст позволяет писать понятнее и не заставляет читать английский идентификатор как предложение.

### Playwright-теги отделяются от названия

Тег `@prod` переносится в объект `TestDetails` через `{ tag: "@prod" }`. Установленный Playwright 1.63 поддерживает эту форму и учитывает метаданные при `--grep @prod`. Заголовок остаётся чистым русским сценарием.

### Точные ссылки меняются вместе с тестом

Для k3s-сценариев одновременно меняются функции в `operator/integration` и выражения в `scripts/operator_test_scenarios.tsv`. Префикс envtest меняется с `TestEnvtest` на `Test_Envtest`; соответствующие `-run` и шаблоны отчётов обновляются вместе с функциями. Искусственные имена в shell-проверках получают тот же формат, чтобы проверки не закрепляли старое соглашение.

Архивные документы остаются неизменными: они описывают имена и результаты на момент прежнего запуска.

### Области работы не пересекаются

Переименование выполняется параллельно четырьмя направлениями:

1. `api` и общий `internal`.
2. `operator/api` и `operator/internal`.
3. `operator/integration`, каталог и скрипты с точными именами Go-тестов.
4. `web`, `tests/e2e`, корневой `AGENTS.md`, объединение и проверки.

Каждое направление читает тело теста перед выбором имени. Массовое преобразование по регулярному выражению допускается только после составления смыслового соответствия старых и новых имён.

### Проверка не запускает инфраструктурные сценарии

Go-пакеты компилируются без выполнения тестов обычного, envtest и integration-вариантов через `go test -run '^$'` с нужными build tags. Frontend и e2e проходят проверку типов. Изменённые shell-файлы проверяются через `bash -n`, а `scripts/validate_operator_test_scenarios.sh` подтверждает соответствие 62 integration-тестов каталогу.

После объединения с `unify-just-commands` команда `just test` в корне и приложениях обозначает быстрый набор, а `just test-full` добавляет тесты с тяжёлой инфраструктурой. Эта миграция не запускает ни один из этих рецептов: для переименования достаточно прямой компиляции без выполнения тестов. Также не запускаются `pnpm test`, Playwright и отдельные e2e-команды. Итог сообщает, что проверены компиляция, типы и каталог, но не поведение быстрых или полных наборов.

## Risks / Trade-offs

- Длинные Go-имена ухудшают компактность вывода и выражений `-run` -> смысловые части разделяются `_`, а краткость не считается целью.
- Название может пообещать больше, чем проверяет тело теста -> каждый тест переименовывается после чтения его подготовки и утверждений, без догадок по старому имени.
- Параллельная работа может рассинхронизировать integration-функции и каталог -> одна область владеет обоими наборами файлов, затем запускается проверка полного назначения.
- Фильтр может незаметно выбрать ноль envtest -> меняются и `-run`, и проверка строки `PASS`; компиляция выполняется отдельно с тегом `envtest`.
- Переименование может случайно затронуть рабочий код -> изменения ограничиваются именами тестов, строками сценариев, тестовыми данными запуска и документацией соглашения; итоговый diff проверяется отдельно.

## Migration Plan

1. Добавить общее правило в корневой `AGENTS.md`.
2. Параллельно переименовать тесты в четырёх непересекающихся областях.
3. Синхронизировать каталог, фильтры и проверки отчётов с новыми Go-именами.
4. Найти оставшиеся объявления, которые нарушают соглашение, и проверить diff на отсутствие изменений поведения.
5. После объединения с актуальными командами из `unify-just-commands` выполнить прямую компиляцию Go без тестов, проверки типов, синтаксиса shell и каталога оператора; не запускать `just test`, `just test-full`, `pnpm test` и e2e-команды, а в отчёте перечислить эти ограничения.

Откат выполняется обратным переименованием функций, строк и точных ссылок одним изменением. Миграции данных и совместимость рабочих компонентов не требуются.
