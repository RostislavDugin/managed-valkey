## Context

См. мотивацию в `proposal.md`. Общий интеграционный набор уже создаёт отдельную учётную запись и экземпляр в режиме `single` через настоящий HTTP API, ждёт согласованного состояния в API и Kubernetes и подключается к Valkey. Его клиент Kubernetes читает `Namespace`, `ValkeyInstance` и `Pod`, но текущая проверка учитывает только часть меток. Тестовый клиент HTTP не поддерживает маршрут метрик.

Оператор, собранный с тегом `integration`, собирает метрики раз в секунду и записывает последний снимок процесса в `ValkeyInstance.status.metrics`. Фоновый импорт API переносит снимок в PostgreSQL, а маршрут метрик читает агрегированный временной ряд из базы. Ответ может содержать пустые точки для интервалов, в которых снимка не было. Загрузка CPU остаётся необязательной в рабочем контракте, однако общий интеграционный стенд запускает `Metrics Server`.

Адрес электронной почты нельзя хранить в значении метки Kubernetes из-за символа `@`, поэтому контракт использует аннотацию `valkey.h3llo-demo.com/user-email`. Новые метки содержат идентификаторы экземпляра и пользователя, а `Pod` также получает метку подтверждённой роли `valkey.h3llo-demo.com/role`.

## Goals / Non-Goals

**Goals:**

- Проверить полный путь метрик на общем стенде без подмены оператора, фонового импорта или PostgreSQL.
- Проверить перенос метаданных от зарегистрированной учётной записи до объектов, создаваемых API и оператором.
- Использовать существующие сроки ожидания, диагностику и один из уже создаваемых экземпляров Valkey.

**Non-Goals:**

- Проверять все варианты агрегации, окна метрик, авторизацию и ошибки маршрута HTTP API. Эти случаи остаются в тестах API.
- Повторять проверку метрики после изменения ресурсов или ротации пароля. Замену процесса и новый снимок уже проверяет интеграционный набор оператора.
- Читать PostgreSQL или менять объекты Kubernetes из общего интеграционного теста.
- Расширять клиент Kubernetes чтением всех дочерних ресурсов оператора. Их метаданные уже покрыты модульными тестами и тестами `envtest`.

## Decisions

### Проверять метрики через публичный маршрут HTTP API

Тестовый клиент HTTP получит структуры ответа метрик и метод чтения окна `range=5m`. Сценарий будет опрашивать этот маршрут через общий помощник ожидания, пока ряд узла `ordinal=0` не получит хотя бы одну непустую точку с ожидаемыми именем и ролью.

Проверка не будет читать PostgreSQL напрямую. Маршрут строит ответ из таблицы метрик, а база каждого запуска изолирована и изначально пуста. Поэтому непустая точка для нового экземпляра подтверждает оба перехода: из `ValkeyInstance.status.metrics` в PostgreSQL и из PostgreSQL в HTTP.

Тест будет искать непустую точку внутри ряда, а не ожидать, что первая точка содержит данные. API заполняет пропуски `null` и может вернуть их перед актуальным интервалом. Обязательные показатели Valkey должны присутствовать и быть неотрицательными. Загрузка CPU также должна присутствовать, поскольку общий интеграционный стенд включает `Metrics Server` и может проверить эту часть настоящего сбора.

Альтернатива с сопоставлением снимка из `ValkeyInstance.status.metrics` и точки HTTP по точному времени не подходит: HTTP группирует снимки по временным интервалам и возвращает время интервала, а не исходное `collected_at`. Прямое чтение строки базы нарушило бы границы общего набора.

### Выполнить проверку метрик один раз в сценарии создания

Ожидание метрик будет отдельным шагом `Test_CreateSingleValkey_WithRealApiAndOperator_BecomesReachableAndRunning` после подтверждения готовности. Метрики не являются условием готовности Valkey, поэтому их ожидание не войдёт в общий помощник `waitForReady`.

Такой шаг проверяет новый сквозной путь и не связывает изменение ресурсов, ротацию пароля и удаление с доступностью телеметрии. Новый самостоятельный тест потребовал бы пятого участника общего барьера, дополнительной учётной записи и ещё одного `Pod`.

### Проверять метаданные на уже читаемых объектах

Общий предикат готовности Kubernetes будет дополнен следующими проверками:

- `Namespace`: идентификатор экземпляра, идентификатор пользователя и аннотация с адресом электронной почты;
- `ValkeyInstance`: идентификатор экземпляра, идентификатор пользователя и аннотация с адресом электронной почты;
- `Pod`: идентификатор экземпляра, идентификатор пользователя, роль `primary` в метке `valkey.h3llo-demo.com/role` и аннотация с адресом электронной почты.

Эти три объекта пересекают обе границы ответственности. API создаёт метаданные `Namespace` и `ValkeyInstance`, а оператор переносит их на `Pod` и назначает роль после проверки процесса. Чтение `StatefulSet`, `Service`, `PodDisruptionBudget` и `NetworkPolicy` не добавит нового сквозного перехода и усложнит тестовый клиент.

Диагностическая строка ожидания будет содержать только идентификаторы и факт совпадения метаданных. Адрес электронной почты не следует записывать в журнал, хотя тестовое значение не является секретом.

### Расширить локальную проверку тестового клиента HTTP

Существующий тест клиента проверит путь, параметры запроса, заголовок авторизации и разбор минимального ответа метрик. Это отделит ошибки клиента от ошибок общего стенда и не потребует нового сетевого окружения.

## Risks / Trade-offs

- [`Metrics Server` ещё не успел опубликовать свежую загрузку CPU] -> Ждать точку с CPU до общего срока операции вместо проверки первого ответа.
- [В окне метрик есть только заполнители `null`] -> Искать любую непустую точку и сохранять последний ответ HTTP в диагностику при истечении срока.
- [Общая проверка метаданных задержит готовность при ошибке одного компонента] -> Включить в последнее наблюдение, на каком объекте метаданные ещё не совпали.
- [Телеметрия сломана, но остальные сценарии жизненного цикла исправны] -> Проверять метрики только в сценарии создания, чтобы остальные сценарии сохранили самостоятельный результат.

## Migration Plan

1. Расширить тестовый клиент HTTP и его локальную проверку поддержкой маршрута метрик.
2. Добавить ожидание непустой метрики в сценарий создания.
3. Дополнить проверку готовности Kubernetes метками и аннотацией с адресом электронной почты.
4. Запустить локальные тесты обвязки, затем общий интеграционный набор с контролем ресурсов и очистки стенда.

Откат удаляет новые утверждения и поддержку метрик из тестового клиента. Рабочие данные и интерфейсы не меняются.
