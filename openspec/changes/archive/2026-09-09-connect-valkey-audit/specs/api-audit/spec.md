## MODIFIED Requirements

### Requirement: Сервисы записывают аудит через общий контракт

Сервисы пользователей и Valkey SHALL записывать аудит через отдельный внутренний сервис аудита. Он SHALL принимать автора, снимок email, действие, service/resource ID, request ID и время операции без загрузки модели пользователя или Valkey. Сервис Valkey SHALL зависеть только от контракта записи аудита. HTTP-слой SHALL обращаться к сервису Valkey для проверки владельца, а к сервису аудита для чтения событий. Сервис аудита MUST NOT вызывать сервис Valkey или зависеть от его модели. Публичный HTTP API SHALL разрешать только чтение аудита и MUST NOT принимать события от клиента.

#### Scenario: ID новой базы доступен до аудита

- **WHEN** создание инстанса получило ID внутри незавершённой транзакции
- **THEN** сервис Valkey передаёт этот ID сервису аудита по контракту записи
- **AND** сервис аудита сохраняет событие в той же транзакции без обратного вызова сервиса Valkey

#### Scenario: Событие аккаунта

- **WHEN** пользователь регистрируется или успешно входит
- **THEN** сервис пользователей вызывает общий аудит с `user.register` или `user.login`, `resource_id=null` и `service=null`

#### Scenario: Чтение журнала Valkey

- **WHEN** аутентифицированный пользователь запрашивает аудит инстанса
- **THEN** HTTP-слой сначала проверяет владельца через сервис Valkey
- **AND** затем читает события через отдельный сервис аудита

## ADDED Requirements

### Requirement: API отдаёт аудит выбранного инстанса

`GET /v1/managed/valkey/instances/{id}/audit` SHALL после проверки владельца возвращать только события сервиса Valkey с `resource_id`, равным `{id}`. Каждая строка ответа SHALL содержать `id`, `action`, `user_email` и `created_at`. Поля `request_id`, `user_id` и другие данные таблицы MUST NOT попадать в ответ. Порядок событий SHALL быть `created_at DESC, id DESC`.

#### Scenario: Владелец читает журнал

- **WHEN** владелец запрашивает аудит инстанса, для которого сохранены события
- **THEN** API возвращает события этого инстанса от новых к старым
- **AND** каждое событие содержит только публичные поля журнала

#### Scenario: Чужой или неизвестный инстанс

- **WHEN** пользователь запрашивает аудит чужого или несуществующего инстанса
- **THEN** API возвращает `404 NOT_FOUND`
- **AND** не раскрывает наличие инстанса или его событий

#### Scenario: Запись события не доступна через HTTP

- **WHEN** клиент пытается отправить изменяющий запрос на путь аудита
- **THEN** API не принимает событие и не добавляет строку в `audit_logs`

### Requirement: API загружает аудит по непрозрачному курсору

Параметр `limit` SHALL принимать целое число от 1 до 200, по умолчанию 50. API SHALL читать на одну строку больше лимита и возвращать `{items, next_cursor}`. Если старых событий нет, `next_cursor` SHALL быть `null`. Иначе курсор SHALL кодировать пару `{created_at, id}` последнего возвращённого события в base64url без padding и сохранять микросекундную точность времени. Параметр `before` SHALL принимать курсор без необходимости разбирать его на клиенте. Следующая страница SHALL содержать строки, для которых `(created_at, id)` меньше позиции курсора.

#### Scenario: Есть следующая страница

- **WHEN** после первых `limit` событий есть более старые строки
- **THEN** API возвращает первые `limit` строк и непустой `next_cursor`
- **AND** запрос с этим курсором возвращает следующую страницу

#### Scenario: События имеют одинаковое время

- **WHEN** граница страниц проходит между событиями с одинаковым `created_at`
- **THEN** последовательная загрузка страниц не пропускает и не повторяет события

#### Scenario: Журнал загружен полностью

- **WHEN** после возвращённых событий нет более старых строк
- **THEN** API возвращает `next_cursor=null`

#### Scenario: Неверные параметры страницы

- **WHEN** `limit` не является целым числом от 1 до 200 или `before` нельзя разобрать как допустимый курсор
- **THEN** API возвращает `400 VALIDATION_FAILED`
- **AND** не выполняет частичную загрузку с другим значением параметра
