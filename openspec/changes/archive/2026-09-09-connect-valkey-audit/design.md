## Context

`audit_logs` уже хранит события аккаунтов и Valkey. Пакет `api/internal/audit` владеет записью, а `valkey.Service` получает узкий интерфейс `AuditWriter`. Чтения в репозитории и сервисе нет. Маршрутизатор проверяет владельца инстанса через общий middleware, но путь `/audit` не зарегистрирован.

Во фронтенде осталась только заглушка `ValkeyAuditPage`. В прежней реализации страницы уже были группировка по местным датам, постраничная загрузка и оформление строк, но источник данных находился в локальном хранилище и не знал про действие `instance.whitelist.update`. Эту реализацию можно использовать как основу, не возвращая локальное хранение.

## Goals / Non-Goals

**Goals:**

- Сохранить `audit` самостоятельной предметной границей для записи и чтения событий.
- Исключить циклическую зависимость между сервисами `audit` и `valkey`.
- Подключить страницу к серверу без изменения таблицы и формата существующих записей.
- Обеспечить устойчивую постраничную загрузку и изоляцию журналов разных владельцев.

**Non-Goals:**

- Публичная запись событий аудита.
- Экран аудита действий аккаунта.
- Фильтрация, поиск, экспорт и автоматическая очистка журнала.
- Подключение метрик Valkey.

## Decisions

### 1. HTTP-слой связывает сервис владельца и сервис аудита

Сервис аудита владеет моделями события, курсора и страницы, проверкой параметров, кодированием курсора и чтением репозитория. Он принимает `service` и `resource_id`, поэтому не импортирует пакет `valkey` и не загружает инстанс.

Сервис Valkey продолжает зависеть только от контракта записи аудита. В обработчике запроса общий middleware сначала проверяет `(instance_id, user_id)`, затем обработчик передаёт ID отдельному сервису аудита.

```text
cmd/api
  |
  +--> audit service --> audit repository --> audit_logs
  |
  +--> valkey service --> valkey repository
           |
           `--> audit writer

GET /instances/{id}/audit
  |
  +--> valkey ownership check
  `--> audit reader
```

При запуске `audit.Service` создаётся раньше `valkey.Service` и передаётся в его конструктор как реализация узкого интерфейса записи. Передавать аудит после создания через сеттер не нужно: такой объект мог бы принять изменение без обязательной записи события.

Альтернатива: добавить чтение журнала в `valkey.Service`. Она уменьшает число аргументов маршрутизатора, но смешивает управление базой с хранением аудита и делает границу формальной. Поэтому чтение остаётся в `audit`.

### 2. Событие создания записывается после INSERT и до commit

Создание Valkey сначала вставляет строку инстанса и получает UUIDv7. Затем оно передаёт этот ID сервису аудита в рамках той же транзакции. Commit выполняется только после успешной записи события.

Это не создаёт зависимости `audit` от `valkey`: сервис аудита получает обычный UUID и идентификатор сервиса. Ошибка аудита по-прежнему отменяет создание, а ошибка последующей записи отменяет уже добавленное событие.

Альтернатива: заранее генерировать ID или записывать аудит после commit. Предварительный ID здесь не нужен, а отдельный commit нарушил бы атомарность.

### 3. Репозиторий читает страницы по составному ключу

Запрос фильтрует строки по `service = 'valkey'` и `resource_id`, затем сортирует по `created_at DESC, id DESC`. При наличии курсора добавляется условие `(created_at, id) < (?, ?)`. Существующий индекс `audit_logs_resource_created_id_idx` соответствует фильтру по ресурсу и порядку страницы; дополнительная миграция для первой версии чтения не нужна.

Сервис запрашивает `limit + 1`, отделяет лишнюю строку и строит курсор по последнему событию, которое попало в ответ. Репозиторий и сервис используют отдельные узкие контракты чтения и записи, чтобы тестовая подмена отказа записи не должна была изображать чтение.

Альтернатива: пагинация через `OFFSET`. Она проста, но новые вставки сдвигают страницы и приводят к повторам или пропускам.

### 4. Курсор кодируется и проверяется в сервисе аудита

Курсор содержит JSON с `created_at` в UTC и `id`, закодированный через base64url без padding. Время разбирается без потери микросекунд, ID проверяется как UUID. Пустые, лишние или неверно типизированные поля не принимаются. HTTP-обработчик проверяет допустимые query-параметры и целочисленный диапазон `limit`, после чего передаёт нормализованный запрос сервису.

Курсор не подписывается. Изменение его позиции не даёт доступа к другому журналу, потому что проверка владельца и фильтр по `resource_id` выполняются для каждого запроса.

### 5. Фронтенд хранит код аудита внутри среза `pages/valkey`

Запрос используется одной страницей, поэтому по правилам FSD остаётся в `pages/valkey/api/valkey-audit.ts`. Типы, подписи действий и группировка дат находятся в `pages/valkey/model/valkey-audit.ts`; отдельные слои `features` и `entities` не создаются. Транспортный тип преобразует `user_email`, `created_at` и `next_cursor` в имена модели клиента.

`ValkeyAuditPage` получает только `instance.id` из контекста карточки. Идентификатор пользователя в запрос не передаётся: API берёт владельца из JWT. Первая загрузка и запрос следующей страницы используют `AbortController` и номер поколения запроса. При смене инстанса, повторе первой загрузки или размонтировании старый ответ игнорируется.

В основу интерфейса берётся прежняя серверно-независимая разметка журнала. В неё добавляется `instance.whitelist.update`, а локальный клиент и `ownerId` не возвращаются. Относительное время пересчитывается раз в минуту.

### 6. Тесты проходят через рабочие границы

Интеграционные тесты API отправляют запросы через `httptest.Server` и настоящий маршрутизатор в PostgreSQL. Прямой доступ к таблице используется только для подготовки событий с одинаковым временем, очистки и проверки отсутствия лишних данных. Тесты покрывают владельца, чужой ID, публичный состав ответа, значения лимита, неверный курсор, несколько страниц и историю после принятого удаления.

Во фронтенде отдельные тесты проверяют преобразование HTTP-ответа и передачу непрозрачного курсора, группировку местных дат, подписи шести действий, состояния страницы, защиту от двойной загрузки и игнорирование отменённого ответа.

## Risks / Trade-offs

- [Новое событие появляется после загрузки первой страницы] -> Курсорная пагинация продолжает читать только более старые строки без повторов. Новое событие станет видно после повторного открытия или обновления журнала.
- [Поддельный курсор задаёт произвольную позицию] -> Каждый запрос заново проходит проверку владельца и фильтрацию по выбранному ресурсу, поэтому курсор не расширяет доступ.
- [Старый запрос завершается после смены базы] -> Клиент отменяет запрос и сверяет поколение перед изменением состояния.
- [Будущее действие отсутствует в словаре интерфейса] -> Добавление действия в контракт аудита требует одновременного дополнения подписи, иконки и теста исчерпывающего списка.

## Migration Plan

1. Выпустить API с новым безопасным `GET`-маршрутом. Существующая запись аудита и схема базы не меняются.
2. Выпустить фронтенд, который заменяет заглушку запросом к новому маршруту.
3. При откате сначала вернуть фронтенд к состоянию недоступности. Неиспользуемый `GET`-маршрут можно удалить отдельным откатом без изменения данных.
