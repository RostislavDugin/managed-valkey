# database-migrations Specification

## Purpose

Определяет безопасный и воспроизводимый порядок изменения схемы PostgreSQL через SQL-миграции `goose`, общий для локальной разработки, тестов и production.

## Requirements

### Requirement: Единый каталог SQL-миграций

Все изменения схемы PostgreSQL SHALL храниться как SQL-миграции `goose` в корневом каталоге `migrations`. API SHALL считать их единственным источником структуры базы; оператор MUST NOT импортировать миграции или обращаться к PostgreSQL.

#### Scenario: Поиск изменения схемы

- **WHEN** разработчик проверяет, как была создана или изменена таблица сервиса
- **THEN** соответствующая операция находится в упорядоченной SQL-миграции каталога `migrations`

### Requirement: Создание миграции через проектную команду

`api/Justfile` SHALL создавать миграцию командой `migration-generate name` через закреплённую проектом версию `goose`. Имя новой миграции SHALL включать переданное разработчиком описание и уникальный временной префикс.

#### Scenario: Создание SQL-миграции

- **WHEN** разработчик запускает `just migration-generate create_users` в `api`
- **THEN** в `migrations` появляется новый SQL-файл `goose` с уникальным префиксом и именем `create_users`

### Requirement: Применение и откат миграций через API Justfile

`api/Justfile` SHALL предоставлять `migration-up` для применения всех ожидающих миграций и `migration-down` для отката одной последней применённой миграции. Обе команды SHALL использовать `DATABASE_URL`; автоматический запуск production SHALL использовать только `migration-up`.

#### Scenario: Применение ожидающих миграций

- **WHEN** разработчик запускает `just migration-up` в `api`
- **THEN** `goose` применяет все ожидающие миграции по порядку к базе из `DATABASE_URL`

#### Scenario: Локальный откат последней миграции

- **WHEN** разработчик запускает `just migration-down` в `api`
- **THEN** `goose` выполняет секцию Down только последней применённой миграции и обновляет служебную версию

### Requirement: Последовательное однократное применение

Команда применения SHALL читать `DATABASE_URL`, выполнять ещё не применённые миграции по порядку и сохранять их версии в PostgreSQL. Повторный запуск на той же версии SHALL завершаться успешно без повторного выполнения уже применённых операций.

#### Scenario: Новая база

- **WHEN** миграции применяются к пустой поддерживаемой PostgreSQL 18
- **THEN** все миграции выполняются по порядку и база получает актуальную версию схемы

#### Scenario: Повторное применение

- **WHEN** команда применения запускается повторно без новых файлов
- **THEN** структура и данные не меняются, а команда завершается успешно

### Requirement: Ошибка не считается применённой миграцией

Миграция SHALL выполняться в транзакции, если файл явно не объявляет техническую необходимость выйти из неё. При ошибке версия миграции MUST NOT отмечаться применённой, а последующие миграции MUST NOT запускаться.

#### Scenario: Ошибка SQL

- **WHEN** очередная транзакционная миграция содержит недопустимую операцию
- **THEN** её изменения откатываются, версия остаётся неприменённой и команда возвращает ненулевой код

### Requirement: Миграции сохраняют совместимость выкладки

Production-миграции SHALL быть аддитивными относительно работающей версии API. Удаление или переименование используемой колонки MUST NOT происходить до выкладки версии, которая перестала её читать. Порядок выкладки SHALL оставаться таким: миграции PostgreSQL и CRD, оператор, API.

#### Scenario: Добавление обязательного поля

- **WHEN** новая версия API начинает записывать обязательную колонку
- **THEN** совместимая миграция создаёт колонку до запуска этой версии API

### Requirement: Согласованные типы и имена схемы

Миграции SHALL использовать UUIDv7 для первичных ключей, `TIMESTAMPTZ` для времени, UTC в значениях приложения и префикс `is_` или `has_` для булевых колонок. Таблицы Managed Valkey SHALL использовать префикс `valkey_`, кроме общих таблиц аккаунтов и служебной таблицы версий `goose`.

#### Scenario: Проверка новой таблицы Managed Valkey

- **WHEN** миграция добавляет таблицу предметной области с первичным ключом, временем создания и булевым признаком
- **THEN** таблица имеет префикс `valkey_`, ключ UUIDv7, колонку времени `TIMESTAMPTZ` и булеву колонку с допустимым префиксом

### Requirement: Ограничения и индексы читаются отдельно

SQL-файлы SHALL создавать таблицу до внешних ключей и вторичных индексов. Каждый внешний ключ и индекс SHALL находиться в отдельной декларации с явным именем; колонки таблицы SHALL быть отформатированы для чтения структуры без горизонтального поиска.

#### Scenario: Миграция со связью и индексом

- **WHEN** новая таблица ссылается на другую таблицу и требует вторичного индекса
- **THEN** сначала создаётся таблица, затем отдельными SQL-операциями создаются именованные внешний ключ и индекс
