# project-skill-layout

## Purpose

Определяет единое хранение проектных навыков и одинаковый доступ к ним из Codex и Claude без расходящихся копий инструкций.

## Requirements

### Requirement: Каноническое хранение навыков
Каждый проектный навык SHALL иметь единственную каноническую копию в корневом каталоге `.skills`.

#### Scenario: Проверка уникальности навыка
- **WHEN** один и тот же навык доступен нескольким агентам
- **THEN** его обычные файлы существуют только под `.skills/<skill-name>`

### Requirement: Обнаружение навыков агентами
Каталоги `.agents/skills` и `.claude/skills` SHALL предоставлять каждый общий проектный навык через относительную символическую ссылку на его канонический каталог в `.skills`.

#### Scenario: Загрузка навыка из Codex
- **WHEN** Codex открывает `.agents/skills/<skill-name>/SKILL.md`
- **THEN** ссылка разрешается в `.skills/<skill-name>/SKILL.md`

#### Scenario: Загрузка навыка из Claude
- **WHEN** Claude открывает `.claude/skills/<skill-name>/SKILL.md`
- **THEN** ссылка разрешается в тот же `.skills/<skill-name>/SKILL.md`

### Requirement: Перенос существующих навыков
Схема SHALL включать `humanizer` и все установленные навыки OpenSpec без потери общих инструкций.

#### Scenario: Проверка перенесённых навыков
- **WHEN** перенос завершён
- **THEN** `humanizer` и каждый ранее установленный навык OpenSpec доступны через обе директории агентов и не имеют сломанных ссылок

### Requirement: Общие инструкции OpenSpec
Канонические навыки OpenSpec SHALL использовать нейтральные формулировки либо явно называть команды Codex и Claude, когда синтаксис запуска различается.

#### Scenario: Различающийся синтаксис команды
- **WHEN** навык предлагает запустить следующий этап OpenSpec
- **THEN** инструкция содержит корректное имя вызова для Codex и корректную команду `/opsx:*` для Claude

### Requirement: Официальные навыки FSD и Mantine
Схема SHALL включать полный официальный пакет `feature-sliced-design` и официальные пакеты `mantine-combobox`, `mantine-form` и `mantine-custom-components` вместе с их справочными файлами.

#### Scenario: Проверка установленного пакета
- **WHEN** агент следует ссылке на установленный навык FSD или Mantine
- **THEN** доступны `SKILL.md` и все reference-файлы, на которые он ссылается

### Requirement: Зафиксированное происхождение внешних навыков
Репозиторий SHALL хранить URL источника и ревизию каждой загруженной группы навыков.

#### Scenario: Проверка происхождения
- **WHEN** разработчик проверяет происхождение внешнего навыка
- **THEN** он может определить репозиторий и точную ревизию, из которой навык был установлен

### Requirement: Документированное правило хранения
Корневой `AGENTS.md` SHALL объявлять `.skills` единственным источником проектных навыков и SHALL запрещать независимые копии в каталогах отдельных агентов.

#### Scenario: Добавление нового навыка
- **WHEN** агент добавляет новый общий проектный навык
- **THEN** он сохраняет навык в `.skills` и создаёт относительные ссылки в `.agents/skills` и `.claude/skills`

### Requirement: Цепочка инструкций web
Файл `web/CLAUDE.md` SHALL ссылаться на `web/AGENTS.md`, а `web/AGENTS.md` SHALL подключать корневые инструкции, `web/DESIGN.md` и применимые навыки FSD и Mantine.

#### Scenario: Работа агента в web
- **WHEN** агент начинает задачу в каталоге `web`
- **THEN** по цепочке локальных ссылок ему доступны общие правила проекта, дизайн-гайд и архитектурные навыки

### Requirement: Цепочка инструкций API

Файл `api/CLAUDE.md` SHALL быть относительной символической ссылкой на `api/AGENTS.md`. Локальные инструкции API SHALL сначала подключать корневой `AGENTS.md`, затем применимые разделы `SYSTEM.md`, правила Go, HTTP, PostgreSQL и миграций.

#### Scenario: Работа агента в API

- **WHEN** Codex или Claude начинает задачу в каталоге `api`
- **THEN** по локальной цепочке ему доступны общие правила проекта и инструкции по ответственности API, времени, логам, миграциям и современному Go

### Requirement: Цепочка инструкций оператора

Файл `operator/CLAUDE.md` SHALL быть относительной символической ссылкой на `operator/AGENTS.md`. Локальные инструкции оператора SHALL сначала подключать корневой `AGENTS.md`, затем применимые разделы `SYSTEM.md` и правила Go, Kubernetes, времени и логирования. Они SHALL запрещать доступ оператора к PostgreSQL и HTTP API сервиса.

#### Scenario: Работа агента в операторе

- **WHEN** Codex или Claude начинает задачу в каталоге `operator`
- **THEN** по локальной цепочке ему доступны общие правила проекта, границы ответственности оператора и правила работы с `controller-runtime`

### Requirement: Адаптированные правила Go

Локальные инструкции API и оператора SHALL содержать правила пустых строк между логическими блоками, редких комментариев о причине решения, времени в UTC, структурированного `slog`, идиом поддерживаемой версии Go и запуска тестов через локальный `Justfile`. Они MUST NOT переносить соглашения другого проекта, для которых нет соответствующего компонента или решения в Managed Valkey.

#### Scenario: Проверка заимствованных правил

- **WHEN** разработчик сравнивает локальные инструкции с указанным исходным Go-гайдом
- **THEN** в них нет чужих имён, обязательного Swagger, чужой схемы DI или структуры CRUD, а применимые правила сформулированы для API и оператора Managed Valkey

### Requirement: Корневые инструкции описывают pre-commit

Корневой `AGENTS.md` SHALL описывать проверки frontend и Go в `.githooks/pre-commit`, включая автоматическое добавление исправленного форматтером staged-кода и отмену коммита при ошибке линтера или сборки.

#### Scenario: Разработчик готовит коммит с Go-кодом

- **WHEN** разработчик читает раздел о pre-commit в корневом `AGENTS.md`
- **THEN** он видит, какие команды выполняются для API и оператора и какие изменения hook добавляет в индекс автоматически
