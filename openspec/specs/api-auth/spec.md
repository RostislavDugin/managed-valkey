# api-auth

## Purpose

Авторизация API создаёт постоянные аккаунты, выдаёт проверяемые JWT и не допускает доступ заблокированного пользователя к защищённым данным.

## Requirements

### Requirement: Проверка почты определяет следующий шаг входа

API SHALL предоставлять `POST /v1/auth/check-email` с телом `{email}` и ответом `{exists}`. Перед проверкой API SHALL убрать пробелы по краям почты и привести регистр к нижнему. Значение неверного формата MUST приводить к `400 VALIDATION_FAILED`.

#### Scenario: Аккаунт существует

- **WHEN** клиент отправляет почту существующего аккаунта в другом регистре или с пробелами по краям
- **THEN** API отвечает `200` и `{"exists": true}`

#### Scenario: Аккаунт не существует

- **WHEN** клиент отправляет допустимую почту, которой нет в базе
- **THEN** API отвечает `200` и `{"exists": false}`

#### Scenario: Почта имеет неверный формат

- **WHEN** клиент отправляет значение, которое не является допустимой почтой
- **THEN** API отвечает `400 VALIDATION_FAILED`

### Requirement: Регистрация создаёт аккаунт и начальную квоту

API SHALL предоставлять `POST /v1/auth/register` с телом `{email, password}` и обязательным заголовком `Idempotency-Key` в формате UUID. Пароль SHALL содержать от 8 символов до 72 байт UTF-8. В одной транзакции API SHALL создать пользователя с UUIDv7 и `is_blocked=false`, квоту 4 vCPU и 16 GB, запись аудита `user.register` и запись ключа регистрации. Пароль MUST храниться только как bcrypt-хеш с cost 12.

#### Scenario: Успешная регистрация

- **WHEN** клиент отправляет свободную допустимую почту, допустимый пароль и новый ключ
- **THEN** API создаёт один аккаунт и его квоту
- **AND** отвечает `200` с JWT в поле `token`

#### Scenario: Почта уже занята

- **WHEN** клиент регистрирует существующую почту с новым ключом
- **THEN** API отвечает `409 CONFLICT`
- **AND** не создаёт пользователя, квоту или запись успешной регистрации

#### Scenario: Пароль слишком короткий

- **WHEN** пароль содержит меньше 8 символов
- **THEN** API отвечает `400 VALIDATION_FAILED`

#### Scenario: Пароль не помещается в bcrypt

- **WHEN** пароль длиннее 72 байт UTF-8
- **THEN** API отвечает `400 VALIDATION_FAILED`

#### Scenario: Ключ регистрации отсутствует или повреждён

- **WHEN** клиент не передаёт `Idempotency-Key` или передаёт значение не в формате UUID
- **THEN** API отвечает `400 VALIDATION_FAILED`

#### Scenario: Конкурентная регистрация одной почты

- **WHEN** два запроса с разными ключами одновременно регистрируют одну нормализованную почту
- **THEN** ровно один запрос создаёт аккаунт
- **AND** второй получает `409 CONFLICT`

### Requirement: Повтор регистрации не создаёт второй аккаунт

Повтор `POST /v1/auth/register` с тем же `Idempotency-Key` и теми же учётными данными SHALL вернуть новый действующий JWT существующего пользователя без повторного создания данных. Ключ с другой почтой или другим паролем MUST приводить к `422 IDEMPOTENCY_MISMATCH`. Ключ SHALL действовать 24 часа.

#### Scenario: Ответ регистрации потерян

- **WHEN** первый запрос создал аккаунт, но клиент не получил ответ и повторил те же данные с тем же ключом
- **THEN** API возвращает действующий JWT того же пользователя
- **AND** в базе остаются один пользователь, одна квота и одна запись `user.register`

#### Scenario: Ключ использован с другими данными

- **WHEN** клиент повторяет ключ регистрации с другой почтой или другим паролем
- **THEN** API отвечает `422 IDEMPOTENCY_MISMATCH`
- **AND** не раскрывает сведения об аккаунте, связанном с ключом

### Requirement: Вход выдаёт JWT существующего пользователя

API SHALL предоставлять `POST /v1/auth/login` с телом `{email, password}`. После проверки bcrypt-хеша API SHALL выдать JWT HS256 на 10 лет. Поле `sub` SHALL содержать UUIDv7 пользователя, а `exp` SHALL содержать срок действия. Успешный вход SHALL создать запись аудита `user.login`.

#### Scenario: Верные учётные данные

- **WHEN** незаблокированный пользователь отправляет верные почту и пароль
- **THEN** API отвечает `200` с действующим JWT в поле `token`
- **AND** записывает успешный вход без пароля и токена

#### Scenario: Неверные учётные данные

- **WHEN** почта не существует или пароль не совпадает
- **THEN** API отвечает `401 UNAUTHORIZED` с одинаковым сообщением для обоих случаев
- **AND** не создаёт запись успешного входа

#### Scenario: Заблокированный аккаунт входит с верным паролем

- **WHEN** у пользователя `is_blocked=true`
- **THEN** API отвечает `401 UNAUTHORIZED` и не выдаёт JWT

### Requirement: JWT защищает пользовательские маршруты

Каждый защищённый маршрут SHALL требовать `Authorization: Bearer <jwt>`, принимать только JWT с алгоритмом HS256, проверять подпись и `exp`, загружать пользователя из `sub` и проверять `is_blocked` при каждом запросе. Ошибка любой проверки MUST приводить к `401 UNAUTHORIZED`.

#### Scenario: Действующий JWT

- **WHEN** незаблокированный пользователь обращается к защищённому маршруту с действующим JWT
- **THEN** обработчик получает проверенный UUID пользователя

#### Scenario: Срок JWT истёк

- **WHEN** клиент отправляет JWT с прошедшим `exp`
- **THEN** API отвечает `401 UNAUTHORIZED`

#### Scenario: Алгоритм JWT подменён

- **WHEN** клиент отправляет токен с допустимыми полями, но алгоритмом не HS256
- **THEN** API отвечает `401 UNAUTHORIZED`

#### Scenario: Пользователя заблокировали после входа

- **WHEN** действующий JWT принадлежит пользователю, которому установили `is_blocked=true`
- **THEN** следующий защищённый запрос отвечает `401 UNAUTHORIZED`

### Requirement: Текущий пользователь доступен через API

API SHALL предоставлять защищённый `GET /v1/me` и возвращать пользователя, его квоту и текущее использование ресурсов. До появления серверных ресурсов использование SHALL быть равно нулю.

#### Scenario: Пользователь восстанавливает сессию

- **WHEN** клиент вызывает `/v1/me` с действующим JWT
- **THEN** ответ содержит UUID и нормализованную почту пользователя, квоту 4 vCPU и 16 GB и текущее использование

#### Scenario: Запрос без JWT

- **WHEN** клиент вызывает `/v1/me` без заголовка авторизации
- **THEN** API отвечает `401 UNAUTHORIZED`

### Requirement: Запросы авторизации ограничены по частоте

API SHALL применять один скользящий лимит к `check-email`, `register` и `login`: не больше 10 запросов за 60 секунд на адрес прямого соединения. Успешные и ошибочные запросы SHALL учитывать один общий предел. API MUST NOT доверять forwarded-заголовкам при определении адреса.

#### Scenario: Лимит исчерпан

- **WHEN** с одного адреса приходит одиннадцатый запрос в пределах 60 секунд
- **THEN** API отвечает `429 RATE_LIMITED`
- **AND** целое число секунд до освобождения окна присутствует в `details.retry_after` и `Retry-After`

#### Scenario: Клиент подменяет forwarded-заголовок

- **WHEN** запрос содержит чужой IP в `X-Forwarded-For`
- **THEN** API учитывает адрес прямого соединения

#### Scenario: Окно освободилось

- **WHEN** самый ранний из десяти учтённых запросов вышел за границу 60 секунд
- **THEN** следующий запрос допускается

### Requirement: Ошибки API имеют единый формат

Все ответы API со статусом 4xx или 5xx SHALL иметь JSON вида `{"error":{"code":"...","message":"...","details":{...}}}`. Ответы и логи MUST NOT содержать пароль, bcrypt-хеш, JWT или заголовок `Authorization`.

#### Scenario: Обработчик возвращает известную ошибку

- **WHEN** запрос нарушает правило валидации, авторизации, конфликта или ограничения частоты
- **THEN** HTTP-статус и поле `error.code` соответствуют причине

#### Scenario: Обработчик завершается паникой

- **WHEN** при обработке запроса возникает паника
- **THEN** API отвечает `500 INTERNAL` в общем формате
- **AND** значение паники и секретные данные не попадают в ответ или лог
