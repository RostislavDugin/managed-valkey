# api-valkey-management Specification

## Purpose

API Valkey сохраняет пользовательские настройки в PostgreSQL, проверяет допустимость изменений и предоставляет постоянные данные для консоли независимо от будущей синхронизации с Kubernetes.

## Requirements

### Requirement: Маршруты инстансов проверяют владельца

API SHALL предоставлять защищённые маршруты под `/v1/managed/valkey`: `GET /instances`, `POST /instances`, `GET /instances/{id}`, `PATCH /instances/{id}`, `POST /instances/{id}/resize`, `PUT /instances/{id}/whitelist`, `GET /instances/{id}/credentials`, `POST /instances/{id}/credentials/rotate`, `DELETE /instances/{id}`. Владелец SHALL определяться по проверенному JWT. Чужой и отсутствующий UUID SHALL давать одинаковый `404 NOT_FOUND`; неверный формат UUID SHALL давать `400 VALIDATION_FAILED` после аутентификации. Перед идемпотентным повтором существующего ресурса SHALL проверяться владелец, включая сохранённую удалённую запись.

#### Scenario: Изоляция владельцев на всех маршрутах

- **WHEN** пользователь читает, изменяет или удаляет инстанс другого пользователя, включая credentials и повтор с известным ключом
- **THEN** API отвечает `404 NOT_FOUND` без сведений о ресурсе и без изменения данных

#### Scenario: Недействительная сессия

- **WHEN** любой маршрут Valkey вызван без JWT, с истёкшим JWT или от заблокированного аккаунта
- **THEN** API отвечает `401 UNAUTHORIZED`, не возвращая сохранённый идемпотентный ответ

### Requirement: Создание атомарно сохраняет намерение

`POST /instances` SHALL принимать `{name, prefix, mode, vcpu, ram_gb, password, is_whitelist_enabled?, whitelist_cidrs?}` и обязательный UUID `Idempotency-Key`. Неуказанный whitelist SHALL означать `false` и `[]`. Имя SHALL содержать от 1 до 40 символов, префикс от 3 до 20; оба допускают `[a-z0-9-]`, начинаются и заканчиваются буквой либо цифрой. Имя SHALL быть уникальным у владельца среди строк с `deleted_at IS NULL`. Режим SHALL быть `single` либо `ha`. Пароль SHALL содержать ровно 32 символа `[A-Za-z0-9_-]`. Создание SHALL сохранять инстанс, аудит, открытый биллинговый период и идемпотентный ответ одной транзакцией, затем возвращать `202` с DTO инстанса.

#### Scenario: Начальные значения

- **WHEN** API принимает допустимое создание в пределах квот
- **THEN** ответ содержит UUIDv7, `status=provisioning`, `desired_generation=1`, `observed_generation=0`, `password_version=1`, `applied_password_version=0`, `applied_vcpu=0`, `applied_ram_gb=0`, `observed_at=null`, `is_stale=true`, `is_updating=true`
- **AND** `created_at`, `updated_at` и `configuration_requested_at` имеют одну временную отметку принятия
- **AND** повторное чтение после перезапуска API возвращает сохранённый инстанс

#### Scenario: Whitelist задаётся при создании

- **WHEN** клиент передаёт включённый whitelist с допустимыми CIDR
- **THEN** API сохраняет нормализованный список в первоначальном поколении
- **AND** не выполняет вторую операцию настройки и не создаёт второе событие аудита

#### Scenario: Занятое имя

- **WHEN** у владельца есть неудалённый инстанс с таким именем, в том числе `deleting`
- **THEN** API отвечает `409 CONFLICT` с `details.reason=name_taken` и `details.field=name`
- **AND** такое же имя у другого владельца не мешает созданию

#### Scenario: Ошибка одной из связанных записей

- **WHEN** запись инстанса, аудита, периода или идемпотентного ответа завершается ошибкой
- **THEN** API не возвращает `202`, а все записи этой попытки откатываются

### Requirement: Адреса и секреты имеют постоянный контракт

API SHALL создавать глобально уникальный slug `<prefix>-<6 случайных символов [a-z0-9]>` и повторять подбор при коллизии. `prefix` SHALL использоваться только как вход создания, не сохраняться отдельно и не возвращаться в DTO. Slug SHALL оставаться занятым после soft delete. Адреса и порт SHALL фиксироваться при создании из конфигурации сервера; `host_ro` SHALL быть `null` в `single` и адресом `<slug>-ro.<domain>` в `ha`. `mode`, `slug`, адреса, владелец и ID MUST NOT изменяться через публичные мутации. Credentials SHALL содержать `{host, host_ro, port, username, password_hint, password_version, applied_password_version}`, где `username=app`. API SHALL хранить только SHA-256 пароля и первые четыре символа; полный пароль и хеш MUST NOT появляться в DTO, аудитах, логах или сохранённых ответах.

#### Scenario: Коллизия slug

- **WHEN** генератор сначала возвращает занятый slug, затем свободный
- **THEN** создание завершается с новым slug и ровно одним набором связанных записей

#### Scenario: Смена настроек домена

- **WHEN** сервер перезапущен с новым доменом или портом
- **THEN** существующий инстанс сохраняет свои адреса, новые инстансы используют новую конфигурацию

#### Scenario: Проверка секретов

- **WHEN** клиент создаёт инстанс, читает список, карточку, credentials или повторяет создание
- **THEN** ответы содержат только маску и версии пароля
- **AND** исходный пароль отсутствует в хранимых данных и логах, а ACL-хеш доступен только во внутренней записи инстанса

### Requirement: Чтение различает намерение и наблюдения

Список SHALL возвращать `{items: [...]}` только для текущего владельца и строк с `deleted_at IS NULL`, включая `deleting`, в порядке `created_at DESC, id DESC`. Карточка SHALL возвращать публичные настройки, адреса, маску, desired/applied размеры и режим, поколения, версии, временные отметки, признаки восстановления и проверки сети. Вычисляемый `status` SHALL учитывать сначала подтверждённое удаление, затем запрос удаления, затем фазу. `is_stale` SHALL быть true при отсутствии `observed_at` или возрасте строго больше 60 секунд; `is_updating` SHALL означать неравенство поколений. HTTP API MUST NOT имитировать наблюдения, готовность или подтверждённое удаление.

#### Scenario: Синхронизация ещё не реализована

- **WHEN** после создания выполняются повторные GET-запросы
- **THEN** база остаётся `provisioning` с неприменённым поколением и без свежего наблюдения
- **AND** чтение не меняет строку инстанса

#### Scenario: Запоздалое наблюдение после запроса удаления

- **WHEN** у инстанса есть `deletion_requested_at`, но сохранённая фаза равна `running`
- **THEN** список и карточка показывают `deleting`

### Requirement: Изменения конфигурации образуют одну последовательность

Создание, PATCH метаданных, ресайз, whitelist, смена пароля и удаление SHALL сериализовать проверку и запись под общим транзакционным advisory lock. После ожидания существующий инстанс SHALL читаться заново. Успешный повтор SHALL предшествовать проверке удаления; далее SHALL проверяться удаление, отсутствие изменения для resize/whitelist, занятость поколения, фаза и свежесть, специфические ограничения операции, квоты. Новая конфигурация SHALL приниматься только в `running` или `degraded`, при свежем наблюдении и равных поколениях. Вся операция SHALL использовать одно время принятия после получения lock.

#### Scenario: Предыдущее изменение не применено

- **WHEN** новый resize, whitelist или пароль меняет конфигурацию при неравных поколениях
- **THEN** API отвечает `409 OPERATION_IN_PROGRESS` даже при одновременно устаревшем наблюдении

#### Scenario: Инстанс не готов

- **WHEN** поколения равны, но фаза не `running`/`degraded` либо наблюдение отсутствует или старше 60 секунд
- **THEN** новое изменение получает `409 INSTANCE_NOT_READY`

#### Scenario: Ресайз принят

- **WHEN** `POST /instances/{id}/resize` с `{vcpu, ram_gb}` и новым ключом проходит проверки
- **THEN** API отвечает `202`, меняет desired-размер, увеличивает поколение на один и обновляет `updated_at` и `configuration_requested_at`
- **AND** сохраняет все наблюдаемые поля, пароль, slug и режим

#### Scenario: Повтор текущей конфигурации без старого ключа

- **WHEN** клиент запрашивает текущий desired-размер с новым ключом либо тот же нормализованный whitelist, а удаление не начато
- **THEN** API отвечает `200` с текущим DTO, даже при активном поколении или неподходящей фазе
- **AND** не меняет поколение, аудит, биллинг и временные отметки инстанса
- **AND** для resize сохраняет идемпотентный ответ `200`

#### Scenario: Запрос ждал удаления

- **WHEN** удаление принято, пока другой запрос ожидает общий lock
- **THEN** ожидавшее изменение после получения lock отвечает `409 INSTANCE_NOT_READY` с `reason=deleting`
- **AND** не восстанавливает прежние данные из снимка middleware

### Requirement: Whitelist нормализуется и допускает закрытие доступа всем

Whitelist SHALL принимать флаг и не более 100 IPv4-адресов/CIDR, преобразовывать одиночный адрес в `/32`, маскировать биты хоста, удалять дубликаты и сортировать канонические сети. IPv6 и неверные значения SHALL отклоняться и при выключенном флаге. Включённый пустой список SHALL означать deny-all. Новое значение SHALL увеличивать только общее поколение конфигурации; пароль, наблюдения и биллинг SHALL сохраняться.

#### Scenario: Эквивалентные списки

- **WHEN** запрос переставляет сети, добавляет дубликаты либо заменяет `192.0.2.1/24` на `192.0.2.0/24`
- **THEN** после нормализации API распознаёт отсутствие изменения

#### Scenario: Нулевые значения

- **WHEN** клиент выключает whitelist и передаёт пустой список
- **THEN** API сохраняет `false` и `[]` явно

### Requirement: Пароль меняется с проверкой версии

Смена пароля SHALL принимать `{password, expected_password_version}` и обязательный ключ. После общих проверок несовпадение ожидаемой версии SHALL давать `409 CONFLICT` с `reason=password_version_mismatch`; совпадение нового хеша с текущим SHALL давать `400 VALIDATION_FAILED`. Успех SHALL увеличивать версию пароля и desired-поколение на один, менять хеш и префикс, обновлять времена изменения и конфигурации и возвращать `202` с credentials. Применённая версия SHALL оставаться прежней.

#### Scenario: Принята смена пароля

- **WHEN** пароль новый, версия совпадает, инстанс готов
- **THEN** ответ содержит новую маску, увеличенную версию и прежнюю applied-версию
- **AND** квота и периоды не меняются

#### Scenario: Повтор после принятия

- **WHEN** клиент повторяет тот же ключ и тело после роста версии
- **THEN** получает первоначальный `202`, без конфликта версии и второго аудита

### Requirement: Метаданные меняются независимо от конфигурации

PATCH SHALL принимать только `{name?, maintenance?}`. Maintenance SHALL быть `null` либо полным объектом `{dow, hour_utc, duration_min}` с целыми значениями `0..6` (воскресенье 0), `0..23`, `1..1440`. Отсутствующее поле SHALL сохранять значение, `maintenance=null` SHALL очищать окно. Пустой PATCH SHALL давать `400 VALIDATION_FAILED`. Имя и maintenance SHALL меняться до начала удаления независимо от фазы и поколения; изменение SHALL давать `200`, обновлять `updated_at` и писать один аудит без изменения поколения, биллинга и `configuration_requested_at`. Совпадающие значения SHALL возвращать `200` без записи события и изменения времён. В v1 maintenance MUST NOT задерживать операции.

#### Scenario: Переименование во время ресайза

- **WHEN** пользователь меняет имя при активном поколении
- **THEN** имя сохраняется, desired-размер и наблюдаемые поля остаются прежними

#### Scenario: Очистка maintenance

- **WHEN** PATCH содержит `maintenance=null`
- **THEN** все колонки окна становятся NULL без роста поколения

### Requirement: Удаление сохраняет инстанс и историю

DELETE SHALL быть разрешён при любой фазе и незавершённой операции. Первый запрос SHALL одной транзакцией установить `deletion_requested_at`, обновить `updated_at`, закрыть открытый биллинговый период и записать `instance.delete`, затем вернуть `202` без тела. Поколение и `configuration_requested_at` SHALL сохраняться. `deleted_at` SHALL заполняться только после подтверждения удаления будущей синхронизацией. Физическое удаление инстанса через API MUST NOT выполняться. Подтверждённо удалённые записи SHALL исключаться из обычных GET и давать `404`; повтор DELETE владельца SHALL давать `202` даже после soft delete.

#### Scenario: Удаление во время операции

- **WHEN** пользователь удаляет инстанс при активном resize, whitelist или пароле
- **THEN** API принимает удаление без ожидания завершения конфигурации и сохраняет резерв квоты

#### Scenario: Повтор удаления

- **WHEN** владелец повторяет DELETE при заполненном `deletion_requested_at` либо `deleted_at`
- **THEN** получает `202`, времена и количество записей аудита и биллинга не меняются

#### Scenario: Подтверждённое удаление

- **WHEN** в сохранённом состоянии заполнены обе отметки удаления
- **THEN** API скрывает инстанс из списка и карточки, квота его не учитывает
- **AND** строка инстанса, аудит, идемпотентные ответы и история периодов сохраняются

### Requirement: Идемпотентность связывает ответ с одной отправкой

Создание, resize и rotate SHALL хранить успешный ответ и HTTP-статус на 24 часа по паре `(user_id, key)`. Отпечаток SHALL включать метод, путь с ID и каноническое тело; перестановка JSON-полей и пробелы между ними SHALL быть несущественны. Совпадение SHALL возвращать исходный ответ до проверок текущего состояния. Другой отпечаток SHALL давать `422 IDEMPOTENCY_MISMATCH`. Ошибочные операции MUST NOT занимать ключ. На границе 24 часов запись SHALL считаться истёкшей независимо от фоновой очистки. Ответ SHALL сохраняться в общей транзакции; тело запроса MUST NOT сохраняться.

#### Scenario: Конкурентный повтор

- **WHEN** два HTTP-запроса с одним ключом и телом поступают одновременно
- **THEN** оба получают одинаковый успешный DTO и статус, а изменение, аудит и биллинг выполняются один раз

#### Scenario: Один ключ для другого действия

- **WHEN** пользователь повторно использует ключ для другого тела, метода или ID ресурса
- **THEN** получает `422 IDEMPOTENCY_MISMATCH`
- **AND** такой же UUID ключа у другого пользователя обрабатывается независимо

#### Scenario: Ошибку можно исправить

- **WHEN** операция отклонена по квоте или валидации и клиент снова отправляет запрос с тем же ключом после устранения причины
- **THEN** ключ не препятствует первой успешной операции

### Requirement: Ошибки мутаций имеют проверяемые причины

Все ошибки SHALL использовать `{error:{code,message,details}}`. Невалидное тело, неизвестное или повторяющееся JSON-поле, неизвестный query-параметр мутации, неверный тип, JSON null вместо обязательного значения и несколько JSON-документов SHALL давать `400 VALIDATION_FAILED`. Тело SHALL ограничиваться 16 KiB; превышение SHALL давать тот же код с `reason=body_too_large`. Валидация SHALL возвращать `details.fields` с именами полей и машинными причинами, не отражая пароль. Известные коды SHALL сохранять статусы: `409` для конфликтов состояния, `422` для квот и несовпадения ключа, `503 UNAVAILABLE` для таймаута lock, `500 INTERNAL` для неожиданного сбоя. Ошибка MUST NOT оставлять частичные записи.

#### Scenario: Lock недоступен

- **WHEN** общий lock не получен за 3 секунды
- **THEN** API отвечает `503 UNAVAILABLE` с `details.reason=lock_timeout`, а транзакция откатывается
- **AND** обычные GET-запросы не ждут этот advisory lock

#### Scenario: Отмена ожидания

- **WHEN** клиент отменяет HTTP-запрос до получения lock
- **THEN** обработка прекращается без записи изменения и не удерживает соединение или lock после завершения

#### Scenario: Проверка исходной схемы

- **WHEN** клиент пытается передать owner, applied-поля, slug или служебный статус в мутации
- **THEN** API отвечает `400 VALIDATION_FAILED` и не меняет эти поля
