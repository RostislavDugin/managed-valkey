# test-orchestration Specification

## Purpose

Определяет единый запуск тестов проекта, владение изолированными окружениями и достоверный отчёт о выполненных проверках без воздействия на рабочие dev-данные.

## Requirements

### Requirement: Корневая команда запускает все подключённые наборы

Корневой `just test` SHALL параллельно запускать все реализованные наборы подсистем и подключённые общие интеграционные и Playwright e2e-тесты. Каждый набор SHALL сам готовить своё окружение и выполнять необходимые этапы по порядку. Каталог `web` SHALL предоставлять `just test`, запускающий все тесты фронта через pnpm. Наборы, использующие общую кластерную квоту в PostgreSQL, MUST NOT конкурентно изменять одну тестовую базу.

#### Scenario: Полная проверка

- **WHEN** разработчик запускает `just test` из корня
- **THEN** независимые наборы выполняются параллельно, включая все медленные проверки подсистем

### Requirement: Результат отражает фактически выполненные проверки

Корневой запуск SHALL дождаться каждого начатого набора, вывести отдельные результаты и вернуть ненулевой код при ошибке подготовки, тестов или обязательной очистки. Неудача одного набора MUST NOT прерывать независимые наборы. Реализованный обязательный набор MUST NOT пропускаться из-за отсутствия инфраструктуры, переменной окружения или найденных тестов. Пока общий integration-набор API с настоящим оператором ещё не реализован, отчёт SHALL явно указывать это отдельно от результатов тестов; отсутствие MUST NOT обозначаться как успешная проверка. Пустая команда-заглушка MUST NOT считаться подключённым набором.

#### Scenario: Ошибка подготовки

- **WHEN** k3s не достиг готовности до deadline
- **THEN** соответствующий набор получает ошибку, остальные продолжают работу, а корневая команда возвращает ненулевой код

#### Scenario: Общий integration-набор ещё не существует

- **WHEN** запущены существующие тесты, включая Playwright-проверку регистрации, до реализации общего набора API + operator
- **THEN** отчёт обозначает общий integration-набор как не реализованный и не утверждает, что цепочка API + operator проверена

### Requirement: Запуск владеет только своими ресурсами

Каждый запуск SHALL иметь идентификатор и точный перечень созданных процессов, кластеров, баз и сетевых настроек. Тестовые стенды SHALL готовиться независимо от постоянного dev и освобождаться после завершения, ошибки или прерывания. Очистка MUST NOT удалять общую PostgreSQL, dev-данные, посторонние маршруты или ресурсы другого запуска. Повторный запуск одного набора SHALL получать отдельное окружение либо явно отклоняться до изменения занятых ресурсов.

#### Scenario: Прерывание тестов

- **WHEN** пользователь прерывает корневой `just test`
- **THEN** запуск завершает своих потомков и освобождает принадлежащие ему тестовые ресурсы, сохраняя dev и соседние запуски

#### Scenario: Повторный запуск набора

- **WHEN** два процесса одновременно запускают тесты API
- **THEN** они не используют одну базу и кластер; при невозможности выделить второе окружение второй процесс сообщает конфликт до записи

### Requirement: Диагностика сохраняется отдельно по наборам

Запуск SHALL сохранять отдельные журналы наборов и при ошибке собирать доступную диагностику до удаления стенда. Для Kubernetes диагностика SHALL включать состояния ресурсов и Events без содержимого Secret; для Playwright после его подключения SHALL сохраняться диагностические артефакты браузера с исключением секретов. Итоговый отчёт SHALL указывать пути к журналам.

#### Scenario: Падение медленного теста

- **WHEN** тест оператора завершается ошибкой
- **THEN** пользователь получает путь к его журналу и доступным состояниям Kubernetes после очистки кластера

### Requirement: Границы наборов сохраняются при подключении синхронизации

API-тесты SHALL проверять HTTP, PostgreSQL и доставку Namespace/Secret/spec и импорт status через настоящий Kubernetes API без оператора. Набор оператора SHALL начинаться с прямого создания CR без HTTP и PostgreSQL. Общий интеграционный набор SHALL проверять HTTP → PostgreSQL → CR → оператор → status → PostgreSQL. Playwright e2e SHALL выполнять пользовательский путь через браузер и полный стек без подмены backend. Реализация синхронизации и новых сквозных сценариев SHALL выполняться отдельными изменениями, которые подключают полный набор к локальному запуску и явно определяют ограниченный набор CI по спецификации ci-cd. Ресурсоёмкие сценарии MUST NOT включаться в CI/CD.

#### Scenario: Имитация наблюдений в API-тесте

- **WHEN** будущий тест API проверяет импорт наблюдений или ожидание удаления CR с finalizer
- **THEN** тестовая обвязка меняет status или снимает finalizer своим административным клиентом, а приложение продолжает работать с ограниченным kubeconfig API

#### Scenario: Подключение сквозного сценария

- **WHEN** отдельное изменение реализует проверку создания инстанса через API с настоящим оператором
- **THEN** проверка использует integration-окружение и становится обязательной частью корневого `just test`; включение в CI определяется ограниченным набором по спецификации ci-cd, ресурсоёмкие проверки остаются локальными

### Requirement: Обязательная матрица оператора на k3s

`operator just test` SHALL выполнять unit/envtest и все сценарии k3s из матрицы в design.md изменения add-operator-ha-and-mutations: HA, отказ процессов и worker-нод, сетевое разделение, ресайз, ротацию пароля и восстановление незавершённых операций. Поведение Valkey и Envoy SHALL проверяться настоящими процессами и клиентскими подключениями. Unit/envtest SHALL дополнять эти сценарии проверками таймеров, CRD, конфликтов и недоступных ответов Kubernetes, но MUST NOT заменять k3s-проверки отказов. API и PostgreSQL MUST NOT требоваться. Отсутствующая возможность создать обязательный отказ SHALL завершать набор ошибкой, а не skip или успехом.

Подготовка образа оператора для тестового кластера SHALL входить в набор и MUST NOT зависеть от включения публикации релизных образов или развёртывания. Лимиты времени полного локального запуска SHALL учитывать обязательный набор с подготовкой, диагностикой и очисткой. CI оператора SHALL выполнять unit/envtest без k3s; полная аварийная матрица SHALL оставаться обязательной локально.

#### Scenario: Полный локальный запуск

- **WHEN** запускается локальный `operator just test` непосредственно либо через корневой `just test`
- **THEN** выполняются все обязательные группы матрицы, результат включает каждый сценарий и ненулевой код при любой неуспешной обязательной проверке

#### Scenario: Невозможно создать отказ

- **WHEN** стенд не может отправить сигнал, остановить agent, установить сетевое ограничение либо запустить оператор внутри кластера
- **THEN** соответствующая проверка падает с причиной; сценарий не считается проверенным по изменённому вручную status

#### Scenario: Ограниченный запуск CI

- **WHEN** CI запускает обязательное задание `test-operator`
- **THEN** выполняются unit/envtest без подготовки k3s; отчёт обозначает ограниченный набор и не утверждает, что аварийная матрица проверена

#### Scenario: Превышение ориентира длительности

- **WHEN** полный локальный набор оператора на Ryzen 9 7950X с 32 потоками и примерно 32 GiB свободной RAM при скачанных образах занимает больше 10 минут с подготовкой и очисткой
- **THEN** превышение само по себе не делает запуск неуспешным; длительности анализируются, но дальнейшее ускорение не требуется при несоразмерных затратах или усложнении сопровождения

#### Scenario: Сборка релизов отключена

- **WHEN** полный локальный набор оператора выполняется без заданий сборки релизов и развёртывания
- **THEN** набор самостоятельно готовит образ и запускает оператор внутри k3s, включая добавленную или восстановленную ноду

### Requirement: Топология стенда и изоляция аварий

Каждый параллельный сценарий оператора SHALL владеть независимым k3s с минимальной необходимой топологией: одна нода для обычного `single`, две для переноса `single` после потери worker или разнесённых Envoy, три для HA и четыре для восстановления полного HA на запасной ноде. Число нод SHALL включать server; размещение и число реплик Envoy SHALL соответствовать проверяемому сценарию. В одном кластере SHALL выполняться не больше одного сценария одновременно. По умолчанию очередь SHALL допускать не более 12 одновременных сценариев и не более шести одновременных bootstrap. По умолчанию общий бюджет SHALL составлять 28672 MiB с минимум 3072 MiB доступной памяти после нового резерва; явные ограничения пользователя MAY снижать эти значения. Отказы нод SHALL затрагивать worker-agent, сохраняя k3s-server для Kubernetes API. Для потери оператора вместе с primary SHALL запускаться единственная копия рабочего оператора внутри k3s с его StatefulSet, ServiceAccount и Lease; хостовая копия SHALL быть остановлена. Все fault-действия SHALL проверять принадлежность ресурсов текущему запуску и сохранять точные идентификаторы целей.

#### Scenario: Общая потеря оператора и primary

- **WHEN** тест разместил оба процесса на выбранном agent и подтвердил размещение
- **THEN** уничтожение этого agent действительно останавливает оба процесса, а восстановление выполняет новый оператор внутри кластера

#### Scenario: Три ноды без запаса

- **WHEN** тест уничтожает одну worker-ноду без запасной
- **THEN** HA восстанавливает запись в degraded с третьим Pod в Pending; добавление чистой ноды возвращает полный состав

#### Scenario: Два независимых запуска

- **WHEN** одновременно работают два набора или постоянный dev
- **THEN** аварийные действия и очистка одного набора не затрагивают чужие контейнеры, правила сети, ноды и данные

### Requirement: Согласованная адресация тестового стенда

Каждый тестовый запуск SHALL сохранять выделенный `K3S_DOCKER_GATEWAY` и явно задавать его при создании Docker-сети. Gateway, адреса нод, включая дополнительный agent, и адреса тестовых клиентов SHALL принадлежать своей подсети и не совпадать. Доступ хостового оператора через `VALKEY_OPERATOR_CIDRS` SHALL соответствовать фактическому gateway. Добавление и восстановление agent MUST NOT менять адрес gateway или нарушать доступ оператора и изоляцию соседнего запуска. Отсутствие обязательного gateway SHALL останавливать подготовку тестового Compose до создания сети.

#### Scenario: Расширение до четырёх нод

- **WHEN** тест добавляет четвёртую ноду в выделенное окружение
- **THEN** её адрес не конфликтует с gateway, другими нодами и клиентами, а хостовый оператор продолжает подключаться к Valkey при действующей NetworkPolicy

#### Scenario: Замена agent после аварии

- **WHEN** уничтоженный agent заменяется чистым
- **THEN** gateway и разрешённый адрес хостового оператора сохраняются; повторная проверка административного подключения проходит до следующего аварийного сценария

#### Scenario: Gateway отсутствует

- **WHEN** тестовый Compose вызван без обязательного K3S_DOCKER_GATEWAY
- **THEN** подготовка завершается ошибкой до создания сети, вместо запуска стенда с неявно выбранным gateway

### Requirement: Проверяемые способы вызвать отказ

Тесты SHALL отдельно вызывать аварийную остановку процесса Valkey, штатное удаление Pod, SIGSTOP, BUSY и уничтожение worker-agent. При имитации уничтожения VM тест SHALL сначала подтвердить остановку agent вместе с вложенными процессами и исключить его автоматический рестарт, затем удалить Node. При сетевом разделении тест SHALL сохранять старую ноду и процессы живыми и подтверждать, какие пути связи нарушены. Тест MUST NOT вручную снимать finalizers, назначать роли или писать доказательства в CR ради завершения автоматического восстановления. Отдельная проверка ручного fencing SHALL сначала физически остановить целевую тестовую ноду.

#### Scenario: Остановка ноды

- **WHEN** выполнено аварийное отключение agent
- **THEN** тест проверяет остановку до удаления Node, а дальнейшую замену Pod и сохранение доказательства делает оператор

#### Scenario: Изолированный живой primary

- **WHEN** тест разорвал связь оператора с primary и сохраняет рабочее старое клиентское соединение
- **THEN** он проверяет отсутствие второго доступного для записи primary в течение окна дольше порогов отказа, NODE_LOST и ожидания пустого primary

#### Scenario: Потеря ответа выполненной команды

- **WHEN** тест проверяет неопределённый результат ACL, CLIENT KILL или REPLICAOF
- **THEN** настоящая команда доходит до Valkey и выполняется, а её ответ теряется контролируемо; проверка не ограничивается подменой результата без изменения реального процесса

### Requirement: Проверки во время отказа и после восстановления

Каждый аварийный сценарий SHALL подтверждать исходное состояние, наступление отказа, ограничения во время ожидания и конечное состояние. Проверки SHALL включать прямые роли и ACL процессов, идентичности, сведения о репликации, старые TCP-соединения и публичный доступ с проверкой TLS/SNI. Сохранность контрольных данных SHALL проверяться только для ключей, чью синхронизацию на необходимых репликах тест подтвердил до отказа. Сценарии допустимой потери кэша SHALL проверять отсутствие старого ключа и возможность новой записи.

#### Scenario: Успешный status без работающего Valkey

- **WHEN** CR показывает running, но клиент не может выполнить ожидаемые SET/GET либо прочитать синхронизированную реплику
- **THEN** сценарий падает и не считает status достаточным доказательством

#### Scenario: Рестарт на промежуточной стадии

- **WHEN** сохранена стадия перед изменяющей командой или команда выполнена до подтверждения в CR
- **THEN** тест останавливает оператор в этой точке, перезапускает его и проверяет продолжение той же операции без нарушения fencing и без преждевременного подтверждения поколения

### Requirement: Сроки ожидания и повторяемость аварийных тестов

Все ожидания SHALL иметь конечный deadline и понятное условие завершения; отрицательные проверки SHALL наблюдать запрет весь заданный интервал. Достижение стадии SHALL синхронизироваться по наблюдаемому состоянию или управляемой тестовой границе, а не случайной задержке. Сценарии, разрушающие общие ноды или сеть одного стенда, SHALL выполняться последовательно. Повтор SHALL создавать чистое состояние и сохранять исходное падение в результате, а не скрывать его удачным повтором. K3s-набор SHALL собирать тестовый процесс и образ оператора с отдельным профилем сокращённых интервалов, включая период и допустимое число неудач проверки готовности, сохраняя рабочие пороги в обычной сборке. Unit/envtest SHALL проверять рабочие пороги с подменяемыми часами. Тестовый профиль MUST NOT включаться в release-образ.

Длительность каждого сценария SHALL быть видна в отчёте `go test -v`. После каждого этапа изменения SHALL выполняться отдельный просмотр самых долгих сценариев и ожиданий. Для обычного переключения Pod или процесса на исправном стенде SHOULD использоваться ориентир 15–30 секунд. Превышение ориентира SHALL приводить к анализу ожиданий, но MUST NOT ослаблять проверку безопасности или скрывать нестабильность повторным успешным запуском.

#### Scenario: Таймаут восстановления

- **WHEN** ожидаемая роль, доказательство остановки или публичная готовность не достигнуты в срок
- **THEN** тест завершается ошибкой с последним наблюдением и собирает диагностику до очистки

#### Scenario: Восстановление agent

- **WHEN** закончился сценарий уничтожения ноды
- **THEN** стенд поднимает чистый agent, не возвращая прежние процессы Valkey, и подтверждает готовность инфраструктуры перед следующим сценарием

#### Scenario: Сценарий дольше ориентира

- **WHEN** обычное переключение на исправном стенде заняло больше 30 секунд
- **THEN** отчёт сохраняет фактическую длительность, а задача этапа проверяет фиксированные паузы, частоту наблюдения, сверку Envoy, повторную подготовку кластера и образа до увеличения общего timeout

### Requirement: Диагностика и очистка после аварий

Запуск SHALL сохранять идентификатор сценария, последовательность аварийных действий с временем, состояния CR/Node/Pod/EndpointSlice, Events и логи оператора и доступной инфраструктуры. Диагностика MUST NOT содержать Secret, хеши ACL, пароли или аргументы чувствительных команд. Очистка SHALL удалять собственные сетевые ограничения и аварийные вспомогательные процессы при успехе, ошибке и прерывании. При невозможности сохранить безопасный снимок SHALL сохраняться причина его отсутствия.

#### Scenario: Прерывание во время сетевого разделения

- **WHEN** тестовый запуск прерван после установки сетевого ограничения
- **THEN** очистка снимает только принадлежащее этому запуску ограничение, завершает его потомков и сохраняет доступные журналы

#### Scenario: Недоступный Kubernetes при падении

- **WHEN** Kubernetes API не отвечает во время сбора диагностики
- **THEN** сбор ограничен deadline, сохраняет доступные журналы контейнеров и причину отсутствия снимка Kubernetes, затем освобождает стенд

### Requirement: Каталог покрывает все сценарии без повторений

Полный запуск SHALL проверять соответствие каталога обнаруженным исполняемым сценариям до подготовки k3s. Каждый сценарий SHALL иметь ровно одно назначение, минимальную топологию и профиль инфраструктуры. Итоговый отчёт SHALL проверять выполнение всех назначенных сценариев и полной обязательной матрицы.

#### Scenario: Тест переименован

- **WHEN** каталог содержит отсутствующее имя или новый тест не назначен сценарию
- **THEN** запуск завершается ошибкой до создания кластеров и перечисляет несовпадения

#### Scenario: Сценарий назначен дважды

- **WHEN** два назначения охватывают один исполняемый сценарий
- **THEN** проверка каталога отклоняет запуск и указывает повтор

### Requirement: Параллелизм учитывает общий бюджет хоста

Запуск SHALL учитывать ресурсы подготовки, тестов и очистки вместе с резервами других активных наборов. Сценарии SHALL выполняться параллельно на независимых кластерах в пределах бюджета. Недостаток ресурсов MUST NOT приводить к пропуску обязательной проверки или запуску за пределами согласованного бюджета.

#### Scenario: Одновременно запущены API и оператор

- **WHEN** оба набора запрашивают ресурсы на одном хосте
- **THEN** их резервы учитываются совместно, а ожидающий сценарий стартует после освобождения достаточного бюджета

#### Scenario: Сценарий не помещается

- **WHEN** требуемый сценарий превышает весь настроенный бюджет даже без соседей
- **THEN** запуск сообщает недостаток ресурсов и завершается ошибкой вместо бесконечного ожидания

### Requirement: Остатки завершённых запусков очищаются адресно

Запуск SHALL обнаруживать оставшиеся тестовые ресурсы по зарегистрированному владельцу. Очистка SHALL проверять отсутствие активного владельца и принадлежность ресурсов, сохранять доступные безопасные журналы и не затрагивать dev или соседние запуски. Повторная очистка SHALL быть безопасной. Неопределённая принадлежность SHALL сообщаться без удаления.

#### Scenario: Владелец аварийно завершился

- **WHEN** обнаружены остатки запуска после потери его процесса и отсутствие владельца подтверждено с учётом повторного использования PID
- **THEN** очищаются только его процессы, контейнеры, тома, сети, маршруты и ограничения; результат перечисляет неустранённые остатки

#### Scenario: Владелец ещё работает

- **WHEN** обнаруженные ресурсы принадлежат активному запуску
- **THEN** очистка сохраняет их и учитывает занятый ими бюджет

### Requirement: Отмена дожидается завершения потомков

Отмена SHALL прекращать назначение новых сценариев, останавливать и дожидаться дочерних процессов перед окончательной очисткой. Ошибка очистки SHALL отражаться ненулевым результатом и перечнем остаточных ресурсов. Диагностика SHALL иметь ограниченный срок сбора и сохраняться после удаления инфраструктуры.

#### Scenario: Отмена во время подготовки

- **WHEN** пользователь отменяет запуск, пока часть кластеров ещё создаётся
- **THEN** после завершения отмены потомки не продолжают создавать ресурсы; каждый зарегистрированный стенд очищен либо указан как ошибка очистки

### Requirement: Playwright проверяет регистрацию через полный пользовательский путь

Подключённый e2e-набор SHALL открыть настоящий личный кабинет в браузере,
зарегистрировать аккаунт через интерфейс и получить авторизованную страницу через
настоящие HTTP API и PostgreSQL. Для каждой регистрации набор MUST создавать новую
почту и использовать пароль `testpassword`. Набор MUST NOT вызывать API или менять
PostgreSQL напрямую для подготовки пользовательского состояния.

#### Scenario: Новый пользователь зарегистрирован

- **WHEN** Playwright открывает страницу авторизации, вводит уникальную почту и дважды вводит `testpassword`
- **THEN** личный кабинет создаёт аккаунт, открывает `/valkey/management` и показывает почту этого аккаунта в авторизованной оболочке

#### Scenario: Локальная регистрация изолирована от dev

- **WHEN** разработчик запускает `just test-e2e` или корневой `just test`
- **THEN** сценарий выполняется в headless Chromium с настоящими frontend и API на отдельной временной PostgreSQL, а завершение запуска удаляет эту базу без изменения dev-базы

### Requirement: Первый e2e-сценарий не зависит от готовности Valkey

Сценарий регистрации SHALL завершаться без создания инстанса Valkey и без ожидания
работы оператора. Выделенное e2e-окружение SHALL оставаться совместимым с будущими
сценариями полного жизненного цикла и отказов Valkey.

#### Scenario: Оператор ещё не запущен

- **WHEN** frontend, API и PostgreSQL готовы, но процесс оператора не запущен
- **THEN** сценарий регистрации проходит и не обращается к ресурсам Valkey

### Requirement: Регистрацию можно безопасно проверить на рабочем сайте

Корневая команда `just test-prod` SHALL запускать тот же сценарий регистрации с
видимым Chromium по точному адресу `https://app.h3llo-demo.com`. Команда MUST быть
только ручной и MUST NOT запускаться из CI или после deploy. Созданный аккаунт может
остаться в рабочей базе, пока личный кабинет не предоставляет его удаление.

#### Scenario: Ручная production-проверка

- **WHEN** разработчик запускает `just test-prod`
- **THEN** Playwright регистрирует новый аккаунт на `https://app.h3llo-demo.com`, проверяет авторизованную страницу и не создаёт ресурсы Valkey

### Requirement: Имя теста описывает действие, условия и результат

Каждый именованный тест SHALL по возможности сообщать проверяемое действие, существенные условия и ожидаемый результат без чтения тела теста. Go-функции SHALL называться по форме `Test_<WhatWeDo>_<WhatWeExpect>` или `Test_<WhatWeDo>_<WhichConditions>_<WhatWeExpect>` с английскими сегментами в `PascalCase`. Идентификаторы обязательной матрицы MAY занимать отдельный сегмент сразу после `Test_`.

Когда тестовый фреймворк принимает произвольную строку, самостоятельный сценарий SHALL получать длинное понятное название по-русски. Группы сценариев и варианты одного табличного случая MAY использовать короткие названия без префикса `Test_`, если они лишь уточняют значение параметра или общий контекст.

#### Scenario: Go-тест имеет имя идентификатора

- **WHEN** разработчик добавляет или переименовывает самостоятельную Go-функцию теста
- **THEN** её имя начинается с `Test_` и явно называет действие, существенное условие при его наличии и ожидаемый результат

#### Scenario: Фреймворк принимает строковое название

- **WHEN** самостоятельный сценарий объявляется через `t.Run`, Vitest или Playwright и его имя не обязано быть идентификатором кода
- **THEN** сценарий получает самодостаточное русское название, по которому понятны действие, условия и ожидаемый результат

#### Scenario: Имя обозначает только группу или вариант

- **WHEN** название относится к группе сценариев, версии движка или отдельному значению параметра таблицы
- **THEN** оно остаётся короткой понятной меткой и не изображает самостоятельный тест

#### Scenario: Бывшая тестовая функция запускается как подтест

- **WHEN** запускатель вызывает бывшую самостоятельную Go-функцию как подтест
- **THEN** строка `t.Run` дословно совпадает с полным именем этой функции

### Requirement: Ссылки на имена тестов остаются согласованными

Переименование теста SHALL одновременно обновлять каждый активный каталог, фильтр запуска, проверку отчёта и тестовые данные, которые ссылаются на его точное имя. Исторические архивные документы и сохранённые журналы MUST NOT переписываться ради соответствия текущим именам.

#### Scenario: Integration-тест оператора переименован

- **WHEN** меняется имя сценария, назначенного в каталоге оператора
- **THEN** каталог выбирает новое точное имя, а проверка полноты подтверждает единственное назначение до подготовки k3s

#### Scenario: Изменился общий префикс набора

- **WHEN** переименование меняет префикс, которым скрипт выбирает envtest или другой набор
- **THEN** фильтр запуска и проверка его отчёта используют новый префикс

### Requirement: Проверка соответствует характеру изменения

После добавления или изменения поведения теста исполнитель SHALL запустить затронутый тест и убедиться в его успешном результате. Для массового переименования без изменения поведения исполнитель MAY ограничиться компиляцией Go-тестов, проверкой типов TypeScript, синтаксической проверкой затронутых скриптов и проверкой точных назначений каталога. Такой запуск MUST быть явно отделён от полного прохождения тестов в итоговом отчёте.

#### Scenario: Изменено поведение теста

- **WHEN** вместе с именем изменились подготовка, действие или проверки тестового сценария
- **THEN** затронутый тест запускается и успешно завершается

#### Scenario: Изменены только имена

- **WHEN** изменение ограничено именами тестов и связанными точными ссылками
- **THEN** все варианты исходников компилируются или проходят проверку типов, каталог оператора согласован, а полный ресурсоёмкий набор не требуется
