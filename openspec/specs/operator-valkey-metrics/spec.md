# operator-valkey-metrics Specification

## Purpose

Оператор публикует в `status.metrics` последние проверенные снимки текущих процессов Valkey, чтобы API мог сохранять историю для страницы мониторинга.

## Requirements

### Requirement: Активный оператор периодически публикует метрики Valkey

Оператор с активным `LeaseScope` SHALL раз в `config.MetricsInterval` собирать для каждого текущего процесса Valkey поля `usedMemoryBytes`, `maxmemoryBytes`, `connectedClients`, `opsPerSec`, `keyspaceHits`, `keyspaceMisses` и `evictedKeys` из `INFO`. Снимок SHALL содержать `ordinal`, `podUID`, `containerID`, `runId`, роль процесса и `collectedAt` в UTC с точностью до микросекунд. `status.metrics` SHALL хранить не больше одного последнего успешного снимка на `ordinal` и не больше трёх элементов на ресурс `ValkeyInstance`.

#### Scenario: Снимок одного процесса

- **WHEN** процесс с подтверждённой идентичностью отвечает на `INFO` и наступил очередной период сбора
- **THEN** оператор записывает в `status.metrics` один снимок с полученными показателями и идентификаторами этого процесса

#### Scenario: Метрики экземпляра HA

- **WHEN** три текущих процесса экземпляра HA успешно отвечают на сбор
- **THEN** `status.metrics` содержит по одному снимку для `ordinal` 0, 1 и 2 без повторов

#### Scenario: Период ещё не наступил

- **WHEN** после последнего прохода сбора прошло меньше `config.MetricsInterval` и идентичность процесса не менялась
- **THEN** оператор не выполняет внеплановый сбор и не меняет `collectedAt`

### Requirement: Снимок относится к одному текущему процессу

До и после сбора оператор SHALL проверять `podUID`, `containerID` и `runId`. Новый снимок SHALL записываться только при совпадении этих значений между проверками и с актуальным элементом `status.nodes`. При смене процесса прежний снимок того же `ordinal` SHALL удаляться, а новый SHALL появляться только после успешного сбора нового процесса.

#### Scenario: Процесс сменился во время сбора

- **WHEN** `podUID`, `containerID` или `runId` изменился между первой и последней проверкой
- **THEN** оператор не публикует собранные значения как снимок нового процесса

#### Scenario: Новый процесс ещё не отвечает

- **WHEN** `status.nodes` уже содержит новую идентичность, но сбор для неё завершается ошибкой
- **THEN** `status.metrics` не содержит прежний снимок этого `ordinal` и не создаёт нулевой снимок нового процесса

#### Scenario: Состояние изменилось перед записью

- **WHEN** процесс сменился после чтения показателей, но до обновления `status`
- **THEN** оператор сверяет актуальный `status.nodes` и отбрасывает снимок прежнего процесса

### Requirement: CPU берётся из метрик текущего контейнера

Оператор SHALL читать CPU контейнера `valkey` из `PodMetrics` API `metrics.k8s.io`. Значение SHALL переводиться в целые милликоры. Оператор SHALL использовать значение только тогда, когда отметка `PodMetrics.timestamp` не старше одной минуты относительно времени сбора и не предшествует запуску текущего контейнера. При недоступном API, отсутствии контейнера или CPU, устаревшей отметке либо недопустимом значении `cpuMillicores` SHALL быть `null`, а остальные поля снимка SHALL сохраняться.

#### Scenario: Доступен свежий CPU

- **WHEN** `PodMetrics` содержит свежее неотрицательное значение CPU для текущего контейнера `valkey`
- **THEN** снимок содержит это значение в целых милликорах

#### Scenario: CPU недоступен

- **WHEN** `metrics.k8s.io` недоступен или не возвращает пригодное значение для текущего контейнера
- **THEN** оператор публикует успешный снимок `INFO` с `cpuMillicores=null`

#### Scenario: Метрика относится к прежнему контейнеру

- **WHEN** `PodMetrics.timestamp` предшествует времени запуска текущего контейнера
- **THEN** оператор не связывает это значение CPU с новым процессом и записывает `cpuMillicores=null`

### Requirement: Ошибка сбора не влияет на управление экземпляром

Ошибка чтения или разбора `INFO`, чтения CPU либо проверки идентичности MUST NOT задерживать обновление `status.observedAt`, переключение основного процесса, восстановление процесса и применение конфигурации. Ошибка `INFO` MUST NOT создавать снимок, подставлять нулевые показатели или обновлять время прежнего успешного снимка того же процесса. Следующая попытка SHALL выполняться в очередной период сбора без непрерывных повторов.

#### Scenario: INFO возвращает ошибку

- **WHEN** текущий процесс не возвращает полный допустимый набор полей `INFO`
- **THEN** оператор сохраняет прежний успешный снимок того же процесса без изменения, а `ValkeyInstanceReconciler` продолжает работу

#### Scenario: Требуется переключение основного процесса

- **WHEN** сбор метрик завершается ошибкой во время отказа процесса с ролью `primary`
- **THEN** оператор продолжает переключение основного процесса независимо от результата сбора

### Requirement: Тесты оператора проверяют рабочий путь без нового стенда

Быстрые тесты оператора SHALL проверять разбор `INFO`, периодичность, проверку идентичности и независимые отказы `INFO` и CPU без запуска k3s. Существующий интеграционный сценарий `single` SHALL дождаться снимка от настоящих Valkey и `metrics.k8s.io`, а после замены Pod SHALL подтвердить публикацию идентичности нового процесса. Для этой проверки MUST NOT создаваться отдельный сценарий k3s.

#### Scenario: Быстрый набор

- **WHEN** выполняется `operator just test`
- **THEN** модульные тесты проверяют успешный снимок, `cpuMillicores=null`, отказ `INFO` и смену идентичности без настоящего Metrics Server

#### Scenario: Полный набор

- **WHEN** выполняется существующий сценарий `single` из `operator just test-full`
- **THEN** он получает снимок с CPU и после замены Pod видит снимок только нового процесса
