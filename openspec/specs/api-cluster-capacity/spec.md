# api-cluster-capacity Specification

## Purpose
Определяет настройку полной CPU/RAM-ёмкости Managed Kubernetes и вычисление суммарного бюджета, который API разрешает резервировать под процессы Valkey.

## Requirements

### Requirement: Конфигурация задаёт полную ёмкость кластера

API SHALL принимать обязательные целые положительные параметры `MANAGED_K8S_CLUSTER_VCPU` и `MANAGED_K8S_CLUSTER_RAM_GB`. CPU SHALL задаваться в целых vCPU, RAM SHALL задаваться в GiB. API MUST NOT требовать число нод, размер отдельной ноды или настраиваемый понодовый резерв.

Все прежние параметры `MANAGED_K8S_NODE_COUNT`, `MANAGED_K8S_NODE_CAPACITY_VCPU`, `MANAGED_K8S_NODE_CAPACITY_RAM_GB`, `MANAGED_K8S_NODE_RESERVED_CPU_MILLI`, `MANAGED_K8S_NODE_RESERVED_RAM_MIB`, `MANAGED_K8S_NODE_VCPU` и `MANAGED_K8S_NODE_RAM_GB` SHALL считаться устаревшими. Наличие любого из них MUST завершать запуск ошибкой с именем параметра, даже если новые параметры тоже заданы.

#### Scenario: Задана только суммарная ёмкость

- **WHEN** окружение содержит положительные целые `MANAGED_K8S_CLUSTER_VCPU` и `MANAGED_K8S_CLUSTER_RAM_GB` без устаревших параметров
- **THEN** API начинает запуск с этой физической ёмкостью и не требует сведений о нодах

#### Scenario: Осталась прежняя топология

- **WHEN** окружение содержит хотя бы одну устаревшую переменную топологии или понодового резерва
- **THEN** API завершает запуск с ошибкой, называющей эту переменную

#### Scenario: Суммарная ёмкость неверна

- **WHEN** новый параметр отсутствует, равен нулю, отрицателен, дробный, имеет неверный формат либо переполняет расчёт
- **THEN** API завершает запуск с ошибкой, называющей этот параметр

### Requirement: API оставляет фиксированный запас инфраструктуре

Доступный процессам Valkey бюджет CPU SHALL равняться 85% настроенного CPU, а бюджет RAM SHALL равняться 90% настроенной RAM. Расчёт SHALL выполняться в тысячных долях CPU и MiB без арифметики с плавающей точкой и MUST округлять дробный результат вниз. Проценты резерва MUST NOT настраиваться отдельными переменными окружения.

Публичный лимит `/v1/managed/valkey/capacity` SHALL содержать целые vCPU и GiB, полученные округлением внутреннего бюджета вниз. Дробный остаток MUST NOT использоваться для принятия резервов, выраженных целыми размерами каталога.

#### Scenario: Рабочий кластер 12 vCPU и 48 GiB

- **WHEN** заданы `MANAGED_K8S_CLUSTER_VCPU=12` и `MANAGED_K8S_CLUSTER_RAM_GB=48`
- **THEN** внутренний бюджет равен 10200m CPU и 44236 MiB RAM
- **AND** `/capacity` сообщает кластерный лимит 10 vCPU / 43 GiB

#### Scenario: Кластер равен максимальному размеру одного процесса

- **WHEN** заданы `MANAGED_K8S_CLUSTER_VCPU=4` и `MANAGED_K8S_CLUSTER_RAM_GB=16`
- **THEN** внутренний бюджет после инфраструктурного резерва равен 3400m CPU и 14745 MiB RAM
- **AND** `/capacity` сообщает кластерный лимит 3 vCPU / 14 GiB
- **AND** полный физический размер 4 vCPU / 16 GiB не считается доступным процессам Valkey

#### Scenario: Процент даёт дробный результат

- **WHEN** применение резерва не даёт целого числа тысячных долей CPU или MiB
- **THEN** API округляет соответствующий внутренний бюджет вниз и не завышает доступную ёмкость

### Requirement: Суммарный бюджет не обещает физическое размещение

Кластерный лимит SHALL означать максимальный суммарный резерв Valkey по данным PostgreSQL. Он MUST NOT описываться как текущий `allocatable`, свободное место на нодах или гарантия размещения любой комбинации размеров. API SHALL вычислять и проверять этот лимит без чтения Kubernetes, числа нод и распределения уже работающих Pod.

Создание или изменение размера, которое не превышает личную квоту, суммарный кластерный бюджет и предел числа инстансов, SHALL приниматься независимо от возможной фрагментации нод. Фактическую возможность запуска SHALL определять Kubernetes; невозможный по жёстким условиям Pod SHALL оставаться `Pending` до появления подходящих ресурсов.

#### Scenario: Общего бюджета хватает, а подходящей ноды нет

- **WHEN** резерв кандидата укладывается в личный и суммарный лимиты, но ни одна нода не может удовлетворить его `resources.requests`
- **THEN** API принимает намерение без расчёта раскладки
- **AND** Kubernetes сохраняет Pod в `Pending` до появления подходящей ноды или изменения намерения

#### Scenario: Изменилась фактическая топология

- **WHEN** число, размер или занятость нод меняются без изменения двух параметров суммарной ёмкости API
- **THEN** опубликованный учётный лимит не меняется автоматически
- **AND** Kubernetes заново применяет фактические ограничения только при планировании новых или заменяемых Pod
