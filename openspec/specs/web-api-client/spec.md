# web-api-client

## Purpose

Общий HTTP-клиент фронтенда добавляет JWT, единообразно разбирает ошибки и безопасно повторяет запросы после кратких сбоев сети или API.

## Requirements

### Requirement: Все запросы фронтенда проходят через общий клиент

Фронтенд SHALL отправлять обращения к API через один клиент, который добавляет `Accept: application/json`, JSON `Content-Type` для JSON-тела и JWT из `mv_token` в `Authorization`. Базовый адрес SHALL браться из `VITE_API_BASE_URL`, а при отсутствии значения использовать `/v1`.

#### Scenario: Пользователь вошёл

- **WHEN** фронтенд отправляет защищённый запрос при наличии `mv_token`
- **THEN** запрос содержит `Authorization: Bearer <token>`

#### Scenario: Запрос содержит JSON

- **WHEN** вызов передаёт JSON-тело без собственного `Content-Type`
- **THEN** клиент отправляет `Content-Type: application/json`

### Requirement: Временный сбой вызывает ограниченный повтор

Клиент SHALL выполнять не больше трёх попыток одного логического запроса. Повтор допускается после сетевой ошибки, кроме явной отмены, и после статусов `408`, `425`, `500`, `502`, `503`, `504`. Между попытками SHALL расти задержка со случайным разбросом. Остальные HTTP-статусы MUST возвращаться вызывающему коду без автоматического повтора.

#### Scenario: Вторая попытка успешна

- **WHEN** первая безопасная попытка завершается сетевой ошибкой, а вторая получает успешный ответ
- **THEN** вызывающий код получает успешный результат

#### Scenario: API остаётся недоступным

- **WHEN** все три попытки завершаются временной ошибкой
- **THEN** клиент возвращает последнюю ошибку вызывающему коду
- **AND** четвёртая попытка не отправляется

#### Scenario: API отклоняет данные

- **WHEN** API отвечает статусом 4xx, кроме `408` и `425`
- **THEN** клиент не повторяет запрос

#### Scenario: API ограничивает частоту

- **WHEN** API или Caddy отвечает `429`
- **THEN** клиент не повторяет запрос автоматически
- **AND** ошибка содержит срок ожидания из JSON или `Retry-After`, а при отсутствии обоих источников 60 секунд

### Requirement: Повтор разрешён только для безопасной операции

Клиент SHALL автоматически считать безопасными `GET`, `HEAD` и `OPTIONS`. Остальные запросы SHALL повторяться только при явном признаке безопасной операции или наличии `Idempotency-Key`. `check-email` и `login` SHALL быть явно разрешены для повтора; регистрация SHALL повторяться с одним ключом на одну отправку формы.

#### Scenario: Изменяющий POST содержит ключ

- **WHEN** запрос `POST` с `Idempotency-Key` получает временную ошибку
- **THEN** клиент повторяет запрос с тем же ключом

#### Scenario: Изменяющий запрос не защищён

- **WHEN** небезопасный запрос без ключа и без явного разрешения получает временную ошибку
- **THEN** клиент возвращает ошибку без повтора

### Requirement: Попытки сохраняют личность логического запроса

Все попытки SHALL использовать одинаковые метод, путь, тело, `Idempotency-Key` и `X-Request-Id`. Новый пользовательский запуск той же операции SHALL получить новые ключи. Клиент MUST NOT повторять тело, которое нельзя воспроизвести безопасно.

#### Scenario: Ответ потерян после принятия операции

- **WHEN** запрос с JSON-телом и ключом принят сервером, но ответ теряется
- **THEN** следующая попытка отправляет то же тело и те же идентификаторы

#### Scenario: Пользователь отправляет исправленную форму

- **WHEN** пользователь после ошибки меняет данные и отправляет форму снова
- **THEN** клиент создаёт новые `Idempotency-Key` и `X-Request-Id`

### Requirement: Отмена прекращает весь логический запрос

Переданный `AbortSignal` SHALL отменять текущую попытку и ожидание перед следующей. Отмена MUST NOT преобразовываться в ошибку API или запускать новый запрос.

#### Scenario: Отмена во время запроса

- **WHEN** вызывающий код отменяет активную попытку
- **THEN** клиент возвращает ошибку отмены без следующей попытки

#### Scenario: Отмена во время задержки

- **WHEN** вызывающий код отменяет сигнал между попытками
- **THEN** ожидание завершается и новая попытка не отправляется

### Requirement: Ответ API преобразуется в типизированный результат

Успешный JSON SHALL возвращаться вызывающему коду как данные. Ответ в общем формате ошибки SHALL преобразовываться в ошибку с `code`, `status` и `details`. Недействительный JSON SHALL давать `INVALID_RESPONSE`. Любой `401 UNAUTHORIZED` SHALL удалить `mv_token` и уведомить приложение о завершении сессии.

#### Scenario: API возвращает предметную ошибку

- **WHEN** ответ содержит `error.code` и `error.details`
- **THEN** вызывающий код получает типизированную ошибку с теми же значениями

#### Scenario: Защищённый запрос отвергает токен

- **WHEN** API отвечает `401 UNAUTHORIZED`
- **THEN** клиент удаляет `mv_token` и отправляет событие завершения сессии

#### Scenario: Ответ нельзя разобрать

- **WHEN** API возвращает тело, которое не является допустимым JSON
- **THEN** клиент возвращает `INVALID_RESPONSE` с HTTP-статусом ответа
