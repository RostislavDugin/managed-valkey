# api-valkey-sync Specification

## Purpose

Определяет доставку принятых API настроек Valkey в Kubernetes и возврат подтверждённых наблюдений в PostgreSQL, включая продолжение после сбоев и завершение удаления ресурсов.

## Requirements

### Requirement: API постоянно сверяет намерения и наблюдения

API SHALL выполнять независимые циклы доставки и импорта с интервалом планирования 1 секунда и первым проходом сразу после запуска. Проходы одного цикла MUST NOT перекрываться или накапливаться при медленных запросах. Ошибка отдельного инстанса MUST NOT прерывать обработку остальных. HTTP-обработчики MUST NOT обращаться к Kubernetes. Недоступность Kubernetes MUST NOT делать API неготовым при доступной PostgreSQL.

#### Scenario: Запуск и периодическая сверка

- **WHEN** API запускается с доступной PostgreSQL и Kubernetes
- **THEN** оба цикла начинают первый проход без ожидания интервала и планируют следующие раз в секунду
- **AND** медленный проход не запускает параллельную копию того же цикла

#### Scenario: Kubernetes временно недоступен

- **WHEN** Kubernetes перестаёт отвечать, а PostgreSQL работает
- **THEN** HTTP продолжает принимать допустимые намерения и возвращать последние сохранённые наблюдения
- **AND** после восстановления связи циклы продолжают сверку без повторных HTTP-запросов пользователя

#### Scenario: Один объект повреждён

- **WHEN** один инстанс не проходит проверку принадлежности или операция с ним завершается ошибкой
- **THEN** API сообщает ошибку и продолжает обработку остальных инстансов

#### Scenario: Штатная остановка

- **WHEN** процесс получает сигнал остановки
- **THEN** циклы прекращают новые проходы, отменяют активные обращения и завершаются до закрытия пула PostgreSQL

### Requirement: Объекты принадлежат конкретному инстансу

До изменения или импорта API SHALL проверять ID, `slug`, ожидаемые имена, метки владельца и сохранённые UID объектов. `Namespace` SHALL иметь имя `valkey-<slug>`, CR имя `<slug>` и `spec.instanceId`, равный ID строки. API MUST NOT принимать объект с тем же именем, но иной сохранённой идентичностью, за прежний инстанс. `Namespace` без строки в БД SHALL оставаться на месте с сообщением для ручного разбора.

#### Scenario: Совпало имя чужого объекта

- **WHEN** ожидаемый `Namespace` или CR существует, но относится к другому инстансу
- **THEN** API не изменяет его, не импортирует его `status` и не удаляет его

#### Scenario: Объект заменён

- **WHEN** UID найденного CR отличается от сохранённого UID
- **THEN** API блокирует автоматическую доставку и импорт для этого объекта и сообщает о необходимости восстановления

### Requirement: Доставка создания и конфигурации восстанавливается после прерывания

Для активной строки API SHALL доставлять `Namespace`, `Secret` и CR с защитной отметкой удаления `valkey.h3llo-demo.com/instance-protection`. CR SHALL содержать режим, размер, публичный порт, `whitelist`, версию пароля и желаемое поколение из PostgreSQL. Имя и `maintenance` MUST NOT менять CR. API SHALL перечитывать актуальное намерение перед изменениями и после конфликтов. Доставка MUST NOT уменьшать поколение или версию пароля, менять `status`, удалять `finalizers` или служебные аннотации. Уже удаляемый CR MUST NOT обновляться или пересоздаваться.

#### Scenario: Первоначальная доставка

- **WHEN** пользователь создаёт инстанс через HTTP
- **THEN** в Kubernetes появляются принадлежащие инстансу `Namespace`, `Secret` и CR с выбранной конфигурацией и защитной отметкой удаления
- **AND** сама доставка не подтверждает готовность или применение поколения

#### Scenario: Прерывание до создания CR

- **WHEN** API перезапускается после создания `Namespace` и `Secret`, содержащего только хеши `app`, до появления первого CR
- **THEN** доставка продолжает создание с существующими объектами без смены их идентичности

#### Scenario: Изменение размера или настройка `whitelist`

- **WHEN** HTTP принимает изменение размера или `whitelist`
- **THEN** доставка переносит новое поколение и настройки в `spec`, сохраняя прежние наблюдения до подтверждения оператора

#### Scenario: Совпадающее состояние

- **WHEN** объекты уже содержат актуальное намерение
- **THEN** повторный проход не выполняет записей в эти объекты и не меняет их `resourceVersion`

#### Scenario: Конфликт с оператором

- **WHEN** оператор меняет объект между чтением и записью API
- **THEN** API повторяет сверку по свежему объекту и свежей строке PostgreSQL, сохраняя изменения оператора

### Requirement: Версии пароля доставляются без потери действующего хеша

API SHALL добавлять хеш новой версии в `app-password-hash.<version>` `Secret` до записи соответствующей версии в `spec`. Он SHALL сохранять действующий хеш, служебные пароли, ACL и прочие поля `Secret`. Очистка предыдущего хеша после подтверждения принадлежит оператору; API MUST NOT восстанавливать удалённые старые версии из устаревшего намерения. Пароли, хеши и содержимое `Secret` MUST NOT появляться в ответах, аудитах или логах.

#### Scenario: Прерывание между `Secret` и CR

- **WHEN** новый хеш записан, но обновление CR не завершилось
- **THEN** `Secret` сохраняет хеш версии из действующего `spec`, а следующий проход доставляет новое намерение
- **AND** `applied_password_version` остаётся прежним до подтверждения оператора

#### Scenario: Подтверждение ротации

- **WHEN** `status` подтверждает новую `appliedPasswordVersion`
- **THEN** API импортирует её, а последующая доставка не возвращает старый хеш, очищенный оператором

### Requirement: Потеря истории требует восстановления

API MUST NOT создавать пустой `Secret` вместо потерянного `Secret` существующего CR. Отсутствие служебных полей после `credentialsInitialized`, пропажа ранее известного CR или наличие служебных полей в оставшемся `Secret` без CR SHALL блокировать автоматическое пересоздание. API SHALL сохранять `is_recovery_required` и сообщать причину без секретов. Признак MUST NOT сниматься только потому, что повторное чтение не вернуло ошибку; необходимо подтверждение устранения причины.

#### Scenario: Потерян служебный `Secret`

- **WHEN** у существующего CR отсутствует `Secret`
- **THEN** API не создаёт новый комплект и отмечает необходимость восстановления

#### Scenario: Пропал CR работающего инстанса

- **WHEN** CR отсутствует вне сохранённого протокола удаления, а БД или `Secret` подтверждают начавшуюся обработку
- **THEN** API не пересоздаёт CR и не удаляет оставшийся `Namespace`

### Requirement: Импорт сохраняет подтверждения без отката намерений

API SHALL импортировать `phase`, `reason`, `observedGeneration`, `appliedPasswordVersion`, применённые размеры, `network`, `nodes` и условие `RecoveryRequired` в принадлежащую CR строку. Контракт CRD SHALL принимать фазы `provisioning`, `running`, `updating`, `degraded`, `unavailable`, `error`. Импорт SHALL обновлять только наблюдения и сохранять исходный `observedAt`. Подтверждённые поколение, версия пароля и время наблюдения MUST NOT уменьшаться. Будущие версии сверх намерения PostgreSQL или `spec` CR SHALL отклоняться. Импорт MUST NOT менять пользовательские настройки, `updated_at`, биллинговые периоды или возвращать удалённую запись в работу.

#### Scenario: Повторное чтение старого `status`

- **WHEN** API несколько раз импортирует `status` с прежним `observedAt`
- **THEN** `observed_at` не становится новее, а `is_stale` по-прежнему определяется возрастом исходного наблюдения

#### Scenario: Новое намерение во время импорта

- **WHEN** HTTP принимает новую конфигурацию после чтения CR циклом импорта
- **THEN** импорт сохраняет новую конфигурацию и переносит только допустимые наблюдения прежнего поколения

#### Scenario: Устаревший или невозможный снимок

- **WHEN** наблюдение уменьшает подтверждённую версию либо подтверждает ещё не запрошенное поколение
- **THEN** API отклоняет такой снимок без частичной записи несовместимых полей применённой конфигурации

#### Scenario: Уменьшение размера

- **WHEN** пользователь запросил меньший размер, но `status` ещё подтверждает прежний
- **THEN** квота продолжает учитывать больший размер
- **AND** после импорта подтверждённого меньшего размера резерв уменьшается

#### Scenario: Нулевые и очищенные значения

- **WHEN** допустимое новое наблюдение очищает `reason`, снимает `RecoveryRequired` или устанавливает `readiness`=`false`
- **THEN** импорт сохраняет эти изменения, включая `false` и `null`

### Requirement: История фаз и состояние нод согласованы с наблюдениями

API SHALL сохранять актуальные ноды и изменение фазы в одной транзакции с наблюдением инстанса. Исчезнувшие из принятого снимка ноды MUST NOT оставаться текущими. История SHALL содержать исходную и новую фазы, причину и время `observedAt`. Повторный импорт MUST NOT создавать дубликаты переходов. История MUST NOT выдумывать промежуточные фазы между опросами.

#### Scenario: Новый процесс и фаза

- **WHEN** `status` содержит новую фазу и новый процесс для прежнего `ordinal`
- **THEN** API атомарно сохраняет фазу, переход и идентичность нового процесса

#### Scenario: Ошибка записи события

- **WHEN** запись истории фазы завершается ошибкой
- **THEN** вся транзакция наблюдения откатывается и следующий проход повторяет импорт

### Requirement: Удаление завершается после освобождения ресурсов

API SHALL удалять ресурсы только при `deletion_requested_at` и SHALL сохранять достаточные сведения об идентичности и ходе удаления для продолжения после рестарта. Сначала удаляется CR с защитной отметкой удаления, после его подтверждённого завершения `Namespace`. `Secret` SHALL сохраняться до снятия защиты удаления. Только подтверждённый `NotFound` `Namespace` SHALL разрешать атомарную запись `deleted_at` и события `deleted`. Ошибки соединения и доступа MUST NOT считаться отсутствием объекта. Неожиданное исчезновение CR вне подготовленного удаления MUST NOT разрешать удаление `Namespace`.

#### Scenario: Оператор ещё выполняет удаление

- **WHEN** CR имеет `deletionTimestamp` и защитную отметку удаления
- **THEN** API оставляет `Namespace` и `Secret`, сохраняет `deleting` и занятые квоту и имя

#### Scenario: Удаление завершилось

- **WHEN** CR штатно исчез в ходе сохранённого удаления и затем исчез `Namespace`
- **THEN** API записывает `deleted_at` и одно событие `deleted`, освобождает квоту и исключает инстанс из обычного чтения

#### Scenario: Перезапуск при удалении

- **WHEN** API перезапускается до или после запроса удаления CR, после его исчезновения либо после удаления `Namespace`
- **THEN** он продолжает сохранённый протокол, не создаёт ресурсы заново и не дублирует событие `deleted`

#### Scenario: Создание отменили до первого CR

- **WHEN** удаление принято до первого CR и отсутствуют следы начавшейся работы оператора
- **THEN** API удаляет только принадлежащие этому созданию остатки `Namespace` и подтверждает завершение без запуска CR

### Requirement: CR принимает последние снимки метрик нод

`status.metrics` ресурса `ValkeyInstance` SHALL принимать не более трёх элементов с уникальным `ordinal`. Каждый элемент SHALL содержать `ordinal`, `podUID`, `containerID`, `runId`, `collectedAt`, `role`, `usedMemoryBytes`, `maxmemoryBytes`, `connectedClients`, `opsPerSec`, `keyspaceHits`, `keyspaceMisses`, `evictedKeys` и допускающее `null` поле `cpuMillicores`. Идентификаторы SHALL быть непустыми, роль SHALL быть `primary` или `replica`, числовые показатели SHALL быть неотрицательными. `collectedAt` SHALL сохранять время UTC с точностью до микросекунд. Контракт не требует, чтобы оператор заполнял это поле в рамках данного изменения.

#### Scenario: Снимок с недоступным CPU

- **WHEN** административный клиент записывает допустимый снимок с `cpuMillicores=null` и микросекундами в `collectedAt`
- **THEN** Kubernetes принимает снимок и возвращает исходное время с микросекундами

#### Scenario: Повтор номера ноды

- **WHEN** клиент пытается записать два элемента `status.metrics` с одним `ordinal`
- **THEN** схема CRD отклоняет изменение

#### Scenario: Недопустимый показатель

- **WHEN** снимок содержит отрицательный счётчик или неизвестную роль
- **THEN** схема CRD отклоняет изменение

### Requirement: API импортирует допустимые снимки независимо от наблюдения

После проверки принадлежности CR инстансу API SHALL независимо проверять каждый элемент `status.metrics` по элементу `status.nodes` с теми же `ordinal`, `podUID`, `containerID` и `runId`. Допустимый снимок SHALL сохраняться в `valkey_node_metrics` с `spec.instanceId` как `instance_id`, `collectedAt` как `ts` и остальными полями без подстановки отсутствующего CPU. Неизвестный ordinal, снимок другого процесса и снимок старше настроенного срока хранения MUST NOT сохраняться и MUST NOT препятствовать импорту других допустимых снимков того же CR. Отсутствующее, неизменившееся или устаревшее основное наблюдение MUST NOT препятствовать импорту нового допустимого снимка. Повторный импорт одного снимка MUST NOT создавать вторую строку.

#### Scenario: Новый снимок текущего процесса

- **WHEN** `status.metrics` содержит снимок, идентичность которого совпадает с текущим элементом `status.nodes`
- **THEN** следующий проход импорта сохраняет одну строку с исходным временем и показателями

#### Scenario: Метрика меняется без изменения наблюдения

- **WHEN** `status.observedAt`, фаза и состав нод не изменились, а `status.metrics` получил новый `collectedAt`
- **THEN** API сохраняет новый снимок, не требуя изменения основного наблюдения

#### Scenario: Повторное чтение CR

- **WHEN** API несколько раз читает один снимок из неизменившегося CR
- **THEN** в `valkey_node_metrics` остаётся одна строка для его `instance_id`, `ordinal` и `collectedAt`

#### Scenario: Снимок прежнего процесса рядом с допустимым

- **WHEN** один элемент `status.metrics` не совпадает с `status.nodes`, а другой относится к текущему процессу
- **THEN** API не сохраняет чужой снимок и сохраняет допустимый

#### Scenario: Просроченный снимок в CR

- **WHEN** `collectedAt` старше `VALKEY_METRICS_RETENTION` относительно текущего времени PostgreSQL
- **THEN** API не добавляет снимок в историю

### Requirement: API-тесты проверяют настоящий Kubernetes с отдельными полномочиями

Единая команда `just test` в каталоге `api` SHALL проверять синхронизацию через настоящий TCP HTTP, PostgreSQL и выделенный однонодовый k3s без оператора, Envoy и Valkey. Рабочая синхронизация SHALL использовать файл подключения с правами API; отдельный административный клиент теста SHALL подготавливать `status`, включая `status.metrics`, и имитировать штатное снятие защиты удаления. Тесты MUST NOT выдавать приложению права на `status` или управление подами. Отсутствие требуемого стенда в полном запуске SHALL завершать запуск ошибкой. Тот же набор SHALL выполняться через действующее задание CI `test-api` со штатной подготовкой отдельного окружения. Асинхронные проверки SHALL ожидать требуемое состояние с ограниченным сроком ожидания.

#### Scenario: Двусторонний сценарий

- **WHEN** тест создаёт инстанс через HTTP, проверяет доставленный `spec` и записывает подготовленный `status` административным клиентом
- **THEN** HTTP возвращает импортированные наблюдения без запуска оператора

#### Scenario: Импорт метрик без оператора

- **WHEN** административный клиент записывает согласованные `status.nodes` и `status.metrics`
- **THEN** фоновый процесс API сохраняет снимок в PostgreSQL, а существующий HTTP API возвращает его владельцу
- **AND** повторное чтение того же CR не увеличивает число строк

#### Scenario: Проверка полномочий

- **WHEN** клиент приложения пытается изменить `status` или управлять подами
- **THEN** Kubernetes запрещает действие, а разрешённые операции доставки и импорта продолжают работать

#### Scenario: Запуск в CI

- **WHEN** задание `test-api` выполняет `just test` в каталоге `api`
- **THEN** новые сценарии синхронизации входят в тот же полный набор и используют отдельное окружение, подготовленное штатными скриптами
- **AND** проверка ждёт требуемого результата доставки или импорта, даже если период фонового прохода больше времени выполнения одного HTTP-запроса
