# backend-foundation Specification

## Purpose

Определяет воспроизводимую основу двух Go-приложений, которую можно собирать, запускать, проверять и расширять без смены структуры проекта и набора инструментов.

## Requirements

### Requirement: Общий Go-модуль

API, оператор и общий серверный код SHALL собираться из одного Go-модуля в корне репозитория. Каталоги приложений MUST NOT содержать вложенные `go.mod` или независимые наборы версий общих зависимостей.

#### Scenario: Загрузка зависимостей из корня

- **WHEN** разработчик загружает зависимости Go из корня репозитория
- **THEN** зависимости API и оператора разрешаются из одного `go.mod` и зафиксированного `go.sum`

### Requirement: Воспроизводимые инструменты Go

Проект SHALL закреплять версии инструментов генерации, тестового Kubernetes-окружения и миграций вместе с Go-модулем. Команды приложений MUST NOT зависеть от произвольной версии одноимённого исполняемого файла в системе разработчика.

#### Scenario: Чистая рабочая среда

- **WHEN** разработчик имеет поддерживаемую версию Go, но не устанавливал серверные инструменты глобально
- **THEN** локальные `Justfile` запускают закреплённые проектом версии инструментов

### Requirement: Локальные команды API

Каталог `api` SHALL содержать `Justfile` с публичными командами `migration-up`, `migration-down`, `migration-generate name`, `run`, `format`, `lint`, `test` и `test-full`. `just test` SHALL готовить выделенную PostgreSQL-базу, применять миграции и выполнять все тесты API, которым не нужен k3s. `just test-full` SHALL дополнительно готовить однонодовый k3s и выполнять весь набор API, включая Kubernetes-синхронизацию. В тестовом кластере API MUST NOT запускаться оператор или поды Valkey.

#### Scenario: Список команд API

- **WHEN** разработчик запускает `just --list` в `api`
- **THEN** он видит единые команды приложения и предметные команды миграций

#### Scenario: Тесты API

- **WHEN** разработчик запускает `just test` в `api`
- **THEN** команда создаёт отдельную базу, применяет миграции и выполняет все тесты без подготовки k3s

#### Scenario: Полные тесты API

- **WHEN** разработчик запускает `just test-full` в `api`
- **THEN** команда создаёт отдельные базу и однонодовый k3s и выполняет также Kubernetes-зависимые тесты без оператора и Valkey

### Requirement: Команды запуска и проверки оператора

Каталог `operator` SHALL содержать `Justfile` с публичными командами `run`, `format`, `lint`, `test` и `test-full`. `just test` SHALL выполнять unit-тесты и envtest без k3s и сообщать, что полная аварийная матрица не запускалась. `just test-full` SHALL выполнять быстрый набор и медленные проверки жизненного цикла `single` и HA, восстановления после отказов, ресайза и смены пароля с настоящими Valkey и Envoy без HTTP API и PostgreSQL. Каждый k3s-сценарий SHALL получать независимый кластер с минимальной топологией от одной до четырёх нод и одной или двумя репликами Envoy. Команда SHALL самостоятельно готовить стенды и один тестовый образ оператора. Для потери оператора вместе с worker-нодой SHALL использоваться оператор внутри тестового k3s без одновременно работающей хостовой копии. K3s-проверки SHALL использовать отдельный тестовый профиль длительностей и показывать время сценариев; обычная сборка SHALL сохранять рабочие пороги. `run` SHALL запускать оператор на хосте с отдельным kubeconfig dev k3s. `test-ci` и `test-fast` MUST NOT оставаться публичными командами.

#### Scenario: Этапы полного запуска оператора

- **WHEN** разработчик запускает `just test-full` в `operator`
- **THEN** unit/envtest и однократная подготовка тестовых артефактов запускаются независимо; после готовности артефактов начинаются сценарии с настоящими Valkey и Envoy на независимых k3s

#### Scenario: Ограниченные тесты оператора в CI

- **WHEN** задание CI запускает `just test` в `operator`
- **THEN** команда выполняет unit/envtest без подготовки k3s и сообщает, что полная аварийная матрица не запускалась

#### Scenario: Запуск оператора с dev k3s

- **WHEN** разработчик запускает `just run` в `operator`
- **THEN** команда готовит CRD и RBAC и запускает manager через `go run` с kubeconfig dev-окружения под `tmp/k3s`

#### Scenario: Самостоятельные полные тесты

- **WHEN** `just test-full` доходит до тестов на k3s
- **THEN** тесты напрямую создают Kubernetes-объекты и проверяют TLS/SNI/AUTH, SET/GET, изоляцию, whitelist, рестарты и штатное удаление без API и PostgreSQL, затем выполняют обязательные проверки HA, аварий, ресайза и пароля

#### Scenario: Потеря worker-ноды

- **WHEN** полный набор проверяет восстановление после аварийной остановки agent
- **THEN** он выполняет сценарии без запасного хоста и с четвёртой нодой, включая потерю оператора вместе с primary, без ручного исправления ролей и finalizers ради успешного результата

#### Scenario: Стенд недоступен или тест не прошёл

- **WHEN** подготовка стенда либо проверка завершается неудачно
- **THEN** команда возвращает ненулевой код с причиной, не пропускает проверку молча и не снимает finalizers принудительно для получения успешного результата

#### Scenario: Анализ длительности

- **WHEN** этап реализации добавил или изменил сценарии оператора
- **THEN** разработчик видит их длительность, проверяет самые медленные ожидания и ускоряет обвязку без удаления настоящих воздействий и конечных проверок

### Requirement: Локальные команды Go форматируют и проверяют область приложения

`api just format` и `operator just format` SHALL форматировать Go-код приложения и используемый им общий код, после чего добавлять изменения этой области в индекс Git. `api just lint` и `operator just lint` SHALL проверять соответствующие пакеты и общий код по корневому `.golangci.yml`, проверять сборку и чистоту `go mod tidy -diff`, не меняя индекс. Линтинг оператора SHALL также проверять сгенерированные DeepCopy, CRD и RBAC.

#### Scenario: Форматирование API

- **WHEN** разработчик запускает `just format` в `api`
- **THEN** форматируются и добавляются в индекс изменения API и общего Go-кода без добавления файлов оператора или web

#### Scenario: Линтинг оператора

- **WHEN** разработчик запускает `just lint` в `operator`
- **THEN** проверяются общий код, пакеты оператора, сборка, модульные файлы и сгенерированные ресурсы без изменения рабочего дерева или индекса

### Requirement: Общие правила линтинга Go

Репозиторий SHALL иметь один корневой `.golangci.yml` формата v2, адаптированный из конфигурации Databasus. Он SHALL включать проверки ошибок, контекста и современного Go, а также `gofumpt`, `golines` с длиной строки 120 и `gci`. Настройка module path SHALL соответствовать общему Go-модулю Managed Valkey. Пре-коммит хук SHALL использовать этот файл для обоих приложений.

#### Scenario: Линтинг API

- **WHEN** staged-изменение затрагивает исходники API
- **THEN** пре-коммит хук форматирует и проверяет API и используемый им общий код по корневому `.golangci.yml`

#### Scenario: Линтинг оператора

- **WHEN** staged-изменение затрагивает исходники оператора
- **THEN** пре-коммит хук форматирует и проверяет оператор и используемый им общий код по корневому `.golangci.yml`

### Requirement: Проверки Go перед коммитом

Корневой `.githooks/pre-commit` SHALL сохранять проверки frontend и запускать форматирование, линтинг и сборку для Go-приложений, затронутых staged-изменениями. Изменение общего Go-кода, `go.mod`, `go.sum` или корневого `.golangci.yml` SHALL затрагивать оба приложения. Хук SHALL проверять чистоту `go mod tidy -diff`. Он MUST добавлять в индекс исправления форматтера только для Go-файлов, которые уже были staged, и MUST NOT добавлять посторонние незакоммиченные файлы. Ошибка форматирования, замечание линтера, расхождение модульных файлов или ошибка сборки SHALL отменять коммит.

#### Scenario: Форматтер исправил staged Go-файл

- **WHEN** staged Go-файл требует только автоматического форматирования, а остальные проверки проходят
- **THEN** hook добавляет исправленную версию этого файла в индекс и разрешает коммит

#### Scenario: Go-файл добавлен в индекс частично

- **WHEN** staged Go-файл содержит незакоммиченные изменения вне индекса
- **THEN** hook отменяет коммит до форматирования и не добавляет эти изменения в индекс

#### Scenario: Проверка нашла проблему

- **WHEN** линтер сообщает замечание, `go mod tidy -diff` находит расхождение или приложение не собирается
- **THEN** hook возвращает ненулевой код и коммит не создаётся

#### Scenario: Изменён общий Go-код

- **WHEN** staged-изменение затрагивает общий Go-пакет или модульные файлы
- **THEN** hook проверяет линтинг и сборку API и оператора

### Requirement: Проверки состояния API

API SHALL предоставлять отдельные HTTP-проверки живого процесса и готовности принимать рабочие запросы. Проверка готовности SHALL завершаться ошибкой, пока API не установил соединение с PostgreSQL; недоступность Kubernetes MUST NOT делать HTTP API неготовым.

#### Scenario: PostgreSQL доступна

- **WHEN** процесс API запущен и соединение с PostgreSQL установлено
- **THEN** проверки живого процесса и готовности отвечают успешно

#### Scenario: PostgreSQL недоступна

- **WHEN** процесс API работает, но соединение с PostgreSQL установить нельзя
- **THEN** проверка живого процесса отвечает успешно, а проверка готовности сообщает ошибку

#### Scenario: Kubernetes недоступен

- **WHEN** PostgreSQL доступна, но API не может обратиться к Kubernetes
- **THEN** проверка готовности API остаётся успешной, а фоновые операции смогут повторить обращение после восстановления связи

### Requirement: Готовность manager и управление инстансами

Оператор SHALL предоставлять проверки живого процесса и готовности manager. Контроллер SHALL управлять жизненным циклом single согласно capability single-instance-lifecycle. Готовность manager MUST NOT означать публичную готовность инстансов.

#### Scenario: Manager запущен

- **WHEN** оператор подключился к Kubernetes и запустил manager
- **THEN** проверки живого процесса и готовности отвечают успешно

#### Scenario: Ресурс попал в reconcile

- **WHEN** контроллер получает полный поддерживаемый ValkeyInstance
- **THEN** он приводит ресурсы к принятой конфигурации и записывает подтверждённые наблюдения в status

#### Scenario: Инстанс ещё не готов

- **WHEN** manager работает, но инстанс ожидает готовности маршрута или процесса
- **THEN** manager остаётся готовым, а status инстанса не сообщает running до выполнения его проверок

### Requirement: Штатное завершение процессов

API и оператор SHALL обрабатывать завершение процесса через контекст отмены. API SHALL перестать принимать новые соединения и завершить начатые запросы в пределах заданного срока; оператор SHALL остановить manager и активные фоновые задачи. Оба процесса SHALL попытаться отправить накопленные логи перед выходом.

#### Scenario: Получен SIGTERM

- **WHEN** API или оператор получает `SIGTERM`
- **THEN** процесс прекращает новую работу, освобождает ресурсы и завершается с нулевым кодом в пределах срока остановки

### Requirement: Единые структурированные логи

Оба приложения SHALL писать структурированные логи через `slog` в stdout и, когда задан `VL_OTLP_URL`, отправлять их по OTLP/HTTP. Записи SHALL содержать `service.name` и `env`; ключи атрибутов SHALL использовать `snake_case`. Пароли, токены, заголовки авторизации, содержимое Secret и полные тела запросов MUST NOT попадать ни в один обработчик логов.

#### Scenario: Локальный запуск без VictoriaLogs

- **WHEN** `VL_OTLP_URL` не задан
- **THEN** приложение пишет читаемые структурированные записи в stdout и продолжает работу без OTLP-экспортера

#### Scenario: Экспорт логов недоступен

- **WHEN** приложение не может доставить лог в VictoriaLogs
- **THEN** HTTP API или reconcile продолжают работу, а ошибка экспорта не раскрывает содержимое исходной записи

### Requirement: Воспроизводимая генерация Kubernetes-артефактов

Проект SHALL использовать закреплённый генератор DeepCopy, CRD и RBAC для Go-маркеров. Повторная генерация из неизменённых исходников MUST NOT менять рабочее дерево. Тестовые команды SHALL проверять соответствие сгенерированных файлов во временном каталоге и MUST NOT перезаписывать отслеживаемые файлы при параллельной компиляции приложений.

#### Scenario: Повторная генерация

- **WHEN** разработчик дважды запускает внутренний шаг генерации без изменения Go-типов и маркеров
- **THEN** второй запуск не создаёт различий в отслеживаемых файлах

#### Scenario: Параллельная компиляция

- **WHEN** API и оператор тестируются одновременно
- **THEN** проверка генерации не изменяет файлы, которые читает компилятор API или оператора

#### Scenario: Устаревший сгенерированный файл

- **WHEN** проверка обнаруживает расхождение генерации с исходниками
- **THEN** команда сообщает ошибку и оставляет рабочее дерево без изменений

### Requirement: Авторизация OTLP не допускает передачу пароля по HTTP

Экспортёр SHALL поддерживать `VL_OTLP_USERNAME` и `VL_OTLP_PASSWORD_FILE`. При заданной авторизации он SHALL требовать HTTPS и обе настройки, читать пароль из файла и формировать Basic Auth в памяти. Экспортёр MUST NOT следовать перенаправлениям, отключать проверку TLS или повторять запрос без авторизации после отказа. Ошибка настройки SHALL отключать экспорт с сообщением в stdout без раскрытия пароля; приложение SHALL продолжать работу.

#### Scenario: Защищённый экспорт

- **WHEN** заданы HTTPS URL, имя пользователя и доступный файл пароля
- **THEN** экспортёр отправляет OTLP с Basic Auth и проверяет сертификат сервера

#### Scenario: Небезопасная или неполная конфигурация

- **WHEN** авторизация задана для HTTP, отсутствует имя пользователя или файл пароля недоступен
- **THEN** экспортёр не отправляет запросы, сообщает об ошибке без пароля и сохраняет вывод приложения в stdout

#### Scenario: Отказ или перенаправление сервера

- **WHEN** сервер возвращает 401 или перенаправление на HTTP
- **THEN** экспортёр не переходит на HTTP и не повторяет запрос анонимно
