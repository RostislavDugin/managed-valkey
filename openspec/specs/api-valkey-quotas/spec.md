# api-valkey-quotas Specification

## Purpose

Серверный учёт ресурсов не допускает превышения квот пользователя и фиксированного бюджета Valkey в Kubernetes, включая конкурентные запросы и ещё не завершённые изменения.

## Requirements

### Requirement: Сервер задаёт доступные размеры и цены

Защищённый `GET /v1/managed/valkey/sizes` SHALL возвращать `{items, pricing, connection}`. Items SHALL содержать пары `{vcpu, ram_gb}` из списка `[{1,1},{1,2},{1,4},{2,8},{4,16}]` в пределах `VALKEY_INSTANCE_MAX_VCPU` и `VALKEY_INSTANCE_MAX_RAM_GB`. Pricing SHALL содержать `vcpu_coins_per_hour`, `ram_gb_coins_per_hour`, `hours_per_month=720`; connection SHALL содержать `{domain, port}` для предварительного адреса. Цена SHALL считаться в целых копейках как `(cpu_rate*vcpu + ram_rate*ram_gb)*node_count`. Недопустимый размер в мутации SHALL давать `400 VALIDATION_FAILED`, независимо от свободной квоты.

#### Scenario: Границы сетки

- **WHEN** клиент запрашивает сетку при ограничениях размера из env
- **THEN** каждая возвращённая пара допустима для создания и все допустимые пары присутствуют в порядке CPU, RAM по возрастанию
- **AND** текущая занятость квоты не удаляет пары из каталога

#### Scenario: Стоимость HA

- **WHEN** ставки равны 125 и 50 копейкам, размер равен 1 CPU и 2 GB
- **THEN** цена `single` равна 225 копейкам в час, `ha` равна 675

### Requirement: Квота учитывает все неподтверждённо удалённые инстансы

Для каждой строки с `deleted_at IS NULL` резерв SHALL равняться `node_count*greatest(vcpu, applied_vcpu)` и `node_count*greatest(ram_gb, applied_ram_gb)` независимо от фазы, свежести и запроса удаления. `node_count` SHALL быть 1 для single и 3 для ha. При resize SHALL заменяться резерв изменяемого инстанса на резерв кандидата с прежними applied-размерами. Использование пользователя SHALL суммировать только его строки, кластера SHALL суммировать всех владельцев. Подтверждённо удалённые строки MUST NOT учитываться.

#### Scenario: Создание ещё не доставлено

- **WHEN** новый инстанс находится в `provisioning` с нулевыми applied-размерами
- **THEN** его полный desired-размер уже занимает личную и общую квоту

#### Scenario: Ошибка и удаление удерживают резерв

- **WHEN** инстанс переходит в `error` либо получает запрос удаления
- **THEN** резерв CPU, RAM и места в лимите числа инстансов сохраняется

#### Scenario: Уменьшение ещё не применено

- **WHEN** single изменён с 4 CPU / 16 GB на 2 CPU / 8 GB, applied остаётся 4 CPU / 16 GB
- **THEN** резерв остаётся 4 CPU / 16 GB до изменения applied

#### Scenario: Смешанное изменение ресурсов

- **WHEN** single с прежним applied-размером 4 CPU / 4 GB меняется на desired 2 CPU / 8 GB
- **THEN** резерв равен 4 CPU / 8 GB

### Requirement: Кластерный бюджет проверяется в исходном запросе

`MANAGED_K8S_NODE_VCPU` и `MANAGED_K8S_NODE_RAM_GB` SHALL означать суммарный доступный Valkey бюджет всего кластера, без умножения на число Kubernetes-нод. В v1 SHALL отсутствовать автоматическое расширение и очередь создания, ожидающая добавления ресурсов. После получения общей блокировки создание и resize SHALL проверять бюджет и предел 32 неудалённых инстанса. Нехватка SHALL давать `422 NOT_ENOUGH_RESOURCES` в том же HTTP-запросе до записи намерения. API MUST NOT принимать заведомо не помещающийся запрос с `202` и ждать таймаута provisioning или scheduler. Проверка SHALL использовать PostgreSQL и конфигурацию без вызовов Kubernetes.

#### Scenario: Немедленный отказ при нехватке CPU

- **WHEN** при общей квоте 4 CPU / 16 GB уже зарезервированы 3 CPU / 3 GB, а пользователь со свободной личной квотой создаёт single 2 CPU / 8 GB
- **THEN** исходный POST возвращает `422 NOT_ENOUGH_RESOURCES` с `reason=cluster_quota` и дефицитом 1 CPU
- **AND** новый инстанс, его аудит, период и ключ отсутствуют, использованная квота не меняется
- **AND** ответ не требует фонового прохода или истечения таймаута запуска

#### Scenario: Немедленный отказ при нехватке RAM

- **WHEN** CPU достаточно, но резерв кандидата превышает общий RAM-бюджет
- **THEN** исходный POST возвращает `422 NOT_ENOUGH_RESOURCES` с дефицитом RAM и без частичных записей

#### Scenario: Ровно доступный бюджет

- **WHEN** создание доводит CPU и RAM до лимитов без превышения
- **THEN** API принимает запрос с `202`

#### Scenario: Последнее место на Gateway

- **WHEN** существуют 31 неудалённый инстанс и два пользователя одновременно создают ещё по одному при достаточных CPU/RAM
- **THEN** ровно один запрос получает `202`, второй получает `422 NOT_ENOUGH_RESOURCES` с `reason=instance_limit`
- **AND** resize существующего инстанса при 32 записях не отклоняется только из-за их числа

#### Scenario: Конкуренция между владельцами

- **WHEN** два пользователя через разные экземпляры API одновременно запрашивают последний свободный ресурс
- **THEN** ровно один запрос принимается, второй видит уже обновлённый резерв и получает `422`
- **AND** сумма резервов не превышает лимит

### Requirement: Личная квота и общий бюджет дают разные ошибки

Лимиты пользователя SHALL читаться из `user_quotas`; значения по умолчанию остаются 4 CPU / 16 GB. Личная квота SHALL проверяться раньше общей. Ошибка SHALL быть `422 QUOTA_EXCEEDED` с `reason=user_quota`. Для ресурсных ошибок details SHALL содержать `limit`, `used`, `requested`, `missing`, где каждая величина содержит `vcpu` и `ram_gb`, а requested означает суммарный резерв после принятия кандидата. Для предела числа details SHALL содержать `limit`, `used`, `requested` как целые числа. Отказ по квоте MUST NOT занимать ключ идемпотентности.

#### Scenario: CPU и RAM проверяются независимо

- **WHEN** кандидат превышает только один личный лимит
- **THEN** API отклоняет его и возвращает ненулевой дефицит только соответствующего ресурса

#### Scenario: Два запроса одного пользователя

- **WHEN** каждый из двух конкурентных запросов отдельно помещается в личный остаток, но вместе они превышают квоту
- **THEN** один запрос принимается, другой получает `QUOTA_EXCEEDED`

#### Scenario: Лимит уменьшен ниже занятого объёма

- **WHEN** новый resize не увеличивает резерв ни CPU, ни RAM относительно текущего, но текущий резерв уже выше нового лимита
- **THEN** API допускает уменьшение при выполнении остальных правил готовности
- **AND** увеличение любой превышающей лимит величины отклоняется

### Requirement: Конфигурация квот проверяется при запуске

API SHALL проверять целые положительные лимиты ресурсов и порта, непустую допустимую сетку и корректный домен до приёма HTTP-запросов. Общие CPU/RAM SHALL браться из обязательных env; отсутствие или неверный формат MUST NOT заменяться неограниченной квотой. Ставки SHALL быть целыми неотрицательными и не приводить к переполнению расчёта для разрешённых размеров.

#### Scenario: Ошибочная конфигурация

- **WHEN** лимит отсутствует, отрицателен, дробный либо сетка пуста
- **THEN** приложение не начинает обслуживать запросы и сообщает имя ошибочного параметра
