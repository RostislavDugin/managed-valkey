# TODO: сквозные тесты личного кабинета

Набор начат с регистрации через браузер, настоящий HTTP API и PostgreSQL. Полный
путь через Kubernetes, оператор, Envoy и публичное подключение к Valkey остаётся
в плане ниже. Тесты пишем на TypeScript с Playwright.

## Границы набора

- Регистрацию и все действия с инстансами выполняем через личный кабинет.
- Не вызываем HTTP API напрямую и не меняем PostgreSQL, CR или другие объекты
  Kubernetes для подготовки пользовательского состояния.
- Адрес, порт и одноразовый пароль Valkey берём из интерфейса.
- К Valkey подключаемся из процесса Playwright отдельным клиентом TypeScript.
  Соединение использует TLS, SNI, пользователя `app` и данные из интерфейса.
- Kubernetes используем только для внесения сбоя в сценариях `@local-k8s` и
  для диагностики упавшего локального запуска.

## Команды

| Команда | Стенд | Браузер | Сценарии |
| --- | --- | --- | --- |
| `just test-e2e` | временная PostgreSQL и отдельный k3s | headless Chromium | все локальные |
| `just test-e2e-headed` | тот же временный стенд | видимый Chromium | все локальные |
| `just test-prod` | `https://app.h3llo-demo.com` | видимый Chromium | только `@prod` |

`just test-e2e` работает через `scripts/test_environment.sh exec e2e`. Этот
сценарий выделяет базу
`managed_valkey_test_e2e_*`, отдельный трёхнодовый k3s, сеть, домен,
сертификат и случайные внешние порты. После теста он удаляет временную базу,
кластер и сеть, не затрагивая dev-окружение.

Текущий сценарий запуска внутри подготовленного окружения:

- применяет миграции к `TEST_DATABASE_URL`;
- запускает `api` и `web` на свободных портах;
- дожидается readiness обоих процессов;
- передаёт Playwright фактический URL личного кабинета;
- останавливает дочерние процессы при успехе, ошибке и сигнале завершения.

Оператор начнёт запускаться здесь после появления сценариев Valkey. Тогда же API
получит внешний порт тестового Envoy, чтобы адрес из интерфейса подходил для
подключения.

`tests/e2e/Justfile` предоставляет обычный, headed- и production-запуск.
Корневой `Justfile` вызывает эти команды через `test-e2e`, `test-e2e-headed` и
`test-prod`. Корневой `just test` запускает e2e параллельно с API, оператором и
`web`; общий интеграционный набор пока остаётся неподключённым.

Конфигурация Playwright по умолчанию запускает один headless Chromium без
повторов теста. `just test-e2e-headed` меняет только режим браузера.
Фиксированные `sleep` не используем: ждём состояния интерфейса, ответа сети
или результата команды Valkey с ограниченным сроком ожидания.

## CI

После успешного завершения всех заданий lint обязательное задание `test-e2e`
запускается независимо и параллельно с `test-api`, `test-operator` и
`test-web`. Оно использует собственную базу и трёхнодовый k3s, устанавливает
зависимости `web` и `tests/e2e`, ставит Chromium через Playwright и вызывает
ту же команду `just test-e2e`, что используется локально. Будущее задание
`test-integration` должно подключаться параллельно по тем же правилам.

Задания сборки зависят от `test-e2e`. После реализации `test-integration` его
также нужно добавить в зависимости сборки. Ошибка подготовки, тестов или очистки
e2e блокирует сборку и развёртывание, но не прерывает уже запущенные независимые
задания.

При ошибке сохраняем отчёт Playwright, снимок экрана и диагностику из
`tmp/k3s/e2e/*/diagnostics`. Трассировку для сценариев авторизации не сохраняем:
она содержит введённый пароль и тело запроса регистрации. Перед публикацией
введённый пароль удаляется из HTML-отчёта, после чего отдельная проверка ищет его
в обычных файлах, ZIP и встроенных данных отчёта. Небезопасная диагностика не
публикуется. Диагностику публикуем только после попытки удалить созданные
инстансы.

`just test-prod` не запускается в CI или после deploy. Это ручная локальная
проверка настоящего сайта.

## Учётные записи и очистка

Каждая регистрация использует новый адрес вида
`e2e+<run-id>-<scenario>-<random>@example.test`. Для всех тестовых аккаунтов
используем пароль `testpassword` и не выводим его в отчёт.

Текущий тест регистрации не создаёт инстансы. Для будущих сценариев фикстура
должна записывать аккаунт и каждый созданный инстанс сразу после появления
одноразового пароля. Основной сценарий удаляет инстансы через личный кабинет.
Очистка после теста повторяется независимо от его результата: новый контекст
браузера входит под тем же аккаунтом, удаляет оставшиеся инстансы и ждёт их
исчезновения из списка и освобождения квоты.

Прямые DELETE-запросы, SQL, удаление CR и namespace для пользовательской
очистки запрещены. Если очистка через интерфейс не завершилась, весь запуск
считается неуспешным. В сообщении оставляем только почту, имя и slug, чтобы
инстанс можно было найти вручную; пароли не печатаем.

После успешного `just test-prod` в production не остаётся инстансов Valkey.
Тестовые аккаунты остаются в базе: личный кабинет пока не умеет их удалять.

## Группы сценариев

Сценарии помечаем по месту запуска:

- `@prod` не требует доступа к Kubernetes, не проверяет квоты и после
  завершения не занимает ресурсы Valkey;
- `@local` использует только пользовательские действия, но меняет общую
  загрузку временного кластера;
- `@local-k8s` вносит сбои через административный kubeconfig временного k3s.

`just test-prod` выбирает только `@prod`. Обычный локальный и CI-запуск
выполняет все три группы последовательно внутри своего окружения.

## `@prod`: жизненный цикл `single`

- [ ] Зарегистрировать новый аккаунт через личный кабинет.
- [ ] Создать `single` минимального доступного размера и сохранить пароль из
      одноразового окна.
- [ ] Пока инстанс создаётся, проверить статус и недоступность кнопок смены
      тарифа, пароля и whitelist.
- [ ] Дождаться `running`. Проверить основной адрес, порт и отсутствие
      RO-адреса. Кнопки изменения конфигурации должны стать доступны.
- [ ] Подключиться по данным из интерфейса, выполнить `SET` и `GET`, затем
      проверить `maxmemory` через `INFO`.
- [ ] Увеличить инстанс до следующего доступного размера. Дождаться завершения
      обновления и совпадения выбранного и применённого размера.
- [ ] Проверить новый размер в интерфейсе и `maxmemory` в Valkey. Старый ключ
      после ресайза `single` может отсутствовать, поэтому записать новый и
      проверить его чтение.
- [ ] Уменьшить инстанс до исходного размера и повторить проверки размера,
      подключения, записи и чтения.
- [ ] Сменить пароль через интерфейс и сохранить новое значение из
      одноразового окна.
- [ ] Дождаться применения пароля. Старое соединение должно закрыться, новый
      вход со старым паролем должен завершиться отказом, а новый пароль должен
      разрешать `SET`, `GET` и `INFO`.
- [ ] Удалить инстанс с подтверждением по slug, дождаться исчезновения из
      списка и нулевого использования квоты.
- [ ] Проверить, что новое подключение по прежнему адресу невозможно.

## `@prod`: жизненный цикл `ha`

- [ ] Зарегистрировать новый аккаунт и создать минимальный допустимый
      HA-инстанс.
- [ ] Сохранить пароль, дождаться `running` и проверить доступность действий с
      конфигурацией.
- [ ] Проверить основной адрес и отдельный RO-адрес. Оба адреса и порт должны
      быть показаны в личном кабинете.
- [ ] Записать значение через основной адрес и прочитать его через основной и
      RO-адреса. Запись через RO должна вернуть `READONLY`.
- [ ] Проверить размер одной ноды и суммарные ресурсы трёх нод в интерфейсе,
      затем сверить `maxmemory` через оба адреса.
- [ ] Увеличить размер до следующего допустимого в текущей квоте, дождаться
      завершения перекатки и снова проверить оба подключения и размеры.
- [ ] Уменьшить размер до исходного, дождаться завершения и повторить проверки.
      Данные после уменьшения RAM сохранять не требуется.
- [ ] Сменить пароль. Проверить закрытие старых соединений, отказ старого
      пароля и работу нового пароля на основном и RO-адресах.
- [ ] Удалить инстанс через интерфейс, дождаться нулевой квоты и проверить, что
      оба адреса перестали принимать подключения.

## `@local`: личная квота

- [ ] На новом аккаунте выбрать HA-размер, который с учётом трёх нод превышает
      свободные 4 vCPU или 16 GB.
- [ ] Проверить видимое объяснение недостающих ресурсов и недоступную кнопку
      создания. Запрос на создание не должен уходить.
- [ ] Создать минимальный `single`, затем через тот же интерфейс создать второй
      минимальный `single`, который займёт часть квоты.
- [ ] Для первого инстанса выбрать размер, при котором суммарное использование
      превысит личную квоту. Проверить сообщение и недоступную отправку формы.
- [ ] Удалить вспомогательный инстанс через интерфейс и дождаться уменьшения
      занятой квоты.
- [ ] Повторить допустимый ресайз первого инстанса и дождаться его завершения.
- [ ] Удалить первый инстанс и проверить нулевое использование квоты.

Размеры не зашиваем в тест. Выбираем из показанного каталога минимальный
доступный, следующий больший доступный и первый недоступный вариант.

## `@local`: общая ёмкость кластера

- [ ] Прочитать настроенный для стенда общий бюджет
      `MANAGED_K8S_NODE_VCPU` и `MANAGED_K8S_NODE_RAM_GB`.
- [ ] До запуска убедиться, что этот бюджет можно исчерпать раньше предела в
      32 инстанса. Иначе завершить подготовку с понятной ошибкой.
- [ ] Последовательно регистрировать новые аккаунты и создавать через личный
      кабинет `single`, пока следующий запрос не превысит общий бюджет. Размер
      каждого инстанса должен помещаться в личную квоту его владельца.
- [ ] Для последней попытки начать создание из интерфейса и через наблюдение
      Playwright за ответом проверить HTTP `422`, код
      `NOT_ENOUGH_RESOURCES` и `reason=cluster_quota`.
- [ ] Проверить сообщение о нехватке ресурсов кластера и отсутствие новой
      карточки инстанса.
- [ ] Убедиться, что ранее принятые инстансы продолжают отвечать на `SET` и
      `GET`.
- [ ] При очистке по очереди войти во все созданные аккаунты и удалить каждый
      инстанс через личный кабинет.

Этот сценарий не входит в `just test-prod` и не должен зависеть от занятой
ёмкости dev- или production-кластера.

- [ ] Проверить подключения и удалить инстанс через личный кабинет.
