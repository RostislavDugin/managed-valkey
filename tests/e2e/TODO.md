# Сквозные тесты личного кабинета

Playwright проверяет пользовательский путь от регистрации до подключения к
Valkey. Локальный и CI-запуск используют настоящий web, HTTP API, PostgreSQL,
оператор, Kubernetes и Envoy. Тесты написаны на TypeScript и выполняются без
повторов. Внутри одного стенда работает один browser worker.

## Каталог

| Сценарий | Тег |
| --- | --- |
| пользователь проходит полный жизненный цикл single-инстанса | `@prod` |
| новый пользователь регистрируется через форму и попадает в авторизованную консоль | `@prod` |
| пользователь проходит полный жизненный цикл HA-инстанса | `@prod` |
| личная квота запрещает недопустимое создание и изменение размера | `@local` |
| общая ёмкость кластера отклоняет новый инстанс без влияния на работающие | `@local` |
| HA-инстанс восстанавливается после потери primary Pod | `@local-k8s` |
| HA-инстанс восстанавливается после потери worker-ноды через прежний адрес | `@local-k8s` |

Теги хранятся в метаданных теста. `scripts/check_e2e_catalog.sh` проверяет точные
русские названия, теги, выбранную группу и положение жизненного цикла `single`
первым сценарием до создания k3s. Локальный запуск выполняет весь каталог
последовательно. CI параллельно запускает группы
`lifecycle` (`@prod`), `quotas` (`@local`) и `failures` (`@local-k8s`) на трёх
отдельных стендах. Внутри группы сценарии идут последовательно. После ошибки
одного сценария Playwright продолжает остальные, поэтому тесты не объединены в
общий `serial`-блок.

## Команды и окружения

| Команда | Окружение | Браузер | Интервал действий | Сценарии |
| --- | --- | --- | ---: | --- |
| `just test-e2e` | временный полный стенд | headless Chromium | 0 мс | все |
| `just test-e2e-group <group>` | временный полный стенд | headless Chromium | 0 мс | выбранная CI-группа |
| `just test-e2e-headed` | временный полный стенд | видимый Chromium | 1000 мс | все |
| `just test-e2e-prod` | `https://app.h3llo-demo.com` | видимый Chromium | 0 мс | только `@prod` |

Локальный запуск один раз создаёт отдельную базу, трёхнодовый k3s, две реплики
Envoy, один API, один оператор и один Vite. Все сценарии используют этот стенд,
но получают отдельные аккаунты и контексты браузера. Публичный порт принадлежит
`k3s-server`; межнодовая передача NodePort сохраняет адрес из интерфейса после
остановки одного agent. API публикует случайный порт хоста, оператор сохраняет
общий listener Envoy на `41379`, а Docker перенаправляет внешний порт на
закреплённый NodePort `31379`.

После повторной регистрации agent k3s может назначить ему новый Pod CIDR.
Kubernetes-помощник добавляет для этого диапазона маршрут с хоста и записывает
его в состояние запуска, чтобы оператор снова видел заменённый процесс, а
штатная очистка удалила и старый, и новый маршруты.

Обычный запуск выполняется через `scripts/test_environment.sh exec e2e`. Каждый
запуск получает собственные Compose project, базу, сеть, kubeconfig, сертификат,
порты и диапазоны адресов. Профиль резервирует 8192 MiB в общем бюджете тестовых
стендов. Очистка удаляет только инфраструктуру текущего запуска. E2e не входит
в корневые `just test`, `just test-full` и `just test-integrations`.

На двухъядерной виртуальной машине CI сборка оператора с тегом `integration`
задаёт поля `resources.requests` у Pod равными `100m` CPU и `128Mi` RAM.
Выбранные в интерфейсе `resources.limits`, `maxmemory`, тариф и применённая
конфигурация не меняются. Без этого Kubernetes не размещает тариф
`4 vCPU / 16 GB` на двухъядерном объекте `Node`, хотя тест использует мало памяти.

## Пользовательские действия и ожидания

Интервал применяется перед следующим переходом, вводом, выбором, переключением
или нажатием в браузере. Проверки Playwright, ожидания состояния, наблюдение за
HTTP, команды Valkey, действия Kubernetes и очистка начинаются без этой паузы.
Перед взаимодействием с элементом страница прокручивается до него. В headed
прокрутка плавно помещает элемент в центр, после чего тест ждёт 500 мс. Headless
и production используют обычную прокрутку без этой паузы. Глобальный `slowMo`
не используется.

Создание, изменение размера, смена пароля, удаление и восстановление после сбоя
ожидаются по наблюдаемому состоянию до отдельного срока. Исключения составляют
только демонстрационный интервал действий и период 100 мс у фоновых проб отказа.

## Границы сценариев

Регистрация, создание, изменение и удаление выполняются только через личный
кабинет. Тесты не вызывают HTTP API напрямую, не меняют PostgreSQL, не создают и
не редактируют CR и не снимают `finalizers`. Административный kubeconfig нужен
для чтения и диагностики, а в `@local-k8s` также для удаления primary Pod либо
адресной остановки agent текущего Compose project.

Адрес, порт и одноразовый пароль читаются со страницы. Клиент подключается к
Valkey по TLS с SNI и пользователем `app`; локально он доверяет CA стенда.
Сценарии проверяют основной и RO-маршруты, `SET`, `GET`, `INFO memory`, смену
пароля, квоты и восстановление через прежний публичный адрес.

## Очистка

Каждый тест регистрирует аккаунт до отправки формы. После основного тела новый
контекст браузера входит в каждый аккаунт, удаляет все видимые инстансы через
личный кабинет и ждёт пустого списка и нулевой занятой квоты. Перед этим
аварийный сценарий останавливает фоновые пробы и восстанавливает остановленный
agent.

Очистка выполняется после успеха, ошибки и прерывания. Она не использует прямые
DELETE-запросы, SQL, удаление CR или Namespace. Ошибка очистки делает запуск
неуспешным. В сообщении остаются только почта, имя и slug ресурса. После
успешного `just test-e2e-prod` в production нет созданных тестом
Valkey-инстансов; аккаунты остаются, пока интерфейс не поддерживает их удаление.

## Диагностика и секреты

Пароль аккаунта, JWT-секрет тестового процесса и одноразовые пароли Valkey
записываются в закрытый файл `tmp/k3s/e2e/<run-id>/e2e-secret-values`. Перед
публикацией HTML-отчёт очищается по этим значениям, затем
`scripts/check_e2e_artifacts.sh` проверяет обычные файлы, ZIP и встроенные данные
отчёта. Если значение осталось, CI не публикует диагностику и завершает job с
ошибкой.

Trace отключён. Снимок при ошибке создаёт общая фикстура, которая маскирует
видимые поля одноразового пароля. В артефакты не входят файл контрольных
секретов, kubeconfig, JWT, тела запросов с паролями и содержимое Kubernetes
Secret. Журнал host-оператора хранится отдельно от Kubernetes-диагностики.

## CI

Обязательный job `test-e2e` создаёт matrix из `lifecycle`, `quotas` и `failures`.
Каждая запись устанавливает зависимости web и e2e, проверяет свою группу,
устанавливает Chromium и вызывает `just test-e2e-group <group>` на отдельном
runner. Группы начинают работу независимо от lint, быстрых тестов, общей
интеграции и сборок. При ошибке CI публикует отчёт Playwright и очищенную
диагностику с именем группы после успешной проверки на секреты. Каждая запись
ограничена 60 минутами.

Job `ci-success` ждёт результаты всех lint, test, integration, e2e и build jobs.
Любой результат, отличный от `success`, запрещает deploy. Production-проверка
`just test-e2e-prod` остаётся ручной и не запускается из CI или после deploy.
